여섯 단계

단계하는 일남기는 것
1 관찰어떤 문항이 어떤 상태로 끝났는지 확인상태와 중단 원인
2 요구 확인원본 작업 지시가 무엇을 요구했는지 다시 읽음기대 산출물
3 계약 확인도구 입출력·경로 계약이 지켜졌는지 로그로 확인어긋난 호출 기록
4 구현 수정원인 한 곳만 고침변경 내용
5 검증 추가같은 실패를 다시 잡을 검사를 테스트에 추가회귀 검사
6 재실행같은 조건으로 다시 돌려 비교전·후 결과
📌 5단계를 건너뛰면 같은 실패가 반복됩니다 — 고친 사실보다 다시 잡을 장치를 남긴 사실이 제출물에서 더 중요합니다
3단계에서 대부분의 원인이 드러납니다.

회귀 검사

  • 회귀(regression)는 전에 되던 것이 다시 안 되는 것. 한 곳을 고치다 다른 곳이 깨지는 상황
  • 고칠 때마다 검사를 하나 추가해 두면, 이후 변경에서 자동으로 다시 확인됩니다
  • 제출 전에 전체 검사를 한 번 통째로 돌려 봅니다 — 마지막 수정만 확인하고 끝내지 않습니다
uv run python -m pytest -q
⚠️ 검사가 몇 개는 통과하고 몇 개는 실패한다면 — "대체로 된다"가 아니라 실패 목록을 그대로 적습니다. 숨긴 실패는 평가에서 더 크게 드러납니다
테스트 파일 자체를 고쳐 통과시키는 것은 해결이 아닙니다.

측정과 미측정

기록의미쓰는 법
측정값실제로 돌려서 얻은 숫자조건과 함께 적음
NOT_RUN시간·비용·환경 때문에 돌리지 않음빈칸이나 0이 아니라 명시
error돌렸으나 채점이 실패실패 이유를 함께
📌 돌리지 않은 항목을 0으로 채우면 성능이 나쁜 것처럼, 빈칸으로 두면 잰 것처럼 보입니다 — NOT_RUN이라고 쓰는 것이 가장 정확합니다. ⑪의 usage_known=False와 같은 원칙
왜 돌리지 않았는지 한 줄 사유를 같이 적으면 더 좋습니다.

개발용 세트의 한계

  • 이 10문항은 개발하면서 반복해서 본 세트입니다 — 여기에 맞춰 고치다 보면 이 10문항에만 잘 맞는 하네스가 될 수 있습니다
  • 개발용 세트 점수는 일반 성능의 상한이 아니라 참고값으로 씁니다
  • 제출 문서에 "이 점수는 개발 과정에서 반복 사용한 세트의 결과"라고 적습니다
⚠️ 특정 문항의 정답을 코드에 심어 통과시키는 것은 개선이 아닙니다. 채점 통과는 일반적인 방법으로 문제를 푼 결과여야 합니다
같은 이유로 원본 정답과 채점 코드를 하네스 입력에 넣지 않습니다.

넣을 것

  • PRD와 설계 문서 — 사용자·작업·완료 조건·플랫폼·제공자 결정
  • 구현 코드 — 실행 방법(설치·실행 명령)을 README에 명시
  • 제품 검증 결과 — ⑦의 시나리오별 통과/실패
  • 벤치마크 결과 표 — n/10, 난이도별 분해, 상태 분포
  • 실행 메타데이터 — run-metadata.json, execution_mode: local-port
  • 비교 실험 기록 — 가설, 바꾼 변수 하나, 전·후 비교
  • 실패 추적 기록 — 관찰부터 회귀 검사 추가까지
📌 다른 사람이 같은 명령으로 재현할 수 있는가가 기준입니다 — 실행 명령이 빠진 코드는 검증할 수 없습니다
재현 가능성이 제출물 평가의 핵심입니다.

❓ 이해도 확인

Q1. 돌리지 않은 측정 항목은 어떻게 적나?
A1. NOT_RUN. 0으로 채우면 성능이 나쁜 것처럼, 빈칸이면 잰 것처럼 보인다.
Q2. 실패를 고친 뒤 반드시 남겨야 할 것은?
A2. 같은 실패를 다시 잡을 회귀 검사. 고친 사실보다 다시 잡을 장치가 더 중요하다.
Q3. benchmark/upstream/을 빼면 실패 기록도 빼야 하나?
A3. 아니다. 실패 행은 그대로 남긴다. 원본 자료 사본을 배포하지 않는 것과 내 결과를 기록하는 것은 별개다.
Q3은 제출 직전에 자주 혼동되는 부분입니다.
