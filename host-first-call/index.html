호스트 연결과
첫 도구 호출

파일을 저장했다는 사실만으로 새 MCP 서버에 연결되지는 않습니다

여기서 필요한 일이 서버 등록입니다.

서버 등록이란

📝 호스트에 알려 주는 것 — "이 서버의 이름은 weekly-records이고, 이 프로그램을 이 인자와 함께 실행하면 연결할 수 있다"
학생: 첫 주 업무 기록을 읽어 줘.
  ↓
모델: 제공받은 도구 설명을 바탕으로 get_weekly_records 호출을 요청
  ↓
호스트: 연결한 서버에 {"week": "week-one"} 전달
  ↓
업무 기록 서버: data/week-one.json을 읽어 반환
  ↓
호스트: 도구 결과를 모델에 전달
  ↓
모델: 반환된 기록을 바탕으로 답변
  • 호스트는 그 설정으로 서버를 시작하고 도구의 이름·설명·입력 형식을 확인합니다 — 앞 절의 Python 함수가 대화에서 사용할 수 있는 도구가 되는 순간
Claude Code와 OpenCode 중 현재 사용하는 앱 하나로 진행하면 됩니다.
1

설정이 가리키는 위치

실행 프로그램과 프로젝트의 위치

④ 호스트 연결
AI에게 설정을 맡기기 전에, AI가 바꿀 내용에서 무엇을 읽어야 할지 알아봅니다.

절대 경로와 상대 경로

  • 이번에는 호스트가 uv를 실행하고, uv가 프로젝트의 가상환경 안에서 mcp run weekly_records_server.py --transport stdio를 실행하게 합니다
  • 데이터 위치는 서버 소스가 알고 있으므로 — 호스트 설정에 JSON 파일마다 항목을 만들 필요는 없습니다
  • 절대 경로는 맨 위 폴더부터의 위치, 상대 경로는 어떤 폴더를 출발점으로 삼은 위치
  • weekly_records_server.py만 쓰면 프로그램은 자신의 현재 작업 폴더에서 찾습니다 — 호스트를 어디서 실행했는지에 따라 출발점이 달라지므로 uv --directory에 실습 폴더의 절대 경로를 지정
  • --directory는 uv가 명령을 실행할 작업 폴더를 바꿉니다 — 그곳의 pyproject.toml을 기준으로 프로젝트를 찾고, 뒤의 상대 경로도 그 폴더에서 읽습니다
📌 호스트 설정은 소스 파일까지 정확히 가리키고, 소스 파일은 자기 곁의 데이터를 찾는 구조입니다. 터미널에서 가상환경을 활성화할 필요는 없습니다 — 활성화는 이미 실행 중인 다른 앱의 환경까지 바꾸지 않기 때문
--locked는 uv.lock을 임의로 갱신하지 않게 하며, 잠금 파일이 없거나 선언과 맞지 않아 갱신이 필요하면 오류로 멈춥니다.
2

AI에게 연결 요청하기

내가 준비한 폴더를 가리켜야 합니다

④ 호스트 연결
실습 폴더를 연 Claude Code 또는 OpenCode에서 요청합니다.

요청과 확인할 것

이 폴더의 업무 기록 서버를 uv로 실행하도록
지금 쓰는 앱에 MCP로 연결해 줘. 바꾼 설정도 설명해 줘.
  • 살펴볼 것 — weekly-records라는 이름, 실행 프로그램 uv, --directory 뒤의 실습 폴더 위치와 서버 파일 이름
  • 예시 작성자의 폴더가 아니라 내가 준비한 폴더를 가리켜야 합니다. 기존 MCP 연결이 있다면 그 항목을 유지하면서 추가되었는지도 확인
  • 완성 예제는 mcp run이 읽어 실행하도록 만들었습니다 — 그대로 쓰면서 python weekly_records_server.py만 등록했다면 실행 방식을 다시 확인해 달라고 요청하세요
🔎 OpenCode는 V1과 V2의 설정 구조가 다릅니다 — "내 OpenCode 버전을 확인하고, 그 버전에 맞게 연결해 줘". V1은 mcp 바로 아래, V2는 mcp.servers 아래에 등록합니다
파일 이름만 보고 어느 명령이 맞는지 결정하기보다 실제 소스가 어떻게 서버를 시작하는지 확인합니다.

Claude Code 등록 명령

cd "/Users/student/Projects/mcp-skill-practice"
claude mcp add --transport stdio --scope project weekly-records \
  -- uv --directory "/Users/student/Projects/mcp-skill-practice" \
     run --locked mcp run weekly_records_server.py --transport stdio
부분역할
claude mcp add ... weekly-records서버를 등록. --scope project는 현재 프로젝트의 .mcp.json에 저장하는 범위
가운데의 --등록 옵션과 실제로 실행할 서버 명령을 구분
uv부터 마지막 stdio까지호스트가 시작할 명령. 첫 run --locked는 프로젝트 환경에서 실행, 이어지는 mcp run이 소스를 읽음
📌 --transport stdio가 두 번 보이는 것은 오타가 아닙니다 — 앞은 호스트가 사용할 연결 방식, 뒤는 서버의 실행 방식
Windows PowerShell에서도 같은 uv 명령을 쓰고 경로만 Windows 형식으로 적습니다. 경로 안에 공백이 있어도 한 값으로 전달되도록 따옴표를 유지합니다.

OpenCode의 command 배열

"weekly-records": {
  "type": "local",
  "command": [
    "uv", "--directory",
    "/Users/student/Projects/mcp-skill-practice",
    "run", "--locked", "mcp", "run",
    "weekly_records_server.py", "--transport", "stdio"
  ],
  "enabled": true
}
  • type: "local"은 내 컴퓨터의 프로그램을 실행하는 연결. command는 실행 파일과 각 인자를 나눈 배열로, 공백으로 이어 붙인 하나의 문자열로 바꾸지 않습니다
  • Windows 경로는 JSON에서 역슬래시 하나를 \\로 적습니다 — PowerShell 명령의 경로를 그대로 복사하면 이 차이 때문에 오류
  • V1은 enabled: true로 활성화. V2는 mcp.servers 아래에 두고 disabled가 true일 때만 끕니다 — V1의 enabled는 넣지 않습니다
  • V2에서는 codemode의 기본값이 true입니다. 지금은 기본값을 유지합니다
⚠️ 터미널에서는 uv가 실행되는데 앱에서는 못 찾을 수 있습니다 — PATH는 실행 파일을 찾을 폴더 목록이며 앱과 터미널이 서로 다른 목록을 쓸 수 있습니다. command -v uv / (Get-Command uv).Source로 확인한 절대 경로를 넣습니다
기존 설정 파일이 있다면 전체를 덮어쓰지 말고 해당 항목만 합칩니다. 같은 이름의 키를 두 번 만들지 않습니다.
3

연결 상태에서 실제 호출로

호출 기록에서 세 가지를 찾습니다

④ 호스트 연결
이 방식에서는 호스트가 서버 프로세스를 관리하므로 별도 터미널에서 서버를 켜 둘 필요가 없습니다.

호출 기록에서 찾을 세 가지

연결한 MCP로 첫 주 업무 기록을 읽어 줘.
확인할 부분찾을 내용
호출한 도구get_weekly_records가 포함된 이름 — 호스트가 서버 이름을 앞에 붙여 표시할 수 있습니다
보낸 입력week의 값이 week-one인 입력
받은 결과첫 주의 날짜와 네 개 업무 기록
🎯 자연어의 '첫 주'가 도구 입력 week-one으로 바뀌었습니다 — 서버 함수의 설명에 지원하는 값이 있었기 때문에 모델이 그 값을 선택할 수 있습니다
  • AI가 파일 읽기 도구로 week-one.json을 직접 읽었다면 내용은 맞을 수 있지만 — 확인하려던 MCP 경로는 아직 관찰하지 못한 것입니다. "이번에는 weekly-records MCP 도구를 사용해서 읽어 줘"
호출 기록(trace)은 어느 도구에 어떤 값을 보냈고 무엇을 받았는지 남긴 기록입니다. 연결한 서버가 같은 데이터를 읽을 수 있다는 사실과 모델이 이번 대화에서 그 도구를 선택했다는 사실을 구분하세요.

원본과 반환값 대조

{
  "week": "week-one",
  "report_date": "2026-09-04",
  "records": [
    {
      "id": "TASK-102",
      "title": "로그인 안내 문구 개선",
      "owner": "지우",
      "status": "개발 완료",
      "deployed_at": null,
      "verification": "미실시"
    }
  ]
}
  • 실제 전체 결과에서는 records에 TASK-101부터 TASK-104까지 네 건이 있어야 합니다
  • TASK-102의 status는 '개발 완료'인데 deployed_at은 null — AI 답변에 새로운 배포 날짜가 생겼다면 원본이 준 것인지, 문장을 만드는 과정에서 생긴 것인지 구분해야 합니다
  • TASK-103의 owner도 null — 누가 담당하는지 기록에 없는 상태 그대로 반환되는지 살펴보세요
📌 지금의 도구는 기록을 읽어 전달하는 역할입니다 — 빈 값을 추정해 채우거나 보고서에서 '완료'로 분류할 기준을 정하는 일은 하지 않습니다
이는 화면 캡처가 아니라 실습 원본에서 확인할 값의 발췌입니다. 실습 자료의 SDK 검증에서는 week-one과 week-two를 호출해 원본과 반환값이 일치함을 확인했습니다.

오류가 알려 주는 연결 단계

마지막으로 성공한 단계 다음을 봅니다

④ 호스트 연결
정상 결과를 받았다면 지원하지 않는 주도 요청해 봅시다.

week-three의 거절은 실패가 아닙니다

✅ 관찰한 것

요청이 도구에 도달했고, 함수가 입력을 확인한 뒤 거절했습니다 — 앞 절의 허용 주차 검사가 작동한 셈

🤔 다른 경우

모델이 도구 설명을 읽고 호출 전에 "지원하지 않는 주입니다"라고 답할 수도 있습니다 — 그 경우엔 모델의 사전 판단을 관찰한 것

📝 호출 기록에 week-three 입력과 오류 반환이 함께 있을 때 서버의 거절을 관찰했다고 기록합니다. 한국어 오류 문장이 완전히 같을 필요는 없습니다
이것은 서버가 실행되지 않는 상황과 다릅니다.

먼저 볼 곳

관찰한 상황먼저 볼 곳이해할 내용
목록에 서버가 없음설정을 저장한 프로젝트와 현재 연 폴더프로젝트 설정은 해당 프로젝트에서 읽습니다
서버가 시작되지 않음호스트가 uv를 찾는지, uv sync --locked 결과앱의 실행 파일 검색 경로와 환경 준비 상태
잠금 파일 관련 오류pyproject.toml과 uv.lock이 함께 있는지--locked는 잠금 파일을 새로 만들거나 고쳐서 진행하지 않습니다
소스나 데이터를 못 찾음--directory의 절대 경로와 그 안의 서버 파일·data작업 폴더를 지정하면 상대 경로의 출발점도 정해집니다
연결은 되지만 MCP 호출이 없음모델이 선택한 도구와 호출 기록파일 직접 읽기 등 다른 행동을 골랐을 수 있습니다
소스를 고쳐도 이전 동작이 계속됨실행 중인 서버의 재시작 여부디스크 파일을 저장해도 실행 중인 프로세스가 새 소스를 다시 읽어야 합니다
📌 오류가 길어 보여도 설정을 전부 지울 필요는 없습니다 — "이 오류를 보고, 어느 단계에서 막혔는지부터 설명해 줘"
AI가 패키지 문제라고 하면 uv가 선택한 프로젝트와 환경을, 데이터 문제라고 하면 원본 폴더를 확인합니다. 수정 뒤에는 같은 입력으로 다시 호출해 결과가 어떻게 달라졌는지 봅니다.

❓ 이해도 확인

Q1. --transport stdio가 두 번 나오는 이유는?
A1. 앞은 호스트가 사용할 연결 방식, 뒤는 서버의 실행 방식. 오타가 아니다.
Q2. AI가 week-one.json을 직접 읽어 정답을 말했다면?
A2. 내용은 맞을 수 있지만 MCP 경로는 관찰하지 못한 것. 도구를 사용해 다시 읽도록 방향을 보충한다.
Q3. 소스를 고쳤는데 이전 동작이 계속되면?
A3. 실행 중인 서버 프로세스가 새 소스를 다시 읽어야 한다. 재연결하거나 같은 프로젝트에서 앱을 다시 시작한다.
Q2의 구분이 없으면 "연결이 잘 됐다"고 잘못 결론냅니다.
