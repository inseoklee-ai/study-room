1

네 가지 규율

막힐 때 여러분을 구해 줄 것

⑦ 막혔을 때
네 가지를 외우게 하세요. 실제로 막혔을 때 꺼내 쓸 수 있어야 합니다.

1) 한 번에 하나만 · 2) 작동하면 저장

1한 번에 하나만. 프롬프트 하나에 다섯 가지를 요구하면 AI는 몇 개는 맞고 몇 개는 틀립니다 — 그럼 디버깅이 더 어려워집니다. 고칠 때도 "필요한 것만 바꿔줘"라고 말하세요. 버그 하나 고치고 → 확인 → 다음
2작동하면 저장(커밋). 바뀔 때마가 아니라 '작동할 때마다' 저장하세요. 이게 안전망입니다. 뭔가 깨지면 마지막으로 잘 되던 지점으로 되돌리면 됩니다
💾 커밋은 '저장 버튼'이 아니라 되돌릴 지점을 만드는 행위입니다
2번은 소단원 ④의 매 단계 "통과하면 커밋"과 같습니다. 이미 실습에서 해 본 것입니다.

3) 막히면 되돌리고 리셋 · 4) 이해 못 한 코드는 배포 안 함

3막히면 되돌리고, 리셋한다. AI가 같은 버그를 못 고치고 빙빙 돌면 랜덤하게 이것저것 바꾸라고 시키지 마세요 — 그게 코드를 이해 불가능하게 만드는 지름길입니다. 대신 5~10번마다 "지금까지 뭐가 됐고, 뭐가 남았고, 지금 문제는 뭐다"라고 요약해 AI의 초점을 다시 맞춰 주세요
4이해 못 한 코드는 배포하지 않는다. 시제품 단계에선 "다 수락"도 괜찮지만, 남에게 내보낼 거라면 그 코드가 무엇을 하는지 알아야 합니다. Veracode 평가에서 조사한 AI 생성 코드 샘플의 약 45%가 보안 테스트에 실패했으니, 내보내기 전 "안전한지 한 번 봐 줘"는 필수
🗣️ "일을 구조화하고, 프롬프트를 다듬고, 체계적으로 진행하라" — 이 원칙은 AI 시대에도 그대로입니다 (Andrew Ng)
능숙한 바이브 코더와 헤매는 사람의 차이는 작업을 얼마나 구조적으로(과정 있게) 하느냐입니다.

심화 — Git은 '저장 버튼'이 아닙니다

실험을 안전하게 만드는 기록 장치

⑦ 막혔을 때
AI가 파일 여러 개를 바꾼 뒤 앱이 망가졌을 때, Git을 모르면 "어제 되던 파일을 기억으로 복사"하게 됩니다. 그 순간 무엇이 원인이었는지도 함께 사라집니다.

세 장소를 책상 비유로

장소비유무엇인가
working tree
작업 트리		지금 손으로 펼쳐 놓은 원고에디터에서 저장한 변경이 여기 있다
staging area
index		다음 기록 상자에 넣기로 골라 둔 묶음git add 파일명은 자동 백업이 아니라 '이 상태를 다음 기록에 포함하겠다'는 선택
repository
저장소		확정된 사진첩git commit -m "..."이 묶음과 설명을 하나의 체크포인트로 남긴다
  • 빠른 생성 속도는 빠른 실수도 뜻하기 때문에, 바이브 코딩에서 이 구분이 특히 중요합니다
Git은 파일의 현재 상태를 한 장만 저장하는 도구가 아니라, 변화의 이유와 순서를 되짚게 하는 기록 장치입니다.

이 구분이 필요한 장면

빈 입력 검증을 고치다가 AI가 버튼 색과 데이터 형식까지 수정했습니다.

git status                 # 무엇이 바뀌었는지 먼저 본다
git add LoginForm.tsx      # 의도한 파일만 올린다
git diff --staged          # 커밋될 줄을 읽는다
git commit -m "빈 이메일 제출 시 안내 문구 표시"
  • 커밋 메시지는 나중의 내가 이해할 문장으로
  • 색 변경은 아직 확신이 없다면 작업 트리에 둡니다
  • 이 작은 분리가 AI가 만든 많은 변화 속에서 '검증한 변화'와 '아직 실험 중인 변화'를 나눕니다
커밋 뒤에도 작업 트리는 계속 바꿀 수 있습니다. 이 감각이 있으면 AI의 대량 수정이 두렵지 않습니다.

되돌리기 — 이름은 비슷해도 위험이 다릅니다

명령무엇을 바꾸나주의
git restore 파일명작업 트리의 아직 커밋하지 않은 변경을 버리고 마지막 커밋 상태로사라질 내용을 먼저 git diff로 보는 습관
git reset --hard <커밋>브랜치·스테이징·작업 트리를 함께 그 커밋으로커밋하지 않은 작업을 실제로 지울 수 있는 강한 명령. 공유 브랜치의 기록까지 바꾸면 더 큰 혼란
git revert <커밋>과거를 지우지 않고 효과를 반대로 적용하는 새 커밋을 만든다팀 저장소·이미 푸시한 변경을 취소할 때 이력이 남아 안전
🧭 reset은 내 로컬 실험의 책상 정리, revert는 공유된 역사에 남기는 취소 메모 — '안 되면 하드 리셋'은 진단법이 아닙니다
  • 실제 명령 전에는 git log --oneline · git status · git diff로 내가 어디에 서 있는지 확인
예를 들어 배포된 기능이 장애를 냈다면, 원인 커밋을 revert해 서비스는 되돌리되 '무엇을 왜 되돌렸는지'는 기록에 남깁니다.

AI에게도 Git을 작업 규율로 요구하세요

"수정 전에 git status와 관련 파일 diff를 요약해줘.
 테스트가 통과하면 변경 목적 하나만 담아 커밋 후보를 제안해줘.
 reset --hard 나 강제 푸시는 내가 명시적으로 승인하기 전에는 실행하지 마."
  • AI가 커밋 메시지를 써도 최종 선택은 내가 합니다
  • 비밀키가 diff에 보이면 커밋하지 말고 .gitignore와 환경변수 설정을 먼저 점검 — Git은 비밀을 자동으로 막아 주지 않습니다
🎯 좋은 체크포인트는 '오후 작업'처럼 시간으로 쓰지 않습니다 — "게시물 작성 뒤 새로고침해도 남는다"처럼 행동과 관찰 가능한 결과로 씁니다
Git의 목적은 실수하지 않는 사람이 되는 것이 아니라, 실수해도 작은 비용으로 배우고 돌아오는 사람이 되는 것입니다.

브랜치와 커밋 전 점검

🌿 브랜치

"이 체크포인트에서 다른 실험을 해 보겠다"는 가벼운 갈래. 정상 작동하는 기본 브랜치를 보존한 채 실험하고, 통과하면 diff를 읽고 합치고 아니면 브랜치만 버린다. 이름은 feature/post-create처럼 목적이 보이게

✅ 커밋 전 점검 (짧아야 지속됩니다)

git status로 대상 확인 → 앱을 실행해 핵심 흐름 한 번 확인 → git diff로 의도하지 않은 비밀값·대량 삭제 확인 → 목적 하나의 커밋

  • 실패한 실험도 즉시 지울 필요는 없습니다 — 왜 실패했는지 한 줄 메모를 남기고 되돌리면 같은 제안을 또 적용하는 일을 막습니다
  • ⚠️ .env나 토큰이 한 번 원격에 올라갔다면 커밋을 지우는 것만으로 안전해지지 않습니다 — 키를 폐기·재발급하고 노출 범위를 점검
복구 연습을 한 번 해 보면 차이가 선명해집니다 — 테스트 파일에 문장 하나를 추가해 status·diff를 보고, add·commit한 뒤 다시 바꿔 restore와 log를 확인해 보세요. 중요한 프로젝트에서 처음 명령을 쓰지 않게 됩니다.

'고무 오리'에게 설명하기

막힘을 푸는 오래된 비법

⑦ 막혔을 때
개발자들 사이에 러버덕 디버깅(rubber duck debugging)이라는 유명한 방법이 있습니다.

인형에게 소리 내어 설명하기

문제가 안 풀릴 때, 책상 위 고무 오리 인형에게 코드를 한 줄씩 소리 내어 설명하는 겁니다. 우스워 보이지만 신기하게도 설명하다가 스스로 답을 찾는 경우가 아주 많습니다.

  • 이름은 1999년 책 『실용주의 프로그래머』의 일화에서 왔습니다 — 한 개발자가 가방에 고무 오리를 넣고 다니며 막힐 때마다 오리에게 문제를 설명했다는 이야기
  • 원리는 심리학의 '자기 설명 효과' — 머릿속으로 볼 때는 슬쩍 넘어가던 당연하다고 여긴 전제가, 말로 옮기는 순간 빈틈이 드러나기 때문
🦆 바이브 코딩에서 여러분의 '고무 오리'는 바로 AI입니다 — "지금 뭘 하려는 거고, 무엇까지 됐고, 어디서 막혔는지"를 처음부터 또박또박 적어 설명해 보세요. 그 설명을 쓰는 동안 문제의 상당 부분이 스스로 보입니다
출처: Hunt & Thomas, 『The Pragmatic Programmer』, 1999; Wikipedia, "Rubber duck debugging".

오리는 답을 주지 않습니다 — 내 모델을 밖으로 꺼내 줍니다

이유는 마법이 아니라 인지 외현화입니다. 머릿속에서 "로그인이 안 돼"라는 덩어리로 뭉쳐 있던 생각이, 말이나 글로 바뀌면서 입력·처리·출력이라는 순서로 분해됩니다. 설명할 수 없는 빈칸이 바로 다음 조사 지점이 됩니다.

"사용자가 제목을 입력하고 저장을 누른다.
 브라우저의 handleSubmit 이 실행되어야 한다.
 여기서 API에 POST 요청을 보낸다.
 서버는 제목을 검사하고 DB에 저장한 뒤 새 게시물 JSON을 돌려준다.
 화면은 그 JSON을 목록에 추가한다."
  • 이 설명 중 "POST 요청이 실제로 나가는지는 모르겠다"에서 멈췄다면, 문제는 '저장이 안 됨' 전체가 아니라 네트워크 요청이라는 좁은 가설이 됩니다
  • 개발자 도구 Network 탭에서 요청이 생기는지, 상태 코드가 200/400/500 중 무엇인지 확인할 수 있습니다
"설명할 수 없는 빈칸이 다음 조사 지점"이 이 슬라이드의 핵심 문장입니다.

설명은 관찰과 추측을 구분합니다

❌ 추측

"아마 DB가 고장 났다"

✅ 관찰

"저장 클릭 뒤 콘솔에 Cannot read properties of undefined가 보인다"

1재현 절차를 적는다 — ① 제목에 '테스트' 입력 ② 저장 클릭 ③ 화면 변화 없음 ④ 콘솔 오류 한 줄 복사
2기대값도 적는다 — "목록 맨 위에 제목이 보이고 새로고침 뒤에도 남아야 한다"
🎯 이 두 문장만 있어도 AI에게 훨씬 검증 가능한 질문을 만들 수 있습니다
AI는 오리의 대체재가 아니라, 이 외현화된 정보를 읽는 조력자로 쓰면 좋습니다.

'한 줄씩 설명'할 때 유용한 다섯 질문

1이 값은 어디서 왔나?
2지금 무슨 형태인가 (문자열·숫자·객체·비어 있음)?
3어느 함수가 언제 실행되나?
4성공하면 화면이나 DB에서 무엇이 달라져야 하나?
5실패하면 오류는 어디에 기록되나?
🔐 비밀번호처럼 민감한 값은 말하거나 로그에 남기지 말고 — 존재 여부·길이처럼 안전한 정보만 확인
  • 범위를 좁힐수록 말은 정확해지고, AI의 답도 검증하기 쉬워집니다 — 마지막 정상 체크포인트와 첫 실패 사이의 한 흐름만 설명하세요
오리는 실제 인형일 필요가 없습니다. 빈 문서, 보내기 전 메시지 초안, 음성 메모도 됩니다. 오리에게 설명한 기록은 내일의 나에게 가장 좋은 버그 보고서가 됩니다.

도움을 청할 때 — 네 가지를 전달합니다

1목적 한 문장
2재현 단계
3기대 결과와 실제 결과
4오류 전문 또는 관련 파일의 작은 부분
"2단계 화면 만들기에서 실패합니다. 로그인 후 제목 '우산'을 입력하고
 저장을 누르면 목록이 비어 있습니다.
 기대 결과는 새 항목이 즉시 보이고 새로고침 뒤에도 남는 것입니다.
 실제로는 Network 탭에 POST /posts 요청이 없고 콘솔 오류는 없습니다.
 버튼 클릭 함수가 호출되는지 확인할 방법 하나만 알려 주세요."
🎯 "왜 안 돼요?"보다 이런 보고서가 답하기 좋습니다 — 원인까지 단정하지 않으면서 다음 관찰을 작게 만듭니다
AI가 서버 코드 전체를 바꾸자고 하면, '아직 요청조차 없다'는 관찰과 맞지 않는다고 판단할 수 있습니다. 받은 답도 곧바로 적용하지 말고, 왜 그 변경이 내 가설을 시험하는지 한 문장으로 설명해 보세요.

함정 — 마지막 10%의 늪, '둠 루프'

운이 아니라 구조적입니다

⑦ 막혔을 때
바이브 코딩에서 초보가 가장 자주 빠지는 함정에 이름이 있습니다.

"거의 다 됐는데" — 둠 루프(doom loop)

1버그 하나가 안 잡히고
2AI는 "고쳤다"는데 실제론 안 고쳐지고
3프롬프트를 더 넣을수록 멀쩡하던 기능까지 깨진다

이건 운이 나빠서가 아니라 구조적입니다 — 대화가 길어지며 맥락이 오염되고, AI에겐 "무엇이 무엇에 의존하는지"의 지도가 없어서 원인이 아니라 증상만 계속 땜질하기 때문입니다.

⏱️ 막힘이 30분을 넘기면, 더 파기 전에 멈추고 되돌리는 것이 대개 더 빠릅니다
출처: Product Talk, "Vibe coding best practices"; Nicholas Ayala, "Escaping the Doom Loop". 강 4에서 배운 '컨텍스트 부패'가 원인입니다.

⑦ 막혔을 때
실무자들이 공통으로 꼽는 함정들입니다.

네 가지 지뢰와 처방

증상처방
검증 없이 그대로 믿기 — AI 코드는 깔끔해 보여서 근거 없는 안심을 준다 (Veracode 2025 보고서: 조사한 AI 생성 코드의 45%에서 보안 결함)'완성품'이 아니라 '초안'으로 대하고, "이 코드가 뭘 하는지 설명해줘"로 스스로 검토
비밀키를 코드에 박아 커밋 — API 키·비밀번호를 GitHub에 올리면 몇 분 만에 긁혀간다비밀값은 .env에 넣고 곧바로 .gitignore에 등록. 이미 노출했다면 삭제가 아니라 키 재발급
예외·에러 처리 빼먹기 — AI는 "모든 게 정상인 경우"만 만들기 쉬워, 빈칸 입력·인터넷 끊김·잘못된 값에서 무너진다"빈 입력·네트워크 실패·잘못된 값도 처리해줘"라고 명시
불필요한 복잡도 쌓기 — 세 줄이면 될 일에 라이브러리 다섯 개(딸려 오는 취약점까지)"이거 없이 기본 기능만으로 안 돼?"라고 한 번 되묻기
⚖️ 공통점은 하나 — 편함과 위험은 같이 옵니다. AI를 '목발'이 아니라 '가정교사'로 쓰는 것, 그게 초보와 능숙한 사람을 가릅니다
45%는 Veracode의 해당 연구 표본·스캔 기준 결과이지, 모든 AI 코드의 일반 비율이 아닙니다. 출처: Veracode, 2025 GenAI Code Security Report; CSA, "Secure Vibe Coding Guide"; base44; ShiftMag.

오래된 무기들

⑦ 막혔을 때
AI가 못 풀 때를 대비한 방법들입니다.

검색 · 질문 · 최소 재현 예시

1에러 메시지를 '그대로 복사'해 검색 — 손으로 다시 치지 마세요(오타로 검색이 엉킵니다). 결과가 없으면 파일명·변수명처럼 내 프로젝트에만 있는 부분을 지워 더 일반적인 검색으로. 긴 오류라면 맨 마지막 줄이 대개 가장 잘 맞습니다
2커뮤니티에 '잘' 묻기 — ① 목표 한 줄 ② 재현되는 최소 코드 ③ 정확한 에러 텍스트(스크린샷 말고) ④ 이미 시도한 것. 올리기 전 같은 질문이 있는지 검색하는 성의는 기본
3최소 재현 예시(MRE) — "남이 그대로 돌려도 같은 문제가 나는, 가능한 한 짧은 코드". 자동차가 이상할 때 차 전체가 아니라 "브레이크 밟을 때 나는 소리"만 떼어 보여주는 것과 같습니다
🧭 순서를 기억하세요 — ① 에러 그대로 AI에게 → ② 그대로 검색 → ③ 문제를 좁혀(MRE) 커뮤니티에 질문
출처: Hartley Brody, "Debugging Tips for Beginners"; Data School. MRE로 좁히는 과정에서 답을 스스로 찾는 경우도 많습니다. 막힘은 실패가 아니라, 모든 만드는 사람이 매일 지나는 길입니다.

❓ 이해도 확인

Q1. 네 가지 규율은?
A1. 한 번에 하나만 · 작동하면 저장 · 막히면 되돌리고 리셋 · 이해 못 한 코드는 배포 안 함.
Q2. reset --hard와 revert의 차이는?
A2. reset --hard는 브랜치·스테이징·작업 트리를 함께 되돌려 커밋 안 한 작업을 지울 수 있다(내 로컬 실험용). revert는 과거를 지우지 않고 효과를 반대로 적용하는 새 커밋을 만든다(공유된 역사에 안전).
Q3. 둠 루프가 '구조적'인 이유는?
A3. 대화가 길어지며 맥락이 오염되고, AI에겐 의존 관계의 지도가 없어 원인이 아니라 증상만 땜질하기 때문. 30분 넘으면 멈추고 되돌린다.
Q4. 비밀키를 실수로 커밋했다면?
A4. 삭제가 아니라 키 재발급. 원격에 한 번 올라간 키는 커밋을 지워도 안전해지지 않는다.
Q4는 실제 사고로 이어지는 유일한 항목입니다. 반드시 짚어 주세요.
