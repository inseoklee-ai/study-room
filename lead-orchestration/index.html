모델이 정하는 흐름
— 리드가 나누기

악보에 미리 고정하는가, 지휘자가 연주 중에 정하는가

워크플로 실행(B)과 오케스트레이션 실행(C)은 같은 문제와 같은 읽기 전용 locator를 재료로 씁니다.

차이는 조율 주체 하나입니다

🎼 워크플로 실행(B)

코드가 locator 다음 fixer를 반드시 실행했습니다 — 연주 순서를 악보에 미리 고정

🎩 오케스트레이션 실행(C)

리드가 상황을 보고 다음 행동을 정합니다 — 지휘자가 연주 중 상황을 보고

  • C에도 읽기 전용 locator가 있습니다. agents={"locator": ...}는 이 읽기 전용 도구를 리드 세션에 제공한다는 뜻
  • 리드는 locator를 부를지와 받은 내용을 어떻게 쓸지를 스스로 정하고, 최종 수정도 직접 합니다
  • C의 리드 세션은 최대 40턴
📌 같은 역할 구성이더라도 조율 주체가 달라지면 실행 기록에서 확인할 것이 달라집니다
B와 C는 재료가 같고 조율 주체만 다릅니다.
1

AgentDefinition으로 워커를 등록합니다

arms.py의 오케스트레이션 실행(C)

⑥ 모델이 정하는 흐름
_run_once 안에서 리드의 query()를 한 번 호출하고, C에서는 읽기 전용 locator를 등록한 옵션을 그 호출에 넘깁니다.

C의 호출 부분

elif arm == "C":
    locator = AgentDefinition(
        description="Read-only locator: finds the likely cause "
                    "of a bug in this repo. Cannot edit files.",
        prompt=SYS_B_LOCATE,
        tools=["Read","Grep","Glob"],
    )
    msg, err = await asyncio.wait_for(_run_once(
        f"Fix this bug:\n\n{problem}",
        ClaudeAgentOptions(cwd=str(repo), model=MODEL, max_turns=40,
                           system_prompt=SYS_C,
                           permission_mode="bypassPermissions",
                           agents={"locator": locator},
                           forward_subagent_text=True)), 1500)
  • description에 "Cannot edit files"를 적고 tools를 읽기 전용으로 제한 — B의 allowed_tools와 같은 뜻
_run_once 도우미는 A·B·C에서 동일합니다. 턴 소진도 예외로 죽지 않고 남은 상태를 그대로 채점합니다.

실행과 확인

.venv/bin/python arms.py C sympy__sympy-24909

cat runs/C-sympy__sympy-24909/result.json
cat runs/C-sympy__sympy-24909/changes.diff
파일볼 것
result.json리드 세션의 턴 수와 종료 결과
changes.diff그 판단이 실제 수정으로 이어졌는지
judgment.json의 evidence_quote리드가 locator를 실제로 사용했는지와 locator의 탐색이 최종 편집에 반영됐는지
⚠️ 서브에이전트를 정의했다는 사실만으로 분업이 일어났다고 볼 수 없습니다 — 사용하지 않았다면 어떤 탐색을 대신 했는지도 세션 기록과 함께 읽습니다
이 문장이 오케스트레이션 실행(C)의 핵심 관찰점입니다.
2

바이브 코딩으로 따라하기

요약만 받지 않습니다

⑥ 모델이 정하는 흐름
이 실행도 코딩 에이전트에게 위임할 수 있습니다.

위임 요청문

오늘 바이브 코딩으로 만든 실험에서 오케스트레이션 실행(C)을
돌려 줘. 이 프로젝트에서 필요한 실행 방법과 대상 문제를 찾아
진행하고, 끝나면 결과 파일과 수정 내용을 함께 보여 줘.
리드가 locator를 실제로 불렀는지도 기록과 판정 결과에서
확인해 알려 줘. 내 결과가 예시와 조금 달라도 괜찮으니,
나온 기록을 기준으로 설명해 줘.
  • 위임한 뒤에는 .venv/bin/python judge.py를 실행해 만든 judgment.json의 evidence_quote와 changes.diff를 함께 확인합니다
  • 전자는 기록에서 인용한 근거이고, 후자는 최종 수정이 남은 파일입니다
📌 "내 결과가 예시와 조금 달라도 괜찮으니, 나온 기록을 기준으로 설명해 줘" — 이 문장이 예시에 맞춰 결과를 꾸미는 일을 막습니다
실행을 시킨 뒤 요약만 받지 말고, 리드가 locator를 실제로 불렀는지와 수정 결과를 기록에서 확인하도록 요청합니다.

세 실행 — 다음 행동을 정하는 주체

기준선 실행(A)   다음 행동: 한 에이전트
  질문 → 에이전트 1회 → 결과

워크플로 실행(B)  다음 행동: 파이썬 코드
  질문 → locator → 보고서 → fixer → 결과

오케스트레이션 실행(C)  다음 행동: 리드 모델
  질문 → 리드 모델: 판단 ─┬─ locator 선택 호출
                          └─ 직접 수정 → 결과
이 도식이 소단원 ⑧의 비교표를 읽는 틀입니다.

세 실행을 한꺼번에 돌릴 때

.venv/bin/python arms.py A,B,C
  • 첫 인수에 쉼표로 실행 이름을 나열합니다
  • 이미 result.json이 있는 실행은 러너가 건너뜁니다
  • 이 명령 뒤에는 각 runs/<실행 이름>-<인스턴스>/result.json이 남습니다
⚠️ 실행을 다시 하기 전에 기존 결과가 있는지 확인합니다 — 같은 파일을 덮어쓴 뒤 이전 기록과 비교하면, 무엇이 달라졌는지 알 수 없게 됩니다
이 건너뛰기 규칙이 소단원 ⑨에서 다루는 '재현이 안 되는 문제'의 첫 방어선입니다.

❓ 이해도 확인

Q1. B와 C의 차이는?
A1. 재료(문제·읽기 전용 locator)는 같고 조율 주체만 다르다. B는 코드가 반드시 fixer를 실행하고, C는 리드가 부를지 스스로 정한다.
Q2. 서브에이전트를 정의하면 분업이 일어난 것인가?
A2. 아니다. 리드가 실제로 불렀는지를 judgment.json의 evidence_quote와 세션 기록에서 확인해야 한다.
Q3. 러너가 기존 result.json을 건너뛰는 이유는?
A3. 덮어쓰면 이전 기록과 비교할 수 없어 무엇이 달라졌는지 알 수 없기 때문.
Q2가 이 소단원의 핵심 관찰 규율입니다.
