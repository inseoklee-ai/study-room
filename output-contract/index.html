답의 모양을
약속한다

자동화에 넘길 답은 문장이기 전에 인터페이스

답을 재려면 먼저 답이 어떤 모양이어야 하는지부터 계약해야 합니다. 이 소단원은 "JSON으로 답해 주세요"라는 희망과, 어떤 키·어떤 값·빠진 값은 어떻게 처리할지 정한 계약을 구분합니다. 그리고 그 계약을 검사하는 validator가 무엇을 재고 무엇을 못 재는지까지 봅니다.

1

형식을 약속하는 것과 내용을 보장하는 것

답은 어떤 모양이어야 하는가 — 먼저 계약한다

인터페이스 · 구조화 출력 계약 · 스키마
답을 재려면 먼저 답이 어떤 모양이어야 하는지 계약해야 합니다. 사람이 읽고 끝낸다면 자연스러운 문장이 먼저지만, 표에 저장하고 알림을 보내며 다른 프로그램 입력으로 넘긴다면 답은 인터페이스입니다.

📦 문장이기 전에 인터페이스

사람이 읽고 끝낸다면

자연스러운 문장이 먼저다. 사람은 애매한 표현도 짐작해서 읽는다.

자동화에 넘긴다면

표에 저장하고 알림을 보내며 다른 프로그램 입력으로 넘기면 답은 인터페이스다.

  • 필요한 것은 "JSON으로 답해 주세요"라는 희망이 아니다
  • 어떤 키 · 어떤 값 · 빠진 값은 어떻게 정한 계약 — 이것이 구조화 출력 계약
  • 스키마는 이 계약을 기계가 읽게 적는 방법
필드 · 값의 종류 · 필수 여부 · 빈값 표현을 정해 둔 것이 계약이다.
여기서 핵심 구분은 두 가지입니다. 하나는 소비자가 사람이냐 프로그램이냐, 다른 하나는 희망(부탁)이냐 계약(스키마)이냐. 프로그램은 같은 칸에 넣을 값을 판정해야 하므로 희망만으로는 부족합니다.

📝 계약이 없으면 — 값이 섞인다

회의록 행동 항목에서 "행동 항목·담당자·기한을 알려 주세요"만 요청하면:

답 A민수가 맡습니다
·
답 B담당자: 민수
·
답 C확인 필요
  • 사람은 짐작해도 프로그램은 같은 칸에 넣을 값을 판정 못 한다
  • 기한이 빠진 게 미확정인지 누락인지 모른다
답의 모양을 약속하는 것 = 이런 추측 비용을 결과를 쓰기 전에 줄이는 것.
같은 요청에도 표현이 제각각인 것은 모델이 나빠서가 아니라 계약이 없어서입니다. "확인 필요"가 담당자 칸에 들어오면 프로그램은 이것이 담당자 이름인지 상태 표시인지 구분할 수 없습니다.

🧩 스키마 — 계약을 기계가 읽게

{
  "type": "object",
  "required": ["items"],
  "properties": {
    "items": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["task", "owner", "due_date", "evidence"],
        "properties": {
          "task":     {"type": "string"},
          "owner":    {"type": ["string", "null"]},
          "due_date": {"type": ["string", "null"]},
          "evidence": {"type": "string"}
        }
      }
    }
  }
}
items는 반드시 있고 각 항목은 네 필드. 담당자·기한이 원문에 없으면 억지로 채우지 않고 null. evidence는 근거 문장.
owner와 due_date의 자료형이 문자열 또는 null인 점이 핵심입니다. 원문에 없는 값을 지어내지 말고 null로 두라는 계약이 자료형 안에 새겨져 있습니다. evidence는 그 항목의 근거가 된 원문 문장을 담습니다.

🔧 계약의 빈자리를 줄이는 네 가지

1필드명 — 어떤 키를 쓸지 못박는다 (task · owner · due_date · evidence)
2허용값 — 각 필드가 받는 값의 종류(자료형·필수 여부)를 정한다
3빈값 표현 — 원문에 없을 때 어떻게 나타낼지 정한다(예: null)
4예시 — 실제 답의 모양을 함께 보인다

실제 답의 모양

{"items":[{"task":"보고서 작성","owner":"민수","due_date":"금요일",
  "evidence":"민수가 금요일까지 보고서를 작성하기로 했다"}]}
필드명·허용값·빈값 표현·예시를 함께 주면 계약의 빈자리가 준다.
스키마만으로는 담기 어려운 뉘앙스가 예시로 채워집니다. 특히 빈값을 어떻게 표현하는지는 문장 설명과 예시가 어긋나면 결과가 흔들리므로, 예시를 계약의 일부로 다뤄야 합니다.
2

validator가 재는 경계

형식은 값싸게 잡지만, 사실은 재지 못한다

형식 vs 사실 · 스키마에 맞는 거짓말
validator는 결과가 규칙에 맞는지 기계적으로 검사하는 프로그램입니다. 이 파트의 핵심은 validator가 잡는 것과 못 잡는 것 사이에 뚜렷한 경계가 있다는 점, 그리고 그 경계를 넘는 "스키마에 맞는 거짓말"입니다.

✅ validator가 값싸게 잡는 것 — 형식

validator = 결과가 규칙에 맞는지 기계적으로 검사하는 프로그램. JSON 파서·validator가 잡는 형식 오류:

  • 쉼표 빠진 객체
  • 없는 필수 필드
  • 문자열 자리에 온 배열
  • 허용 안 된 추가 필드
  • task가 빈 문자열인지, owner가 문자열/null인지
자동화가 멈추는 형식 오류를 빠르고 값싸게 걸러 내며 재현 가능하다.
형식 검사의 장점은 값싸고 재현 가능하다는 것입니다. 같은 입력에 항상 같은 판정을 내리므로, 자동화 파이프라인이 도중에 멈추는 사고를 앞단에서 막아 줍니다.

⚠️ 그러나 validator가 못 재는 것 — 사실

  • evidence가 문자열이어도 그 문장이 회의록에 실제 있는지는 모른다
  • 인용이 주장을 뒷받침하는지, "금요일"이 이번 주인지 모른다
  • 담당자를 지어냈는지 모른다
스키마에 맞는 거짓말은
잘 포장된 틀린 답형식은 완벽히 지켰지만 내용이 사실과 다른 답
→ 원문 포함 검사·업무 규칙 검사·사람 검토처럼 내용에 맞는 별도 검사가 필요하다. 형식 준수와 사실 정확을 한 점수로 합치면 어느 약속이 깨졌는지도 사라진다.
이 슬라이드가 소단원의 심장입니다. 형식이 완벽한 답일수록 오히려 방심하기 쉽습니다. 형식 점수와 사실 점수를 반드시 분리해야, 실패했을 때 형식 계약이 깨진 것인지 사실이 틀린 것인지 가려낼 수 있습니다.
3

부탁과 강제의 차이

같은 "JSON으로" 요청도 보장 범위가 다르다

부탁 · JSON mode · Structured Outputs
출력 형식을 얻는 방법은 세 층위입니다. 프롬프트로 부탁하기, 파싱 가능한 JSON을 목표로 하는 JSON mode, 그리고 JSON Schema를 API에 전달해 강제하는 방식. 각각 무엇까지 보장하는지가 다릅니다.

🎚️ 세 방식 — 보장 범위와 적합한 곳

방식어떻게보장 범위적합
부탁프롬프트에 "JSON으로, 네 필드" + 예시유효 JSON·필수 필드·자료형을 보장 안 함탐색·사람이 읽을 초안
JSON mode파싱 가능한 JSON 객체 목표특정 스키마 일치까지는 보장 안 함호출 뒤 validator 검사·재시도 가능할 때
강제Structured Outputs / strict tool use — JSON Schema를 API에 전달지원 범위에서 필드·자료형·필수값 강제UI 폼·DB 기록·워크플로 분기 등 기계가 곧바로 소비
OpenAI는 JSON mode와 json_schema의 strict 계약을 구분한다(공식 문서).
세 방식은 보장 범위가 계단처럼 올라갑니다. 부탁은 아무것도 보장하지 않고, JSON mode는 파싱 가능성까지, 강제는 스키마 일치까지 보장합니다. 소비자가 기계면 강제 쪽으로, 사람이면 부탁 쪽으로 갑니다.

🧱 강제도 대신하지 못하는 것

  • 강제 스키마도 사실성·업무 규칙·거절/잘림 처리를 대신하지 않는다
  • 공급자의 지원 범위·실패 응답을 확인하고 소비자 쪽 validator를 남긴다

자연어 계약이 나을 때

사람이 읽고 판단하는 한 문단이면 자연어 계약이 낫다.

스키마가 나을 때

자동 실행이면 빈값·오류 경로까지 명시한 스키마가 낫다.

복잡한 스키마가 언제나 낫지는 않다. 계약이 길수록 지킬 조건도 늘어난다.
강제는 형식을 보장할 뿐 내용을 보장하지 않으므로, 소비자 쪽 validator를 없애면 안 됩니다. 또한 도구는 목적에 맞춰 고릅니다. 사람이 읽을 한 문단에 억지로 스키마를 씌우면 오히려 지킬 조건만 늘어납니다.
4

소비자를 거꾸로 확인하고, 예시도 계약이다

필드가 있다고 값이 유용한 것은 아니다

거꾸로 확인 · 경계 예시 · 소비 순서
형식 계약을 설계할 때는 소비자가 실제로 무엇을 하는지 거꾸로 짚어 봐야 합니다. 화면에 보여 주기만 하는 것과 일정 시스템으로 날짜를 보내는 것은 필요한 필드와 형식이 다릅니다.

🔁 소비자를 거꾸로 확인한다

화면에 보여 주기만

사람이 읽을 제목·근거 문장이 우선이다.

일정 시스템으로 보내기

due_date의 날짜 형식·시간대·미확정값 상태를 먼저 정한다.

  • 필드가 있다고 값이 유용한 게 아니다
  • 각 필드가 어느 다음 단계에서 쓰이는지 적어 보고, 안 쓰이는 필드는 뺀다
계약이 길수록 지킬 조건도 늘어난다 — 소비자가 쓰는 필드만 남긴다.
필드를 늘리는 것은 공짜가 아닙니다. 쓰이지 않는 필드도 모델이 채워야 하고, validator가 검사해야 하며, 틀릴 여지를 만듭니다. 소비자의 다음 단계에서 실제로 쓰이는 필드만 남기는 것이 계약을 지키기 쉽게 합니다.

🧾 예시도 계약이다 — 그리고 소비 순서

한 예시에서 없는 담당자를 확인 필요로, 다른 예시에선 null로 쓰면, 문장으로 null을 요구해도 결과가 흔들린다.

  • 긍정 예시 하나 + 빈값·거절·잘림 같은 경계 예시를 같은 형식으로 보인다
  • 그러면 validator 규칙과 모델이 따를 모양이 가까워진다

예시가 서로 어긋나면 문장 설명이 아무리 정확해도 결과가 흔들립니다. 소비 순서도 중요합니다. 잘린 응답을 파싱하려 하면 엉뚱한 오류가 나므로, 먼저 종료 사유를 확인하고 파싱한 뒤 스키마를 검사하고 마지막으로 내용을 검토합니다.

📌 이것만은 꼭 — 핵심 4문장

1자동화에 넘길 답은 문장이기 전에 인터페이스 — 필드·값·빈값을 정한 계약이 필요하다.
2validator는 형식을 값싸게 잡지만 사실은 못 잡는다 — 스키마에 맞는 거짓말이 있다.
3부탁·JSON mode·강제의 보장 범위가 다르다. 강제도 사실성·업무 규칙은 대신하지 않는다.
4소비자를 거꾸로 확인하고 예시도 계약으로 다룬다 — 쓰이는 필드만 남긴다.
📚 더 읽기 — OpenAI 공식 문서의 JSON mode와 Structured Outputs(json_schema strict) 구분.
2번이 이 소단원의 태도입니다. 형식 준수와 사실 정확을 한 점수로 합치지 말고 나눠서 재야, 실패했을 때 어느 약속이 깨졌는지 알 수 있습니다. 이 분리가 다음 소단원의 평가지표로 이어집니다.

✅ 정답 & 해설

A1. 답을 표에 저장·알림 발송·다른 프로그램 입력으로 넘겨 자동화가 소비할 때. 사람이 읽고 끝나면 문장이 먼저다.
A2. 형식: 쉼표 누락·없는 필수 필드·자료형 불일치. 사실: evidence가 원문에 실제 있는지, 담당자를 지어냈는지.
A3. 형식은 완벽히 지켰지만 내용이 틀린 답. 대응: 원문 포함 검사·업무 규칙 검사·사람 검토로 내용을 별도 검사.
A4. 부탁=보장 없음 · JSON mode=파싱 가능한 JSON까지(스키마 일치는 아님) · 강제=지원 범위에서 필드·자료형·필수값까지.
A5. 소비자가 각 필드로 실제 무엇을 하는지 짚어, 쓰이는 필드·필요한 형식만 남기는 것. 안 쓰이는 필드는 뺀다.
