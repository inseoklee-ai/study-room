1

테트리스에서 내 게임까지

1차 한 줄 요청 · 2차 규칙부터 설계

④ 실습
1차는 웹 채팅형 AI에서, 2차는 Day 4에 차린 작업대(개발 에이전트)에서 만듭니다.

🕹️ 1차 — "테트리스 만들어줘"

테트리스 만들어줘.

정말 이게 전부. 잠시 뒤 채팅 옆에 게임 미리보기가 뜨고 바로 플레이된다(대개 방향키·줄 삭제까지).

한 줄이 통하는 이유테트리스는 1984년부터 전 세계가 공유해 규칙이 이미 AI 안에 — "테트리스"라는 이름 자체가 규칙 명세서
요청이 통하고 안 통하고는 길이가 아니라 담긴 정보량이 가른다 — "테트리스"는 짧지만 규칙이 가득한 한 줄. 뒤에 만들 '내 게임'엔 공용 이름이 없어 규칙을 직접 적어 정보를 채워야 한다.
방향키가 안 먹으면 게임 화면을 한 번 클릭해 선택한 뒤 다시 누릅니다. 미리보기 없이 코드만 나오면 "바로 실행해서 볼 수 있게 해줘"라고 요청합니다.

🔍 관찰까지가 연습 · 한 번에 하나씩

겹코드에서 찾아볼 것
HTML게임판(<canvas>·격자)과 점수 표시가 어디에
CSS보드·블록 색, 배치 — 보통 한 문서의 <style> 태그
JS키 입력·블록 낙하·줄 삭제 — 보통 <script> 태그
플레이가 아니라 "어느 겹이 어디에 있는가"만 찾는다(코드를 다 이해할 필요 없음). 부가 기능은 한 번에 하나씩 재요청(미리보기·점수/레벨·일시정지·다시하기·색테마) — 더할 때마다 플레이해서 이전 기능이 안 망가졌나 함께 본다.
  • ⚠️ 같은 요청이라도 결과는 사람마다·실행마다 다르다(블록 색·조작감·코드 구성). 어떤 결과든 세 겹은 그대로 들어 있다 — AI의 비결정성과 프롬프트 영향력을 보는 관찰
이 게임은 대화 창 안에 있어 내 컴퓨터에 파일이 하나도 안 생깁니다 — 대화를 잃으면 게임도 사라집니다. 이 차이가 2차의 출발점입니다.

🎮 2차 — 방향이 반대, 규칙을 내가

  • 테트리스는 이름이 규칙 명세서였지만, 2차는 이름만으론 AI에게 안 통하는 게임 — 규칙을 내가 적는다. 도구도 바꾼다(채팅 → 작업대의 개발 에이전트, 파일이 내 컴퓨터에 남아야 이어서 고친다)

📐 게임의 최소 재료 셋 — 보이는 것(점수판·게임판·버튼)·상태(몇 점·진행/끝·이김/짐)·규칙(무엇을 하면 상태가 어떻게 바뀌나). 이 셋으로 나눠 적으면 AI에게 또렷이 전하고, 어긋났을 때 어느 부분인지 짚기 쉽다

보이는 것상태규칙
가위바위보점수판·버튼·결과이김/짐/무, 선택 강조내 선택 vs 무작위 판정, 3승 종료
두더지 잡기3×3 칸·점수·시간두더지 나온 칸무작위 칸 등장, 클릭 +1, 30초 종료
한 화면 크기 기준 — 각 칸이 한두 줄이면 오늘 적당. 어느 칸이 문단이 되면(레벨·저장·랭킹) 오늘보다 크니 규칙을 잘라 첫 판만.
한 화면에서 끝나고 클릭·키보드로 조작하는 작은 게임이면 충분합니다(가위바위보·숫자 맞히기·반응속도·두더지·카드 뒤집기 등, 목록에 없으면 더 좋음).

🔧 2차 요청문 — 규칙은 내가 적는다

새 폴더 my-game을 만들고, 그 안에 아래 게임을 만들어줘.

만들 게임: [예: 가위바위보 / 숫자 맞히기 / 내가 정한 게임]
규칙: [게임이 어떻게 진행되는지 2~3문장으로 직접 적기]
끝나는 조건: [예: 5판 승부 / 기회 10번 / 제한시간 30초]

파일은 index.html, styles.css, script.js 세 개로 나눠줘.
- 화면: [내 게임의 화면 요소]를 담아줘.
- 모바일에서도 조작 편한 크기로, [내 게임의 상태]가 색·문구로 보이게.
- 내가 적은 규칙 그대로 동작하고, 끝나는 조건이 되면 결과·다시하기 버튼.

규칙에 애매한 부분이 있으면 만들기 전에 나에게 물어봐.
완료 후 브라우저 확인 방법과 수정 체크리스트를 알려줘.
중요한 건 "세 파일로 나눠줘"가 아니라 화면·상태·규칙을 구체적으로 적었다는 것. 테트리스와 달리 이 규칙은 AI 안에 없으므로, AI에게 규칙까지 맡기면 결과가 이상해도 판정 기준이 없다.
브라우저 확인 — index.html을 열어(더블클릭) 이기고 지는 경우를 다 만들어 점수·문구·색이 바뀌는지, 연타로 꼬이지 않는지, 모바일 폭에서 편한지, 끝나는 조건·다시하기, Tab 키 이동·Console 오류까지 봅니다.

계획하고, 만들고, 다듬기

PRD 먼저 · 관찰하고 재요청

⑤ 루프
AI와 일하는 리듬은 한 방향이 아니라 루프입니다 — 계획을 맞추고 → 만들게 하고 → 관찰하고 → 다시 요청하고. 게임 앞뒤에 붙는 두 요령을 익힙니다.

📋 만들기 전에 PRD부터

  • 전문팀은 코드 전에 PRD(제품 요구사항 문서)를 쓴다 — "무엇을, 누구를 위해, 어떤 규칙으로"를 먼저 글로 못 박는다. 바이브 코딩엔 더 중요 — AI는 내 마지막 한 마디에 맞춰 움직여, 목표가 글로 고정 안 되면 대화가 길어질수록 방향이 흘러간다
  • 거창할 필요 없이 15~30분, 한 장 — 게임을 화면·상태·규칙으로 나눈 표가 PRD의 뼈대. 여기에 누가 플레이하나·예외 상황을 더한다
바로 코드를 쓰지 말고, 위 PRD대로 어떻게 만들지 계획을 먼저 알려줘.
- 어떤 순서로 만들지
- 내가 미리 정해줘야 할 것이 있는지
계획이 내 생각과 맞으면 "진행"이라고 할게. 그때 만들어줘.
이러면 AI가 내 요청을 어떻게 이해했는지 코드가 나오기 전에 확인 — 방향이 틀리면 문서 한 줄만 고치면 되지 수백 줄 코드를 되돌릴 필요가 없다. 💡 손으로 빨리 쓰는 힘은 AI가 가졌다. 남는 실력은 무엇을 만들지 또렷이 정의하는 힘.
이 방식을 스펙 주도 개발(spec-driven development)이라 부릅니다. PRD 초안도 AI와 함께 잡고 틀린 가정만 바로잡으면 됩니다.

🔁 관찰하고 재요청하기

[어디서] [무슨 문제가 있고], [어떻게 되면 좋겠다]재요청은 해법(CSS 속성)을 외워 말하는 게 아니라 — 관찰·기대를 평소 말로
  • "결과 문구가 무슨 뜻인지 알기 어려워. '이겼습니다/졌습니다'처럼 분명하게 바꿔줘"
  • "모바일에서 버튼이 좁아 누르기 불편해. 커지거나 줄바꿈되게 해줘"
  • "무승부인데 점수가 올라가. 이겼을 때만 오르게 해줘"
고쳐서 돌려주면 내가 말한 부분이 실제로 바뀌었는지 직접 플레이하거나 코드를 열어 확인 — 무작정 믿지 않는 이 습관이 핵심. "전체를 다시 만들어줘"보다 문제 부분만 짚어야 괜찮은 부분이 덜 흔들린다.
해법까지 지정할 필요 없습니다 — "모바일 간격" 정도로 말해도 AI가 알아듣습니다. 규칙이 안 전달되면 화면의 글, 글자가 잘리면 크기·배치, 게임이 안 끝나면 종료 조건을 손보게 요청합니다.

🔧 재지시 템플릿

지금 결과에서 [관찰한 문제]가 있어.

- 유지할 것: [마음에 드는 부분]
- 바꿀 것: [어떻게 되면 좋겠는지, 눈으로 확인 가능한 조건으로]
- 확인 방법: [브라우저에서 내가 해볼 행동]

수정 후 어떤 파일을 어떻게 바꿨는지 짧게 알려줘.
세 줄이 핵심 — 유지할 것·바꿀 것·확인 방법. "유지할 것"이 있어야 AI가 괜찮은 부분을 덜 건드리고, "확인 방법"이 있어야 내가 결과를 검증할 수 있다.
키보드 이동처럼 화면 구조·동작·표시가 함께 걸리는 문제는 한 곳만이 아니라 관련된 부분을 함께 봐 달라고 요청합니다.

웹에 올리고 링크 제출하기

GitHub Pages 배포 · 루브릭

⑥ 과제 + 프로젝트 제출
오늘 만든 게임은 아직 내 컴퓨터(또는 대화창) 안에만 있습니다. 누구나 링크만으로 열어볼 수 있게 만들어 그 링크를 제출합니다 — '나만 보는 결과물'이 '세상에 내보내는 서비스'로 바뀌는 첫걸음입니다.

🚀 GitHub Pages로 배포 — 바이브 코딩으로

HTML·CSS·JS를 무료로 웹에 올려 주는 서비스. 파일을 올리고 Pages를 켜면 https://내아이디.github.io/저장소이름/ 주소가 생겨 전 세계 누구나 접속. 준비물은 GitHub 계정 하나.

이 폴더의 게임을 GitHub Pages로 배포하고 싶어.
1. 이 폴더를 깃 저장소로 만들고, 내 GitHub에 새 공개 저장소로 올려줘.
2. GitHub Pages를 켜서 웹에서 열 수 있는 주소를 만들어줘.
3. 로그인·권한 확인처럼 내가 직접 눌러야 하는 단계는 멈추고 알려줘.
4. 배포가 끝나면 접속 주소를 알려주고, 잘 열리는지 확인 방법도.
⚠️ 배포엔 계정 로그인·권한 승인처럼 사람이 직접 해야 하는 단계가 섞여 있다 — AI가 그 대목에서 멈추고 안내하면 그 부분만 웹 화면에서 처리하고 다시 이어간다. 배포 직후 주소가 뜨기까지 1~2분.
배포도 바이브 코딩으로 합니다. 작업대(Day 4의 Claude Code)에서 게임 폴더를 열고 요청합니다.

✅ 제출 전 체크와 루브릭

제출 전 체크
새 창(시크릿)에서 열어도 게임이 뜬다 · 내 컴퓨터가 아니라 그 웹 주소에서 조작이 동작한다 · 휴대폰으로도 플레이된다 · 동료에게 보내도 열린다
학습목표평가기준
배운 내용이 잘 적용되었나HTML·CSS·JS가 적절하게 만들어졌는가
기획한 게임 로직 구현게임이 원하는 대로 흘러가는가
만든 게임 제출배포된 페이지에서 게임이 잘 동작하는가
제출물 = 배포된 게임 링크(예: https://내아이디.github.io/my-game/). 제출은 파일 또는 URL 중 하나로만, 제출 후 수정 불가 — 링크로 여는 게임이라 URL 제출이 이 과제에 맞다.
🤔 마무리 3문장 — ①웹 링크로 처음 열었을 때 내 컴퓨터에서 열 때와 뭐가 달랐나 ②배포 중 AI가 멈추고 나에게 넘긴 단계는 무엇이고 왜 사람이 해야 했나 ③딱 하나만 더한다면?

🎯 이 덱의 핵심 정리

개념한 문장
이름 = 명세서테트리스는 이름에 규칙이 담겨 한 줄로 되지만, 내 게임은 규칙을 직접
게임 최소 재료보이는 것·상태·규칙 — 한 화면 크기로 잘라 첫 판만
판정 기준규칙을 내가 정하니 AI가 바꿔치기했는지 판정할 수 있다
PRD 먼저코드 전에 계획을 맞춘다 — 문서 한 줄이 수백 줄 코드보다 싸다
재요청관찰·기대·유지할 것을 나눠 말하고 직접 확인
배포웹 링크로 — 사람이 할 단계(로그인)는 AI가 멈추고 넘긴다
이로써 대단원 2 중단원① 강 2 "웹페이지를 이루는 세 겹 & 게임 만들기"를 완주했습니다.

🎯 이해도 확인 질문

Q4. 재요청을 해법(CSS 속성)이 아니라 무엇으로 말해야 하나?

✅ 정답 & 해설

A1. 테트리스는 규칙이 이미 AI 안에 있어 이름이 명세서 역할을 하지만, 내 게임엔 공용 이름이 없어 규칙을 적어 정보를 채워야 AI가 만들 수 있다.
A2. 보이는 것·상태·규칙. 각 칸이 한두 줄이면 한 화면 크기로 적당, 문단이 되면(레벨·저장·랭킹) 오늘보다 커 잘라야 한다.
A3. AI가 내 요청을 어떻게 이해했는지 코드가 나오기 전에 확인 — 방향이 틀리면 문서 한 줄만 고치면 되지 수백 줄 코드를 되돌릴 필요가 없다.
A4. 관찰(어디서 무슨 문제)·기대(어떻게 되면 좋겠다)로. 해법을 사람이 추측해 지정하면 틀려도 AI가 따르니, 해법 고르기는 AI의 몫으로 남긴다.
A5. 계정 로그인·권한 승인은 본인 확인이 필요한 일이라 AI가 대신 못 한다 — 그 부분만 웹 화면에서 처리하고 다시 이어간다.
A5는 앞 강(작업대)의 "사람이 직접 해야 하는 단계에서 AI가 멈춘다"와 이어집니다.
