실제 벤치마크의
로컬 10문항 평가

직접 만든 하네스가 실제 문제에서 어떻게 동작하는지 확인합니다

여기서부터는 만든 하네스를 실행해 보는 단계입니다.

무엇을 재는가

  • 지금 재는 것은 모델의 성능이 아니라, 같은 모델을 쓰는 서로 다른 하네스 구성의 차이입니다
  • 고정한 10개 작업을 같은 방식으로 실행해 기준 성능(baseline)을 남기고, 이후 개선이 실제로 효과가 있었는지 비교할 자리를 만듭니다
  • Docker는 필요하지 않습니다 — 원본 컨테이너 대신 로컬 작업 폴더로 이식한 판(local-port)을 실행
📌 기준선이 없으면 "좋아졌다"를 말할 수 없습니다. 개선을 시도하기 전에 먼저 한 번 돌려 숫자를 남기는 것이 이 소단원의 목적
baseline은 비교의 출발점이 되는 첫 측정값입니다.

난이도는 원본 벤치마크의 메타데이터 분류입니다.

정확한 문항 목록과 원본 이름은 benchmark/tasks.json의 manifest에 있습니다.
2

준비와 첫 실행

--dry-run으로 먼저 확인

⑩ 로컬 10문항
실행 전에 원본 자료가 제대로 준비되었는지 확인합니다.

세 명령

uv run python -m harness_lab.benchmark_source --prepare

uv run python -m harness_lab.bench --name baseline \
  --provider openai --model gpt-4.1-mini --dry-run

uv run python -m harness_lab.bench --name baseline \
  --provider openai --model gpt-4.1-mini
1
--prepare — manifest의 커밋과 파일 SHA256을 확인하고 원본 자료를 내려받아 로컬 경로로 이식. 여기서 실패하면 이후 점수는 의미가 없습니다
2
--dry-run — 모델을 호출하지 않고 작업 목록·경로·설정만 점검. 오타나 준비 누락을 비용 없이 잡는 단계
3
본 실행 — 10개 작업을 순서대로 실행하고 jobs/baseline에 기록. --name은 나중에 비교할 때 쓰는 실험 이름이므로 의미 있게 붙입니다
📌 --name baseline처럼 무엇을 바꾼 실행인지 이름에 담으면 나중에 폴더만 봐도 구별됩니다 — baseline, steps60, ollama-qwen
실행 중 비용이 발생하는 것은 3단계뿐입니다.

시행(trial)의 단위

  • 작업 하나마다 새 작업 폴더를 복사해서 시작합니다 — 앞 작업이 남긴 파일이 다음 작업에 영향을 주지 않도록
  • 한 시행 = 준비된 작업 폴더 → 하네스 실행 → 원본 pytest 채점 → 기록. 이 네 단계가 모든 문항에서 동일
  • 기본 한도: 40 스텝, 에이전트 전체 300초, Python 도구 1회 실행 10초
한도값넘으면
스텝 수40step_limit으로 중단 → 미완료
에이전트 시간300초timeout으로 중단
Python 실행10초/회해당 도구 호출만 오류로 반환
⚠️ 한도 때문에 끝난 실행을 "모델이 못 푼 것"으로 기록하지 않습니다 — 한도 초과와 오답은 다른 원인이므로 나중에 한도를 바꾸는 실험의 근거가 됩니다
기본값은 run-metadata.json에 함께 저장되어 나중에 어떤 조건이었는지 확인할 수 있습니다.

남는 기록

파일내용
jobs/baseline/실행 결과 전체가 모이는 폴더
run-metadata.json제공자·모델·한도·실행 모드·시각 — 나중에 "무슨 조건으로 잰 숫자인가"에 답하는 파일
작업별 로그모델·도구 호출 기록, 채점 출력, 상태
📌 점수만 적어 두고 조건을 적지 않으면 비교가 불가능해집니다. run-metadata.json이 있기 때문에 한 달 뒤에도 같은 조건으로 재현을 시도할 수 있습니다
제출할 때도 이 메타데이터를 함께 냅니다.

내 에이전트를 끼워 넣기

--agent 로 교체하는 계약

⑩ 로컬 10문항
제공된 하네스 대신 직접 만든 구현을 평가에 연결할 수 있습니다.

교체 계약

uv run python -m harness_lab.bench --name mine \
  --agent my_agent:solve_task

async def solve_task(instruction, workspace, logs_dir, options):
    ...
    return {"status": "completed", "answer": text, "metrics": {...}}
인수의미
instruction작업 지시문
workspace이번 시행 전용 작업 폴더 경로
logs_dir기록을 남길 폴더
options한도·작업 디렉터리 등 실행 설정
📌 반환값은 status·answer·metrics — 이 세 가지만 맞추면 내부 구현이 무엇이든 같은 채점을 받습니다. 언어·구조가 달라도 계약만 지키면 비교 가능
⚠️ status: "completed"를 돌려준다고 점수가 되지 않습니다 — 점수는 원본 pytest가 산출물을 확인한 결과입니다
이 계약이 있기 때문에 ⑧에서 만든 자기 하네스를 그대로 평가에 붙일 수 있습니다.

❓ 이해도 확인

Q1. 이 평가를 돌리려면 Docker가 필요한가?
A1. 필요 없다. 원본 컨테이너 대신 로컬 작업 폴더로 이식한 local-port를 실행한다.
Q2. --dry-run은 무엇을 하나?
A2. 모델을 호출하지 않고 작업 목록·경로·설정만 점검한다. 오타와 준비 누락을 비용 없이 잡는 단계.
Q3. 왜 작업마다 폴더를 새로 복사하나?
A3. 앞 작업이 남긴 파일이 다음 작업에 영향을 주지 않게 하려고. 시행 단위를 동일하게 유지해야 비교할 수 있다.
Q1은 실습 시작 전에 가장 많이 나오는 질문입니다.
