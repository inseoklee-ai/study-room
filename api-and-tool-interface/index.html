API와 도구의 인터페이스

화면에는 "승인" 버튼 하나여도 프로그램에는 더 많은 정보가 필요합니다

어느 작업의 어떤 변경을 승인했는지 알아야 하고, 같은 승인이 두 번 들어왔을 때의 처리도 정해야 합니다.

인터페이스와 API

  • 인터페이스 — "무엇을 입력하면 어떤 결과가 돌아오며, 잘못된 요청은 어떻게 알려 주는가"에 대한 약속
  • API는 프로그램이 다른 기능을 호출할 때 사용하는 인터페이스 — 반드시 인터넷 주소를 뜻하지는 않습니다. CLI 내부에서 작업을 시작하는 함수를 호출하는 것도 입력과 반환값에 대한 계약이 필요합니다
이번 절은 세 연결을 모두 구현하는 단계가 아니라, INTERFACES.md에 책임과 예제를 적어 이후 AI가 서로 다른 가정으로 구현하지 않도록 준비하는 단계입니다.
1

서로 다른 세 가지 연결

이름이 비슷해도 책임이 다릅니다

⑥ 인터페이스
어댑터는 서로 다른 형태를 맞춰 주는 연결부입니다.

세 연결

연결호출하는 쪽 → 받는 쪽계약의 예
앱의 작업 인터페이스터미널·웹 화면 → 작업 처리부요청을 시작하고 작업 ID를 받기, 상태 조회, 변경 승인
모델 제공자 연결부하네스 → 모델 제공자대화와 도구 설명 전달, 응답과 도구 요청 해석
도구 인터페이스하네스 → 파일 읽기·쓰기·테스트경로와 내용을 받아 작업하고 결과 또는 오류 반환
  • 제공자마다 요청·응답의 세부 형태가 다를 수 있으므로 — 제공자별 연결부에서 차이를 처리하고 하네스에는 정한 형태로 돌려주도록 설계합니다
  • 모델 응답을 받았다고 파일이 바뀐 것은 아닙니다 — 하네스가 도구 요청을 확인하고 권한을 검사한 뒤 실제 도구를 실행해야 합니다
  • 연결부에서 정할 것 — 일반 답변과 도구 요청을 어떻게 구별할지, 도구 요청과 실행 결과를 어떤 ID로 연결할지, 여러 요청을 받았을 때 처리 순서
  • 지원하지 않는 응답이나 해석할 수 없는 입력을 받으면 오류로 알려야 하며 빈 답변으로 바꾸어 숨기지 않습니다
OpenAI와 Ollama에 같은 필드를 보내면 같은 기능이 동작한다고 가정하지 않고, 선택한 API의 공식 문서와 실제 응답으로 확인할 항목을 남깁니다.

호출 ID와 파싱 ≠ 실행 허가

  • 호출 ID는 도구 요청 한 건에 붙이는 이름표 — 모델이 read_text로 notes.txt를 읽어 달라는 요청을 call_a로 보냈다면, 하네스는 실행 결과가 그 요청에 대한 것임을 연결해 반환합니다. 두 파일을 읽으라는 요청에서 어느 내용이 어느 요청의 결과인지 섞이지 않게 하려는 목적
  • 이 이름은 설명용이며 실제 제공자가 요구하는 식별자와 반환 구조는 어댑터에서 맞춥니다
  • 파싱은 응답을 프로그램이 다룰 구조로 해석하는 과정 — 응답을 해석할 수 있다는 것과 실행해도 된다는 것은 다릅니다. 해석한 뒤에도 도구 이름, 인자의 종류, 경로와 권한을 검사해야 합니다
이 구분이 없으면 "모델이 요청했으니 실행한다"는 흐름이 되기 쉽습니다.
2

시작·조회·승인·결과의 약속

기다리는 동안에도 시작 여부를 알아야 합니다

⑥ 인터페이스
작업 시작과 완료 결과를 구별하면 CLI든 웹이든 같은 흐름을 표현할 수 있습니다.

네 동작의 계약

동작입력에서 정할 것출력에서 정할 것
작업 시작사용자 요청, 허용된 작업 폴더, 이어 갈 세션 여부작업 ID와 시작 상태
작업 조회작업 ID현재 상태, 진행 정보, 승인 대기 여부
승인 응답작업 ID, 승인 요청 ID, 허용 또는 거절반영 여부와 현재 상태
결과 확인작업 ID완료 결과 또는 종료 이유, 관련 실행 기록
  • 작업 ID는 실행 하나를 구별하는 이름표로 대화를 이어 가는 세션 ID와 역할이 다릅니다 — 하나로 합치려면 그 선택이 조회와 기록에 어떤 영향을 주는지 먼저 설명할 수 있어야 합니다
  • 결과가 아직 없다는 상태와 결과가 빈 문자열이라는 상태도 구별합니다. 진행 중이면 진행 중이라고, 없는 작업 ID라면 찾을 수 없다는 오류를
  • 실제 도구 실행이 실패했는데 모델이 친절한 문장을 작성했다는 이유만으로 전체 작업을 성공으로 표시하지 않도록 완료 기준도 연결합니다
함수 이름이나 필드 이름을 그대로 채택할 필요는 없으며, 아직 실행된 결과를 보여 주는 것도 아닙니다.

화면 선택에 맞춰 계약 연결

💻 CLI

터미널 입력을 읽는 코드가 작업 시작 함수를 호출하고 진행 정보를 글자로 출력. 승인 대기가 생기면 제안된 변경을 출력하고 입력을 대기 — 내부 함수를 쓴다는 이유로 입력 검사나 오류 계약이 없어지지 않습니다

🌐 로컬 웹

같은 동작을 HTTP에 연결 — 작업 시작·상태 조회·승인 응답을 각각 웹 경로에. CLI만 만들 학생이 이 웹 경로까지 구현할 필요는 없습니다

⚠️ 웹에서 버튼을 눌렀다는 사실과 서버가 요청을 받았다는 사실도 구별해야 합니다 — 통신이 끊겼을 때 화면이 무조건 작업 시작을 다시 보내면 같은 요청이 두 개 생길 수 있습니다. 재시도할 때 기존 작업을 조회할지 새 작업을 만들지 정하고 그 한계를 기록합니다
첫 설계부터 모든 통신 장애를 해결하려고 범위를 넓힐 필요는 없습니다.

승인과 도구 실행을 연결하는 정보

  • "승인됨"이라는 값 하나로는 부족합니다 — 사용자가 확인한 변경 내용과 실제로 실행할 변경 내용이 같아야 합니다. 승인 요청을 만들 때 대상 파일과 제안된 변경에 연결된 식별 정보를 남기고, 다른 변경으로 바뀌면 새 승인을 받도록
  • 멱등성(idempotency) — 같은 요청을 반복해도 의도한 효과가 추가로 생기지 않게 만드는 성질. 이름을 외우기보다 "이미 처리한 승인인지 확인하고 다시 실행하지 않는다"는 동작으로 이해하면 됩니다
  • 처리 완료 여부를 저장하는 시점과 실행 중 중단되는 경우까지 살펴야 하므로, 승인 ID만 추가했다고 모든 중복 문제가 해결된 것은 아닙니다
  • 승인 대기 중 파일을 사람이 수정했다면 이전 변경안을 그대로 덮어써도 되는지도 정합니다 — 처음에는 파일이 달라졌음을 발견하면 멈추고 새 변경안을 확인받는 방식으로
📌 구현하지 않은 충돌 처리까지 갖췄다고 쓰지 않고, 선택한 처리와 검증할 상황을 명세에 남깁니다
사용자가 승인 버튼을 두 번 눌렀다고 같은 작업을 두 번 실행해서는 안 됩니다.
3

도구의 입력·출력·오류

이름보다 허용하는 동작이 중요합니다

⑥ 인터페이스
첫 읽기 도구부터 계약을 작성해 봅니다.

파일 읽기 도구의 계약

구분정할 내용
입력작업 폴더를 기준으로 한 파일 경로, 허용할 파일 종류
성공 결과실제 읽은 내용과 그 내용을 식별할 경로
오류파일 없음, 읽기 불가, 허용 범위 밖 경로 등을 구별
제한너무 큰 파일을 거절할지 일부만 읽을지, 일부라면 그 사실을 어떻게 표시할지
정상 읽기  {"path": "notes.txt"}
        → {"ok": true, "path": "notes.txt", "text": "회의 자료"}

파일 없음  {"path": "missing.txt"}
        → {"ok": false, "error": {"code": "FILE_NOT_FOUND",
                                  "message": "파일을 찾을 수 없습니다."}}
  • 스키마는 데이터에 어떤 항목이 필요하고 값의 종류가 무엇인지 정한 규칙 — 경로가 허용 폴더 안인지의 판단은 별도의 실행 검사입니다
  • 정상 파일이 비어 있다면 성공 결과의 text가 빈 문자열일 수 있습니다 — 파일을 찾지 못한 오류와 구별되는지 예제로 확인
위 필드와 내용은 학생이 채택 여부를 판단할 설계 예이며 제공된 도구의 실제 반환값이 아닙니다. 이 동작은 파일을 바꾸지 않는다고 부작용 항목에 적고, 재시도하면 변경된 최신 내용을 읽을 수 있다는 점도 기록합니다.

설명과 실제 검사는 같은 계약을 따라야

⚠️ 설명에는 작업 폴더 안만 읽는다고 써 놓고 실제 함수는 어떤 경로든 읽게 두면 설명만으로 범위가 제한되지 않습니다. 언어의 타입 검사 역시 허용 경로 판단을 대신하지 않습니다
  • 오류 결과에는 프로그램이 구별할 수 있는 오류 종류와 사람이 이해할 설명을 함께 둘 수 있습니다
  • "파일 없음"을 빈 내용으로 반환하면 모델이 빈 파일을 읽었다고 오해할 수 있습니다
  • 모델 제공자 연결 실패, 도구 입력 오류, 사용자 승인 거절도 서로 다른 사건으로 남겨야 원인을 찾고 다음 행동을 정할 수 있습니다
선택한 플랫폼에 맞춰 작업 시작·조회·승인과 첫 읽기 도구의 계약을 정리해 줘.
정상 요청과 잘못된 요청 예를 넣고, 아직 결정이 필요한 부분은 남겨 줘.
코드는 아직 만들지 마.
정상 읽기, 없는 파일, 허용 범위 밖, 같은 승인 재전송을 사례로 적습니다. 승인 판단은 D06, 대화와 작업의 연결은 D07의 결정과 대조합니다.

양쪽 입장에서 읽기

📤 호출하는 쪽

입력만 보고 실행 대상을 알 수 있는지

📥 받는 쪽

결과만 보고 성공·실패·대기를 구별할 수 있는지

  • 세션 이어가기는 기존 세션에 새 작업을 연결하는 계약으로 적고 — 저장 기록이 없을 때도 복원했다고 응답하지 않도록 정합니다
  • 파일 변경·테스트 도구는 이어지는 구현 단계에 맞춰 변경 내용과 승인, 고정된 테스트 실행 범위 및 종료 코드·출력을 구체화합니다
  • 아직 결정하지 못한 사항은 AI가 임의로 기능을 늘리지 않도록 미결정으로 남깁니다
📌 예제 응답은 설계를 설명하는 가상 데이터이며 실행 증거가 아닙니다

❓ 이해도 확인

Q1. 파싱에 성공하면 실행해도 되나?
A1. 아니다. 해석과 실행 허가는 다르다. 해석 뒤에도 도구 이름·인자 종류·경로와 권한을 검사한다.
Q2. 승인 ID만 추가하면 중복 실행이 해결되나?
A2. 아니다. 처리 완료 여부를 저장하는 시점과 실행 중 중단되는 경우까지 살펴야 한다.
Q3. "파일 없음"을 빈 내용으로 반환하면?
A3. 모델이 빈 파일을 읽었다고 오해할 수 있다. 오류는 구별 가능한 종류로 반환한다.
