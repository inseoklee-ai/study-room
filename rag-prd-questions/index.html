바이브 코딩의 첫 문장
— PRD를 스스로에게 질문하기

에이전트가 빠르게 코드를 만든다는 사실이, 그 코드가 무엇을 증명해야 하는지를 대신 정하지 않습니다

에이전트에게 화면 구현을 요청하기 전에, 방문자가 답을 통해 무엇을 확인해야 하는지와 공개 자료로 답할 수 없는 질문을 받으면 화면이 어떤 상태로 남아야 하는지를 PRD에 먼저 정리해야 합니다.

화면이 보인다는 사실만으로 성공을 판정할 수 없습니다

바이브 코딩은 요구를 말하면 에이전트가 화면과 파일을 만들어 주는 경험에서 시작되지만, 그 요청이 무엇을 성공으로 볼지 비워 둔 채 길어지면 결과물은 빠르게 생겨도 검증할 대상이 사라집니다.

PRD는 에이전트에게 넘길 답안을 미리 쓰는 문서가 아니라
만들 사람 스스로가 아직 결정하지 못한 경계를 발견하는 질문지입니다
  • 공개 정보에 답해야 하는 제품에서는 특히 "답할 수 있는 질문"과 "답하지 않아야 하는 질문"이 같은 중요도를 가집니다
  • 요구를 받는 일보다 요구의 경계를 질문으로 정리하는 일이 먼저입니다
성공으로 읽힐 장면과 이번에 만들지 않을 기능을 문장으로 고정합니다.
1

스스로에게 묻는 여덟 질문

정답을 채우는 양식이 아니라 경계를 탐색하는 질문

② PRD 질문지
모두콘에서 확인한 답을 함께 보되, 그대로 베끼지 않습니다.

여덟 질문과 모두콘의 답

스스로에게 묻는 질문모두콘에서 확인할 답
① 누구의 어떤 불편을 다룹니까행사 정보를 찾는 방문자가 공개 사실에 접근하도록 돕습니다
② 사용자가 끝내 할 수 있어야 합니까질문 뒤 답변의 근거와 원문 출처를 확인합니다
③ 제품의 한 문장 목표는 무엇입니까소개와 RAG를 연결해 근거 있는 안내를 제공합니다
④ 이번 범위에서 하지 않을 일은 무엇입니까로그인과 전문 DB 검색을 포함하지 않습니다
⑤ 어떤 자료를 사실로 삼습니까공개 원문과 그 URL을 함께 보관합니다
⑥ 답하지 못할 때 어떤 행동을 합니까근거 부족을 드러내고 보수적으로 제한합니다
⑦ 사용자가 성공을 어떻게 알아봅니까스트리밍 답과 출처 칩, 판정 배지를 확인합니다
⑧ 어떤 관찰로 수용 여부를 판정합니까수용 기준의 질문과 화면 상태를 하나씩 확인합니다
아직 판단할 근거가 없는 칸에는 모른다고 적거나 [결정 필요]로 남기는 것이 답이며, 그 표식이 추가 조사나 에이전트의 확인 질문이 필요한 위치를 드러냅니다. 이 항목들은 에이전트 툴에게 인터뷰를 받으며 구체화하면 더 풍부하게 작성할 수 있습니다.

목표는 기능 목록이 아니라 사용자의 변화입니다

"모두콘 챗봇을 만든다"는 문장은 작업 목록으로는 쓸 수 있지만 제품 요구로는 충분하지 않습니다.

✍️ 사용자가 행사 소개를 읽고 역대 정보를 찾으며, 질문한 답의 출처를 열어 본다는 변화까지 적어야 소개 페이지·청크·검색·생성 UI가 하나의 목표를 향하게 됩니다
  • 모두콘 PRD의 목표에는 2018~2025 소개, 검색 단계를 공개하는 RAG, 출처 표시, 스트리밍, judge, 좋아요·싫어요 피드백, KST 상대시간 해석이 함께 들어갑니다
  • 각각은 화려한 부가 기능이 아니라 사용자가 답을 믿거나 유보할 근거를 제공하는 장치입니다
기능 하나하나를 "왜 넣는가"로 되물으면 목록이 정리됩니다.

비목표는 사과가 아니라 안전 장치입니다

비목표는 목표를 축소하는 사과가 아니라, 이번 구현에서 어떤 계약을 약속하지 않는지 선언하는 장치입니다.

비목표로그인
비목표전문 DB 검색
비목표다국어
비목표모바일 최적화
비목표서버 수집
  • 이렇게 적으면 에이전트는 사용자 계정이나 서버 동기화가 필요한 것처럼 구조를 부풀리지 않아도 됩니다
  • 정적 브라우저 앱이라는 선택과도 맞물립니다 — 공개 문서를 정적 파일로 두고 브라우저에서 검색하며 사용자의 로컬 Ollama를 호출하는 구조에서, 서버 측 계정 관리와 비공개 데이터 검색을 한 요청 안에 섞는 것은 목표의 확장이 아니라 다른 제품의 시작일 수 있습니다
비목표가 없으면 검색 범위도 무한히 넓어집니다.

수용 기준을 읽는 법

"좋은 챗봇"을 화면에서 확인할 문장으로

② PRD 질문지
해석이 갈리는 표현을 관찰 가능한 문장으로 바꾸는 장치입니다.

모두콘의 수용 기준

1소개에 출처를 표시할 것
2"모두콘이 뭐야?"라는 질문에 [ID] 근거를 가진 스트리밍 답변을 보일 것
3"내일 날씨"처럼 도메인 밖 질문에는 refusal=true로 제한할 것
4모든 답변에 판정 배지를 보일 것
  • 이 기준들은 모델이 말을 잘하는가만 묻지 않고, 근거의 존재와 제품 경계가 실제 UI까지 도착했는지를 묻습니다
기준 하나는 기능 하나를 추가하라는 명령이 아니라, 실패해도 사용자가 사라진 상태를 겪지 않게 하는 관찰 가능성의 약속입니다.

실패했을 때도 사라지지 않게

5API 키가 없어도 로컬 자기평가를 시도할 것
6판정에 실패해도 기존 UI를 무너뜨리지 않을 것
7상대시간 질문은 질문 시점의 KST로 해석할 것
8출처 칩에서 원문을 열 수 있을 것
9Ollama가 꺼졌을 때 배너와 재시도를 보일 것
10CORS 설정 뒤 github.io 환경에서도 동작할 것
⚠️ 여기서 로컬 judge는 같은 2B 모델이 답과 판정을 모두 다루므로 독립 평가가 아니며, 교육용의 거친 신호로 읽어야 합니다
이 한계를 숨기지 않고 기준 안에 적어 두는 것이 이 프로젝트의 태도입니다.

모두콘 버전 PRD 발췌

# 모두콘 안내 챗봇 PRD

## 목표
- 2018~2025 모두콘의 공개 소개 정보를 안내합니다.
- 공개 문서를 검색한 단계와 출처를 드러내는 RAG 답변을 제공합니다.
- 답변을 스트리밍으로 표시하고, judge 결과와 좋아요·싫어요 피드백을
  함께 기록할 수 있게 합니다.
- 상대시간이 들어간 질문은 KST 기준의 질문 시점 맥락을 사용합니다.

## 비목표
- 로그인과 사용자 계정 관리를 만들지 않습니다.
- 전문 데이터베이스 검색과 서버 수집을 만들지 않습니다.
- 다국어 지원과 모바일 최적화를 이번 범위에 포함하지 않습니다.

## 수용 기준
- 소개 정보에는 확인 가능한 출처가 표시됩니다.
- "모두콘이 뭐야?"에 [ID] 근거를 포함한 스트리밍 답변이 표시됩니다.
- "내일 날씨"에는 refusal=true로 도메인 밖 질문임을 드러냅니다.
- 모든 답변에는 판정 배지가 있으며, 판정 실패 뒤에도 UI가 유지됩니다.
- 출처 칩을 누르면 원문을 확인할 수 있고, Ollama가 꺼지면 배너와 재시도가 보입니다.
이 발췌는 형태를 따라 하기보다, 앞의 여덟 질문을 자기 도메인에 적용해 답을 채운 새 PRD를 만들기 위한 참고입니다. 행사명만 치환하지 말고 공개 자료의 범위와 도메인 밖 질문의 처리까지 함께 바꾸어야 합니다. "공개 문서", "도메인 밖", "판정 실패" 같은 표현은 구현 전에 예시 질문으로 검토해야 나중에 해석이 갈리지 않습니다.
3

자기 도메인의 PRD 초안 만들기

세 걸음

② PRD 질문지
모두콘을 기준점으로 삼되 자기 도메인으로 옮깁니다.

세 걸음과 [결정 필요]의 뜻

1안내하고 싶은 도메인을 하나 정합니다. 그 도메인은 자료를 공개 URL로 확인할 수 있어야 하며, 자료가 충분한지 확신할 수 없다면 그 불확실성 자체를 PRD의 조사 항목으로 남깁니다
2여덟 질문에 한 문장씩 답한 뒤, 답을 목표·비목표·수용 기준의 세 제목 아래로 재배열합니다 — 어느 답도 사라지지 않았는지 확인
3수용 기준은 실제로 입력할 질문과 관찰할 화면 상태를 포함한 문장으로 바꿉니다

❌ 검증 불가

"정확한 정보를 제공한다"

✅ 검증 가능

"소개 정보에 출처가 표시된다", "행사 밖 질문에는 근거 부족 또는 거절 상태가 드러난다"

📌 초안의 빈칸을 에이전트가 임의로 채우게 하지 말고 [결정 필요]를 남깁니다 — 빈칸은 실패가 아니라, 에이전트가 확인 질문을 해야 할 위치를 보이게 하는 관찰 표식
반대로 "자료가 없는 주제를 그럴듯하게 답하게 한다"는 문장은 RAG의 목표와 맞지 않습니다.

첫 대화에서 에이전트에게 맡길 범위

이 요청의 목적은 즉시 모든 파일을 생성하게 하는 것이 아니라, 에이전트가 PRD의 모순과 빠진 판정 기준을 먼저 찾아내게 하는 데 있습니다.

당신은 브라우저 기반 RAG 안내 챗봇의 제품 설계 검토자입니다.
아래 PRD 초안을 읽고 구현을 시작하지 말고 먼저 검토합니다.

도메인: [내 도메인]
목표: [사용자가 할 수 있어야 하는 일]
비목표: [이번 범위에서 하지 않을 일]
공개 자료 후보: [URL 또는 자료 종류]
수용 기준: [질문과 관찰 가능한 결과]

반드시 다음 순서로 답합니다.
1. 목표와 비목표가 충돌하거나 모호한 지점을 질문으로 제시합니다.
2. 공개 자료만으로 검증할 수 없는 수용 기준을 표시합니다.
3. 도메인 밖 질문, 근거 부족, 판정 실패의 처리 기준을 제안합니다.
4. 수정된 PRD 목차를 작성하되, 확인되지 않은 사실과 수치를 추가하지 않습니다.
5. 파일 생성이나 코드 작성은 제가 명시적으로 요청할 때까지 하지 않습니다.
🚧 마지막 문장은 속도를 늦추는 장식이 아니라 — 설계와 구현을 분리해 검토 결과가 코드에 의해 덮이지 않게 하는 경계입니다
에이전트의 제안이 목표를 넓힌다면 기능의 매력보다 이번 계약에 필요한가를 먼저 판단합니다. PRD의 문장 하나하나가 나중에 채점 문항이 됩니다.

❓ 이해도 확인

Q1. PRD는 무엇을 위한 문서인가?
A1. 에이전트에게 넘길 답안이 아니라 스스로가 아직 결정하지 못한 경계를 발견하는 질문지.
Q2. 아직 정하지 못한 칸은 어떻게 하나?
A2. 에이전트가 임의로 채우게 하지 말고 [결정 필요]를 남긴다 — 확인 질문이 필요한 위치를 보이게 하는 표식.
Q3. "정확한 정보를 제공한다"가 수용 기준으로 부적절한 이유는?
A3. 화면에서 관찰할 수 없다. "소개 정보에 출처가 표시된다"처럼 입력할 질문과 관찰할 화면 상태로 바꿔야 한다.
Q4. 첫 대화 프롬프트의 마지막 문장(코드 작성 금지)의 목적은?
A4. 설계와 구현을 분리해 검토 결과가 코드에 의해 덮이지 않게 하는 경계.
Q4가 이 소단원의 실전 핵심입니다.
