🗺️ 오늘의 흐름

  • 같은 PDF인데 왜 못 읽나 — 텍스트 레이어 vs 스캔 이미지, 그리고 OCR의 '광학'
  • OCR 도구의 계보와 PaddleOCR라는 조립 가능한 도구 상자
  • 조립 라인 네 정거장(전처리·검출·인식·레이아웃)과 각각이 깨지는 곳
  • 한국어가 특히 어려운 이유, 그리고 오류 전파
🎯 한 줄: OCR은 하나의 알고리즘이 아니라 여러 정거장을 잇는 파이프라인이고, 화살표가 한 방향이라 앞의 실수가 뒤에서 다른 얼굴로 번집니다.
지난 강의의 계약서 사고(0 하나 빠짐, 부가세 오인)가 이 파이프라인의 어디서 생겼는지를 이번에 정확히 짚습니다.

❓ "PDF인데 왜 AI가 못 읽나요"

PDF는 완전히 다른 두 물건을 같은 확장자로 담습니다.

텍스트 레이어 PDF

워드·한글 "PDF로 내보내기" → "이 위치·글꼴에 이 문자열" 정보가 그대로. 인식이 아니라 읽기 (파이썬 몇 줄)

스캔 이미지를 감싼 PDF

복합기·휴대폰 촬영 → 글자가 하나도 없음, 픽셀 덩어리뿐. 사람 눈엔 같아 보여도 프로그램엔 텍스트파일 vs 사진파일만큼 다름

🔑 문서 AI의 첫 갈림길: 이 문서는 글자를 꺼내면 되는가, 아니면 글자를 알아봐야 하는가. 뒤쪽에만 붙은 이름이 OCR.
텍스트 레이어가 있으면 광학이 필요 없고, 스캔 이미지면 광학이 필요합니다.

💡 OCR에서 가장 중요한 글자 — O (Optical)

Optical Character Recognition
광학 문자 인식
  • 파일에 저장된 문자 코드를 꺼내는 게 아니라, 종이에 반사된 빛의 밝고 어두움을 측정해 모양을 문자로 판정
  • 이 발상은 컴퓨터보다 먼저 나왔습니다 — 처음부터 "빛으로 종이를 본다"는 생각 위에
텍스트 레이어 PDF = 광학이 필요 없는 일 · 스캔 이미지 PDF = 광학이 필요한 일.
'광학'이라는 단어가 OCR의 본질입니다. 빛의 명암으로 모양을 읽어 문자를 판정하는 문제입니다.
1

OCR 도구는 어떻게 지금 모습이 되었나

입력 통제와 인식 알고리즘이 함께 변해온 계보

1912 → Tesseract → 문서 AI
OCR은 한 번에 등장한 발명이 아니라, 입력을 통제하는 방법과 인식 알고리즘이 함께 변해온 계보입니다.

📜 빛으로 글자를 읽으려는 백 년

  • 1912 푸르니에 달브 — 밝고 어두운 무늬를 소리로 바꿔 사람이 해석
  • 1920s 미리 만든 글자 모양과 포개는 템플릿 매칭
  • 1950~60s 전용 글꼴·정해진 서식으로 입력을 기계에 맞춤

Tesseract

HP 1980~90s 개발 → 2005 오픈소스 → 2006~2017 Google. 3세대까지 전통 엔진, 4부터 LSTM 신경망(글자 줄의 앞뒤 맥락). 지금도 명령줄 한 줄로 로컬 실행 → 클라우드에 안 보내는 가벼운 기준선.

Tesseract는 감사 추적이 필요하거나 문서를 밖으로 보낼 수 없을 때 유용한 로컬 기준선입니다.

🔧 인식 방식의 변화

변화기계가 한 일남은 한계
템플릿 매칭입력과 저장한 글자 모양 비교글꼴·크기·기울기에 약함
특징 기반획·모서리 특징으로 문자 분류글자 분리·규칙 설계 필요
LSTM 행 인식글자 줄의 맥락을 함께 사용표·구조는 별도 분석 필요
문서 AI글자·좌표·레이아웃·표를 함께 구조화모델·언어·배포에 따라 결과 달라짐
⚠️ 이름이 비슷해도 같은 종류가 아닙니다 — Tesseract=OCR 엔진, PaddleOCR=여러 모델·파이프라인을 묶은 도구 모음, PaddleOCR-VL=문서 구조를 생성하는 시각-언어 모델 계열.
도구 이름보다 "어떤 방식의 무엇인가"를 먼저 봐야 합니다.
2

PaddleOCR — 모델 하나가 아니라 도구 상자

조립 가능한 파이프라인

재현하려면 무엇을 남겨야 하나
Baidu가 자사 딥러닝 프레임워크 PaddlePaddle 생태계에서 공개한 오픈소스 OCR·문서 분석 프로젝트입니다.

🧰 PP-OCR의 기본 흐름 = 전통 OCR의 현대식 구현

1텍스트 탐지 — 글자가 있을 픽셀 영역 찾기 (초기 DB 계열 탐지기)
2방향 판별 — 잘라낸 글자 줄이 0°인지 180° 뒤집혔는지 교정
3텍스트 인식 — 줄 이미지를 문자열로 (CRNN → SVTR·CTC로 발전)
4결과 조립 — 문자열·점수·원본 좌표를 묶어 다음 단계로
🔑 "PaddleOCR을 썼다"만으로는 재현 불가 — 어떤 탐지/인식 모델, 어떤 언어 가중치, 어떤 버전인지까지 남겨야 합니다.
같은 저장소가 라이브러리·CLI·학습 코드·사전학습 가중치·파이프라인을 다 제공하기 때문입니다.

🌏 가중치 선택과 중간 결과

  • 최신이라는 이유만으로 아무 가중치나 X — 언어 지원 범위가 모델마다 다름
  • 이 수업 한국어 기준선 = 한국어를 명시 지원하는 PP-OCRv5 다국어 인식 모델
  • 실행 전 코딩 에이전트에게 모델명·버전·언어 설정을 run_manifest.json에 기록
🔑 이 구조의 장점 = 중간 결과를 볼 수 있다는 것. 영역을 못 찾았는지 / 찾았지만 잘못 읽었는지 / 읽은 걸 잘못 묶었는지를 단계별로 확인. 단, 표 병합·의미는 기본 OCR로 안 됨 → 레이아웃 분석기·문서 VLM이 이어짐.
중간 결과를 나눠 볼 수 있다는 점이 감사와 디버깅에서 결정적입니다.

조립 라인의 네 정거장

각 정거장은 자기 일만 하고 다음으로 넘긴다

전처리 · 검출 · 인식 · 레이아웃
통제되지 않은 문서를 읽으려면 문제를 잘게 쪼개야 했고, 그래서 OCR은 여러 단계를 잇는 파이프라인이 되었습니다.

🏭 전통 OCR의 조립 라인

정거장마다 다루는 대상이 바뀝니다. 픽셀에서 시작해 구조로 끝납니다.

화살표는 한 방향입니다. 뒤 정거장은 앞 정거장의 판단을 되돌릴 수 없습니다.
이 그림은 순차형 파이프라인을 단순화한 것입니다. 모든 현대 문서 AI가 한 방향은 아니며, 여러 단계를 함께 학습하거나 언어 후처리로 앞 판단을 다시 조정하는 통합형도 있습니다.

🧽 1번 — 전처리 (원본 → 정리된 이미지)

  • 기울기 보정 — 1도만 삐뚤어도 A4 폭 210mm를 가로지르며 줄이 3.7mm 어긋남(본문 한 줄 높이). 각도별로 돌려 가로 검은 픽셀 대비가 최대인 각을 찾음
  • 이진화 — 픽셀을 흑/백으로 확정. 오츠(1979)는 페이지 전체에 한 경계값 → 반사 구역 글자가 통째로 사라짐 → 실무는 적응형(작은 창별 경계값)
  • 잡음 제거 — 세게 지우면 가는 획도 사라짐. 마침표가 사라지면 1.5 → 15 (열 배!)
⚠️ 눈에 안 띄지만 실무 실패의 상당 부분이 여기서 시작. 전처리가 지운 획은 존재한 적 없는 획이 되고, 이후 어느 단계에서도 복구되지 않습니다.
deskew·binarization·denoise. 전처리는 조용하지만 파이프라인 전체의 성패를 좌우합니다.

🔲 2번 — 검출 (이미지 → 좌표 목록)

  • 옛날: 검은 픽셀을 가로·세로로 투영해 줄·단어 공백을 찾음(깨끗한 문서엔 훌륭)
  • 문제: 문서엔 글자만 있는 게 아님 — 표 테두리·도장·밑줄·로고가 검출기를 혼란에
  • 딥러닝 CNN: 작은 필터를 이미지 위로 밀며 국소 무늬 → 조합. 위치 무관하게 반응. DBNet은 경계값 자체를 학습해 이진화를 신경망 안으로
🔑 성격은 그대로 — 이 단계가 놓친 영역은 다음 단계에 아예 전달되지 않습니다. 검출되지 않은 글자는 인식기 입장에서 존재하지 않습니다.
CNN = 합성곱 신경망. 필터가 이미지 어디에 있든 같은 무늬를 찾으므로 글자가 어느 위치에 있어도 잘 잡아냅니다.

🔤 3번 — 인식 (조각 → 문자열)

  • 1세대 템플릿 매칭 — 정답 모양을 겹쳐 제일 잘 맞는 것
  • 2세대 특징 추출 — 고리 개수·세로획 수로 분류(8=고리 2, 6=1, 1=0). 글꼴 바뀌어도 특징은 유지 → Tesseract가 이 계열에서 출발
  • 3세대 CRNN(2015) — 글자를 하나씩 자르는 걸 포기(손글씨·이탤릭·한글 경계가 어려움). 줄 통째로 받아 CNN→양방향 LSTM→CTC. 글자 경계를 학습 문제 안으로 흡수
🔑 인식기가 보는 세계는 여전히 좁습니다 — 주어지는 건 잘려 나온 줄 하나뿐. 그 줄이 표 헤더인지 각주인지, 왼쪽 칸 항목명이 뭔지 모릅니다(알 필요 없게 설계).
CTC는 어느 픽셀 구간이 어느 글자인지 사람이 안 알려줘도 전체 문자열이 맞도록 학습시키는 손실 함수입니다.

🧩 4번 — 레이아웃 분석 · 파싱 (문자열 → 구조)

흩어진 문자열을 표의 행·열, 제목·본문으로 묶는 일 = 파싱. 가장 자주 무너지는 정거장.

(x=112, y=340) "계약 금액"      (x=318, y=340) "32,000,000"
(x=112, y=372) "부가세"          (x=318, y=372) "3,200,000"

기계에겐 숫자와 문자열이 흩어져 있을 뿐 → "y 비슷=같은 행, x 비슷=같은 열" 규칙을 세워야 하는데, 조금만 복잡해지면 무너집니다.

셀 병합 / 선 없는 표 / 다단 조판 / 페이지 넘는 표 — 모두 이 규칙을 깹니다. 표를 HTML로 생성하거나 행·열로 쪼갠 뒤 병합 셀 되붙이기 연구가 있지만, 병합 셀 있는 복잡한 표는 여전히 어렵습니다.
단순한 표와 복잡한 표 사이의 벤치마크 점수 차이가 좀처럼 좁혀지지 않습니다.

품목수량단가

열을 가르는 선이 없어 여백 폭만으로 경계를 추정 → 자릿수가 달라지면 흔들립니다.

사람에겐 즉시 두 쌍의 항목-값이 보이지만, 기계에겐 흩어진 숫자와 문자열뿐입니다. 병합과 무선(無線) 표가 대표적 붕괴 지점입니다.
4

한국어의 어려움, 그리고 오류 전파

작은 오차가 성질을 바꾸며 번진다

왜 되짚을 수 있어야 하나
지금까지의 어려움 위에 한글 특유의 어려움이 얹히고, 조립 라인 구조 자체가 오류를 키웁니다.

🇰🇷 한국어 문서가 특히 어려운 이유

  • ① 글자 종류가 압도적 — 알파벳은 100여 개, 한글은 조합 음절만 11,172자(초성19×중성21×종성28). 미학습 음절을 만날 확률이 높음
  • ② 글자 안에 구조 — 강/캉, 믿/민은 획 하나 차이. 전처리가 가는 획 하나 지우면 다른 글자. 자모 배치도 음절마다 다름(가·그·광)
  • ③ 한자·영문이 섞임 — 법률·공문서의 한자, 기술 문서의 영문 약어·단위
+ 분야별: 진료 기록 손글씨, 관공서 붉은 직인(획 가림), 팩스 저해상도(<200dpi), 휴대폰 촬영 원근 왜곡.
가로세로로 균일하게 잘라 특징을 뽑는 방식이 알파벳만큼 잘 통하지 않는 이유입니다.

📉 오류는 사라지지 않고 쌓입니다

각 단계 성공률 98%라면
0.98 × 0.98 × 0.98 × 0.98 ≈ 92.2%
100장 중 약 8장이 어긋남 — 실측이 아니라 '작은 실패가 연쇄된다'는 조건부 모형
  • 더 곤란한 건 오류가 성질을 바꾸며 번진다는 것 — 앞 단계는 자기가 틀렸다는 걸 뒤에 알려주지 않음
  • 이 현상이 오류 전파(error propagation)
실제 파이프라인은 단계마다 측정 단위가 다르고 오류끼리 상관이 있어 정확도를 무조건 곱할 순 없습니다. 여기서 보이려는 건 연쇄 가능성입니다.

레이아웃금액 칸에 부가세가 들어감
최종 결과만 보는 사람은 최초 원인이 "기울기 1도"였다는 것을 알 수 없습니다.
🔑 그래서 중간 산출물(좌표·신뢰도)을 남기는 일이 실무 핵심 기술. 감사 추적이 필요한 업무에서 전통 OCR이 선택되는 이유 — 틀리지 않아서가 아니라 왜 틀렸는지 되짚을 수 있어서.
처음의 1도가 마지막엔 "계약 금액이 3,200,000원"이라는 결과로 나타납니다. 원인은 결과만 봐서는 보이지 않습니다.

🧵 글자는 다 있는데 관계가 사라질 수 있습니다

  • OCR이 글자를 정확히 읽었다고 문서를 이해한 건 아님
  • 결과를 평평한 텍스트 한 줄로 내보내면 제목·본문·표의 공간 관계가 사라짐 → "계약 금액"과 "부가세"가 다 있어도 어느 숫자가 어느 항목인지 틀릴 수 있음
🔑 그렇다고 OCR이 항상 좌표를 버리는 건 아닙니다. Tesseract의 TSV·hOCR, PaddleOCR의 원시 결과는 좌표를 함께 보존. 좌표를 버리는 것은 OCR이 아니라 '평탄화된 출력 방식'입니다. 감사 가능한 시스템은 페이지 번호·상자 좌표·원문 조각을 함께 남깁니다.
즉 "OCR이 좌표를 못 준다"가 아니라, 좌표를 버리도록 출력을 설계하면 관계가 사라진다는 뜻입니다.

📌 이것만은 꼭 — 핵심 7문장

1PDF는 텍스트 레이어 vs 스캔 이미지 두 종류 — 뒤쪽만 OCR(광학)이 필요
2OCR = 문자 코드가 아니라 빛의 명암으로 모양을 문자로 판정
3조립 라인 네 정거장: 전처리 → 검출 → 인식 → 레이아웃 (픽셀 → 구조)
4전처리가 지운 획은 복구 불가, 검출이 놓친 글자는 인식기에 존재하지 않음
5인식기는 줄 하나만 봄 → 표 구조·항목값 잇기는 레이아웃의 몫(가장 자주 붕괴)
6화살표가 한 방향 → 오류 전파, 성질을 바꾸며 번짐(1도 → 부가세 오배치)
7전통 OCR의 값어치 = 중간 산출물로 왜 틀렸는지 되짚을 수 있음 (좌표 보존은 출력 설계의 문제)
지난 강의의 계약서 사고가 '레이아웃 정거장의 붕괴 + 오류 전파'였음을 이제 정확히 말할 수 있습니다.

✅ 정답 & 해설

A1. PDF가 텍스트 레이어(문자열 내장)와 스캔 이미지(픽셀뿐) 두 종류라서. 첫 갈림길 = 글자를 꺼내면 되나 vs 알아봐야 하나.
A2. 파일 속 문자 코드가 아니라 빛의 밝고 어두움을 측정해 모양을 문자로 판정. 텍스트 레이어 PDF는 광학이 필요 없는 '읽기'.
A3. 전처리·검출·인식·레이아웃. 화살표가 한 방향이라 앞 단계의 실수를 뒤가 복구 못 함(오류 전파).
A4. 세게 지우면 가는 획도 사라져 다른 글자가 됨. 예: 마침표가 사라지면 1.5 → 15(열 배). 지운 획은 복구 불가.
A5. 셀 병합 · 선 없는 표 · 다단 조판 · 페이지 넘는 표 — "y 비슷=행, x 비슷=열" 규칙이 깨짐.
A6. 앞의 작은 오류가 성질을 바꾸며 뒤로 번지는 것. 전통 OCR은 중간 산출물(좌표·신뢰도)로 어디서 틀렸는지 되짚을 수 있어서 선택됨.
A6의 "틀리지 않아서가 아니라 되짚을 수 있어서"가 핵심입니다.
