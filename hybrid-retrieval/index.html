가까운 청크를 고릅니다
— 하이브리드 검색

검색의 품질은 답변의 상한선입니다

검색은 답변을 대신하는 판단이 아니라, 답변에게 읽힐 자료의 순서를 만드는 판단입니다.

코사인 유사도는 방향이 비슷한지를 읽습니다

L2 정규화된 질문 벡터와 문서 벡터의 내적은 코사인 유사도로 해석할 수 있습니다. 문장 길이보다 의미 표현의 관계를 중심으로 후보를 정렬합니다.

  • 사용자가 참가 절차를 자신의 표현으로 묻더라도, 문서가 다른 낱말로 설명했다면 벡터 검색은 두 문장의 의미적 근접성을 포착할 가능성이 있습니다
  • 점수 하나를 진실의 확률처럼 읽어서는 안 됩니다. 점수는 현재 모델·현재 청크·현재 질문 사이의 상대적 근접성일 뿐입니다
  • 어느 문서가 답을 실제로 뒷받침하는지는 프롬프트의 근거 원칙과 출처 표시로 다시 제한해야 합니다
🔎 발표 신청처럼 고유명사와 절차가 결합된 질문에서 상위 청크가 의미로만 닿고 정확한 표기를 담지 않았다면, 답변 생성 전에 검색 결과를 멈춰 검토해야 합니다
그럴듯한 첫 결과를 그대로 신뢰하는 대신, 고유명사를 놓친 이유와 이를 보충할 검색 경로를 설명할 수 있어야 합니다. 이 검토가 검색 점수의 순위와 답변 근거의 충분성을 구분하는 출발점입니다.
1

BM25가 정확한 표기를 보충합니다

서로 다른 실패 방식을 가진 두 관찰 장치

⑤ 하이브리드 검색
두 검색기를 경쟁시키기보다 배치하는 것이 핵심입니다.

벡터 상위 10개 + 미중복 BM25 5개

의미 검색은 표현이 달라도 가까운 문장을 찾는 데 유용하지만, 특정 행사명·고유명사·정확한 ID·코드처럼 글자 자체가 중요한 질문에서는 필요한 청크를 충분히 높게 올리지 못할 수 있습니다.

검색 방식무엇을 잡는가놓치는가보조
vector표현이 달라도 가까운 의미고유명사와 정확한 표기코사인 상위 10개
BM25질문과 문서의 낱말 일치다른 표현의 같은 뜻미중복 상위 5개
🎯 두 검색기를 경쟁시키기보다 — 서로 다른 실패 방식을 가진 두 관찰 장치로 배치하는 것이 하이브리드 검색의 핵심
BM25는 질문 낱말이 문서에 어떻게 나타나는지를 반영하므로, 의미가 비슷하지만 표기가 다른 청크와 정확한 표기가 들어 있는 청크를 함께 검토하게 합니다.

점수의 단위는 맞추되 근거의 강도와 혼동하지 않습니다

BM25 원점수는 문서 집합과 질문에 따라 크기가 달라지므로, 해당 검색에서 가장 큰 BM25 점수로 나누어 0~1 범위로 정규화합니다.

  • 이 값은 벡터 점수와 완전히 같은 의미가 아니라, UI에서 서로 다른 검색 방법의 상대 강도를 읽기 쉽게 만드는 표기입니다
  • 결과 객체에는 vector 또는 bm25 방법과 점수를 함께 보존하여, 사용자가 어떤 근거 청크가 어떤 경로로 들어왔는지 확인할 수 있어야 합니다
  • 중복을 제거하지 않으면 같은 사실이 여러 번 반복되어 모델이 특정 청크를 과대평가할 수 있고, BM25 후보를 전부 버리면 고유명사와 코드성 표기에 약한 검색기로 되돌아갑니다
🧭 정규화와 방법 표시는 정답을 보장하는 장치가 아니라 — 검색 판단을 검토 가능한 기록으로 바꾸는 장치
화면의 칩에 method와 score를 함께 남기는 이유가 여기 있습니다.
2

0.55는 문을 닫는 수치가 아닙니다

말투를 바꾸는 신호

⑤ 하이브리드 검색
임계값은 숨은 자동 판정기가 아니라 답변의 태도를 조절하는 공개된 경계여야 합니다.

차단도 아니고 평소의 자신감도 아닙니다

❌ 결과를 차단하면

사용자는 검색이 어떻게 실패했는지 알 수 없습니다

❌ 평소처럼 생성하면

약한 연관을 사실처럼 말할 위험이 커집니다

1근거 청크를 버리지 않고 프롬프트를 보수적으로 바꿉니다
2UI에는 약한 근거 경고를 표시합니다
3모델은 근거 안의 내용만 짧게 답하고 자료에 없는 부분은 없다고 말해야 합니다
4사용자는 검색된 근거 청크의 수와 방식, 점수를 열어 판단할 수 있어야 합니다
📌 0.55는 보편적 정답이 아니라 — 현재 코퍼스와 모델 조합에서 불확실성을 드러내는 운영 규칙
임계값을 코드 안에 숨기지 않고 화면에 드러내는 것이 이 설계의 태도입니다.

기대와 다를 때 — 역순으로 점검합니다

top-1이 기대와 다를 때 임계값 조정으로 덮지 않고 결과 목록을 역순으로 점검합니다.

  • 두 방법의 칩과 점수를 함께 남겨 판단의 경로를 화면에 보이게 합니다
  • BM25는 벡터 점수를 더 높은 점수로 바꾸는 마법이 아니라, 질문에 들어 있던 정확한 낱말을 다른 기준으로 찾은 결과임을 구분해야 합니다
  • 표기가 들어 있는 청크가 들어왔더라도 그 청크의 URL과 section을 열어 질문에 답할 사실이 실제로 있는지 확인한 뒤에만 답변 근거로 넘깁니다
이 습관이 소단원 ④의 스팟체크와 같은 형태입니다.

실습 4 — 검색 합성을 계약으로 요구합니다

"관련 문서를 찾아 달라"로는 부족합니다

⑤ 하이브리드 검색
결과 순서·중복 처리·점수 표기·약한 근거 처리까지 계약으로 적습니다.

반환 타입에 method를 포함시킵니다

모두콘 벡터스토어 검색 함수를 구현합니다. 질문 임베딩과 문서 벡터의
코사인 유사도로 상위 10개를 고른 뒤, 중복되지 않은 BM25 상위 5개를 추가합니다.
BM25 점수는 해당 검색의 최고 점수로 나누어 0~1로 정규화합니다.
반환값마다 chunk, score, method("vector" 또는 "bm25")를 보존하고,
최고 유사도가 0.55보다 낮으면 결과를 버리지 말고 약한 근거 상태를 반환합니다.
  • 에이전트가 코사인 결과만 반환하거나 BM25 결과를 덮어써도 화면은 그럴듯하게 보일 수 있으므로, 반환 타입에 chunk, score, method를 요구합니다
  • 구현 뒤 행사 소개·참가 방법 질문으로 vector와 BM25 칩이 어떻게 섞이는지 확인하고, 문서 밖 질문에서는 약한 근거 경고와 보수화된 프롬프트가 함께 작동하는지 읽습니다
🎯 검색 결과는 모델에게 넘길 비공개 배열이 아니라 — 사용자가 답의 출발점을 검토할 수 있게 해야 하는 관찰 기록
이 관점이 소단원 ⑦의 판정 배지와 이어집니다.

더 깊이 갈 사람을 위한 길

1top-k를 5, 10, 20으로 바꿔 같은 질문의 상위 근거와 답변 길이가 어떻게 달라지는지 기록
2약한 근거 임계 0.55를 낮추거나 높여 답변의 보수성이 함께 움직이는지 관찰
3두 검색의 순위를 하나로 합치는 Reciprocal Rank Fusion 같은 융합 방법을 조사해 지금의 정규화 방식과 비교

❓ 이해도 확인

Q1. 벡터 검색과 BM25를 함께 쓰는 이유는?
A1. 벡터는 표현이 달라도 가까운 의미를 잡지만 고유명사·정확한 표기를 놓친다. 둘은 서로 다른 실패 방식을 가진 두 관찰 장치다.
Q2. BM25 점수를 0~1로 정규화하는 이유와 한계는?
A2. 원점수 크기가 질문·문서 집합에 따라 달라져서. 다만 벡터 점수와 같은 의미가 아니며, UI에서 상대 강도를 읽기 쉽게 하는 표기일 뿐이다.
Q3. 최고 유사도 0.55 미만에서 하는 일은?
A3. 결과를 버리지 않고 프롬프트를 보수화 + UI에 약한 근거 경고. 모델은 근거 안의 내용만 짧게 답하고 없는 것은 없다고 말한다.
Q4. top-1이 기대와 다를 때 순서는?
A4. ① 같은 임베딩 경로인지 ② 청크의 사실 경계 ③ BM25가 표기를 보충했는지. 임계값 조정은 마지막이다.
Q4는 소단원 ④에서 배운 역순 점검의 반복입니다.
