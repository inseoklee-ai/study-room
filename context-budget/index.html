컨텍스트 관리 — 창의 크기가 아니라 예산의 배분입니다

문맥 창이 크면 한 번에 읽을 수 있는 기록은 늘어납니다. 그러나 창이 넓다는 사실만으로 지금의 과업에 필요한 정보가 눈앞에 놓이지는 않습니다.

중요한 단서가 위쪽으로 밀려 묻힙니다

긴 실행에서는 명령 결과, 오류 메시지, 파일 내용, 중간 판단이 계속 쌓입니다. 처음에는 유용했던 단서도 새 관측이 이어지면 대화의 위쪽으로 밀려나 찾기 어려워집니다.

🎯 컨텍스트 관리는 이때 다음 행동에 필요한 관측과 저장소 구조를 골라 다시 보여 줍니다
문맥을 다루는 일은 창의 크기를 비교하는 일이 아니라
정해진 토큰 예산 안에 무엇을 넣고, 빠진 정보는 어디에서 다시 찾을지 정하는 일
  • 같은 크기의 창이라도 무엇으로 채우는지에 따라 다음 행동의 질은 달라집니다
Anthropic도 문맥을 단순한 저장 공간이 아니라 매 요청에서 제한된 입력 예산을 배분하는 대상으로 설명합니다(공식 문서 — 설계 원칙이며 특정 요약 정책의 성능을 보증하지 않습니다).

관측을 고르는 방식도 결과를 바꿉니다

SWE-agent · repo map · RepoCoder

④ 컨텍스트 관리
세 근거를 조건과 함께 봅니다.

최근 다섯 개 18.0% vs 전체 이력 15.0%

SWE-agent 연구진은 SWE-bench Lite에서 최근 다섯 개 관측은 자세히 남기고 과거 관측은 축약하는 조건을 전체 이력 조건과 비교했습니다.

조건결과
최근 5개 자세히 + 과거 축약18.0%
전체 이력15.0% (3.0%p 낮음)
  • 이 대조 사례가 보여 주는 것 — 같은 과업과 모델에서도 관측을 고르는 방식이 결과를 바꾼다
  • 다만 다섯 개가 모든 과업에서 항상 최적이라는 의미로 해석해서는 안 됩니다
출처: Yang et al., NeurIPS 2024, arXiv:2405.15793. SWE-bench Lite ablation의 해당 모델·과업 조건이며 다른 모델과 과업으로 일반화하지 않습니다.

파일 전부 대신 구조를 먼저 — repo map

큰 저장소의 파일을 전부 넣으면 문맥 창이 곧 넘칩니다. Aider의 repo map은 대신 저장소의 뼈대만 담은 기호 지도를 만듭니다.

반대 근거 — 먼저 버리는 것이 답은 아닙니다

RAG vs long-context

④ 컨텍스트 관리
검색이나 요약 재진입이 항상 정확도를 높이지는 않습니다.

예산이 충분하면 long-context가 앞섰습니다

RAG와 long-context를 비교한 연구는 예산이 충분할 때 long-context가 평균 성능에서 일관되게 RAG보다 높았고, RAG의 장점은 비용이라고 보고했습니다.

따라서 문맥이 넘칠 때
먼저 정보를 버리는 것이 답은 아닙니다

같은 자리에서 판단할 것 ①

충분한 예산에서 원문 전체가 필요한 과업인가

같은 자리에서 판단할 것 ②

비용을 낮추기 위해 선택과 압축을 할 과업인가

  • 최근 관측 유지, 과거 관측 축약, repo map, 검색 재진입, 서브에이전트의 격리 문맥은 모두 무조건 줄이는 방법이 아니라 — 비용과 정확도가 만나는 경계를 찾는 방법입니다
출처: Li et al., EMNLP 2024 Industry, arXiv:2407.16833. 충분한 자원 조건의 평균 성능 비교이며 과업별 비용과 품질 경계를 대신 판정하지 않습니다.

상태서브에이전트는 맡은 좁은 문맥에서 작업하고, 결과만 메인 대화에 돌려줍니다에이전트별 대화 문맥과 실행 단계가 분리되어 기록됩니다
대표 행동조사를 맡긴 서브에이전트의 결과를 받아 메인 대화가 다음 행동을 정합니다에이전트별 steps 상한을 두어 한 대화가 끝없이 관측을 쌓지 않게 합니다
권한 경계서브에이전트가 쓸 도구와 승인 동작은 해당 설정과 실행 기록에서 확인에이전트별 도구 설정과 단계 상한은 설정 파일 및 실행 기록에서 확인
1차 근거공식 서브에이전트 문서 · 설정 파일 · 실행 기록공식 설정 문서 · 에이전트 설정 파일 · 실행 기록
한계격리된 결과가 메인 대화로 돌아오므로 전달 결과의 충분성을 과업마다 검토단계 상한은 관련 문맥을 골라 넣는 규칙이 아니므로 검색과 요약의 품질을 별도 확인
문서와 설정은 공개 경계를 설명하며 설치 버전과 실제 권한 설정을 대신하지 않습니다(Anthropic 공식 문서; OpenCode 공식 문서 — 에이전트별 설정과 steps 제한은 버전별 문서와 실제 실행 기록을 함께 확인해야 합니다).

실행 기록으로 확인할 세 가지

1요약이 틀린 단서를 버렸는지
2repo map이 필요한 파일을 놓쳤는지
3서브에이전트 결과가 메인 대화에 충분히 돌아왔는지
🧪 실험 — 같은 모델과 같은 과업에서 전체 이력과 요약 뒤 검색 재진입을 비교합니다. 컨텍스트 관리를 같게 두고 성공 여부 · 사용 토큰 · 다시 찾은 정보가 원문과 맞는지를 기록하면, 어느 조건에서 요약이 도움이 되고 어느 조건에서 원문이 필요한지 확인할 수 있습니다
이번 실행에서 버린 정보 중에는 다음 과업에서 다시 쓸 경험도 있습니다 — 그래서 다음 소단원이 경험·스킬 축적입니다.

Q1. 컨텍스트 관리를 한 문장으로?
A1. 창의 크기 비교가 아니라 정해진 토큰 예산에 무엇을 넣고, 빠진 정보는 어디서 다시 찾을지 정하는 일.
Q2. SWE-agent의 18.0% vs 15.0%이 말하는 것과 말하지 않는 것은?
A2. 말하는 것 — 관측을 고르는 방식이 결과를 바꾼다. 말하지 않는 것 — "다섯 개가 항상 최적".
Q3. "문맥이 넘치면 먼저 버린다"가 왜 답이 아닌가?
A3. 예산이 충분하면 long-context가 평균 성능에서 일관되게 RAG보다 높았고 RAG의 장점은 비용이었다. 원문이 필요한 과업인지 비용을 낮출 과업인지 같은 자리에서 판단한다.
Q4. opencode의 steps 상한의 한계는?
A4. 관측 무한 축적은 막지만 관련 문맥을 골라 넣는 규칙은 아니다. 검색과 요약의 품질은 별도로 확인해야 한다.
