이번에는 자신에게 필요한 과업 하나를 골라, 공통 실습에서 무엇을 가져오고 무엇을 바꿀지 직접 결정해 보겠습니다.

입력과 결과가 보이는 과업

'내 업무를 자동화한다'는 시작할 곳이 너무 많습니다

⑭ 자기 과업
실제 자료 하나를 펼쳐 두고 "이 자료로 어떤 결과를 받고 싶은가"부터 생각하면 일이 구체적으로 보입니다.

출발점으로 삼을 세 예

과업넣을 자료받고 싶은 결과업무 기준의 예
학습 피드백문제, 학습자의 답안, 교사의 평가 기준답안의 근거를 짚은 강점·보완점·다음 연습정답이 맞는 것과 풀이에서 이해가 드러나는 것을 구분
변경 안내문변경 기록, 기능 설명, 기존 안내문사용자가 이해할 수 있는 안내 초안내부 작업명을 사용자에게 보이는 변화로 설명
주간 운영 보고업무 기록이나 운영 통계확인된 성과와 다음 조치완료의 정의, 집계 단위, 보고 대상에 맞는 강조점
📌 표의 기준은 연습을 위한 예입니다. 자신의 팀이 사용하는 기준이 있다면 그것을 가져오고, 아직 없다면 결과를 읽을 사람의 관점에서 초안을 정해 보세요
  • AI와 이야기해도 좋지만 — 자료를 보지 않고 추천받은 '멋진 자동화 아이디어'보다 자신이 실제로 읽고 판단할 수 있는 자료에서 시작하세요. 결과가 적절한지 본인이 확인할 수 있어야 다음 수정도 선택할 수 있습니다
여기서는 학습 피드백 사례 하나를 함께 설계합니다. 이 사례를 따라가거나 자신이 선택한 과업으로 바꾸면 됩니다.

학습 피드백의 작은 설계

문제: 8, 10, 12의 평균을 구하고 계산 방법을 설명하세요.
학습자의 답안: 10입니다.
  • 숫자 10은 맞습니다. 하지만 문제는 계산 방법도 설명하도록 요청했고 답안에는 그 설명이 없습니다
  • "평균의 개념을 정확히 이해하고 있군요"라고 하면 답안에서 확인하지 못한 이해까지 추정한 것. 반대로 "평균을 이해하지 못했습니다"도 근거가 부족합니다 — 설명을 쓰지 않은 이유는 이 답안만으로 알 수 없기 때문
답안에서 확인되는 성취를 구체적으로 짚습니다. 정답 여부와 풀이 설명을
구분합니다. 풀이가 없으면 이해 여부를 단정하지 않고, 학습자가 자신의
계산을 설명할 다음 질문을 제안합니다.
평균을 10이라고 답한 것은 맞습니다. 다만 답안에 계산 과정이 없어 어떤
방법으로 구했는지는 아직 확인할 수 없어요. 세 수를 어떻게 사용해 10을
얻었는지 식이나 문장으로 설명해 볼까요?
🎯 강사가 재사용하고 싶은 지식은 '이 학생의 정답은 10'이 아니라 — 정답과 설명을 구분해 피드백하는 기준. 앞에서 TASK-102의 분류 결과 대신 완료 조건을 Skill에 남긴 것과 같은 생각
이 기준은 강사가 정했다고 가정한 연습용 설정입니다.

작은 설계를 적습니다

설계 항목이번 사례의 선택
실제 입력문제 문장과 학습자 답안 한 건
원하는 결과답안의 근거를 포함한 피드백과 다음 연습 질문
확인할 기준맞는 정답을 인정하고, 없는 풀이를 상상하지 않으며, 다음 설명을 유도하는지
그대로 쓸 것참고 문서를 읽고, 결과와 원자료를 대조하고, 새 입력에서 다시 확인하는 작업 방식
바꿀 것주간 기록을 문제·답안으로, 팀 보고 규칙을 피드백 기준으로, 보고서 결과를 피드백 문장으로
📌 완성된 긴 기획서가 필요한 것은 아닙니다 — 입력 한 건, 원하는 결과, 본인이 확인할 기준, 가져올 부분과 바꿀 부분이 드러나면 AI와 구체적인 작업을 시작할 수 있습니다
여러분의 과업도 이 정도로 적어 봅니다.

바꿀 위치를 구분하기

데이터 · 업무 지식 · 실행 기능

⑭ 자기 과업
공통 실습에는 서로 다른 세 종류의 내용이 함께 있었습니다.

세 종류

바꾸는 내용공통 예제에서 살펴볼 곳자기 과업에서의 선택
데이터 — 이번에 처리할 사실data/week-one.json의 업무 기록실제 문제·답안이나 변경 기록. 다음 학생의 답안을 받으면 이 부분이 바뀝니다
업무 지식 — 해석하고 표현할 기준team-weekly-report/references/team-rules.md정답과 풀이를 구분하는 기준, 교사가 원하는 말투, 적절한 피드백 예시. 여러 학생에게 반복 적용할 내용이라면 Skill과 참고 자료에
실행 기능 — 자료를 읽거나 계산하는 동작weekly_records_server.py의 get_weekly_records답안이 로컬 파일에 있고 앱이 읽을 수 있다면 새 MCP 서버를 추가할 필요는 없습니다. 다른 서비스에 있고 읽을 수 없다면 가져오는 기능과 연결을 따로
⚠️ Skill에 "답안을 읽으세요"라고 쓰는 것만으로 접근 기능이 생기지는 않습니다
  • 이 구분은 문제가 생겼을 때도 도움 — 자료는 정확히 읽었는데 '풀이가 없어도 이해했다'고 판단하면 기준과 판단 과정을, 엉뚱한 학생의 답안을 읽었다면 입력 선택이나 조회 기능부터
  • 공통 서버의 이름만 바꾸고 문제·답안을 week-one이라 부르면 의미가 어색해집니다 — 새로 만들기로 했다면 '어느 주의 기록인가' 대신 '어느 답안인가'가 필요할 수 있습니다. 파일 읽기와 입력 검증의 원리는 활용하되 업무 기록용 함수가 새 과업에도 그대로 맞는지 확인
수동 수정에서도 먼저 필요한 기능을 정하고, 그 기능에 해당하는 부분을 바꿉니다.

AI와 필요한 부분만 만들기

이 예제를 학습 피드백 작업에 맞춰 바꾸고 싶어.
답안과 평가 기준을 보고, 그대로 쓸 부분과 바꿀 부분부터 같이 정리해 줘.
  • 함수명과 JSON 구조, 모든 처리 순서를 처음부터 긴 명령에 넣을 필요는 없습니다 — AI의 제안을 읽으며 자신의 입력과 결과에 맞는지를 판단하는 일이 중요
  • AI가 "답안을 읽는 MCP부터 새로 만들겠습니다"라고 했다면 — 지금 호스트의 파일 읽기로 같은 입력을 가져올 수 있는지 생각. 이미 읽을 수 있다면 피드백 기준을 적용한 결과부터 확인할 수 있습니다. 반대로 새 서비스의 자료를 반복해 읽는 것이 핵심이라면 조회 도구를 준비하는 것이 자연스럽습니다
  • Skill을 만든다면 team-weekly-report는 원본으로 남겨 두고 별도의 과업 Skill을(예: learning-feedback) — 이름과 설명만 바꾸는 데서 끝내지 말고 제품팀의 완료·위험 규칙이 남아 있지는 않은지 살펴보세요
  • 참고 자료도 필요에 따라 — 기준이 짧아 본문에 담긴다면 빈 참고 파일을 만들 이유가 없습니다. 여러 과목을 지원하려고 자료를 늘리는 일은 실제로 그 과목을 다룰 때
정한 기준으로 피드백을 한번 만들어 줘.
어떤 답안과 기준을 사용했는지도 알려 줘.
새 MCP 서버를 실제로 추가했다면 앞의 호스트 연결 절 방법으로 등록하고 도구의 입력과 반환값을 확인합니다. 로컬 파일 읽기로 진행했다면 그 경로를 기록하면 됩니다.

결과의 한 문장에서 원인 찾기

"절대로 틀리지 마세요"를 추가하기 전에

⑭ 자기 과업
AI가 다음과 같이 썼다고 가정해 봅시다 — "평균의 개념을 정확히 이해했고 계산 과정도 잘 설명했어요."

어느 부분이 근거인가

  • 정답 10은 있지만 계산 과정은 없습니다 — '과정도 잘 설명했다'는 부분은 원자료와 맞지 않습니다
  • 곧바로 Skill에 "절대로 틀리지 마세요"를 추가하기보다 사용한 입력과 기준을 확인합니다 — 다른 예시 답안을 읽었다면 자료를 고르는 곳을, 기준이 전달되지 않았다면 기준 파일의 접근 경로나 안내를, 기준도 읽었는데 없는 설명을 덧붙였다면 정답과 설명을 구분하도록 한 기준을 실제로 어떻게 적용했는지
답안에는 계산 과정이 없는데 결과에는 잘 설명했다고 되어 있어.
어디서 이런 판단이 나왔는지 확인하고 고칠 부분을 제안해 줘.
🔍 제안을 받은 뒤 원자료나 작업 기록의 어떤 부분이 그 설명을 뒷받침하는지 확인하세요 — "Skill이 짧아서 그렇다"처럼 길이만으로 설명한다면 어떤 기준이 빠졌거나 전달되지 않았는지 더 구체적으로 물을 수 있습니다. 필요한 것은 실제 문제를 해결하는 수정
수정한 뒤에는 같은 답안으로 다시 확인합니다. 처음부터 다음 학생의 답안으로 바꾸면 결과 차이가 수정 때문인지 입력이 달라졌기 때문인지 구분하기 어렵습니다.

이번에는 풀이가 포함된 답안

8 + 10 + 12 = 30이고, 수가 세 개이므로 30을 3으로 나누면 평균은 10입니다.
  • 이 답안에는 합을 구하고 개수로 나누는 과정이 실제로 드러납니다 — 이번에는 그 과정을 근거로 설명의 강점을 짚을 수 있어야 합니다
  • 앞의 문제를 고치려고 "항상 풀이가 없다고 말하라"는 식의 규칙을 넣었다면 이 답안에서 문제가 드러납니다
고치려는 기준과 특정 입력의 답을 구분하는 것은
자기 과업에서도 같습니다
  • 처음 결과부터 적절했다면 수정할 오류를 억지로 찾을 필요는 없습니다 — 어떤 문장이 어떤 근거와 맞았는지 기록하고 다른 입력에서도 기준이 유지되는지 확인하면 됩니다
  • 한 번 잘된 결과는 그 입력에서 확인한 성과입니다. 더 다양한 상황에서도 적절한지는 다음 확인의 질문으로 남겨 둡니다
같은 답안에서 확인을 마쳤다면 이번에는 풀이가 포함된 다른 답안을 넣어 볼 수 있습니다.

상황에 맞는 선택

자신의 과업 상황앞에서 배운 내용의 활용
필요한 자료가 실습 폴더에 있음호스트의 파일 읽기와 Skill로 결과를 만들고 근거를 확인
자료가 Google Sheets에 모여 있음인증과 읽기 연결로 자료를 가져온 뒤 기준 적용
같은 집계·그래프를 반복 실행Colab 셀에 계산을 남기고 입력과 실행 결과를 함께 확인
별도 시스템의 기능을 여러 AI 앱에서필요한 기능을 구현하고 MCP로 제공하는 구조 검토
  • 새 연결을 썼다면 반환된 원자료부터 확인 — 시트를 읽었다는 메시지만 보고 피드백을 믿기보다 내가 고른 답안이 맞는지 먼저. Colab으로 집계했다면 숫자의 입력 범위와 실행한 셀을 함께
  • 보고 기준이 바뀌는 문제와 계산할 데이터를 잘못 고르는 문제를 나누어 볼 수 있습니다
  • 공통 실습의 weekly-records 호출 기록은 그대로 남겨 둡니다 — 자기 과업에 새 서버를 만들어야만 공통 실습이 인정되는 것은 아닙니다. 필요한 연결을 선택하고 그 이유를 설명해 보세요
평균 문제 답안 하나에 피드백을 쓰는 작업이라면 로컬 파일에서 읽어도 충분합니다.
