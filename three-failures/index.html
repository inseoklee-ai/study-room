말하는 모델이 행동하는 에이전트가 될 때 — 도구 호출의 작동 모델

언어 모델은 본래 다음에 올 텍스트를 생성할 뿐입니다. 조회 도구에 연결되는 순간 세계를 관찰하고 바꾸는 에이전트가 되지만, 그 연결은 과업의 완성이 아니라 새로운 판단 연쇄의 시작입니다. 이 소단원은 그 연쇄가 어긋나는 세 순간과, 요청·실행이 오가는 한 바퀴의 작동 모델을 세웁니다.

세 파트를 지나면 도구 호출을 마법이 아니라 요청·검증·실행·반환이 도는 하나의 실행 구조로 보게 됩니다. 그리고 그 구조 안에서 실패가 어느 층에서 생기는지 낱말로 가려 쓸 수 있게 됩니다.
1

말하는 모델이 행동하는 에이전트로

도구를 잇는 일은 완성이 아니라 판단 연쇄의 시작

잘못 고름 · 잘못 읽음 · 같은 실수 반복
언어 모델은 부산 창고에 재고가 몇 개 남았는지 알 길이 없습니다. 조회 도구를 호출할 수 있게 연결되는 순간 모델은 세계를 관찰하고 바꾸는 에이전트로 거듭납니다. 그러나 그 연결 가운데 하나만 어긋나도 답은 그럴듯하지만 쓸 수 없게 됩니다.

🔗 도구에 연결되면 세 가지를 스스로 해야 한다

고객이 지정한 창고의 재고를 묻는 상황에서 모델이 밟아야 하는 판단의 연쇄.

1조회 도구를 스스로 골라야 한다 — 무엇을 부를지 모델이 정한다
2올바른 상품 코드·창고 코드를 채워야 한다 — 인자를 정확히 쓴다
3돌아온 수량을 질문 조건에 맞게 해석해야 한다 — 결과를 근거로 읽는다
이 연결 가운데 하나만 어긋나도 답은 그럴듯하지만 쓸 수 없게 된다.
도구를 잇는 일은 과업의 완성이 아니라 새로운 판단 연쇄의 시작입니다. 세 단계는 각각 뒤에서 볼 세 실패 순간과 그대로 짝을 이룹니다.

⚠️ 어긋나는 세 순간

1도구를 잘못 고르는 순간 — 재고를 확인해야 하는데 주문 조회 도구를 고르거나, 읽기 요청에 변경 도구를 고르면 이후 문장이 자연스러워도 근거가 달라진다
2결과를 잘못 읽는 순간 — 반환값의 수량·시각·창고 식별자를 놓치면 실제 조회를 했어도 다른 사실을 답한다
3같은 실수를 반복하는 순간 — 실패한 호출과 그 이유를 남기고 판정하지 않으면 비슷한 요청에 같은 인자를 다시 보낸다
도구 설계의 질문 = "모델이 도구를 가졌는가"가 아니라 "이 세 순간을 어느 경계에서 알아차리고 막는가".
세 실패는 모델이 도구를 못 써서가 아니라, 선택·해석·기록의 경계가 설계되지 않아 생깁니다. 뒤에서 이 세 순간이 서로 다른 층의 병임을 확인합니다.
2

요청과 실행이 오가는 한 바퀴

모델은 도구를 직접 실행하지 않는다

하네스 · 다섯 단계 · trace
모델이 하는 일은 사용할 도구 이름과 인자를 담은 요청 문장을 쓰는 일뿐입니다. 그 문장을 받아 실제 실행을 이끄는 주체가 하네스입니다. 이 파트는 그 한 바퀴가 어떻게 도는지 단계와 실제 기록으로 봅니다.

🧰 하네스 — 모델과 도구 사이의 실행 장치

모델은 도구를 직접 실행하지 않는다. 모델이 쓴 요청 문장을 받아 실제 실행을 이끄는 주체가 하네스다.

하네스 = 요청된 도구를 검증·실행하고 결과를 돌려주는 사이클의 집행자.
실무에선 시스템 지시·권한·실행 환경까지 묶은 전체를 하네스라 부르기도 합니다. 그 넓은 뜻은 「최소 하네스」편에서 여섯 설계 지점으로 분해하고, 여기서는 실행을 이어 주는 연결 장치로 좁혀 이해합니다.

🐎 어원 — 수레에 채우는 마구

  • 하네스의 어원은 말이 끄는 수레에 채우는 마구
  • 마구는 말의 힘을 그대로 놓아두지 않고 수레와 연결해 힘이 실제 일이 되게 한다
  • 소프트웨어의 테스트 하네스도 같은 계보 — 공통점은 동력 그 자체가 아니라 동력을 실제 일로 바꾸는 연결 장치
모델이 다음 토큰을 고르는 엔진이라면
하네스는 그 선택이 바깥 세계의 조회와 이어지게 하는
차체·연결부
어원을 잡아 두면 하네스가 왜 성능의 주체가 아니라 연결의 주체인지 분명해집니다. 힘은 말에게 있고, 마구는 그 힘이 실제로 수레를 끌게 만드는 장치일 뿐입니다.

🔁 한 바퀴의 다섯 단계

1앱이 도구 정의를 요청에 포함한다
2모델이 호출 요청 JSON을 생성한다 (여기선 요청만)
3하네스·앱이 검증·실행한다
4결과를 모델 입력으로 반환한다
5모델이 근거로 답을 완성한다 (연쇄 호출: 결과 뒤 다시 ②로)
모델이 "재고가 있는가"만 보고 지어내지 않도록, 실행 결과가 답변의 근거로 돌아오는 구조다.
하네스가 결과를 전달하지 않거나 모델이 무시하면 도구는 연결돼 있어도 판단에 쓰이지 않습니다. 그래서 호출 로그는 개발 기록이 아니라, 답이 어떤 관찰을 거쳤는지 확인하는 증거입니다.

🧾 한 번의 재고 조회가 남긴 실행 기록

로컬 재고 조회 도구 1개만 연결, qwen3.5:2b · 온도 0으로 한 바퀴.

[1] 모델의 요청:
    get_inventory(sku='A-17', warehouse_id='BUSAN-02')

[2] 하네스의 실행 결과:
    {"sku": "A-17", "warehouse_id": "BUSAN-02",
     "available_quantity": 7,
     "checked_at": "2026-08-27T01:55:00+09:00"}

[3] 결과를 읽은 최종 답:
    승인된 창고(BUSAN-02)에서 상품 A-17의
    현재 가용 재고는 7개입니다.
[1] 요청 · [2] 실행 결과 · [3] 근거로 완성한 답 — 세 자리가 그대로 세 실패의 자리다.
이 기록은 요청과 실행이 오가는 한 바퀴를 그대로 보여 줍니다. 모델은 [1]에서 이름과 인자만 쓰고, 하네스가 [2]를 채우며, 모델이 [2]를 근거로 [3]을 완성합니다. 다음 장에서 이 세 자리에 세 실패를 겹칩니다.

📍 기록 위에 겹친 세 실패 지점

실패자리어긋나는 방식
도구를 잘못 고름[1] 이전도구 설명을 읽고 선택하는 자리 — 이름이 비슷한 도구가 여럿이거나 설명이 목적·경계를 안 밝히면 잘못된 요청
결과를 잘못 읽음[2]→[3]available_quantity 7과 warehouse_id BUSAN-02 조건을 함께 안 읽으면 다른 창고 재고처럼 답한다
같은 실수 반복한 바퀴 뒤오류 응답·거절된 인자·이미 확인한 결과를 남겨 다음 요청에 반영 안 하면 순환은 학습 없는 반복
첫 실패는 [1]보다 앞, 도구를 고르는 자리에서 이미 시작된다.
둘째 실패의 핵심은 수량과 창고 식별자를 함께 읽어야 한다는 점입니다. 셋째 실패는 한 바퀴 안이 아니라 바퀴와 바퀴 사이, 즉 기록을 남기고 판정하지 않을 때 생깁니다.
3

네 낱말을 가르는 지도

[1]~[3]의 주체를 가르면 경계가 드러난다

모델 · 에이전트 · 하네스 · 루프
낱말을 가려 쓰는 것은 어휘의 문제가 아니라 실패의 층을 가리는 일입니다. 실행 기록의 각 주체가 무엇인지 나누면 네 낱말의 경계와 그 계층이 드러납니다.

🧭 네 낱말 — 각자의 자리

낱말정의
모델다음에 올 텍스트를 고르는 엔진. 그 자체로는 질문에 답하는 것 외에 아무 일도 안 한다
에이전트과업을 스스로 판단해 진행하는 역할. 모델이 그 두뇌를 맡는 하나의 구성 — 단순 질의응답이면 에이전트라 안 부르고, 과업 경계를 정해 실행에 나서는 구성에 놓이면 에이전트
하네스모델과 도구 사이의 허용 목록 확인·인자 검사·실행·결과 재입력을 맡는 집행 장치
루프하네스가 반복하는 호출·실행의 순환 구조. 관찰이 다음 선택을 바꿀 때 비로소 의미가 생긴다
계층 — 모델이 에이전트의 두뇌 → 하네스가 그 두뇌를 도구와 이음 → 루프가 그 연결이 도는 형태.
같은 모델이라도 단순 질의응답이면 에이전트가 아니고, 과업 경계를 정해 실행에 나서는 구성 속에 놓이면 에이전트가 됩니다. 루프는 단순 반복이 아니라 관찰이 다음 선택을 바꿀 때만 의미를 얻는다는 점이 중요합니다.

🩺 세 실패는 각기 다른 층의 병

고잘못 고름 = 에이전트의 판단·계약의 문제
읽잘못 읽음 = 모델이 결과를 해석하는 문제
반같은 실수 반복 = 하네스·루프가 멈춤을 설계하지 않은 문제
낱말을 가려 쓰는 것은 어휘의 문제가 아니라 실패의 층을 가리는 일이다.
실패를 뭉뚱그려 "모델이 약하다"고 말하면 고칠 층을 놓칩니다. 잘못 고름은 판단과 계약, 잘못 읽음은 해석, 반복은 멈춤 설계 — 층을 가려야 어디를 고칠지 말할 수 있습니다.

📌 이것만은 꼭 — 핵심 4문장

1도구에 연결되는 순간 모델은 에이전트가 되지만, 그 연결은 완성이 아니라 판단 연쇄의 시작이다.
2연쇄가 어긋나는 세 순간 = 잘못 고름 · 잘못 읽음 · 같은 실수 반복.
3모델은 요청만 쓰고, 하네스가 검증·실행·반환하는 한 바퀴로 돈다.
4모델·에이전트·하네스·루프를 가려 쓰는 것은 곧 실패의 층을 가리는 일이다.
호출 로그는 개발 기록이 아니라 답이 어떤 관찰을 거쳤는지 확인하는 증거입니다. 모델이 무엇을 읽었는지 펼쳐 보기 전에는 어디를 고칠지 말할 수 없습니다.

✅ 정답 & 해설

A1. 조회 도구를 호출할 수 있게 연결되는 순간 — 다음 텍스트만 생성하던 모델이 세계를 관찰하고 바꾸는 에이전트가 된다.
A2. 도구를 잘못 고름 · 결과를 잘못 읽음 · 같은 실수 반복.
A3. 직접 실행하지 않는다. 모델은 도구 이름·인자를 담은 요청 문장만 쓰고, 하네스가 허용 목록 확인 → 인자 검사 → 실행 → 결과 재입력을 집행한다.
A4. ① 도구 정의 포함 → ② 모델이 호출 요청 JSON 생성 → ③ 하네스·앱이 검증·실행 → ④ 결과를 모델 입력으로 반환 → ⑤ 모델이 근거로 답 완성.
A5. 잘못 고름 = 에이전트(판단·계약) · 잘못 읽음 = 모델(해석) · 반복 = 하네스·루프(멈춤 미설계).
A3과 A5를 자기 말로 설명할 수 있으면 오늘 목표는 달성입니다. 특히 하네스가 성능의 주체가 아니라 연결·집행의 주체라는 점을 짚으세요.
