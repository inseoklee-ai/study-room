파일을 읽는 능력, 명령을 실행하는 능력, 외부 메시지를 받는 능력은 서로 다른 위험을 만듭니다.

능력 1파일을 읽는다
능력 2명령을 실행한다
능력 3외부 메시지를 받는다
🎯 권한·보안 기능은 이 세 행동의 입구와 실행 범위를 나누어 — 한 입력이 곧바로 모든 도구 권한으로 이어지지 않게 합니다

도구 안의 권한 규칙

Claude Code — 권한 모드

어떤 도구 행동을 자동 허용하고 어떤 행동을 승인 대상으로 둘지 정합니다. 정하면 파일 변경·명령 실행이 규칙에 따라 바로 실행되거나 승인 화면에서 멈춥니다

opencode — allow·ask·deny

도구와 행동별로 허용·확인·거부를 정합니다. 여러 규칙이 맞으면 마지막 매치가 적용되고, 에이전트별 규칙이 전역 규칙보다 우선합니다

  • 규칙을 정하지 않으면 — 기본 정책에 따라 처리되어 과업별 예외가 어느 규칙에서 왔는지 읽기 어렵습니다
  • 따라서 특정 에이전트의 편집은 묻고 다른 에이전트의 읽기는 허용하는 식으로 동작을 나눌 수 있습니다
출처: Anthropic 공식 문서, opencode 공식 문서 — 구조·설정 확인용이며 정량 실험은 없습니다.

권한과 격리는 다른 질문입니다

하나가 다른 하나를 대신하지 않습니다

⑧ 권한·보안
이 구분이 이 소단원에서 가장 중요합니다.

권한과 격리

🔑 권한

누가 무엇을 허용할지 — 실행 전의 판단을 다룹니다

📦 격리

허용된 실행의 피해를 어디에 가둘지 — Docker 같은 외부 환경이 파일·네트워크·운영체제 범위를 제한합니다

도구배치
pi내장 권한 체계가 없어 실행 사용자 권한으로 도구를 실행하며, 격리는 Docker 등 외부 환경에 맡깁니다
Claude Code권한 규칙을 도구 안에 두어 행동의 허용과 승인을 먼저 다룹니다
🎯 두 도구는 같은 위험을 없애는 단일 해법이 아니라 — 권한 판단과 실행 환경을 서로 다르게 배치한 답입니다
출처: pi 저자 에세이·공식 문서 — 구조 확인용.

세션 격리 ≠ 컨테이너 격리

  • OpenClaw는 에이전트 · 작업공간 · 발신자별 세션을 분리해 대화 상태가 섞이는 범위를 줄입니다
  • 그러나 이 세션 격리는 컨테이너 격리와 같지 않으며 — host 도구의 실행 범위는 별도 sandbox 정책과 실행 환경에서 확인해야 합니다
  • macOS sandbox-exec나 Docker의 구체 명령은 이 강의 범위 밖이므로 다루지 않습니다
대화가 섞이지 않는 것과
프로세스가 닿는 범위가 좁은 것은 다른 문제입니다
세션 격리는 '누구의 대화인가', 컨테이너 격리는 '무엇에 닿는가'를 다룹니다.

경계의 작동을 과업에서 확인합니다

권한 설정은 안전하다는 선언으로 끝나지 않습니다. 같은 과업에서 허용 규칙을 하나만 바꾸고 함께 기록합니다.

1처리된 요청 수
2승인 횟수
3막힌 정상 작업
4의도하지 않은 도구 호출
  • 외부 메시지가 있는 도구라면 — 허용 발신자와 멘션 없는 메시지가 실제로 어느 세션에도 들어가지 않는지 확인합니다
  • 권한을 촘촘히 할수록 공격을 덜 받는다고 바로 결론 내리지 않습니다 — 정상 작업을 막은 비율과 어떤 경계가 그 차단을 만들었는지를 함께 남겨야 다음 설정을 바꿀 근거가 생깁니다
AgentDojo가 과업 완수율을 함께 재는 이유가 여기서 실무로 이어집니다.

❓ 이해도 확인

Q1. 권한과 격리의 차이는?
A1. 권한은 누가 무엇을 허용할지(실행 전 판단), 격리는 허용된 실행의 피해를 어디에 가둘지(파일·네트워크·OS 범위). 하나가 다른 하나를 대신하지 않는다.
Q2. AgentDojo가 공격 성공률과 과업 완수율을 함께 재는 이유는?
A2. 많이 막으면 안전해 보이지만 과업도 끝내지 못할 수 있기 때문.
Q3. 권한 설정을 바꾼 뒤 무엇을 기록하나?
A3. 처리된 요청 수 · 승인 횟수 · 막힌 정상 작업 · 의도하지 않은 도구 호출.
Q1을 구분하지 못하면 "컨테이너를 썼으니 안전하다" 또는 "승인 화면이 있으니 안전하다"로 잘못 결론냅니다.
