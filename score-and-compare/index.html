점수 모니터링과
비교 실험

기록을 보고서로 만들고, 한 번에 하나만 바꿔 비교합니다

실행 기록만으로는 무엇이 나아졌는지 알기 어렵습니다.

보고서 만들기

uv run python -m harness_lab.report jobs/baseline \
  --manifest benchmark/tasks.json \
  --attempts 1 --watch 5 --output reports/baseline
옵션의미
jobs/baseline읽어 들일 실행 기록 폴더
--manifest전체 문항 목록 — 분모를 고정하는 근거
--attempts 1문항당 시행 횟수
--watch 55초마다 갱신하며 진행 상황을 지켜봄
--output보고서를 저장할 위치
📌 --watch는 실행이 도는 동안에도 중간 상태를 볼 수 있게 합니다 — 전부 끝난 뒤에야 문제를 발견하는 상황을 줄입니다
보고서는 실행 폴더를 읽어 표로 정리하는 별도 단계입니다.
1

분모를 고정한다

언제나 10이 분모입니다

⑪ 점수와 비교
보고서에서 가장 먼저 확인해야 할 규칙입니다.

3/3은 100%가 아닙니다

  • 실행에 성공한 문항만 세어 분모를 줄이면 점수가 부풀려집니다 — 3문항만 돌고 3개 통과했다고 100%가 아님
  • manifest의 전체 문항 수(10)를 분모로 고정합니다. 아직 안 돈 문항은 pending으로 남을 뿐 분모에서 빠지지 않습니다
상태의미점수 계산
pass원본 테스트가 통과분자에 포함
fail테스트는 돌았으나 통과 못 함분자 제외
error채점 자체가 실패·비정상 종료분자 제외 — pass로 올리지 않음
pending아직 실행되지 않음분자 제외, 분모에는 포함
⚠️ 채점이 0 또는 1이 아닌 값을 돌려주면 임의로 반올림하지 않고 error로 기록합니다 — 부분 점수를 통과로 바꾸는 순간 비교가 무너집니다
보고서 상단에 항상 n/10 형태로 표시됩니다.

두 가지 검사 종류

agent_evaluation
에이전트가 실제로 작업을 수행하고 원본 테스트로 채점한 결과. 이것이 성능 숫자
grader_self_check
채점 코드 자체가 제대로 도는지 확인하는 점검. 성능 점수에 섞지 않습니다
📌 kind 필드로 구분합니다 — 두 종류를 합쳐서 보고하면 실제보다 높은 숫자가 나옵니다. 보고서를 읽을 때 먼저 kind를 확인
채점 코드 점검이 통과한 것과 에이전트가 문제를 푼 것은 완전히 다른 사실입니다.
2

쪼개서 보기

난이도별·영역별 분해

⑪ 점수와 비교
전체 점수 하나로는 어디를 고쳐야 할지 알 수 없습니다.

어디서 떨어지는가

분해 기준읽는 법다음 행동
난이도별쉬움에서 떨어지면 도구·경로 처리 문제일 가능성도구 계약과 오류 메시지 점검
난이도별어려움에서만 떨어지면 긴 반복의 유지 문제스텝 한도·요약 전략 검토
영역별특정 작업 성격에 몰려 실패해당 도구나 프롬프트를 우선 수정
중단 원인별step_limit·timeout이 많으면능력 문제가 아니라 한도 문제
📌 쉬운 문항에서의 실패가 가장 정보가 많습니다 — 대개 모델의 한계가 아니라 내 하네스의 계약이나 경로 처리 결함을 가리킵니다
여기서 나온 관찰이 다음 실험의 가설이 됩니다.

반복 시행과 pass@k

  • 평균 — 10문항 × 3회 = 30 시행을 돌려 평균 통과율을 봅니다. 실행마다 흔들리는 폭을 알 수 있습니다
  • pass@k — k번 중 한 번이라도 통과하면 성공으로 세는 방식. 재시도가 허용되는 상황을 반영
⚠️ 3회 중 한 번이라도 통과한 문항이 10개라고 "100%"라고 쓰지 않습니다 — 평균 통과율과 pass@3은 서로 다른 지표이므로 어느 쪽인지 반드시 함께 적습니다. 30 시행을 돌렸다고 분모가 30이 되는 것도 아닙니다
📌 반복 시행은 "이 차이가 실제 개선인가, 실행 편차인가"를 가르는 유일한 방법입니다. 1회 실행의 1문항 차이는 근거로 삼기 어렵습니다
시간과 비용이 늘어나므로 중요한 비교에만 반복 시행을 씁니다.

한 번에 하나만

비교 실험의 규칙

⑪ 점수와 비교
여러 가지를 동시에 바꾸면 무엇이 효과였는지 알 수 없습니다.

가설 → 변경 → 비교

1
가설 — "어려움 문항의 실패는 스텝 한도 40 때문이다"처럼 관찰에서 나온 한 문장
2
한 변수만 변경 — 스텝 한도만 60으로. 동시에 모델도 바꾸면 원인을 가릴 수 없습니다
3
같은 조건으로 재실행 — 이름을 다르게 (--name steps60)
4
비교 — --compare jobs/baseline으로 두 실행의 문항별 차이를 표로
uv run python -m harness_lab.report jobs/steps60 \
  --manifest benchmark/tasks.json \
  --compare jobs/baseline --output reports/steps60
📌 비교표는 전체 점수뿐 아니라 문항별로 바뀐 항목을 보여 줍니다 — 총점은 같은데 통과 문항이 서로 바뀐 경우도 드러납니다
총점만 보면 개선과 우연한 교체를 구별할 수 없습니다.

비교를 지탱하는 메타데이터

기록왜 필요한가
제공자·모델·한도같은 조건인지 확인하고서야 두 실행을 비교할 수 있음
문제 자료 해시입력이 같은 판인지 확인 — 문항이 바뀌었다면 비교 불가
execution_mode: local-port원본 컨테이너가 아닌 로컬 이식 실행임을 명시
hostlimits: unrestricted호스트 자원 제한을 걸지 않았음 — 공식 환경과 다른 조건임을 남김
⚠️ 이 표시를 빼고 점수만 공유하면 공식 벤치마크 점수로 오해됩니다. 항상 실행 모드와 조건을 붙여서 보고합니다
제출물에도 같은 메타데이터가 포함됩니다.

모르는 값은 0이 아닙니다

  • 토큰 사용량처럼 제공자가 보고하지 않으면 알 수 없는 값이 있습니다 — usage_known=False
  • 보고서는 이런 값을 0으로 합산하지 않고 known_sum(확인된 값만의 합)으로 따로 표시합니다
  • "토큰 0"이라고 적으면 무료로 돌았다는 잘못된 결론이 나옵니다
📌 측정하지 못한 것과 값이 0인 것을 구별하는 습관이 실험 기록 전체의 신뢰도를 만듭니다 — 뒤에서 다룰 NOT_RUN 표기도 같은 원칙
비용 비교를 할 때 이 구분이 결정적입니다.

❓ 이해도 확인

Q1. 3문항만 돌아서 3개 통과했다. 점수는?
A1. 3/10. 분모는 manifest의 전체 문항 수로 고정하고, 안 돈 문항은 pending으로 남는다.
Q2. 채점이 0.5를 돌려주면?
A2. 반올림하지 않고 error로 기록한다. 부분 점수를 통과로 바꾸면 비교가 무너진다.
Q3. 실험에서 한 번에 몇 가지를 바꾸나?
A3. 하나만. 모델과 한도를 동시에 바꾸면 어느 쪽이 효과였는지 알 수 없다.
Q1은 보고서를 처음 읽을 때 가장 자주 틀리는 지점입니다.
