MCP — AI를
내 데이터에 꽂는 USB-C

연결 하나를 다시 만들지 않기 위한 업계 공용 약속

하네스를 강하게 만드는 첫 번째 방법입니다. 아무리 똑똑한 AI도 기본적으로는 자기가 학습한 것만 압니다 — 내 데이터베이스, 내 파일, 우리 회사 문서는 모릅니다.

문제 — AI는 '내 것'을 모릅니다

내 데이터베이스, 내 파일, 내 캘린더, 우리 회사 문서를 모릅니다. 그때그때 복사해서 붙여넣을 수도 있지만, 연결할 도구가 많아지면 —

AI 3개 × 도구 5개 = 연결 15개
이걸 일일이 만들어야 하는 지옥 — 이른바 M×N 문제
  • 도구가 하나 늘 때마다 AI 개수만큼 연동을 새로 만들어야 합니다
  • AI를 하나 갈아타면 도구 개수만큼 다시 만들어야 합니다
M×N 문제를 숫자로 보여 주면 표준의 필요성이 바로 이해됩니다. 뒤에서 M+N으로 줄어드는 계산이 다시 나옵니다.

MCP = "AI를 위한 USB-C 포트"

Model Context Protocol

② MCP
Anthropic이 2024년 말에 공개했고, 지금은 업계 표준이 되었습니다.

한 번 만들면 아무 AI에나 꽂힙니다

USB-C를 떠올려 보세요. 예전엔 기기마다 충전기가 달랐지만, USB-C 하나로 통일되니 아무 기기나 아무 충전기에 꽂힙니다.

🔌 MCP는 'AI를 위한 USB-C'입니다 — 도구를 한 번 MCP 규격으로 만들어 두면, MCP를 지원하는 아무 AI에나 꽂힙니다
1AI가 내 데이터베이스를 직접 조회해서 답하기
2Figma 디자인을 읽어서 그대로 화면 만들기
3내 캘린더·Notion·Slack에 접근해 개인 비서처럼 굴기
출처: modelcontextprotocol.io, "What is MCP"; IBM, "What is Model Context Protocol?". MCP는 Model Context Protocol의 약자입니다.

MCP로 실제로 뭘 할까

사례 모음과 실전 목록

② MCP
추상적으로 느껴지지 않게, 사람들이 실제로 연결해 쓰는 예를 봅니다.

사람들이 이렇게 씁니다

  • 디자인 → 코드 — Figma를 연결하면 AI가 디자인을 읽어서 그대로 화면을 만든다
  • 내 문서와 대화 — Notion을 연결해 "이번 주 할 일 정리해 줘", "이 문서 요약해 줘"를 채팅 안에서
  • 웹을 데이터로 — 웹사이트를 훑어 상품·가격·이미지를 정리해 오기(스크래핑)를 자연어로
  • 글을 소리로 — 긴 글을 음성으로 바꾸기
  • 일정 자동화 — "다음 주 화요일 회의 잡아 줘" → 캘린더에 초대장
  • 사내 업무 — 회사 DB·내부 문서·ERP에 붙여 IT 지원·채용·계약 업무를 돕기
💡 흥미로운 현실 — 공개적으로 널리 쓰이는 MCP 서버는 아직 손에 꼽지만, 회사 내부용 MCP(사내 DB·문서 연결)가 가장 값지다는 평가입니다
출처: Merge, "MCP integration examples"; Pragmatic Engineer, "Building MCP servers". Anthropic이 Google Drive·Slack·GitHub·Postgres 같은 기성 MCP 서버를 공개해 뒀고, Cursor·Zed·Replit 등도 MCP를 받아들였습니다. 남에게 공개하지 않아도 내 데이터에 AI를 붙이는 것만으로 큰 힘이 됩니다.

개념 정리 — MCP가 건네는 세 가지

도구 · 자원 · 프롬프트

② MCP
이름만 알아 두면 됩니다.

도구 · 자원 · 프롬프트

1도구(Tools) — AI가 실행하는 기능 (예: 검색하기, DB 조회하기)
2자원(Resources) — AI가 읽어 들이는 데이터 (예: 파일, 문서, 기록)
3프롬프트(Prompts) — 미리 만들어 둔 요청 템플릿

이게 왜 좋을까요? ① 연결을 매번 새로 안 만들어도 되고, ② AI가 실제 최신 데이터를 보니 엉뚱한 답(환각)이 줄고, ③ 학습 시점 이후의 최신 정보도 쓸 수 있습니다.

🎯 결국 이렇게 다가옵니다 — "AI야, 우리 서비스 DB 보고 답해 줘"가 가능해지는 것. 문법을 몰라도 이미 만들어진 연결을 켜기만 하면 됩니다
출처: modelcontextprotocol.io; Descope, "What Is MCP". 세 가지 중 '도구'만 실제 행동을 합니다 — 다음 슬라이드의 권한 이야기로 이어집니다.

구조와 셈 — M×N에서 M+N으로

hostAI를 담은 앱
(코딩 도구 등)
→
client연결 관리
→
serverNotion·파일·DB
tools/resources/prompts
표준이 없으면공통 규약을 따르면
구현 수앱 M개 × 서비스 N개 = M×N개앱은 client 한 번, 서비스는 server 한 번 → 대략 M+N개
  • 한 서버가 무엇을 허용하는지는 서버가 명시하고, host는 그 목록을 AI에게 보여 줍니다
  • USB-C 비유가 여기서 나옵니다 — 단, 플러그 모양이 같다고 모든 기기가 같은 권한을 갖는 건 아닙니다. MCP도 연결 규칙이지 자동 안전 보장은 아닙니다
M+N 계산을 칠판에 써 보면 설득력이 큽니다. AI 앱 5개, 서비스 10개면 50개 → 15개입니다.

특히 tool은 실제 행동을 할 수 있습니다

1처음에는 "읽기" 도구부터 연결한다
2쓰기·삭제·배포처럼 되돌리기 어려운 권한은 승인 과정을 둔다
3AI가 최신 데이터를 읽는다고 해석까지 자동으로 맞는 것은 아니므로, 중요한 결과는 원본과 함께 확인한다
🧭 앞 강의의 DB 실습에서 배운 것과 같습니다 — 읽기 전용부터, 되돌릴 수 없는 것엔 승인
데이터베이스 MCP를 '읽기 전용 권장'이라 적은 이유가 이것입니다. 권한 이야기는 소단원 ④에서 하네스 안전으로 다시 확장됩니다.

❓ 이해도 확인

Q1. MCP가 푸는 문제(M×N)는 무엇인가?
A1. AI 앱 M개와 서비스 N개가 각각 전용 연동을 만들면 M×N개가 필요하다. 공통 규약을 따르면 대략 M+N개로 줄어든다.
Q2. MCP 서버가 건네는 세 가지는?
A2. 도구(Tools) · 자원(Resources) · 프롬프트(Prompts). 이 중 실제 행동을 하는 건 도구다.
Q3. MCP가 '업계 공용 약속'이라고 말할 수 있는 근거는?
A3. Anthropic이 2024-11 공개 → OpenAI(2025-03)·구글(2025-04) 채택 → 2025년 말 리눅스 재단 산하 중립 재단(AAIF)으로 이관.
Q4. "USB-C 비유"의 한계는?
A4. 플러그 모양이 같다고 모든 기기가 같은 권한을 갖는 건 아니다. MCP는 연결 규칙이지 자동 안전 보장이 아니다 — 읽기부터, 위험한 권한엔 승인.
Q4를 빠뜨리면 학습자가 "MCP만 붙이면 안전하다"고 오해합니다.
