메인 프로젝트 — RAG 가이드 챗봇을
만들고 배포하고 평가하기

근거를 공개하고, 판정까지 남기는 제품

오늘 만들 제품은 공개 자료에 근거해 답하고, 그 근거를 화면에 공개하며, 답변 품질의 자동 판정 결과까지 남기는 RAG 가이드 챗봇입니다.

참조 구현 — 서버 없는 모두콘 안내 챗봇

완성형 참조 구현은 모두의연구소 컨퍼런스 모두콘을 안내하는 서버 없는 RAG 챗봇입니다. 브라우저에서 임베딩과 검색을 수행하고, 로컬 Ollama가 답변을 생성하며, 각 답변에 자동 판정을 연결합니다.

1서버에서 답을 만들지 않습니다. 페이지를 연 사용자 컴퓨터의 Ollama(qwen3.5:2b)가 답변을 생성합니다
2처음 열 때 임베딩 모델을 내려받습니다 (첫 방문 1회, 약 200MB)
3Ollama가 실행 중이어야 답변이 시작됩니다
4원격 주소의 페이지가 사용자 컴퓨터의 Ollama와 통신하는 일은 CORS 허용 설정(OLLAMA_ORIGINS)으로 가능합니다 — 구현 단계에서 다룹니다
🔗 suncreation.github.io/moducon-chatbot 에서 직접 열어 동작을 확인할 수 있습니다
오늘 실습에서도 같은 구조를 만들어 배포해 보고, 수업이 끝날 때에는 자신의 도메인에 적용한 근거 기반 답변과 자동 판정 안내 챗봇을 갖추게 됩니다.

기존 실습과 두 가지가 다릅니다

1. 언어와 실행 위치

파이썬 스크립트가 아니라 브라우저에서 동작하는 타입스크립트 앱으로 구현합니다

2. 완성 후의 일

프롬프트와 검색 설정을 바꿔 가면서 직접 설계한 루브릭으로 성능을 측정하는 실험까지 수행합니다

  • 구현과 평가의 출발점은 첫 단계에서 함께 정리합니다
만드는 것으로 끝나지 않고 측정까지 간다는 점이 이 프로젝트의 성격을 결정합니다.

학습 목표 여섯

1자기 도메인의 안내 챗봇을 PRD부터 스스로에게 질문하며 기획합니다
2공개 자료를 수집하고 청크와 임베딩을 구성해 브라우저 벡터스토어를 만듭니다
3로컬 Ollama qwen3.5:2b의 스트리밍과 브라우저 임베딩을 결합한 RAG 파이프라인을 이해합니다
4답변의 근거성과 거절을 판정하고, 사람 피드백과 함께 읽습니다
5자기 루브릭으로 프롬프트와 RAG 세팅을 실험하고 성능 변화를 표로 남깁니다
6정적 앱을 배포한 뒤 수용 기준으로 동작을 다시 확인합니다
여섯 목표가 아홉 소단원에 그대로 대응합니다.

0.55 미만일 때 — 버리지 않고 드러냅니다

하나가 빠지면 무엇이 무너지나

빠지면무너지는 것
청크가 없으면임베딩은 비교할 대상이 없습니다
URL이 없으면생성 문장은 사용자가 확인할 출발점을 잃습니다
judge가 없으면답을 어떻게 읽을지에 관한 별도 신호가 사라집니다
⚠️ 반대로 judge만 추가해도 출처 없는 문장이 근거를 얻지는 않습니다 — 각 상자는 앞 상자의 산출물을 보존해야 합니다
"판정만 붙이면 신뢰가 생긴다"는 오해를 여기서 미리 차단합니다.

기능을 급히 붙이는 순서가 아니라, 검증할 수 있게 쌓는 순서입니다.

①~⑥ — 준비와 자료

①Vite, React, TypeScript의 정적 앱과 GitHub Pages 상대 경로를 준비합니다
②모두콘 소개 화면을 만듭니다
③공개 원문을 출처 URL이 붙은 사실 단위 청크로 수집합니다
④청크 JSON 스키마와 MC-001부터의 ID 규칙을 정합니다
⑤768차원 벡터를 생성하여 정적 벡터스토어에 배치합니다
⑥브라우저 임베딩 경로에서 WASM에서 동작하는 no_gather_q4 경로를 사용합니다
①~⑥이 소단원 ③④에 해당합니다.

⑦~⑫ — 검색·생성·판정·배포

⑦모델과 자료의 캐시 및 진행률을 다룹니다
⑧코사인과 BM25 하이브리드 검색을 붙입니다
⑨시간 컨텍스트와 약한 근거 규칙을 포함해 프롬프트를 조립합니다
⑩Ollama의 상태 확인, 스트리밍, 취소 UI를 결합합니다
⑪출처 칩과 근거 모달, 검색 단계, 경고 배지를 보이게 합니다
⑫선택 엔진, LLM-as-a-Judge, 사람 피드백, Pages 배포와 수용 기준 점검을 한 화면의 사용 경험으로 묶습니다
🎯 이 순서는 특정 도구의 정답이 아니라 — 질문이 입력된 순간부터 근거와 답변과 판정이 각각 관찰 가능해야 한다는 설계 원칙을 구현 순서로 바꾼 것입니다
기본 경로는 로컬 Ollama만으로 완결되지만, 예시 구현에는 Gemini API를 쓰는 선택 엔진도 있어 로컬 무료 경로를 유지하면서 API 키 경로를 비교해 볼 수 있습니다. 두 엔진을 나란히 두면 같은 질문에 대한 답변 리듬과 판정 결과가 어떻게 달라지는지 관찰할 수 있고, 이 비교가 판정 섹션의 실험 재료가 됩니다.

❓ 이해도 확인

Q1. 이 앱에서 답변은 어디서 생성되나?
A1. 서버가 아니라 페이지를 연 사용자 컴퓨터의 로컬 Ollama(qwen3.5:2b). 그래서 Ollama 실행과 OLLAMA_ORIGINS 설정이 필요하다.
Q2. 최고 유사도가 0.55보다 낮으면?
A2. 결과를 버리지 않고 약한 근거를 프롬프트와 UI에 드러낸다. 모델은 단정 대신 자료의 한계를 말한다.
Q3. "judge만 붙이면 신뢰가 생긴다"가 틀린 이유는?
A3. judge를 추가해도 출처 없는 문장이 근거를 얻지는 않는다. 각 상자는 앞 상자의 산출물(청크·URL)을 보존해야 한다.
Q3이 이 프로젝트에서 가장 자주 오해되는 지점입니다.
