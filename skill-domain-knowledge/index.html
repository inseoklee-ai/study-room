Skill의 역할과
업무 지식

기록을 정확히 가져왔더라도, 그 의미는 우리 팀의 기준으로 해석해야 합니다

연결 기술만으로는 해결되지 않는 문제가 하나 나타납니다.

같은 기록을 서로 다른 목적의 보고서에

보고 목적세는 성과TASK-102를 설명하는 문장
팀 A — 개발 진척 공유이번 주 구현을 끝낸 작업로그인 안내 문구 구현을 마쳤으며 배포를 기다리고 있습니다
팀 B — 고객 제공 성과배포하고 운영 확인까지 마친 작업진행 중입니다. 개발을 마쳤고 배포와 운영 확인이 남아 있습니다
  • 어느 쪽도 기록을 바꾸지 않았습니다 — 보고의 목적과 분류 기준이 다를 뿐
  • 팀 A의 "구현을 마쳤다"를 "사용자에게 제공했다"로 바꾸면 원자료가 뒷받침하지 않는 주장이 됩니다. 팀 B에서 개발 완료라는 문자열만 보고 완료 건수를 올려도 기준에 맞지 않습니다
📌 개발은 기능을 구현하는 작업, 배포는 그 변경을 사용자가 이용하는 환경에 반영하는 작업. verification은 운영 환경에서의 확인 결과이며 미실시이므로 실제 서비스에서 확인을 마쳤다는 근거도 아직 없습니다
두 팀의 기준은 차이를 이해하기 위한 가상 설정입니다. 이번 공통 실습의 가상 제품팀은 배포와 운영 확인까지 갖춘 일을 완료로 봅니다.

업무 고유 지식

AI는 일반적인 요약을 잘할 수 있습니다
그렇지만 우리 팀이 어떤 항목을 완료 건수에 포함하는지는
팀의 약속을 알아야 판단할 수 있습니다
  • 업무 고유 지식의 예 — 특정 팀의 용어, 데이터 열의 뜻, 승인된 보고서 예시, 예외 처리 기준처럼 일반 지식만으로 정확히 알기 어려운 정보
별도 지침 없이도 "개발 완료, 배포 대기"를 정확히 표현할 수도 있습니다. 문제는 완료 건수의 기준입니다.

이번 요청에서 다음 요청으로

한 번이면 파일을 읽히면 충분합니다

⑧ Skill
한 번의 보고서가 목적이라면 규칙 파일을 읽히는 방식으로 충분할 수 있습니다. 곧바로 새 도구를 만들 필요는 없습니다.

반복될 때 Skill

  • 다음 주에도 같은 보고서를 만들고 다른 팀원도 새 대화에서 같은 방식으로 작성한다면 — 매번 규칙 파일을 설명하고, 예전 보고서를 찾고, 빠진 요구를 다시 전달하는 일이 반복됩니다
  • Agent Skill은 특정 종류의 일을 할 때 사용할 지침과 자료를 함께 묶는 형식입니다 — 에이전트가 이름과 설명으로 용도를 파악하고, 필요하면 본문과 연결된 자료를 읽어 활용
  • 지침 파일 SKILL.md가 중심이 되고, 필요하면 참조 문서·서식·실행 코드도 함께 둘 수 있습니다
  • 보고서 Skill이라면 — 적용 조건, 완료를 판단하는 기준, 보고서에서 보여 줄 근거를 함께 관리. 이번 주 TASK-102를 외우게 하는 대신 다음 주의 다른 업무에도 적용할 수 있는 기준을 제공
⚠️ 이는 모델을 다시 학습시키는 과정과 다릅니다 — 작업할 때 읽을 자료를 준비합니다. 팀 기준이 바뀌면 Skill이 참조하는 규칙도 고쳐야 하며, 파일을 만들었다는 사실보다 올바른 작업에서 최신 내용을 읽고 활용하는지가 중요합니다
Tool Search와 닮은 점은 처음부터 모든 자료를 읽히기보다 필요한 내용을 찾은 뒤 읽는다는 것입니다. 다만 Tool Search가 찾는 대상은 주로 호출할 도구의 설명이고, Skill에서 읽는 내용은 특정 과업에 사용할 지식·방법·자료입니다. 둘은 함께 쓸 수 있습니다.

네 방식이 맡는 역할

전달 방식주로 맡기는 내용보고서 작업의 예
현재 요청의 프롬프트이번 작업의 목적·대상·범위새 팀원이 이해할 보고서를 작성해 달라고 요청
프로젝트 지침해당 프로젝트에서 넓게 적용할 관례기본 용어, 문서 언어, 공통 작업 관례
Skill특정 종류의 과업에서 반복 사용할 지식·방법·자료주간 보고의 분류 기준과 보고서 예시
MCP프로그램의 도구·자료를 호스트에서 표준 방식으로 사용하도록 연결get_weekly_records로 요청한 주의 기록 조회
🎯 프로젝트 지침과 Skill의 경계는 적용 범위로 — "이 프로젝트의 문서는 한국어로"는 여러 작업에 적용되지만 "주간 보고의 완료 건수는 배포와 운영 확인을 기준으로"는 보고서 과업에 집중된 지식
"이번 보고서는 한국어로 써 줘"처럼 이번 작업에만 필요한 요구는 대화에서 바로 전달하는 편이 자연스럽습니다. 실제 작업에서는 네 가지가 이어질 수 있습니다.

필요한 만큼 조합합니다

  • 자료를 파일로 직접 받았다면 MCP 조회 없이도 같은 Skill을 사용할 수 있습니다
  • 반대로 MCP로 기록을 조회한 뒤 대화에서 준 규칙만으로 보고서를 작성해도 됩니다
  • 같은 정보를 프롬프트에 모두 전달했을 때와 Skill로 읽혔을 때 결과가 같을 수도 있습니다 — Skill 형식 자체가 더 정확한 판단을 만들어 준다고 가정할 이유는 없습니다
  • 반복 작업에서 필요한 자료를 찾아 쓰고 한곳에서 기준을 관리하는 편의와 실제 결과의 변화는 나누어 확인해야 합니다
도구 연결과 업무 지식의 재사용을 각각 필요한 만큼 조합하는 것입니다.

공식 사례의 지침 선택

internal-comms · brand-guidelines

⑧ Skill
공개된 Skill을 하나 읽어 보겠습니다.

어떤 요청에서 어떤 자료를 읽을지

  • Anthropic의 internal-comms는 사내 소통 문서 작성 사례로 상태 공유·사내 소식·자주 묻는 질문 등 여러 요청을 다룹니다
  • 본문은 요청의 문서 유형을 파악한 다음 그 유형에 맞는 예시 지침을 읽도록 안내합니다
  • 중요한 것은 "글을 잘 써라"라는 표현보다 — 어떤 요청에서 어떤 자료를 읽을지 정해 놓은 연결. 주간 진행 공유는 examples/3p-updates.md로, 사내 소식은 다른 지침으로
  • 따라서 모든 소통 문서의 양식을 하나의 긴 지시문에 섞을 필요가 없습니다
📖 3P는 Progress · Plans · Problems — 진행 성과·다음 계획·문제를 나누어 전달하는 방식. 팀의 세부 사정을 충분히 알지 못하는 독자가 빠르게 파악하도록 작성하게 하고, 필요한 자료에 접근할 수 없으면 사용자에게 내용을 받을 수도 있게 합니다
예시 메모 — "검색 오류 수정을 배포했다. 다음 주에는 검색어 추천을 시험하려 한다. 시험용 데이터 사용 승인을 기다리고 있다." 시간과 역할로 나누면 이미 한 일, 앞으로 할 일, 진행을 막는 조건이 드러납니다. 단순히 원문을 짧게 줄이는 것과 다른 편집 판단입니다.

브랜드 기준이 바꾸는 선택

  • brand-guidelines의 원문에는 색상값과 글꼴 이름, 용도별 적용 기준이 있습니다 — 주된 강조색은 #d97757, 제목·본문 글꼴과 없을 때의 대체 글꼴도 안내
  • "회사 분위기에 맞게 만들어 줘"만 받으면 AI는 분위기를 추측해야 합니다. 정확한 색상값과 글꼴 기준을 받으면 선택의 근거가 생깁니다
  • 색상값은 문구를 길게 꾸미는 요소가 아니라 결과물의 실제 색을 결정하는 정보. 대체 기준은 실행 환경이 달라도 취할 다음 선택을 알려 줍니다
⚠️ "공식 문서에 적혀 있으니 알아서 적용되겠지"에서 한 단계 더 — 에이전트가 그 기준을 읽고 결과물 제작에 사용하는지, 만들어진 슬라이드나 문서가 기준을 따르는지 확인해야 합니다
  • 우리 실습에서도 — "정확하고 전문적으로 작성하라"보다 "개발 완료와 배포 완료를 구분한다"는 기준이 어떤 판단을 바꾸는지 설명할 수 있어야 합니다
모든 기준을 강하게 명령하기보다, 이 정보가 필요한 이유를 실제 자료에 연결해 보는 것입니다.

지침과 함께 둘 자료

references · assets · scripts

⑧ Skill
Skill에 들어갈 내용은 글로 된 절차에 한정되지 않습니다.

역할이 다른 자료들

반복해서 필요한 내용함께 둘 수 있는 자료작업에서 달라지는 부분
팀만의 완료·위험 판단팀 규칙 문서 (참조 자료)같은 상태값을 팀의 약속에 따라 해석
기대하는 설명 수준승인된 보고서 예시근거를 어느 정도 보여 주고 어떤 내용을 묶는지 참고
일정한 보고서 외형로고와 문서 서식 (자산)매번 머리글과 표 배치를 새로 만들지 않음
반복되는 숫자 집계검증한 집계용 Python 코드 (스크립트)같은 계산을 새로 작성하는 대신 실행하고 결과를 확인
  • 예시는 "이 정도 근거가 있어야 읽는 사람이 이해한다"는 모습을, 서식은 "채워 넣을 틀"을 제공 — 예시 안의 지난주 수치까지 새 보고서로 복사하지 않도록 참고할 표현과 이번 데이터를 구분해 주어야 합니다
  • 코드 파일을 포함했다고 자동으로 실행되는 것은 아닙니다 — 에이전트가 실행 환경의 도구와 허용된 권한으로 호출해야 하며 외부 계정의 접근 권한도 별도로
  • 첫 Skill부터 이 모든 자료를 만들 필요는 없습니다 — 파일 수보다 그 파일이 해결하는 문제가 분명한지가 중요합니다
위 표는 우리 팀의 작업이 확장되었다고 가정한 수업용 예이며, 공식 브랜드 Skill에 이 파일들이 모두 들어 있다는 뜻은 아닙니다.

CLI 사용법을 담은 Skill

MCP 없이도 외부 업무를 실행할 수 있습니다

⑧ Skill
기록이 Google Sheets에 있고 에이전트가 실행할 수 있는 환경에 Google Workspace CLI인 gws가 준비되어 있다고 생각해 보겠습니다.

두 경로의 실행 주체

CLI 경로: 에이전트 → 호스트의 셸 실행 도구 → gws CLI → Google API
MCP 경로: 에이전트 → 호스트의 MCP 클라이언트 → MCP 서버 → 업무 API
  • 이 경로에서는 별도의 MCP 연결 없이도 외부 서비스의 업무를 수행할 수 있습니다 — 다만 에이전트가 호스트의 셸 실행 도구를 호출하는 과정은 남아 있으므로 도구 호출 자체가 사라지는 것은 아닙니다
  • Skill 파일이 명령을 스스로 실행하거나 API 접근 권한을 만들어 주는 것은 아닙니다 — CLI 경로에서는 셸 실행 도구와 실행 권한이 있어야 하고, 그 환경에서 CLI를 찾을 수 있어야 하며, Google 계정 인증과 대상 문서를 읽을 권한도 별도로 필요합니다
비교할 지점CLI 사용법을 읽고 실행원격 MCP 서버에 연결
호스트가 호출하는 기능셸 실행 도구로 CLI 명령MCP 클라이언트로 서버의 도구
사용법을 알아내는 방법Skill, CLI 도움말, 명령 스키마서버가 제공하는 이름·설명·입력 스키마
실행 환경의 준비명령 실행 환경에 CLI와 인증호스트에 서버 연결과 인증
원격 내부 구현CLI가 원격 API 클라이언트라면 서버 내부 코드를 받지 않아도 됨내부 코드를 받지 않고 공개한 도구를 호출
📌 마지막 행이 핵심 — 서비스 내부 구현을 공개하지 않고 기능만 제공하는 구조는 원격 MCP만의 특징이 아닙니다. MCP는 여러 호스트가 공통 방식으로 발견·호출하도록 연결하고, CLI는 명령과 인자로 프로그램을 사용하게 합니다
Google 인증 준비는 소단원 ⑬에서 다룹니다. gws에 적용할 때는 gws 인증 안내에 맞춰 인증 파일 위치·요청 권한·로그인 방법을 확인합니다.

명령이 성공해도 근거가 부족할 수 있습니다

gws sheets spreadsheets values get \
  --params '{"spreadsheetId": "SPREADSHEET_ID", "range": "Sheet1!A1:C10"}'
  • get은 값을 읽는 작업, --params의 JSON에는 대상 문서와 셀 범위. Sheet1!A1:C10은 Sheet1 탭의 A1부터 C10까지
  • 범위를 지정했다고 "이번 주 기록만" 선택한 것은 아닙니다 — 그 셀에 어느 기간의 기록이 들어 있는지, 날짜와 상태가 어느 열에 있는지 먼저 알아야 합니다
  • 예 — A~C열에 제목과 상태만 있다면 배포일과 운영 확인까지 필요한 우리 팀의 완료 판정에는 부족합니다
  • 응답 읽기 — range는 읽은 범위, majorDimension은 행·열 중 어느 방향으로 값이 묶였는지, values는 실제 셀 값. ROWS라면 배열 하나가 한 행. 끝부분의 빈 행·열은 생략될 수 있으므로 요청한 셀 수만큼 값이 반드시 돌아온다고 가정하면 안 됩니다
⚠️ 명령이 성공했어도 필요한 근거를 모두 가져온 것은 아닐 수 있습니다
이 수업에서는 gws 설치와 인증을 준비하지 않았으므로 명령 구조를 읽는 예시로 사용합니다. gws 저장소의 Skills Index는 서비스별 Skill과 도우미 Skill을 구분해 두었고, gws-sheets는 공통 지침을 먼저 읽도록 연결합니다.

보고서 Skill에 연결한다면

### Google Sheets에 있는 기록을 보고서에 사용할 때

- 사용자가 Sheets 기록으로 주간 보고서를 요청하면 이 절차를 적용한다.
- gws 공통 지침과 Sheets 지침을 읽고, 사용할 명령과 필요한 인자를 확인한다.
- 문서 ID, 탭, 보고 기간, 열의 뜻을 확인한다. 제목·상태뿐 아니라
  배포일과 운영 확인 등 팀의 판정에 필요한 필드가 포함된 범위를 읽는다.
- 응답의 range와 majorDimension을 확인하고 values를 머리글과 대응시킨다.
  조회 오류를 업무 0건으로 해석하지 않고, 빠진 근거는 미확인으로 남긴다.
- 읽어 온 기록에 팀의 완료·진행·위험 기준을 적용하여 보고서 초안을 만든다.
- 보고서 작성 요청만으로 원본 시트를 수정하지 않는다. 기록 갱신을 요청받으면
  대상 셀과 변경값, 허용된 작업 범위를 확인하여 쓰기 절차를 적용한다.
🎯 이 지침의 가치는 명령을 복사해 두는 데서 끝나지 않습니다 — 언제 사용할지, 어떤 필드와 범위가 필요한지, 응답을 어떻게 해석할지, 조회와 변경 중 어떤 작업이 요청에 맞는지를 함께 정합니다
  • 같은 gws를 써도 읽기 보고서와 원본 기록 갱신은 서로 다른 업무이며 읽기 권한과 쓰기 권한도 구분해야 합니다 — Sheets의 값 조회 API는 읽기 전용 OAuth 범위로도 사용할 수 있습니다
위는 공식 Skill을 그대로 옮긴 것이 아니라 우리 가상 제품팀을 위한 교육용 지침 예시입니다. 나중에 기록을 가져오는 경로가 MCP나 CLI로 바뀌더라도 완료 판정 기준은 그대로 재사용할 수 있습니다.

실제 작업에서 찾는 Skill의 재료

오류를 일부러 만들 필요는 없습니다

⑧ Skill
"모든 상황에서 완벽한 보고서를 만들어 줘"로 시작하면 구체적인 기준을 찾기 어렵습니다.

실제 보고서 한 편에서 찾습니다

1어떤 자료가 없어서 판단이 멈췄는지
2어떤 용어를 따로 설명했는지
3결과를 고쳤다면 왜 고쳤는지
  • 처음부터 결과가 적절했다면 그 판단을 뒷받침한 자료를 찾으면 됩니다 — Skill을 만들기 위해 일부러 오류를 만들 필요는 없습니다
  • 반대로 한 번의 특별 요청을 모든 보고서의 규칙으로 만들면 다음 작업에 맞지 않을 수 있습니다 — "이번에는 발표 자료용 한 문장만"과 "우리 팀의 완료는 배포 후 운영 확인까지"는 재사용할 범위가 다릅니다
  • 공식 skill-creator는 원하는 과업과 적용 상황을 파악하고, 초안을 만든 뒤, 실제 요청에 적용한 결과를 평가하고 수정하는 흐름을 안내합니다 — 우리 팀의 기준을 스스로 알아내는 도구라기보다 제공한 경험과 자료를 재사용 가능한 형태로 정리하고 확인하는 데 도움을 주는 사례
📌 "이 기록을 우리 팀 보고서로 쓰려면 어떤 기준이 더 필요할지 같이 찾아보자" — AI의 제안 중 실제 자료나 팀의 약속으로 확인할 수 있는 것을 고르세요
Agent Skills 작성 원칙도 모델이 이미 할 수 있는 일반 작업 설명을 늘리기보다, 해당 업무에 필요한 지식과 관례를 제공하고 실제 적용 결과를 살펴보는 방향을 권장합니다.

Q1. 프로젝트 지침과 Skill의 경계는?
A1. 적용 범위. "문서는 한국어로"는 여러 작업에, "완료는 배포와 운영 확인 기준"은 보고서 과업에 집중된 지식.
Q2. Skill 형식 자체가 결과를 더 정확하게 만드나?
A2. 그렇게 가정할 이유는 없다. 같은 정보를 프롬프트로 줘도 결과가 같을 수 있다. 편의와 실제 결과 변화는 나누어 확인한다.
Q3. Skill에 CLI 사용법을 적으면 실행 권한이 생기나?
A3. 아니다. 셸 실행 도구와 실행 권한, CLI 설치, 계정 인증과 문서 접근 권한이 별도로 필요하다.
Q3은 "적어 두면 된다"는 오해를 끊습니다.
