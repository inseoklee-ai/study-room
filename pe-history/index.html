프롬프트
엔지니어링의 변천

만능 문구의 역사가 아니라 — 바꿀 수 있는 조건의 확장

프롬프트 엔지니어링의 역사는 "더 강력한 주문을 찾아온 여정"이 아닙니다. 설계자가 통제할 수 있는 조건 — 예시, 추론 형식, 도구와 관측, 검증 루프 — 이 하나씩 넓어져 온 과정입니다. 오늘은 그 확장을 논문 속 수치와 함께, 그러나 수치를 등급표가 아니라 관찰 기록으로 읽으며 따라갑니다.

다섯 파트를 지나면 프롬프트 엔지니어링을 "잘 먹히는 문장 모음"이 아니라 "설계자가 통제하는 조건을 넓히고 비교해 온 역사"로 다시 보게 됩니다.
1

수치를 읽는 법

숫자는 영구 등급표가 아니라 특정 실험의 압축 기록

모델 · 데이터셋 · 설정
변천을 따라가기 전에 도구부터 맞춥니다. 논문의 71.8 같은 숫자는 성능의 순위표가 아니라, 특정 모델을 특정 데이터셋에서 특정 설정으로 돌려 얻은 관찰 기록입니다. 이 관점이 없으면 뒤에 나올 모든 수치를 잘못 일반화하게 됩니다.

🔢 71.8만 기억하면 안 되는 이유

O좋은 예 — "GPT-3 175B가 SuperGLUE에서 few-shot 조건으로 71.8을 보고했다" (모델·데이터셋·설정을 한 문장에 복원)
X나쁜 예 — "프롬프트에 예시를 넣으면 성능이 71.8이다" (모델·과업·조건을 지운 잘못된 일반화)
  • 설정 = zero/one/few-shot뿐 아니라 가능하면 프롬프트 형식·평가 절차까지
  • 조건 표기는 인용의 예절이 아니라 비교의 전제
조건이 다른 두 숫자의 차이를 기법 하나의 효과라 부를 수 없다.
수치를 볼 때마다 "어떤 모델이, 무엇에서, 어떤 설정으로"를 복원하는 습관이 핵심입니다. 이 세 가지를 지우면 숫자는 그럴듯한 광고 문구가 됩니다.

🧪 기법이란 무엇인가

기법 = 모델을 더 똑똑하게 만드는 주문이 아니라
같은 과업에서 바꿔 볼 수 있는 실행 조건에 관한 가설모델 · 평가 사례 · 성공 기준을 고정한 채, 한 조건만 바꿔 확인한다
  • 가설이므로 검증 대상이다 — "좋다더라"가 아니라 통과율·실패 유형으로 확인
  • 여러 조건을 함께 바꾸면 원인을 분리할 수 없다
이 정의가 오늘 전체의 축입니다. 기법을 "붙이면 좋아지는 마법"이 아니라 "이 조건을 바꾸면 이 실패가 줄어들 것"이라는 검증 가능한 가설로 보면, 아래 모든 이정표가 같은 방식으로 읽힙니다.

2020 — 인컨텍스트 러닝

재학습 없이, 프롬프트 안의 예시가 과업 계약을 전달한다

GPT-3 175B · Brown 외 · 예시 계약
Brown 등의 GPT-3(175B)는 별도 파라미터 갱신 없이, 자연어 과업 설명과 프롬프트 안의 입출력 예시만 읽고 여러 과업을 수행했습니다. 새 과업엔 새 학습이 필요하다는 관점에서, "새 과업을 새 프롬프트로 제시"할 수 있음을 보인 이정표입니다.

📊 SuperGLUE — 예시가 늘수록

조건 (GPT-3 175B)SuperGLUE 점수읽는 법
zero-shot64.3과업 설명만 제시
one-shot68.2예시 1개 추가
few-shot71.8예시 여러 개 추가 → 입력 형식·출력 관계를 보여 줌
fine-tuned SOTA89.3같은 표의 미세조정 최고치 — few-shot과 여전히 격차
64.3 → 68.2 → 71.8의 상승은 사실이지만, SOTA 89.3과 나란히 보면 "few-shot이 fine-tuning을 대체했다"는 승리 선언이 아니다.
예시가 늘며 점수가 오른 것은 예시가 입력 형식과 출력 관계를 보여 주기 때문이라 종종 유용합니다. 그러나 같은 표의 fine-tuned SOTA가 89.3이라는 사실을, 그리고 이것을 "모든 모델·과업에서 예시가 최선"으로 확대할 수 없다는 점을 함께 읽어야 합니다.

📝 예시는 지식 주입이 아니라 입출력 계약

  • "인컨텍스트 학습"이라는 이름 주의 — 실행 순간 행동을 바꿨을 뿐, 새 지식을 안정적으로 학습·파라미터 업데이트한 건 아니다
  • 더 안전한 설명 = 예시가 입력–출력 계약의 사례 (분류=레이블과 의미, 추출=답의 경계·형식, 생성=독자·구조)

🔬 Min 외 재검토

인컨텍스트 러닝의 이득에서 정답 레이블 자체보다 입력 분포·레이블 공간·형식이 더 중요할 수 있음 → "좋은 정답 예시를 많이 넣을수록 항상 좋다"의 반증.

실무 출발점 — few-shot을 관성으로 붙이지 말고 direct zero-shot을 기준선으로. 홀드아웃 사례·성공 기준을 고정한 뒤 예시 하나·레이블 표기·출력 형식 중 하나만 바꿔 통과율·실패 유형·토큰 비용·지연을 기록한다.
예시의 질은 정답 여부만이 아니라 실제 입력 분포와 닮았는지, 레이블 공간을 드러내는지, 형식을 분명히 하는지로 판단합니다. 그래서 첫 수를 few-shot으로 두지 말고 direct zero-shot을 기준선으로 삼아 한 조건씩 바꿔 비교합니다.
3

2022 — CoT · ReAct · 도구

추론 형식에서 시스템 설계로

중간 절차 · 다수결 · 도구·관측
정답만 요구하던 프롬프트가, 답에 이르는 중간 절차까지 실행 시점에 조건화하기 시작합니다. 여기서부터 역사적 수치를 현재 과업의 성능 약속으로 읽지 않는 것이 특히 중요합니다.

🧠 중간 절차를 조건화하다 — CoT

기법설정변화
CoT (Wei 외)PaLM-540B · GSM8K · CoT 예시 8개standard 17.9% → CoT 58.1%
zero-shot CoT (Kojima 외)text-davinci-002 · MultiArith17.7 → 78.7% (Let's think step by step)
zero-shot CoT (Kojima 외)text-davinci-002 · GSM8K10.4 → 40.7%
핵심은 "긴 생각을 적었다"가 아니라 예시가 출력 절차를 바꿨다는 것 — 수량 찾기 → 변화 계산 → 단위 확인 → 답. step by step은 만능 주문이 아니라 직접 답하기 vs 추론 요청을 같은 문제에서 비교하는 저렴한 기준선이다.
풀이 문장이 내부 계산의 충실한 기록이라는 뜻은 아닙니다. 또 짧은 분류나 외부 사실 검증 과업에서는 긴 출력이 비용과 오류를 오히려 늘릴 수 있으니, zero-shot CoT는 만능이 아니라 저렴하게 켜 보고 비교하는 기준선으로 씁니다.

🗳️ 여러 경로 · 쉬운 것부터 — 답 선택과 분해

  • Self-Consistency — 단일 greedy decoding 대신 여러 추론 경로를 표본화해 다수결. 바뀐 조건 = 표본 수·다양성·답 동치 규칙·호출 비용
  • least-to-most — 하위 문제 먼저, 앞 단계 답을 다음에 넣어 쉬운 것부터 푼다
체인의 목적은 "더 많이 생각"이 아니라 각 중간 산출물을 독립적으로 확인 가능하게 만드는 것. 단계마다 계약·검사·실패 정책이 없으면 초기 오류가 전파되고 지연·비용만 늘어난다.
다수가 같은 오해를 공유하면 투표도 틀립니다. 자유서술이나 코드처럼 답의 동치가 불분명하면 "무엇을 비교할지"부터 정의해야 합니다. least-to-most의 16→99도 SCAN 길이 일반화라는 특정 설정에 묶인 관찰이지 보편 수치가 아닙니다.

ReAct에서 프롬프트 엔지니어링은 문장 다듬기를 넘어 실행 프로토콜 설계가 됩니다. 무엇을 언제 호출하고, 관측을 어떻게 다음 판단의 근거로 쓰고, 언제 재시도하고 언제 멈출지까지 설계해야 합니다.

추론 모델 내장

질문은 사라지지 않는다 — 형태를 바꿀 뿐

thinking budget · 조건 설계
최신 추론 모델은 답 전에 내부적으로 더 긴 추론을 수행하도록 학습·설계될 수 있고, 제품 지침은 짧고 직접적인 요청을 권하기도 합니다. 2022년 zero-shot CoT의 관찰을 그대로 옮길 수 없는 이유입니다.

♻️ 같은 문구, 달라진 실행 정책

Qwen3 Technical Report

thinking / non-thinking 모드 구분, thinking budget으로 추론 토큰 예산 조절. 같은 문구라도 non-thinking에선 긴 추론이 안 나오고, thinking이라도 예산이 작으면 복잡한 문제를 못 끝낸다. 단순 추출에 큰 예산 = 답은 같아도 비용·지연만 오른다.

  • 과거 CoT가 거짓이 된 게 아니라, 실행 정책이 달라졌으니 같은 문구의 효과를 다시 검증해야 한다
  • 질문의 이동: "풀이 문장을 어떻게 끌어낼지" → "모델이 무엇을 보고 무엇을 쥐고 판단해야 하는지"
추론을 맡길수록 바깥 조건(작업 범위·금지, 신뢰 문서, 최신 관측, 도구, 형식, 통과 검사)이 흐리면 능력 있는 모델도 엉뚱한 근거를 읽는다. 긴 추론 노출 요구만으로 최신 정보 부재·잘못된 형식은 안 풀린다.
Qwen3의 모드·예산 설명은 그 모델·평가 조건에 묶인 기능 설명이지 보편 법칙이 아닙니다. 핵심은 CoT 효과가 문구보다 "모델이 선택한 모드와 배정된 추론 예산"에 더 좌우될 가능성을 함께 시험해야 한다는 것입니다.

네 이정표 다시 읽기

설계자가 통제하는 조건의 확장

예시 → 형식 → 시스템 → 조건
네 이정표를 나란히 놓으면 하나의 방향이 보입니다. 넓어져 온 것은 모델의 능력이 아니라, 설계자가 통제할 수 있는 조건의 범위입니다. 이전 단계가 사라진 게 아니라 다음 단계 안의 부품으로 남습니다.

🧭 조건은 이렇게 넓어졌다

이정표확장된 조건무엇이 바뀌었나
2020 인컨텍스트 러닝예시 계약재학습 없이 입출력 사례가 레이블 뜻·답 모양을 실행 시점에 보임
2022 CoT·self-consistency추론 형식중간 상태 요청·여러 경로 답 선택으로 출력 절차 변경
2022–23 ReAct·chaining시스템 설계도구·관측·다음 행동·종료 조건 연결로 모델 바깥 사실을 판단에
현재 추론 모델조건 설계근거·제약·도구·검사를 정확히 배치하고 조합을 비교
시험할 때 — 변화가 줄이려는 실패 + 그 실패가 줄었다고 판정할 독립 기준 + 정확도 이득과 맞바꿀 토큰·지연·권한 위험을 함께 둔다.
예: thinking budget을 512에서 4,096으로 올려 어려운 계산 정답이 늘어도 평균 지연이 4배가 되어 제한 시간 초과 요청이 생기면, 개선 여부는 업무의 응답 시간 약속에 달립니다. 긴 답·큰 숫자만 고르지 말고 성공·실패 사례와 비용 분포를 함께 남깁니다.

🧩 다섯 질문으로 기법을 위치시키기

1지시가 과업·독자·범위·금지를 정하는가 (← few-shot)
2출력 계약이 필드·순서·허용값을 정하는가 (← few-shot)
3중간 추론이 실제로 필요한가 (아니면 direct가 더 빠르고 안전) (← CoT·self-consistency)
4외부 도구·최신 관측이 필요한가 (← ReAct)
5검증·재시도는 무엇을 통과로 삼고 언제 다시 하는가 (← 채택/폐기 루프)
여러 조건을 함께 바꾸면 원인을 모른다 — 입력·성공 기준을 고정한 뒤 한 조건씩 바꾼다.

✅ 정답 & 해설

A1. 모델·데이터셋·설정 (예: "GPT-3 175B가 SuperGLUE에서 few-shot으로 71.8"). 설정엔 zero/one/few-shot과 가능하면 프롬프트 형식·평가 절차까지.
A2. 64.3→68.2→71.8의 상승은 사실이나, 같은 표의 SOTA 89.3과 여전히 격차가 있어 "few-shot이 fine-tuning을 대체했다"는 승리 선언이 아니기 때문.
A3. "좋은 정답 예시를 많이 넣을수록 항상 좋다"를 반증. 예시의 질 = 정답 여부만이 아니라 입력 분포·레이블 공간·형식을 드러내는지.
A4. 도구 호출·관측 교대를 포함한 실행 프로토콜(재시도·중단 조건 포함). 도구는 추측을 사실로 바꾸지 않으므로 오류·권한 실패도 관측으로 다룬다.
A5. 과거 CoT가 거짓이 된 게 아니라 실행 정책이 달라졌기 때문 — 모드·thinking budget에 따라 같은 문구의 효과가 달라질 수 있다.
A1과 A5를 자기 말로 설명할 수 있으면 오늘 목표는 달성입니다. 수치는 조건에 묶인 관찰이고, 기법의 효과는 실행 정책이 바뀌면 다시 검증해야 합니다.
