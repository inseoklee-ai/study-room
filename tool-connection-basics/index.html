에이전트와 도구 연결

도구 설명은 조회 기능의 사용법입니다 — 업무 기록 자체가 아닙니다

금요일 오후, 이번 주 프로젝트 진행 상황을 정리해 달라는 부탁을 받았습니다.

AI에게 아직 빠진 것

AI는 보고서를 읽기 좋게 구성하고 문장을 다듬는 데 익숙합니다. 그런데 빠진 것이 있습니다.

우리 팀에서 이번 주에
실제로 무슨 일이 있었는지
  • 누가 어떤 기능을 만들었는지, 배포까지 끝났는지, 다른 팀의 답변을 기다리고 있는지는 요청 문장만으로 알 수 없습니다
  • 실습 자료는 실제 회사 기록이 아닌 가상 제품팀의 업무 기록입니다 — 첫째 주와 둘째 주가 준비되어 있습니다
먼저 기록을 읽는 통로를 만들고, 그다음 읽은 내용을 팀의 기준에 맞춰 보고서로 바꿉니다.

📋 붙여 넣기

🔁 반복될 때

공유 표나 여러 프로젝트에 나뉘어 있다면 — 자료를 모으는 작업부터 반복하게 됩니다

🎯 중요한 변화는 AI가 더 그럴듯한 문장을 쓰게 되었다는 것이 아니라 — 대화 밖의 자료를 실제로 가져오는 동작이 생겼다는 것입니다
사용자는 보고 싶은 주를 말하고, 프로그램은 그 주의 기록을 읽고, AI는 읽어 온 기록으로 답변합니다.
1

실행할 기능과 모델에게 줄 설명

파일을 저장했다고 알려지지는 않습니다

① 도구 연결
함수의 코드를 만드는 일과 모델이 그 기능을 사용할 수 있게 만드는 일은 연결되어 있지만 같은 단계는 아닙니다.

도구(tool)의 안내

안내 항목제공할 내용모델이 활용하는 정보
이름get_weekly_records어떤 기능을 요청할지 구별
설명지정한 주의 가상 제품팀 업무 기록을 읽습니다이 기능이 필요한지 판단하는 데 사용
입력 항목week어떤 주를 조회할지 값을 채움
입력 형식글자로 된 값이며 반드시 필요값의 모양과 필수 항목을 확인
준비된 주week-one · week-two조회할 수 있는 자료의 범위를 이해
📖 입력 항목과 형식을 정한 규칙이 입력 스키마(input schema) — "이 기능을 실행하려면 어떤 값을 어떤 모양으로 제출해야 하는지 적은 규칙"
주 이름은 숫자가 아니라 글자로 전달합니다. 프로그래밍에서는 이런 글자 자료를 문자열(string)이라고 부릅니다.

형식을 지키는 일과 올바른 주를 고르는 일

  • week-two는 형식에 맞는 값이지만 — 사용자가 첫째 주를 물었는데 이 값을 넣었다면 다른 자료를 읽게 됩니다
  • 그래서 나중에는 "호출이 실행됐는가"와 함께 "어떤 입력으로 실행됐는가"도 확인합니다
도구의 설명은 조회 기능의 사용법입니다
업무 기록 자체가 들어 있는 것은 아닙니다
📌 "기록을 읽을 수 있다"는 안내만 받은 상태에서는 TASK-102의 개발이 끝났는지 아직 알 수 없습니다 — 실제 내용은 조회 후에 도착합니다
이 구분이 이 중단원 전체를 관통합니다.
2

모델의 요청이 만들어지는 지점

요청 생성과 실행의 경계

① 도구 연결
AI 앱은 사용자 요청과 사용 가능한 도구의 설명을 모델에게 전달합니다.

응답은 문장일 수도, 호출 요청일 수도 있습니다

모델에게 전달
  사용자 요청: 첫째 주 기록을 읽고 진행 상황을 알려 줘.
  도구 안내: get_weekly_records는 지정한 주의 업무 기록을 읽음
  필요한 입력: week
  준비된 값: week-one, week-two

모델이 생성한 호출 요청의 예
  사용할 도구: get_weekly_records
  이번 입력: week = week-one
  • '구조화'란 프로그램이 이름과 입력을 구별해 읽을 수 있도록 정해진 항목으로 표현한다는 뜻
  • 따라서 개발자가 매번 사용자 문장에서 '첫째 주'를 찾아 week-one으로 바꾸는 조건문을 작성해야만 하는 것은 아닙니다
⚠️ 여기까지는 "이 도구를 이 값으로 실행해 달라"는 요청이 만들어진 것입니다 — 아직 업무 기록을 읽은 결과는 없고, Python 함수가 모델 안에서 실행된 것도 아닙니다
이 예시는 설명용 메시지이며 특정 앱의 실제 실행 로그는 아닙니다. 앱마다 표시하는 항목 이름과 화면은 다를 수 있습니다.
3

모델 출력에서 호출을 읽어 내는 층

템플릿 · 파서 · API · 어댑터 · MCP

① 도구 연결
파싱(parsing)은 정해진 규칙에 따라 내용을 읽고 각 항목을 구분하는 과정이며, 그 일을 하는 프로그램을 파서(parser)라고 합니다.

채팅 템플릿과 파서

📥 채팅 템플릿

모델이 학습한 형식에 맞추어 입력을 준비하는 쪽의 규칙

📤 파서

생성된 출력을 읽는 쪽의 규칙 — 호출 구간을 찾고 그 안의 도구명과 입력을 추출

  • 모델에 따라 특별한 시작·종료 표시로 감싸거나, JSON처럼 항목 이름과 값을 짝지어 적는 형식으로 표현합니다 — 예: {"week":"week-one"}
  • 규칙은 제공자(provider)와 세부 모델에 따라 달라질 수 있지만 — "제공자마다 반드시 고유한 파서가 하나씩 있다"는 뜻은 아닙니다
  • vLLM에서는 자동 도구 선택 시 --tool-call-parser로 파서를 지정합니다. 공식 문서는 Qwen2.5에 hermes, Qwen3-Coder에 qwen3_xml을 안내 — 같은 계열이라도 세부 모델에 따라 달라지는 사례
서빙(serving)은 모델을 실행하고 외부 프로그램의 요청에 응답하는 일입니다. 이 선택은 모델을 운영하는 쪽의 작업입니다.

첫째 주 조회에서 각 층이 맡는 일

구분다루는 내용맡는 일
모델의 출력 표현도구 호출 표시와 입력 표현조회 도구와 week-one을 선택해 표현
서빙 쪽 파서모델의 표현 규칙도구명과 입력을 읽어 서비스의 호출 구조로 정리
제공자 API앱에 공개된 응답 항목Claude의 tool_use처럼 앱이 읽을 수 있는 호출 전달
앱의 연결 처리제공자별 응답과 실제 도구의 연결호출을 읽고 조회 도구로 보낼 요청을 준비
MCP 메시지앱과 도구 제공 프로그램 사이의 공통 형식tools/call에 name과 arguments를 담아 보냄
⚠️ MCP는 모델 출력의 특수 표시를 읽는 파서가 아닙니다. 제공자 API의 호출 항목과 MCP 호출 메시지는 같은 실행 의도를 전달하더라도 서로 구분해야 합니다
서로 다른 형식 사이를 맞추는 앱의 연결 부분을 어댑터(adapter)라고도 합니다. Claude API의 tool_use는 앱이 받는 공개 응답 형식이며 Claude 내부의 파서 구현을 보여 주는 것은 아닙니다.

세 가지 성공을 나눕니다

①파싱 성공
도구명·입력을 읽음
②실행 성공
조회 프로그램이 처리
③의미가 맞는 호출
원한 주와 도구를 고름
첫째 주를 부탁했는데 week-two를 출력했다면
파싱과 실행이 모두 성공해도 사용자 요청에는 맞지 않습니다
  • 파서는 모델이 고른 입력을 읽는 역할이며 — 그 선택이 사용자의 의도와 맞는지까지 보장하지는 않습니다
지원되는 제공자 API를 쓰면 보통 앱과 서비스가 이 처리를 맡으므로 사용자가 모델별 파서를 직접 설정하지 않습니다.

호출 결과가 답변이 되기까지

TASK-102의 여덟 걸음

① 도구 연결
모델은 호출을 요청하고, 조회 프로그램이 실제 기록을 읽습니다.

요청에서 답변까지

사용자 ──1. 첫째 주 상황 요청──▶ AI 앱
AI 앱 ──2. 요청 + 도구 설명──▶ 모델
모델 ──3. 도구 호출 요청(도구와 입력 선택)──▶ AI 앱
AI 앱 ──4. 조회 실행 요청 (week = "week-one")──▶ 조회 프로그램
조회 프로그램 ──5. 첫째 주 기록 반환──▶ AI 앱
AI 앱 ──6. 도구 결과 전달──▶ 모델
모델 ──7. 기록에 근거한 답변──▶ AI 앱
AI 앱 ──8. 답변 표시──▶ 사용자
이 순서도는 한 번의 조회로 답할 수 있는 요청을 나타냅니다. 실제 에이전트는 필요한 자료에 따라 추가 조회를 이어 갈 수도 있습니다.

항목기록된 값
업무TASK-102 · 로그인 안내 문구 개선

검증미실시
메모코드 작성은 끝났으며 다음 배포를 기다린다
📌 프로그램이 모델에게 전달하는 것은 이런 조회 결과입니다 — "팀 전체 업무가 모두 순조롭다"는 최종 평가가 아닙니다
  • 답변 예 — "로그인 안내 문구 개선은 코드 작성이 끝났고 다음 배포를 기다리고 있습니다. 담당자는 지우이며, 기한은 9월 7일입니다."
  • 이 문장의 '다음 배포를 기다린다'는 도구 설명이 아니라 실제로 반환된 업무 메모에서 왔습니다
'개발 완료'를 주간 보고서에서 최종 '완료'로 분류할지는 아직 별도의 문제입니다 — 코드를 다 만든 것과 배포한 것은 서로 다른 사건입니다.

호출 기록에서 읽을 단서

문장어느 단계인가
"첫째 주 기록을 읽겠습니다."AI가 말한 계획일 수 있습니다
"get_weekly_records에 week-one을 전달했습니다."호출 기록에서 도구명과 입력을 확인할 때 실행 요청의 근거
"TASK-102의 메모에는 다음 배포를 기다린다고 적혀 있습니다."반환된 자료와 맞춰 보아야 할 답변
🔍 AI의 문장만 읽고 끝내지 않고 — 도구명 · 입력 · 반환된 기록을 함께 살펴봅니다
  • 대화에 주 정보가 없는데 "진행 상황을 알려 줘"라고만 하면 — 어떤 주의 기록이 필요한지 먼저 확인하는 답변이 적절할 수 있습니다
문장을 자연스럽게 이해하는 능력과 사용자의 의도를 정확히 맞추는 일은 항상 같지 않습니다.

❓ 이해도 확인

Q1. 도구 설명에 들어 있는 것과 들어 있지 않은 것은?
A1. 들어 있는 것은 조회 기능의 사용법. 들어 있지 않은 것은 업무 기록 자체. 실제 내용은 조회 후에 도착한다.
Q2. 세 가지 성공은?
A2. 파싱 성공(도구명·입력을 읽음) · 실행 성공(프로그램이 처리) · 의미가 맞는 호출(원한 주를 고름). 앞의 둘이 성공해도 셋째는 틀릴 수 있다.
Q3. MCP는 모델 출력의 파서인가?
A3. 아니다. tools/call은 도구 제공 프로그램에 실행을 요청하는 메시지이며, 제공자 API의 호출 항목과 구분해야 한다.
Q2가 이 소단원의 핵심 구분입니다.
