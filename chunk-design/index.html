청크의 경계가 곧 검색의 경계입니다

자료를 많이 모으는 일보다, 답변의 한 문장이 어디에서 왔는지를 되짚을 수 있게 하는 일이 먼저입니다.

검색 가능한 자료와 답할 수 있는 자료는 다릅니다

행사 소개처럼 보이는 문장을 수집하더라도, 원문 URL과 문단의 맥락이 빠져 있으면 사용자가 출처를 눌렀을 때 돌아갈 곳이 없습니다. 이 경우에는 해당 문장을 검색 후보에서 제외하고 원문 URL과 섹션을 다시 확인해야 합니다.

📌 RAG에서 자료를 모은다는 말은 웹페이지를 많이 저장한다는 뜻이 아니라 — 나중에 답변의 문장과 연결할 수 있는 공개 근거를 고르는 일입니다
  • 모두콘 코퍼스는 세 범위의 공개 문서로 만든 37개 청크로 구성됩니다
  • 각 청크는 최소 120자의 사실 단위이며, 본문만 떼어 두지 않고 원문 URL과 섹션을 함께 보관합니다
따라서 검색 결과가 "행사 정보와 비슷한 문장"에 머무르지 않고, 사용자가 실제 출처로 돌아갈 수 있는 경로가 됩니다.
1

수집 단계에서 먼저 물어야 할 것

120자 기준의 뜻

③ 자료와 청크
두 질문을 먼저 던집니다.

두 질문과 두 가지 실패

1"이 페이지가 질문의 답을 포함하는가"
2"그 답이 어느 시점의 어떤 공개 문서에 근거하는가"

❌ 너무 크게 자르면

행사명이나 연도만 있는 페이지를 기계적으로 쪼개면 검색은 돼도 날짜·프로그램·소개처럼 서로 다른 사실이 한 청크에 섞여 생성 단계에서 엉뚱한 결론을 유도

❌ 너무 잘게 자르면

한 문장마다 잘라 버리면 문맥이 사라져 질문과의 관계를 판단하기 어려워집니다

📏 최소 120자는 글자 수가 품질을 보장한다는 뜻이 아니라 — 독립적으로 읽을 수 있는 사실 맥락을 확보하면서도 검색 단위가 지나치게 넓어지지 않게 하는 출발점
기준의 의미를 정확히 짚어 두면 학습자가 120자를 채우려고 주변 사실을 덧붙이는 실수를 피합니다.
2

청크는 본문이 아니라 출처를 가진 레코드입니다

다섯 필드

③ 자료와 청크
청크 JSON은 검색용 텍스트 배열보다 작은 데이터베이스에 가깝습니다.

다섯 필드가 같은 대상을 가리키게 합니다

필드뜻예
id청크를 식별하는 고정 이름MC-001
text최소 120자의 사실 단위 본문모두콘 소개와 행사 사실을 담은 문단
url본문을 확인할 공개 원문 주소모두콘 또는 모두의연구소 공개 페이지 URL
section원문 안의 맥락 또는 주제2025 본행사
vector본문을 임베딩한 검색용 값768차원 임베딩 배열
  • 이 필드가 함께 있어야 검색 순위, 화면의 출처 칩, 생성 프롬프트, 오류 조사에서 같은 대상을 가리킬 수 있습니다
  • vector만 보고 자료를 고르면 안 됩니다 — 숫자 배열은 빠른 비교를 돕지만, 사용자가 확인할 수 있는 것은 원문과 인용된 본문입니다
  • 코퍼스 벡터와 질의 벡터는 같은 모델과 같은 공간이어야 하며, 384차원과 768차원 경로를 혼재시키면 배열이 존재해도 비교 계약은 성립하지 않습니다
마지막 줄이 소단원 ④의 핵심 함정으로 이어집니다.

37청크의 범위를 먼저 명시합니다

모두콘의 37청크는 임의로 수집한 글 모음이 아니라 범위를 먼저 정한 뒤 그 안에서 사실 단위로 나눈 결과입니다.

범위 12025 본행사
범위 22018~2024 역대 행사
범위 3모두의연구소 소개
  • ID는 MC-001부터 연속적으로 부여하며, 새 자료를 추가할 때도 기존 ID가 가리키는 원문을 바꾸지 않는 편이 검색 결과와 인용 기록을 비교하기 쉽습니다
  • section에 어느 행사인지 남기면 "역대 모두콘"처럼 넓은 질문에는 여러 연도의 근거를, 특정 연도 질문에는 해당 맥락을 우선 점검할 수 있습니다
  • 각 연도에 동일한 개수를 억지로 배분하지 않습니다. 자료가 부족한 연도는 부족하다는 사실을 남겨야 합니다
⚠️ 37은 현재 구현에서 확인된 코퍼스 규모이지, 모든 도메인이 따라야 할 목표 수가 아닙니다 — 문서 수가 아니라 각 청크의 URL·본문·경계 이유를 검토할 수 있는가가 기준
숫자를 목표로 삼는 순간 청크 품질이 떨어집니다.

경계를 자를 때 확인할 세 가지

중심 사실 · 단독 가독성 · 원문 충실

③ 자료와 청크
이 세 확인이 120자 기준보다 중요합니다.

셋을 통과했는지 봅니다

1한 청크에는 하나의 중심 사실을 둡니다. 원문에 인접해 있더라도 질문자가 어느 사실을 물을지와 인용할 URL·섹션이 달라진다면 별도 청크 후보
2단독으로 읽어도 주어와 맥락이 충분한지 확인합니다. "그 행사는"처럼 앞 문단을 알아야 이해되는 문장을 떼어 내면, 임베딩과 BM25는 일부 단어를 잡더라도 생성 모델은 대상을 추측하게 됩니다
3원문 표현을 요약하거나 정리했을 때는 URL과 섹션을 더 엄격하게 확인합니다. 원문이 말하지 않은 연결이나 평가를 덧붙이면 출처가 있어도 환각을 감추는 재료가 됩니다
🎯 청크 설계는 생성 모델의 기억을 늘리는 작업이 아니라, 근거를 재현 가능한 단위로 보관하는 작업입니다
URL이 빠진 청크는 점수가 높아도 검증할 수 없고, section이 빠진 청크는 원문을 고칠 때 무엇을 다시 임베딩해야 하는지 알기 어렵습니다.
4

실습 2 — 자기 도메인에서 8~15청크 모으기

작은 코퍼스에서도 검색 경계가 생깁니다

③ 자료와 청크
37개를 빠르게 복제하는 것이 목표가 아닙니다.

세 걸음으로 모읍니다

1공개 원문 후보를 찾고 URL과 페이지의 주제를 먼저 기록합니다. 로그인이나 권한을 요구하는 자료는 브라우저 정적 앱에서 재현 가능한 근거가 되기 어려우므로 공개 자료 후보와 구분합니다
2각 자료를 읽어 최소 120자 이상의 독립된 사실 단위로 나누고, 임시 ID를 일정한 규칙으로 부여합니다 (MC는 예시 접두어 — 다른 접두어를 써도 되지만 한 코퍼스 안에서 규칙을 바꾸지 않습니다)
38~15개가 모이면 id, text, url, section을 채우고, text만 읽어도 질문과 관계를 판단할 수 있는지 교차 검토합니다
🔎 아직 vector가 없어도 — URL이 없는 행, 두 주제가 섞인 행, 너무 짧아 맥락을 잃은 행을 먼저 찾아낼 수 있습니다
청크 수집을 에이전트에게 일부 맡길 때도, 에이전트가 실제로 확인한 URL과 확인하지 못한 추정을 분리하도록 요청해야 합니다. 자동 수집 결과가 표에 들어갔다는 사실은 원문 검증이 끝났다는 증거가 아닙니다.

에이전트에게 질문으로 맡깁니다

당신은 공개 자료 기반 RAG 코퍼스의 수집 보조자입니다.

다음 원칙으로 8~15개 청크 초안을 제안합니다.
1. 각 청크는 최소 120자의 독립된 사실 단위로 제안합니다.
2. id, text, url, section 필드를 모두 제시합니다.
3. URL을 실제로 확인하지 못했으면 추정하지 말고 [검증 필요]로 표시합니다.
4. 한 청크에 서로 다른 행사 연도나 무관한 주제를 섞지 않습니다.
5. 원문에 없는 평가, 날짜, 수치, 관계를 보태지 않습니다.
6. 마지막에 중복 가능 청크와 사람이 원문으로 확인할 항목을 목록으로 정리합니다.
🎯 3번이 핵심입니다 — 그럴듯한 링크가 나중에 검색과 출처 표시를 동시에 오염시키는 일을 막습니다
수집 결과를 받으면 먼저 URL을 열어 text가 원문과 맞는지 확인하고, 그 뒤에야 임베딩 대상 목록으로 옮깁니다. "웹에서 자료를 찾아 JSON을 만들어라"라고 한 번에 지시하지 않습니다.

내 도메인에 적용하기

  • 모두콘이 37청크에 도달한 과정처럼 — 먼저 본행사 자료만 모은 뒤 역대 회차와 주관 소개를 덧붙이는 확장을 자기 도메인에서도 반복해 볼 수 있습니다
  • 청크가 늘어나면 같은 질문의 상위 검색 결과가 어떻게 바뀌는지 기록해 두면, 코퍼스 성장이 검색 품질에 미치는 영향을 관찰할 수 있습니다
  • 시간이 지나면 문서가 낡으므로, 어느 주기로 출처·청크·임베딩을 다시 점검할지 정하는 재수집 루프를 PRD 항목으로 남겨 두는 것도 설계의 범위입니다
청크의 경계가 곧 검색의 경계입니다
재수집 주기를 PRD에 남기라는 조언이 실무에서 가장 자주 빠지는 항목입니다.

❓ 이해도 확인

Q1. URL이 빠진 청크가 문제인 이유는?
A1. 검색 점수가 높아도 사용자가 검증할 수 없다. 출처를 눌렀을 때 돌아갈 곳이 없으므로 검색 후보에서 제외하고 URL·섹션을 다시 확인한다.
Q2. 최소 120자 기준의 진짜 의미는?
A2. 글자 수가 품질을 보장한다는 뜻이 아니라 독립적으로 읽을 수 있는 맥락을 확보하면서 검색 단위가 넓어지지 않게 하는 출발점. 채우려고 주변 사실을 덧붙이면 안 된다.
Q3. "37청크"를 목표 수로 삼으면 안 되는 이유는?
A3. 37은 현재 구현에서 확인된 규모일 뿐이다. 기준은 문서 수가 아니라 각 청크의 URL·본문·경계 이유를 검토할 수 있는가.
Q4. 에이전트에게 수집을 맡길 때 반드시 넣을 지시는?
A4. 확인하지 못한 URL은 추정하지 말고 [검증 필요]로 표시할 것. 그럴듯한 링크는 검색과 출처 표시를 동시에 오염시킨다.
Q4는 실제로 가장 자주 사고가 나는 지점입니다.
