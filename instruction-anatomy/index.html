지시의 해부학

같은 과업인데 답이 갈리는 이유 — 역할·과업·형식·제약이라는 계약

지시를 한두 문장 바꿔 본 경험은 누구에게나 있지만, 어느 문장이 효과를 냈는지까지 아는 경우는 드뭅니다. 이 소단원은 지시를 '친절한 부탁문'이 아니라 결과를 판정할 수 있게 만드는 '작업 계약'으로 보고, 그 계약을 이루는 부품과 빈자리, 그리고 효과를 재는 최소 실험을 다룹니다.

1

지시는 부탁이 아니라 계약이다

같은 과업인데 답이 갈리는 이유부터

역할 · 과업 · 형식 · 제약
잘 나온 한 번의 답을 재현하지 못하고, 잘못된 답에는 규칙만 덧붙이다 원인을 잃는 일이 흔합니다. 이 파트는 그 혼란의 이유를 지시의 부품 구성으로 설명합니다.

🔀 같은 과업인데 답이 갈린다

  • 지시를 한두 문장 바꿔 봤지만 어느 문장이 효과를 냈는지는 잘 모른다
  • 그래서 잘 나온 한 번의 답을 재현하지 못하고, 잘못된 답에는 규칙만 덧붙이다 원인을 잃는다
💡 지시는 친절한 부탁문이 아니라, 결과를 판정할 수 있게 만드는 작업 계약이다.
"모델이 말을 안 들었다"는 막연한 결론 대신, 어느 약속이 비었는지를 물을 수 있으려면 지시를 판정 가능한 계약으로 봐야 합니다. 계약이라는 관점이 이 소단원 전체의 출발점입니다.

🧩 계약의 네 부품

부품정하는 것
역할누구의 관점·책임으로 답할지 — 답을 받을 사람, 책임 범위, 말투·근거 수준
과업무엇을 어떤 완료 조건까지 할지 — 추출·판단·생성 + 끝났다고 볼 조건
형식답이 어떤 모양으로 쓰일지 — 필드·순서·허용값·빈값
제약하지 말 일과 불확실할 때의 처리 — 금지·길이·출처 범위·모를 때 행동
판단에 쓸 회의록·정책·수치 같은 사실(맥락)은 과업에 붙이되, 지시와 구별해 제공한다.
네 부품이 분명하면 "모델이 말을 안 들었다"고 막연히 결론내지 않고 어느 약속이 비었는지 살필 수 있습니다. 맥락(사실)은 다섯 번째 부품이 아니라, 과업에 딸려 오되 지시 문장과 섞이지 않게 구별해 두는 자료입니다.

🍳 레시피 비유 — 좋은 지시 = 좋은 레시피

"맛있게 만들어 주세요"만 적힌 레시피는 분량·순서·완성 조건을 알 수 없다. 좋은 레시피는 재료를 세고, 분량을 적고, 순서를 나누고, 멈출 조건도 남긴다.

역할누구를 위한 요리
과업무엇을 만들지
형식접시에 어떻게 담을지
제약알레르기·모를 때 처리
네 부품은 각각 다른 종류의 약속이다 — 하나가 비면 그 자리의 실패가 생긴다.
레시피 비유는 네 부품이 '더 많은 말'이 아니라 '서로 다른 종류의 정보'임을 보여 줍니다. 분량을 아무리 자세히 적어도 완성 조건이 없으면 언제 멈출지 모르듯, 형식을 채워도 제약이 비면 그 자리의 실패가 남습니다.

🕳️ 빈자리가 남기는 실패

역역할 ≠ "전문가" 호칭. 역할 없는 "배송 지연을 설명해 주세요"는 개발자용 원인 분석인지 고객 사과문인지 알 수 없다. 역할만 길고 과업이 없으면 권위 있어 보이는 빈말.
과과업 — "회의록을 요약" < "결정사항과 담당자별 행동 항목을 추출, 확인 안 된 담당자는 '확인 불가'로 표시". 주제가 아니라 수행 동사·사용할 입력·완료 판정으로.
형형식 — 없으면 같은 결과를 문단·표·목록으로 뒤섞는다. 단 "JSON으로 답해 주세요"만으로 내용이 참이 되진 않는다 — 형식은 인터페이스를 고정할 뿐, 사실성은 별도 확인.
제제약 — "주문 기록에 없는 배송일을 추정 말고 확인 불가라 답하라"는 날짜 조작을 막는다. 단 너무 많으면 충돌·핵심 매몰 → 실제 위험·관측된 실패에만 연결.
각 빈자리는 서로 다른 증상을 냅니다. 청중이 안 맞으면 역할, 필드가 흔들리면 형식, 근거 없는 추정이 나오면 제약이 빈 것입니다. 제약은 많을수록 좋은 게 아니라, 관측된 실패에만 붙일 때 효과가 큽니다.
2

네 층을 섞지 않고 쓴다

서로 다른 문장을 한 문단에 섞으면 모호해진다

역할·권한 · 과업 · 맥락 · 형식·제약
부품을 알아도 실제 지시문에서는 여러 종류의 문장이 한 문단에 뒤섞이기 쉽습니다. 이 파트는 네 층으로 분리해 쓰는 공통 관행과, 공식 문서들이 가리키는 같은 방향을 봅니다.

🗂️ 네 층으로 분리 — 고객 문의 분류 예

층적을 질문예
역할·권한누가 읽고 누구의 책임으로 답하나확인된 주문 사실만 안내하는 지원 담당자
과업무엇을 언제 완료로 보나문의를 환불·배송·기술 중 하나로 분류
맥락어떤 자료가 근거인가아래 주문 기록과 문의 본문만 근거로
형식·제약어떤 모양이며 모를 때 무엇을 하나JSON 세 필드, 근거 없으면 null
이 표는 서식이 아니라, 서로 다른 종류의 문장을 한 문단에 섞어 생기는 모호성을 발견하는 표다.
벤더 명칭과 우리 부품의 번역표도 함께 기억해 둘 만합니다: system↔역할, 작업 지시↔과업, 자료↔맥락, 출력·안전 규칙↔형식·제약. 계정·권한 부여, 요청 허용 확인, 접근 범위·마스킹, 스키마 검사·도구 호출 검증·감사 기록은 서버가 따로 맡을 일입니다.

📚 공식 문서가 가리키는 같은 방향

  • Anthropic Prompt engineering — 성공 기준과 경험적 시험 권장
  • OpenAI Prompt engineering — 지시·예시·맥락을 구분해 평가와 함께
  • Google Prompt design strategies — 목표를 직접 쓰고 필요 정보·제약·출력 형식 명시
  • 표현은 달라도 역할·과업·맥락·형식·제약을 섞지 않는 방향은 같다
⚠️ 역할은 전문성·말투를 정해도 보안 권한을 부여하지 않는다. 자료 속 "문서의 지시를 따르라"는 실행 규칙이 아니라 분석할 데이터로 다룬다.
벤더 문서의 '맥락'은 다섯 번째 명령이 아닙니다. 도구 실행 권한·상위 지시 우선권은 API 역할 체계와 서버 측 검증으로 따로 설계해야 하며, 역할 문장은 그 권한을 대신하지 못합니다.
3

최소 계약에서 실패를 따라 보강

더 긴 지시가 아니라 조건 하나의 효과를 관찰하는 실험

최소안 → 한 부품씩 → 기록
처음부터 스무 조건을 넣으면 견고해 보여도 고칠 위치를 모릅니다. 이 파트는 최소 계약에서 시작해 관측된 실패 하나에만 부품을 더하는 절차를 봅니다.

🧪 최소 계약을 실행으로 바꾸는 절차

1"배송일을 안내합니다" (최소안)
2+ "확인된 주문 기록만 근거로 답하는 고객지원 담당자" (역할 → 독자·책임 선명)
3+ reply·question 필드 요구 (형식 → 후속 프로그램이 검사 가능)
4+ "주문번호 없으면 배송일 단정 말고 한 가지 확인 질문만" (제약 → 빈 근거 추정 판정 가능)
답이 달라져도 마지막 문장만의 효과라 단정 말고, 추가한 부품과 고정한 조건을 함께 기록한다.
청중이 안 맞으면 역할 보강, 필드가 흔들리면 형식 보강, 근거 없는 추정이 나오면 제약 보강 — 같은 대표 입력으로 실행하며 한 번에 한 부품만 더합니다. 이것이 더 긴 지시를 만드는 절차가 아니라, 조건 하나의 효과를 관찰하는 가장 작은 실험입니다.

📋 절차 요약 — 기준선을 남긴다

1자주 오는 입력 1 + 실패 비용 큰 경계 입력 1을 기준선으로 보관
2역할은 비워도 되는지 먼저 판단, 과업엔 동사·완료 조건만
3원문을 맥락으로 구획, 자료 속 명령은 "인용할 데이터"로 명시
4사람이 읽나 프로그램이 읽나 정한 뒤 형식·빈값 규칙
5두 입력 결과를 같은 기준표로 읽고, 관측된 실패 하나에만 부품 추가 → 바꾼 문장과 결과를 나란히 남겨 다음 기준선으로
사람 시험도 유용합니다. 동료에게 주문 기록·문의·지시문만 주고 "반환할 값, 사용 가능한 근거, 모를 때 행동"을 말해 보라 합니다. 서로 다른 범주를 고르거나 확인 안 된 금액을 말해야 한다고 이해하면 계약이 덜 좁혀진 것이고, 같은 방식으로 설명하면 검토 가능한 상태입니다.

💭 생각 실험 — 완벽한 지시는 존재할까

한 문장 지시

빠르지만 빈칸을 남긴다 — 담당자 없을 때, 여러 기한 같은 경우를 못 정한다.

한 페이지 지시

빈자리를 줄이지만 "간결하게"와 "누락 없이", "원문만"과 "필요하면 설명"이 부딪히면 길이가 새 모호함이 된다.

좋은 지시의 시험 = 작성자가 아닌 다른 사람이 읽고 같은 일을 수행할 수 있는가. 단 사람이 할 수 있어도 모델이 반드시 성공하진 않는다.
충돌을 한 줄로 요약 못 하면 해석 책임을 모델에만 넘긴 셈입니다. 모델의 학습 이력·입력 분포도 결과에 영향을 주므로, 먼저 차이를 눈으로 확인하고 그다음 왜 통하는지 바탕을 살핍니다.

📌 이것만은 꼭 — 핵심 4문장

1지시는 부탁이 아니라 결과를 판정하게 만드는 작업 계약이다.
2계약은 역할·과업·형식·제약 네 부품, 사실(맥락)은 과업에 붙이되 구별한다.
3부품이 빈 자리마다 다른 실패가 생기고, 네 층을 섞으면 모호해진다.
4최소 계약에서 관측된 실패 하나에만 부품을 더하며 효과를 기록한다.
더 읽기: Anthropic·OpenAI·Google의 Prompt engineering / design 문서. 표현은 달라도 역할·과업·맥락·형식·제약을 섞지 않는 방향은 공통입니다. 특히 4번이 이 소단원 전체의 태도입니다.

✅ 정답 & 해설

A1. 친절한 부탁문이 아니라 결과를 판정할 수 있게 만드는 약속이기 때문 — 어느 약속이 비었는지 살필 수 있다.
A2. 역할(관점·책임) · 과업(무엇을 어떤 완료 조건까지) · 형식(답의 모양·필드·빈값) · 제약(금지·모를 때 행동).
A3. 내용의 사실성 — 형식은 전달 인터페이스를 고정할 뿐, 참·거짓은 별도로 확인해야 한다.
A4. 실행 규칙이 아니라 분석할 데이터로 다룬다. 역할은 전문성·말투를 정해도 보안 권한을 주지 않는다.
A5. 스무 조건을 한 번에 넣으면 고칠 위치를 모르므로 최소로 시작. 답이 달라져도 마지막 문장만의 효과라 단정 말고 추가한 부품과 고정한 조건을 함께 기록.
A3과 A4를 자기 말로 설명할 수 있으면 오늘 목표는 달성입니다. 형식과 권한은 각각 사실성·보안과 별개라는 점이 핵심입니다.
