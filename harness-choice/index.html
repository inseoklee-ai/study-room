터미널 · 편집기 · 브라우저 · 클라우드

④ 하네스 종류
'어디서 돌아가고, 내가 얼마나 지켜보느냐'로 갈립니다.

네 부류와 대표 도구

1터미널/CLI형 — 검은 명령창에서. 깊고 강력하지만 조금 낯섦. Claude Code, Codex CLI, Antigravity CLI(agy), Aider, OpenCode

3브라우저형 — 웹에서 클릭 몇 번으로, 처음엔 가장 수월함(배포까지 한 번에). Lovable, Bolt, Replit Agent
4클라우드/비동기형 — "이 이슈 고쳐 줘"를 통째로 맡기면 백그라운드에서 일하고 결과를 초안으로 가져옴. Devin, Google Jules, OpenAI Codex(클라우드)
🧭 앞의 셋은 내 컴퓨터에서 내가 지켜보며, 마지막은 멀리 맡겨 두고 결과만 받는 쪽

역사 — "세계 최초의 AI 소프트웨어 엔지니어" 논쟁

Devin, 2024년 3월

④ 하네스 종류
화려한 데모를 어떻게 볼 것인가에 대한 이야기입니다.

시연 영상과 반론

2024년 3월, 한 스타트업(Cognition)이 Devin을 공개하며 "세계 최초의 AI 소프트웨어 엔지니어"라고 내세웠습니다. 프리랜서 플랫폼에서 실제로 일을 받아 돈을 번다는 시연 영상이 큰 화제가 됐죠.

  • 그런데 곧 반론 — 한 개발자가 영상을 뜯어보니 홍보만큼 과제를 제대로 끝내지 못했고, 잘 되는 장면만 골라 담았다는 지적
  • 이후 독립 테스트에서도 성공률이 기대에 크게 못 미쳤습니다
  • "첫 AI 엔지니어"라는 마케팅과 실제 성능 사이의 간극을 둘러싼 논쟁이 한동안 이어졌습니다

교훈 ①

화려한 데모는 가려서 볼 것. "된다"는 시연과 "믿고 맡길 수 있다"는 전혀 다른 이야기입니다

교훈 ②

그럼에도 이 소동은 자율 코딩 에이전트 경쟁에 불을 붙인 촉매였습니다. 과대광고와 진짜 발전은 늘 섞여 옵니다

출처: The Register, 2025; IT Pro. 소단원 ①의 AutoGPT 소동과 같은 구조입니다 — 기대와 실제의 간극이 다음 세대 설계를 만듭니다.

초보라면 무엇부터, 무엇을 보고 고를까

형태 · 다섯 기준 · 섞어 쓰기

④ 하네스 종류
가장 실용적인 파트입니다.

어떤 형태부터?

내 상황권하는 형태
만들기부터 배포까지 클릭으로 끝내고 싶다브라우저형 (Lovable·Bolt·Replit) — 문턱이 가장 낮다
코드를 조금씩 보며 배우고 싶다편집기형 — AI가 고친 걸 눈으로 보고 승인/취소하며 감을 익힌다. 무료로 가볍게는 GitHub Copilot 무료 티어, 본격적으로는 Cursor
검은 화면이 익숙해진 뒤터미널형 — 힘이 세지만 나중에
"알아서 다 해 줌"이 매력적이다클라우드형은 초보의 첫 도구로는 통제감이 떨어진다 — 결과를 검토·판단할 안목이 아직 부족하기 때문
클라우드형을 말릴 때 이유를 분명히 하세요 — 능력이 부족해서가 아니라 '검토할 안목'이 아직 없어서입니다.

고를 때 볼 기준 다섯 가지

1모델을 고를 수 있나 — 한 회사 모델만 되나, 아무 모델이나 꽂나(오픈소스 계열이 자유로움)
2비용 구조 — 월 정액인가, "프로그램은 무료지만 쓴 만큼 API 요금"인가(후자는 많이 쓰면 확 오를 수 있음)
3오픈소스 여부 — 오픈소스면 그 도구가 서비스를 접어도 남이 이어받아 살릴 수 있다(2026년 한 오픈소스 편집기 확장의 종료가 이 리스크를 보여줬다)
4터미널이 편한가 — 편하면 CLI형, 아니면 편집기형
5맡길까 지켜볼까 — 한 줄씩 보며 승인하려면 편집기형, 통째로 맡기고 결과만 검토하려면 클라우드형
🔀 참고 — 실무자들도 하나만 쓰지 않습니다. 어려운 건 터미널 에이전트, 일상 편집은 편집기, 가끔 백그라운드용으로 클라우드를 섞어 씁니다
하나에 정착하기보다 필요에 따라 갈아타는 걸 목표로 두라고 말해 주세요.

에이전트에게 컴퓨터를 맡길 때 — 안전과 권한

승인 93% · 습관 세 가지

④ 하네스 종류
에이전트는 단순 답변기가 아니라 실제로 파일을 지우고 명령을 실행하고 외부에 요청을 보낼 수 있는 존재입니다.

좋은 도구는 묻습니다 — 그런데 93%

좋은 도구는 위험한 행동 전에 "이거 해도 될까요?"를 묻습니다. 문제는 이게 반복되면 사람이 무심코 "예"만 누르게 된다는 점이죠.

사용자들이 권한 요청의 약 93%를 그냥 승인한다는 조사가 있습니다
권한 방식 (도구마다 이름은 달라도 개념은 같다)
매번 확인 / 편집만 자동 / 위험한 것만 막고 나머지 자동 / 아무것도 안 물어봄
⚠️ 마지막(전부 자동)은 폐기해도 되는 실험 환경에서만 쓰라고 공식적으로 경고합니다
출처: Anthropic Engineering. 93%라는 숫자를 말해 주면 학습자가 자기 습관을 돌아봅니다.

누구나 지킬 안전 습관 세 가지

1중요한 폴더에서 '자동 수락'을 켜지 마세요. 문서·사진이 든 폴더, 회사 자료 폴더에선 매번 확인 모드로
2되돌릴 지점을 먼저 만드세요. 위험한 작업 전 저장(커밋)해 두면 잘못돼도 그 지점으로 롤백된다
3핵심 원칙 한 문장 — "아무것도 안 물어봄"과 "중요한 것에 대한 전체 접근"을 동시에 켜지 마라
⚖️ 앞서 백엔드에서 본 'AI 코드의 45% 보안 결함'과 통합니다 — 편함과 위험은 같이 옵니다
편해질수록 "이 작업이 뭘 건드리지?"를 한 번 더 보는 게 사람의 몫입니다. 소단원 ⑥ 실습에서 승인창을 일부러 거부해 보게 합니다.

내 컴퓨터에서 도는 AI — 로컬 모델

지금 쓰는 클라우드 AI는 회사 서버에서 돌지만, Ollama 같은 도구를 쓰면 오픈 모델을 내 컴퓨터에서 직접 돌릴 수도 있습니다.

✅ 좋은 점 (사생활·비용)

입력한 내용이 기기 밖으로 안 나갑니다. "클라우드 AI는 정책으로 사생활을 지키고, 로컬 AI는 구조로 지킨다"고들 합니다. 사용료가 없고 오프라인에서도 됩니다

⚠️ 아쉬운 점 (성능·사양)

집 컴퓨터에서 돌릴 수 있는 모델은 최신 클라우드 모델보다 대체로 뒤처지고, 어려운 추론엔 약합니다. 큰 모델은 고사양 GPU가 필요합니다

🧭 결론 — 아직은 클라우드 모델이 무난합니다. 다만 "민감한 자료는 로컬, 어려운 작업엔 클라우드"라는 섞어 쓰기 감각을 알아 두면 좋습니다
출처: ollama.com. 대단원 3의 '로컬 LLM' 강의와 그대로 이어지는 내용입니다.

요즘 판 — 열린 모델과 닫힌 모델

모델은 갈아 끼우는 부품이 된다

④ 하네스 종류
'모델 + 하네스'에서 모델 쪽 판도입니다. 수치는 2026년 7월 기준으로 빠르게 바뀝니다.

회사마다 태도가 갈립니다

🔒 Anthropic (Claude)

모델의 가중치를 공개하지 않습니다. "최고 성능을 유지하며 값을 받는다"는 전략이라, 반드시 이 회사 서버(API)로만 씁니다

🔓 OpenAI

절충. 최상위(GPT-5.x)는 닫아 두되, 한 급 낮은 gpt-oss는 가중치를 풀어 "AI를 자기 컴퓨터에서 돌려야 하는 곳(병원·은행·정부)"을 붙잡습니다

비용 — 에이전트는 왜 '비쌀' 수 있나

토큰 · 컨텍스트 창 · 누적

④ 하네스 종류
강력함에는 비용이 따릅니다. 여기서 숫자로 봅니다.

보통 채팅의 약 4배, 협업하면 약 15배

앞서 본 루프(계획-실행-관찰-반성)를 여러 번 도는 동안 AI는 매번 상황을 다시 읽고 생각합니다. '토큰'은 AI가 읽고 쓰는 글자 뭉치의 단위이자 곧 요금의 단위입니다.

입력 토큰

지시문·파일·이전 대화·도구 결과를 모델에 넣는 양

출력 토큰

모델이 새로 쓰는 양

  • 한 번의 호출에서 모델이 참고할 수 있는 입력·출력의 총량 한도를 컨텍스트 창(context window)이라고 합니다
  • 창이 크다고 공짜로 더 오래 기억하는 것은 아닙니다
출처: Anthropic, "How we built our multi-agent research system", 2025. 4배·15배는 실측 기반 수치입니다.

왜 눈덩이처럼 커지나

에이전트는 한 작업도 여러 번 호출하고, i번째 호출은 앞선 대화와 도구 결과를 다시 통째로 포함합니다.

총 입력량 ≈ Σ input_i      총 출력량 ≈ Σ output_i

매 단계에 누적 기록을 다시 넣으므로,
단계 수 n 이 늘면 입력량은 선형보다 빠르게 (단순 누적이면 대략 n²에 가깝게) 커진다
  • 비용뿐 아니라 응답을 기다리는 시간도 그만큼 늘어납니다
🎯 실전 규율은 하나 — 한 번에 거대한 작업을 통째로 시키지 말고 작게 쪼개기
큰 파일·긴 로그는 필요한 부분만 주고, 작업이 끝나면 짧은 요약만 남깁니다. "토큰을 무조건 적게"가 아니라 다음 판단에 필요한 증거만 남기는 것이 목표입니다(지난 시간의 '한 번에 하나' 규율과 통합니다). 출처: Anthropic, "Effective context engineering".

대화가 길어지면 왜 헤맬까 — 컨텍스트 부패

컨텍스트 창이 꽉 차기 시작하면 이상한 일이 벌어집니다 — 아까 정한 걸 잊고, 앞뒤가 안 맞고, 없는 파일명을 지어내기도 하죠. 이걸 반쯤 농담으로 '컨텍스트 부패(context rot)'라 부릅니다.

이 바닥은 정말 빠르게 바뀝니다

AI 코딩 도구의 이름·가격·무료 정책·회사는 짧은 기간에도 바뀝니다. 특정 도구의 인수·중단·대체 여부는 이 노트의 고정 사실로 외우기보다, 선택 직전에 공식 공지와 현재 저장소 상태를 확인할 정보로 다루는 편이 안전합니다.

도구 이름을 외우는 건 의미가 적습니다
에이전트 = 모델 + 하네스 · MCP(연결) · 스킬(반복 자동화)
이 개념을 잡아 두면 어떤 새 도구가 나와도 "아, 이건 하네스가 이렇구나, MCP 되나?"로 빠르게 판단할 수 있습니다
AI에게 고르게 하는 프롬프트 —
"'브라우저에서 쓰고 싶고, 무료로 시작하고 싶다'는 조건에 맞는
 AI 코딩 도구 3개를 장단점과 함께 추천하고,
 MCP·스킬 확장이 되는지도 알려줘.
 각 정보의 확인 날짜와 공식 출처도 붙여줘."
비교 글은 출발점일 뿐 최신성의 보증이 아닙니다. 마지막 프롬프트에서 '확인 날짜와 공식 출처'를 요구하는 부분이 중요합니다.

❓ 이해도 확인

Q1. 하네스 네 부류와, 앞의 셋과 마지막의 차이는?
A1. 터미널·편집기·브라우저·클라우드. 앞의 셋은 내 컴퓨터에서 내가 지켜보며, 클라우드형은 멀리 맡겨 두고 결과만 받는다.
Q2. 에이전트 비용이 눈덩이처럼 커지는 이유는?
A2. i번째 호출이 앞선 대화와 도구 결과를 다시 통째로 포함하므로, 단계 수가 늘면 입력량이 선형보다 빠르게(대략 n²에 가깝게) 커진다. 규율은 작게 쪼개기.
Q3. 권한에서 절대 함께 켜면 안 되는 조합은?
A3. "아무것도 안 물어봄" + "중요한 것에 대한 전체 접근". 사용자들은 권한 요청의 약 93%를 그냥 승인한다.
Q4. "오픈웨이트 모델이 곧 공짜"라는 말의 문제는?
A4. 직접 돌리려면 고성능 GPU 수십 장이 필요하고, 가중치가 아직 공개 예정인 경우도 있다. 또 벤치마크 최상단은 여전히 폐쇄 프런티어 모델이고, 점수는 하네스가 더 좌우한다.
Q2는 소단원 ⑤의 Ralph 루프(파일에 상태를 쌓는 이유)로 바로 이어집니다.
