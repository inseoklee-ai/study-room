n8n 직접 띄워 보기
— 셀프 호스팅의 선택지

내 노트북에서 화면이 뜨는 순간, 운영 책임도 함께 옮겨옵니다

여기까지가 필수 판정입니다. 판정한 워크플로를 직접 운영할 필요가 있는 학생이 이 선택 심화로 넘어옵니다.

운영 주체가 누구인가

환경인스턴스를 운영하는 주체
n8n Cloudn8n이 인스턴스를 운영
수업 인스턴스수업 운영 환경이 관리
셀프 호스팅실행 환경 · 데이터 보관 · 업데이트 · 장애 대응을 내가 관리
  • n8n은 Sustainable Use 라이선스를 따르는 fair-code 소프트웨어이므로 이 방식으로 실행합니다
셀프 호스팅은 다른 회사가 운영하는 환경 대신 내가 관리하는 컴퓨터나 서버에서 n8n을 실행합니다.

접속 주소만 달라지는 것이 아닙니다

어디에 남나워크플로 정의
어디에 남나실행 기록
어디에 남나연결에 쓰는 비밀값
  • 백업과 삭제, 접근 권한 회수도 내가 설계하고 확인합니다
  • 데이터가 내 컴퓨터에 있다고 해서 안전하다고 판단하지 않습니다 — 그 컴퓨터에 누가 접근하는지, 백업이 있는지, 비밀값이 어디에 저장되는지를 따로 점검합니다
하네스 중단원 ⑧의 "세션 격리 ≠ 컨테이너 격리"와 같은 종류의 착각을 경계하는 슬라이드입니다.
1

가장 짧은 경로부터

127.0.0.1:5678

⑦ 셀프 호스팅
혼자 살펴보는 로컬 실행에는 도메인과 HTTPS를 먼저 사용하지 않습니다.

로컬 실행 — 공개 범위를 넓히지 않습니다

도메인 없이 내 컴퓨터에서 실행하고
127.0.0.1:5678로 접속합니다
구분뜻과 쓰임
127.0.0.1현재 사용 중인 컴퓨터를 가리킵니다
5678기본 포트로 n8n 화면에 연결됩니다
도메인 · HTTPS다른 사람이 인터넷을 통해 접속하도록 공개할 때 — 주소와 통신 암호화, 접근 경계를 관리합니다
⚠️ 로컬 실행은 공개 범위를 넓히지 않는 대신 — 노트북을 끄면 n8n도 중지됩니다
혼자 관찰할 때는 도메인과 HTTPS가 오히려 관리 대상만 늘립니다.

Docker — 독립된 상자에 함께 담아

  • Docker는 앱과 실행에 필요한 환경을 컨테이너라는 독립된 상자에 함께 담아 실행합니다
  • n8n 이미지를 내려받아 컨테이너로 띄우면 — 운영체제마다 필요한 프로그램을 따로 맞추는 수고를 줄입니다
  • 같은 이미지를 사용하면 내 컴퓨터와 서버에서도 비슷한 조건으로 실행합니다
📌 그래서 Docker는 셀프 호스팅을 시작할 때 널리 사용됩니다
이식성(소단원 ②의 다섯 질문 중 하나)을 실제로 확보하는 방법이 이미지 고정입니다.

깊이 보기 — 컨테이너와 볼륨

📦 컨테이너

실행 중인 n8n 프로그램과 실행 환경을 포함합니다. 지우고 새로 만들면 그 안의 임시 파일도 함께 삭제됩니다

💾 볼륨

컨테이너 바깥에 데이터를 남겨 두는 저장 공간. n8n 데이터를 연결하면 이미지를 바꾸거나 컨테이너를 다시 띄운 뒤에도 워크플로와 설정을 이어서 씁니다

⚠️ 볼륨의 실제 저장 장치와 백업 방법은 Docker 설정과 운영체제에 따라 다르므로 직접 확인합니다
"볼륨을 붙였다"와 "백업이 있다"는 서로 다른 사실입니다.

규모가 아니라 운영 책임으로 고릅니다

SQLite · PostgreSQL · Redis · Kubernetes

⑦ 셀프 호스팅
더 큰 구성을 더 나은 구성으로 판단하지 않습니다.

데이터를 어디에 저장하나

선택저장 방식알맞은 환경
SQLite (기본)내 컴퓨터의 한 파일에 저장혼자 관찰하거나 가볍게 실습하는 환경에서 간단하게
PostgreSQL별도로 실행하는 데이터베이스 프로세스에 저장여러 사람이 지속적으로 사용하거나 백업과 복구를 운영해야 하는 환경에서 권장
기본값(SQLite)이 나쁜 선택이 아니라, 환경에 맞는 선택입니다.

실행이 겹치면 — queue mode

기본 구성

단일 실행 프로세스가 들어온 작업을 모두 처리합니다

queue mode

Redis가 작업 대기열을 관리하고 여러 실행 프로세스가 작업을 나누어 처리합니다

⚖️ 처리량은 증가하지만 — Redis와 실행 프로세스 상태, 실패한 작업 기록까지 확인할 대상도 증가합니다
성능을 얻는 대신 관측 대상이 늘어난다는 교환을 명시합니다.

Kubernetes — 개인 로컬에는 쓰지 않습니다

  • Kubernetes(k8s)는 컨테이너를 여러 서버에 배치하고, 중지된 컨테이너를 다시 실행하며, 트래픽에 따라 수를 조절합니다
  • n8n은 Kubernetes용 Helm 차트 배포를 지원합니다
  • 개인이 로컬에서 살펴보는 환경에는 관리 대상이 너무 많으므로 사용하지 않습니다
  • 여러 서버에서 지속적인 서비스를 운영하는 환경에서는 — 컨테이너 상태를 매번 직접 관리하지 않기 위해 사용합니다
미니멀 소단원(하네스 ⑦)의 논리와 같습니다 — 더 많은 장치가 항상 더 좋은 것은 아닙니다.

요청문과 검증

로컬에서 n8n을 Docker로 띄워 줘.
포트는 5678로 열고, 데이터는 볼륨에 남겨 줘.
실행 뒤에 확인할 주소와 생성된 파일·볼륨도 설명해 줘.
🔍 제안된 설정은 그대로 믿지 않고 — 사용한 이미지, 포트, 볼륨을 다시 읽어 확인합니다
  • 요청문에 목적과 조건을 함께 넣는 것이 요령입니다 — 소단원 ④의 요청문 패턴과 같습니다
"실행 뒤에 확인할 주소와 생성된 파일·볼륨도 설명해 줘"가 검증을 요청문에 심는 부분입니다.

실행 뒤 확인 목록

1브라우저에서 127.0.0.1:5678을 열어 화면이 보이는지
2Docker의 실행 목록에서 n8n 컨테이너가 계속 동작하는지
3화면이 열리지 않으면 포트 충돌 · 컨테이너 중지 · 이미지 내려받기 실패처럼 관찰할 수 있는 신호부터
4비밀번호나 API 키가 요청문·터미널 기록·공유 화면에 남지 않았는지
4번을 습관으로 만들어야 합니다. 실습 화면을 캡처해 공유할 때 가장 자주 새는 지점입니다.

표를 정답표로 쓰지 않습니다

더 큰 구성을 더 나은 구성으로 판단하지 않습니다
  • 기준은 하나 — 내 워크플로가 중지됐을 때 누가 확인하고 복구할 수 있는지에 맞춰 구성합니다
  • 셀프 호스팅에서는 n8n을 내 환경에서 실행하며 — 데이터와 실행 기록을 어디에 두고 어떤 책임을 맡을지 결정합니다
이 기준 한 줄이 이 소단원 전체의 결론입니다.

❓ 이해도 확인

Q1. 셀프 호스팅에서 옮겨오는 것은 접속 주소뿐인가?
A1. 아니다. 워크플로 정의 · 실행 기록 · 비밀값이 어디에 남는지, 그리고 백업 · 삭제 · 접근 권한 회수까지 내가 설계하고 확인한다.
Q2. 컨테이너와 볼륨의 차이는?
A2. 컨테이너는 실행 중인 프로그램과 환경으로 지우면 임시 파일도 사라진다. 볼륨은 바깥에 데이터를 남기는 저장 공간으로 컨테이너를 다시 띄워도 워크플로와 설정이 남는다.
Q3. 구성을 고르는 기준은?
A3. 규모가 아니라 운영 책임 — 내 워크플로가 중지됐을 때 누가 확인하고 복구할 수 있는지.
Q1의 "데이터가 내 컴퓨터에 있으니 안전하다"는 착각이 가장 흔합니다.
