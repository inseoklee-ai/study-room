내 하네스의
사용자와 작업

"코드를 잘 고쳐 주는 에이전트"는 바라는 방향이지만 범위가 넓습니다

회의 자료를 읽다가 "이 일을 AI가 대신 정리해 주면 좋겠다"고 생각한 적이 있을 것입니다.

요청이 구체적이어야 합니다

❌ 넓은 요청

"코드를 잘 고쳐 주는 에이전트" — 무엇을 만들고 확인할지 정하기에는 넓습니다

✅ 좁힌 요청

"내가 지정한 작은 프로젝트에서 실패하는 테스트를 확인하고, 관련 코드를 수정한 뒤 같은 검사를 다시 실행한다" — 작업 대상과 완료의 근거가 보입니다

  • 어느 폴더의 자료인지, 확정된 일과 미정인 일을 어떻게 구별할지, 결과를 화면에만 보여 줄지 파일로 남길지에 따라 필요한 프로그램이 달라집니다
  • 범용이라는 말은 처음부터 모든 일을 해야 한다는 뜻이 아닙니다 — 자료 읽기와 코드 수정처럼 서로 다른 작업이 공유하는 실행 구조를 만들고, 필요한 도구를 연결해 범위를 넓힌다는 뜻
이번에는 자신의 범용·코딩 에이전트 하네스를 설계하고 구현합니다.
1

사용자가 결과를 판단할 수 있는 시나리오

자기 자신이어도 좋습니다

① 사용자와 작업
실제 개인 자료를 가져올 필요는 없으며, 같은 상황을 재현한 가상 자료로 시작할 수 있습니다.

두 시나리오

구분자료 정리 시나리오코딩 시나리오
사용자회의 뒤 다음 할 일을 정리하는 팀원작은 프로그램을 유지·보수하는 개발자
시작 상황회의록과 체크리스트가 여러 파일로 나뉨특정 입력에서 테스트가 실패함
요청확정된 일과 확인할 일을 구별해 정리실패 원인을 확인하고 필요한 코드 수정
필요한 근거실제 읽은 파일과 관련 문장변경 내용과 다시 실행한 검사 결과
원하지 않는 행동없는 담당자나 일정을 추측해 확정테스트의 기대값을 바꿔 실패를 숨김
  • 자료 이름만 바꾸기보다 어떤 결과가 유용한지 생각해 보세요 — 요약이 짧아도 담당자가 빠지면 쓸 수 없고, 코드가 바뀌어도 검사를 하지 않았다면 수정이 맞는지 알기 어렵습니다
  • "파일을 읽었다"는 말과 실제 읽기는 다릅니다 — 사용자는 결과 문장뿐 아니라 어떤 행동이 실행됐는지도 확인하고 싶습니다
이런 기대가 뒤에서 진행 상태와 실행 기록을 설계하는 이유가 됩니다.
2

모델과 직접 만들 하네스

판단만으로 파일이 열리지는 않습니다

① 사용자와 작업
모델은 파일을 읽는 것이 필요하다고 판단할 수 있지만, 그 판단만으로 내 컴퓨터의 파일이 열리지는 않습니다.

하네스가 맡는 다섯 연결

1사용자 요청과 사용할 수 있는 기능을 모델에게 전달
2모델이 어떤 기능을 요청했는지 해석
3실행 가능한 요청인지 확인하고 실제 기능을 실행
4성공 결과나 오류를 모델에게 돌려줌
5다음 행동을 이어가거나 답변·오류·중단 조건에 따라 끝냄
  • 도구(tool)는 모델에게 제공하는 실행 기능 — 파일 읽기, 문자열 검색, 정해진 테스트 실행 등. 도구 호출은 그 기능을 실행해 달라는 모델의 요청
  • 파일을 못 찾았다면 오류를 돌려주고, 모델이 다른 경로를 확인하거나 사용자에게 질문할 수 있어야 합니다
🎯 어떤 파일을 읽을지는 모델이 선택할 수 있지만 — 작업 폴더와 허용한 기능, 승인과 중단 조건은 하네스가 관리합니다. 이 연결을 자신의 소스 코드로 구현합니다
결과를 보고 다시 판단하는 반복이 자료 작업과 코딩 작업의 공통 구조입니다. 제품마다 포함하는 기능은 다를 수 있습니다.
3

PRD에 남길 사용자 기대

빠진 결정은 AI가 대신 채웁니다

① 사용자와 작업
바로 "하네스를 만들어 줘"라고 요청할 수도 있습니다.

빠진 결정이 채워지는 방식

  • 학생은 터미널 도구를 생각했는데 웹 서버가 만들어지거나, 파일 변경 전에 확인하고 싶었는데 곧바로 저장하는 기능이 들어갈 수 있습니다
  • PRD(Product Requirements Document) — 무엇을 만들고 어떤 동작을 기대하는지 적어, 구현과 검증의 기준으로 삼는 문서. 분량을 늘리는 것이 목적은 아닙니다

❌ 넓은 문장

"범용 에이전트 지원"

✅ 구현에 도움되는 문장

"사용자가 지정한 자료 폴더에서 관련 내용을 찾아 정리한다. 자료에 없는 정보는 확정하지 않고, 사용한 파일을 결과에 표시한다."

📌 아직 테스트 명령이나 승인 방식을 모두 결정할 필요는 없습니다 — 이번 단계에서는 누가 어떤 일을 맡기며, 무엇을 좋은 결과로 판단할지를 먼저 적습니다
"사용자가 무엇을 요청했을 때 프로그램이 어떻게 행동해야 하는가"를 함께 확인할 수 있으면 됩니다. 코딩 시나리오를 더하면 같은 하네스가 무엇을 재사용하고 무엇을 추가해야 할지 드러납니다.

개발 AI와 완성할 에이전트 구별

개발 협업 도구Claude Code · OpenCode
설계·구현을 도움
만들 제품내 하네스
모델·도구 반복을 직접
  • AI에게 코드 작성이나 오류 분석을 맡겨도 됩니다 — 다만 개발 AI가 대신 자료를 읽어 답한 결과와, 학생이 만든 하네스가 실제로 실행한 결과를 구분해야 합니다
  • Claude Code에게 "폴더의 자료를 요약해 줘"라고 부탁하면 개발 도구 자체의 기능으로 작업할 수 있습니다 — 이것만으로 자신의 하네스가 구현되었다고 볼 수는 없습니다
  • 만든 프로그램을 별도로 실행하고, 그 프로그램이 모델에 요청하고 도구를 실행한 기록을 확인해야 합니다
⚠️ API 통신 라이브러리 등은 활용하되 — 제품 내부의 모델·도구 반복을 완성된 에이전트 CLI나 Agent SDK에 통째로 넘기지 않습니다
그 방식으로 기존 실행 도구를 조립하는 경험은 다음 카드뉴스 제작 수업에서 다룹니다.

첫 사용자 결정 기록하기

내가 쓸 자료 정리·코딩 하네스를 설계하고 싶어.
PRD의 사용자와 작업부터 같이 구체화하자.
  • 설계 자료를 내려받아 개발 도우미의 작업 폴더로 엽니다. PRD.md에는 일부 결정이 비어 있고, 이번에는 사용자와 업무에 해당하는 D01부터
  • AI가 제시한 기능 목록을 바로 받아들이기보다 — 자기 자료 작업 하나와 코딩 작업 하나를 골라 어떤 입력을 주고, 어떤 결과를 확인하고, 무엇을 원하지 않는지 적어 보세요
  • 이 단계에서는 구현을 시작하도록 요청하지 않습니다
✅ D01을 읽었을 때 다른 사람이 사용 장면을 떠올릴 수 있으면 첫 결정이 구체화된 것입니다
만든 뒤에는 고정된 터미널 과제 열 개로 기준 성능을 측정합니다. 실패 기록에서 개선할 부분을 찾고 같은 조건으로 다시 실행하여, 구현체와 실험 결과를 함께 제출합니다.

❓ 이해도 확인

Q1. 여기서 '범용'은 무슨 뜻인가?
A1. 모든 일을 한다는 뜻이 아니라 — 서로 다른 작업이 공유하는 실행 구조를 만들고 도구를 연결해 범위를 넓힌다는 뜻.
Q2. 개발 AI가 폴더를 요약해 주면 하네스가 구현된 것인가?
A2. 아니다. 개발 도구 자체의 기능이다. 만든 프로그램을 별도로 실행하고 그 실행 기록을 확인해야 한다.
Q3. PRD를 쓰는 이유는?
A3. 빠진 결정을 AI가 대신 채우는 일을 줄이기 위해. 분량이 목적이 아니라 "무엇을 요청하면 어떻게 행동해야 하는가"를 함께 확인하는 것.
Q2가 이 중단원 전체에서 가장 자주 흐려지는 경계입니다.
