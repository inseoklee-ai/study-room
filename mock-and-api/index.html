백엔드 없이 프론트엔드 만들기

프론트/백/API/JSON · 목업 데이터 · 교체

⑤
백엔드 없이도 프론트엔드를 만들고 실제로 쓰는 것처럼 테스트하는 방법입니다.

🍽️ 홀·주방·창구 — HTTP 요청

식당웹하는 일
홀프론트엔드손님이 보고 만지는 공간(메뉴·주문·받기)
주방백엔드안 보이는 곳에서 저장·요리·완성
서빙 창구API홀↔주방 연결점(주문 전달·음식 내보냄)
주문서 양식JSON정해진 규격(이름표-값 묶음)
// 프론트엔드가 백엔드에 "전문가 목록을 주세요"
const response = await fetch('https://내서비스.com/api/experts');
const experts = await response.json();
// experts = [{ name: '김민준', specialty: '형사' }, ...]
문제는 — 이 코드가 돌려면 그 주소에 응답하는 백엔드가 이미 있어야 한다. 없으면 fetch는 실패하고 화면은 빈다. 그래서 가짜 데이터(목업)를 쓴다.
HTTP 요청 = 브라우저가 서버에 "이 데이터 주세요"라고 물으면 서버가 JSON으로 답하는 것. 그 JSON을 컴포넌트에 넘겨 화면을 그립니다.

🎭 목업 데이터가 유용한 이유 넷

1백엔드를 기다리지 않는다 — 프론트를 먼저(실무의 병렬 개발: 프론트팀·백팀 동시)
2디자인·인터랙션을 먼저 검증 — 데이터가 어떻게 들어올지 알면 배치·상호작용을 백엔드 없이 테스트
3AI 코딩에서 특히 강력 — "이 데이터로 화면을 만들어줘"면 연결 없이 완성 화면을 즉시
4나중에 진짜 API로 쉽게 교체 — 목업 구조를 진짜 응답과 맞춰두면 한 줄만 바꿔
💡 한 가지 요령 — 평범한 데이터만 말고 극단적인 경우도 섞어 달라고("목록이 텅 비었을 때", "이름이 유난히 길 때"). 그래야 그런 상황에서도 화면이 안 깨지는지 미리 확인.
목업은 진짜 API가 보내줄 것과 같은 구조의 가짜 데이터를 코드 안에 직접 적어두는 것입니다.

💾 별도 파일로 빼면 교체가 쉽다

// mockData.js — 진짜 API 응답과 "같은 구조"로 만든다
const mockExperts = [
  { id:1, name:'김민준 변호사', specialty:'형사전문', years:15 },
  { id:2, name:'이서연 변호사', specialty:'민사전문', years:12 },
];
export default mockExperts;

// ExpertList.jsx
import mockExperts from './mockData';   // ← 이 한 줄만 바꾸면 끝
function ExpertList() {
  const experts = mockExperts;   // 나중에: useFetch('/api/experts')
  // ... 화면 코드는 그대로
}
데이터를 별도 파일에 두면 백엔드가 생겼을 때 import 한 줄을 API 호출로 바꾸기만. 화면 코드는 손대지 않는다 — 컴포넌트는 experts 배열 구조만 알 뿐 어디서 왔는지는 신경 안 쓰니까. 이것이 지난 시간에 배운 관심사의 분리의 실전 적용.
❌ 컴포넌트 안에 데이터를 직접 박아넣으면 컴포넌트가 열 개일 때 열 곳을 뒤져야 합니다. ✅ 별도 파일이면 한 줄만.

🔧 가짜 데이터는 AI에게 부탁 · JSON 알아보기

  • 손으로 적을 필요 없다 — "내 화면에 쓸 그럴듯한 가짜 데이터를 만들어 줘". 알려줄 건 둘: 어떤 화면인지(쇼핑몰 상품 목록)와 무엇을 보여줄지(이름·가격·품절 여부)
  • "실제 인물·기관 이름은 빼고 가상의 값으로"만 덧붙이면 몇 초 만에 "진짜 같은 가짜"
{"이름": "딸기 생크림 케이크", "가격": 32000, "품절": false}
AI가 돌려주는 데이터는 대개 JSON — 겁먹을 것 없다. 이름표와 값을 짝지어 적어 둔, 사람도 눈으로 읽는 목록일 뿐. 따옴표 규칙 같은 건 AI가 알아서 지키니 "이런 이름표-값 묶음으로 오는구나" 정도만 알아보면 충분.
교체 프롬프트 — "mockData.js에서 가져오는 부분을 진짜 API 호출로. 엔드포인트 /api/experts, 로딩 중엔 '불러오는 중...', 실패 시 '다시 시도해 주세요'." 이 한 줄로 로딩·에러 처리까지 추가됩니다.

API, 프론트엔드가 아는 만큼만

REST 네 동사 · GraphQL · 역사

⑥ CS 교양
창구 너머로 실제로 무엇이 오가는지, 화면을 만들 때 알아야 할 만큼만 봅니다.

🔌 REST API의 네 가지 동사

가장 널리 쓰이는 방식은 URL로 데이터를 요청하는 REST API — 주소창에 URL을 넣는 것과 본질이 같은데, 화면이 아니라 데이터를 달라고 한다.

동사URL 예식당 비유의미
GET/api/experts"메뉴판 보여줘"목록을 가져온다
POST/api/experts"이거 주문할게"새 데이터를 만든다
PUT/api/experts/1"1번 이렇게 바꿔줘"기존 데이터 수정
DELETE/api/experts/1"1번 취소할게"데이터를 지운다
💡 AI에게 "이 화면에 POST 요청 추가해줘"면 AI는 이 약속을 안다. GET으로 "가져오고", POST로 "등록하고" — 이 둘이 프론트엔드 프로토타입에서 가장 자주. 지금은 GET·POST만 알아도 충분.
목업 데이터와 구조가 같으면 화면은 진짜 API에서 온 건지 가짜인지 구분하지 못합니다 — 이것이 목업이 작동하는 이유이기도 합니다.

🎯 GraphQL — 원하는 필드만 골라 받기

# GraphQL: "이름하고 전문분야만 줘"
query {
  experts(specialty: "형사") { name specialty }
}
# 응답: 요청한 필드만 정확히
관점RESTGraphQL
학습 난이도낮음(URL·동사면 충분)중간(쿼리 문법)
데이터 효율정해진 덩어리(필요 없는 것도)요청한 필드만 정확히
백엔드 부담단순쿼리 해석·검증 구조 필요
AI 코딩 친화도자료 많고 AI가 익숙느는 중이나 REST만큼은 아님
🧭 첫 프로토타입은 REST가 기본 — 자료 많고 AI가 잘 다루며 목업과 구조 맞추기 쉽다. 서비스가 커져 "데이터 요청이 너무 많다" 느낄 때 GraphQL을 후보에.
REST는 하나의 URL이 정해진 덩어리를 돌려줍니다 — 이름·전문분야만 필요한데 자기소개·연락처·사진까지 오면 불필요한 왕복이 생깁니다. GraphQL은 그걸 줄입니다.

📜 API 형식은 왜 바뀌어 왔나

시기방식 · 특징
1980s RPC다른 컴퓨터의 함수를 원격으로 부름 — 빠르나 커지면 파악 어려움
1990s SOAPXML로 엄격하게 규격화 — 은행·의료·정부에 여전히, 다만 무겁다
2000s RESTURL로 데이터를 가리키고 HTTP 동사로 조작 — 오늘날 사실상 표준
2015 GraphQLMeta가 — 클라이언트가 원하는 필드만 골라받기
📖 JSON이 XML을 이긴 이유 — XML은 <name>김민준</name>처럼 태그로 감싸 문서엔 좋지만 프로그램이 읽기엔 무겁다. JSON("name": "김민준")은 JavaScript 객체 문법과 같아 브라우저가 거의 가공 없이 바로 쓴다 — 가벼움과 단순함이 이겼다.
형식은 바뀌어도 "요청하고 응답하는" 본질은 같습니다. 프론트엔드 개발자가 알아야 할 것은 세부 스펙이 아니라 "내가 무엇을 요청하고 어떤 형태로 받는가"입니다.

🎯 이 덱의 핵심 정리

개념한 문장
홀·주방·창구프론트·백엔드가 API(JSON)로 대화한다
목업 데이터진짜 응답과 같은 구조의 가짜 — 화면은 진짜든 가짜든 똑같이 그린다
교체가 쉬운 구조데이터를 별도 파일로 빼면 import 한 줄만 바꿔(관심사의 분리)
JSON이름표-값 묶음으로 온다는 것만 알아보면 충분
REST 네 동사GET·POST·PUT·DELETE — 지금은 GET·POST만
REST vs GraphQL첫 프로토타입은 REST(자료·AI 친화), 커지면 GraphQL 후보
다음 덱에서 이 셋(프레임워크 선택·PRD·목업)을 쇼핑몰 예시로 한 흐름에 꿰고, 내 서비스 PRD를 과제로 만듭니다.

🎯 이해도 확인 질문

Q1. 목업 데이터가 작동하는 이유는? (화면과 데이터의 관계)
Q2. 목업에서 진짜 API로 교체가 쉬운 구조는 무엇이며 어떤 원칙인가?
Q3. AI에게 목업을 부탁할 때 알려줄 두 가지와, 요령 하나는?
Q4. REST의 네 동사 중 프로토타입에서 가장 자주 쓰는 둘은?
Q5. JSON이 XML을 이긴 이유는?
Q1과 Q2가 이 덱의 핵심입니다.

✅ 정답 & 해설

A1. 화면이 데이터 구조만 알면 데이터가 진짜든 가짜든 똑같이 그려지기 때문. 컴포넌트는 배열 구조만 알 뿐 출처는 신경 안 쓴다.
A2. 데이터를 별도 파일(mockData.js)로 빼두는 것 — import 한 줄만 API 호출로 바꾸면 화면 코드는 그대로. 관심사의 분리.
A3. 어떤 화면인지·무엇을 보여줄지(+"실제 이름 빼고 가상값으로"). 요령 — 극단적 경우(빈 목록·긴 이름)도 섞어 달라고.
A4. GET(가져오기)·POST(등록하기) — 지금은 이 둘만 알아도 충분.
A5. JSON은 JavaScript 객체 문법과 같아 브라우저가 거의 가공 없이 바로 쓴다 — XML의 태그 감싸기보다 가볍고 단순해서.
A2의 "별도 파일로 빼기"가 목업→진짜 교체를 한 줄로 만드는 열쇠입니다.
