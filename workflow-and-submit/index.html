내일 아침의 장면으로 다시 보기

내일 팀원이 "어제 만든 예약 화면에서 오늘 예약만 보여 줘"라고 합니다. 이때 범용 채팅창에 화면 구조·DB 이름·확인 순서를 매번 길게 설명하면, 일은 되더라도 같은 설명을 계속 반복하게 됩니다.

1하네스를 하나 고르고 (내 조건에 맞게)
2MCP나 앱의 CLI로 내 데이터·도구에 잇고 (규칙 파일로 사용법을 알려 주고)
3자주 하는 일을 스킬로 외워 두면 —
범용 AI가 내 서비스를 아는 전용 조수로 바뀝니다
오늘 배운 것은 그 반복을 줄이는 방법입니다. 세 단계가 각각 소단원 ④·②⑥·③에 대응합니다.

❌ 넘길 수 없는 것

결과에 대한 검토와 판단

  • 소단원 ④의 '승인 93%', 소단원 ①의 '작은 단위·명확한 권한·중간 확인'이 모두 이 한 줄로 모입니다
강의 전체를 관통하는 태도입니다. 조수에게 권한을 준다고 책임까지 넘어가지 않습니다.

과제 — 내가 실제로 쓸 스킬 하나, GitHub에

제출은 저장소 링크 하나

⑦ 과제
오늘 배운 개념이 내 것이 되려면 직접 하나 만들어 봐야 합니다.

1. 스킬 후보 고르기 — "또 이걸 설명하고 있네"

"AI한테 또 이걸 설명하고 있네" 싶은 순간이 후보입니다.

  • 코드를 고칠 때마다 우리 팀 린트·컨벤션을 다시 알려 주는 일
  • 작업을 끝내고 항상 돌리는 정리 — 커밋 메시지·변경 요약
  • 회의록·안내문을 우리 팀 양식으로 바꾸는 일
🎯 스킬의 본질 — '매번 반복하던 일'에서 나와야 합니다. 멋있어 보이는 걸 새로 상상해 만들면 쓰지 않게 됩니다
여기서 후보를 못 고르는 학습자에게는 "지난 2주간 AI에게 같은 말을 두 번 이상 한 게 뭐였나"를 물어 보세요.

2. 저장소를 만들고 스킬 쓰기

새 GitHub 저장소를 하나 만듭니다(예: my-skills). 그 안에 스킬 폴더와 SKILL.md를 만듭니다. Claude Code 기준 경로는 .claude/skills/<스킬이름>/SKILL.md이고, 다른 도구는 각 도구의 스킬 위치에 둡니다.

---
name: commit-summary
description: 오늘 작업을 우리 팀 커밋 메시지 양식으로 요약할 때 사용
---

# 커밋 메시지 요약

1. `git diff`로 바뀐 부분을 확인한다.
2. 바뀐 것을 주제별로 묶어 한 줄씩 요약한다.
3. 양식은 `[범위] 한 일 (#이슈)` 로 맞춘다.
  • 파일은 프론트매터(name·description)와 본문으로 씁니다
소단원 ③의 SKILL.md 형식과 같습니다. 본문은 신입에게 설명하듯 단계로 쓰면 됩니다.

3. README로 '왜' 쓰기 · 4. 올리고 링크 제출

3저장소 최상단 README.md에 왜 이 스킬을 만들었는지를 한 장으로. "무슨 불편이 있었고, 스킬이 어떻게 없앴는지"가 한눈에 들어와야 한다
4push하고 저장소 링크를 제출한다
🎁 보너스 — 친구에게 링크를 주고 "이 스킬 써 봐" 했을 때, 따로 설명하지 않아도 돌아가면 성공입니다
  • 이게 소단원 ⑤의 플러그인·팀 공유가 값진 이유와 같은 원리입니다 — 내 머릿속에만 있던 세팅을 남이 쓸 수 있게 만드는 것
README의 '왜'가 평가에서 가장 갈리는 부분입니다. 기능 설명만 있는 README는 남이 쓰지 않습니다.

제출 전 체크

☐ 스킬이 '매번 반복하던 일'에서 나왔는가? (스킬의 본질)
☐ description만 봐도 언제 쓰는지 아는가?
☐ README에 '왜'가 불편에서 해결로 적혀 있는가?
☐ 다른 대화에서 한마디로 발동시켜 보았는가?
💡 두 번째 항목이 실제로 가장 중요합니다 — AI가 description 한 줄로 이 스킬을 꺼낼지 판단하니까요
네 항목 모두 소단원 ③에서 배운 원리(점진 공개·재프롬프트 문제)와 직접 연결됩니다.

루브릭과 제출 방식

📦 제출
평가 기준을 미리 보여 주고 과제를 하게 하면 결과가 훨씬 좋아집니다.

제출 루브릭

학습목표평가기준
스스로 작업을 효율화 할 수 있습니다충분히 유의미한 내용에 대해서 skill 이 만들어졌는가?
실제 사용할 기능을 직접 설계합니다만들어진 skill 이 재사용 될만한 요소인가?
에이전트 skill 에 대해서 이해합니다만들어진 skill 이 실제로 동작하는가?
🎯 세 기준이 곧 유의미함 · 재사용성 · 실제 동작입니다 — 앞의 '제출 전 체크' 네 항목이 그대로 대응합니다
세 번째(실제 동작)를 확인하려면 반드시 다른 대화에서 한 번 발동시켜 봐야 합니다.

제출 방식 — 한 가지만, 수정 불가

📁 파일 업로드

ZIP · PDF · 이미지만 첨부 가능 (최대 5MB)

🔗 URL 업로드

저장소 링크 하나 — 이 과제는 이쪽이 자연스럽습니다

!파일 또는 URL 중 한 가지 방식으로만 업로드 가능
!제출 후 수정은 불가 — 링크가 열리는지, 저장소가 public인지 미리 확인
제출 후 수정 불가이므로, 링크를 다른 브라우저(로그아웃 상태)에서 한 번 열어 보게 하세요. private 저장소를 제출하는 실수가 가장 흔합니다.

오늘의 회고 세 질문

1MCP를 'USB-C'에 빗댄다면, 내 서비스에서 가장 먼저 꽂고 싶은 것은?
2내가 매번 반복해서 설명하던 일(= 스킬 후보)은 무엇인가?
3새 AI 도구가 쏟아질 때, 나를 덜 휩쓸리게 해 줄 기준 하나는?
✍️ 세 질문 모두 '외웠는가'가 아니라 '내 상황으로 옮길 수 있는가'를 묻습니다
3번의 좋은 답은 "에이전트 = 모델 + 하네스로 분류해 보기" 또는 "내 조건(터미널/편집기·비용·확장·맡길까 지켜볼까)으로 고르기"입니다.

핵심 정리 — 여섯 줄

오늘 배운 것한 문장 정리내가 할 수 있는 행동
에이전트의 구조에이전트 = 모델(지능) + 하네스(껍데기)입니다도구를 볼 때 '하네스'를 봅니다
MCPAI를 내 데이터·도구에 꽂는 'USB-C' 표준입니다연결하고 싶은 데이터를 하나 고릅니다
스킬반복 작업을 외워 두는 재사용 설명서입니다매번 반복하던 지시를 스킬 후보로 적습니다
규칙 파일프로젝트 상시 안내문(AGENTS.md·CLAUDE.md)입니다반복 설명을 파일에 한 번 적어 둡니다
CLI로 잇기앱 명령을 규칙 파일로 알려 두면 AI가 직접 실행합니다자주 쓰는 조회를 명령 하나로 만듭니다
도구 선택종류는 많고 빠르게 바뀌니 '내 조건'으로 고릅니다개념을 잡고, 유행에 덜 휩쓸립니다
세 번째 열이 중요합니다. '안다'가 아니라 '한다'로 끝나야 강의가 남습니다.

❓ 마지막 확인

Q1. 범용 AI를 '내 전용 조수'로 바꾸는 세 단계는?
A1. ① 하네스를 내 조건에 맞게 고르고 ② MCP나 앱의 CLI로 내 데이터에 잇고(규칙 파일로 사용법을 알려 주고) ③ 자주 하는 일을 스킬로 외워 둔다.
Q2. 좋은 스킬 후보를 찾는 신호는?
A2. "AI한테 또 이걸 설명하고 있네" 싶은 순간. 새로 상상해 만든 스킬은 쓰지 않게 된다.
Q3. 제출에서 가장 흔한 실수는?
A3. 저장소가 private이라 링크가 안 열리는 것. 제출 후 수정이 불가하므로 로그아웃 상태에서 미리 열어 본다.
Q3은 매 기수 반복되는 실수라 반드시 짚어 주세요.
