눈금을 성기게 만드는 일

양자화(quantization)의 정체

개념
이름은 거창하지만 하는 일은 단순합니다. 반올림입니다.

📏 양자화 = 가장 가까운 눈금으로 반올림

연속적인 실수값을, 미리 정해 둔 몇 개의 눈금 중 가장 가까운 곳으로 반올림해서 저장하는 것.

16비트 자 (FP16)

눈금 65,536개 — 아주 촘촘한 자
값 하나 = 2바이트

4비트 자

눈금 16개뿐 — 성긴 자
값 하나 = 0.5바이트

저장 공간은 2바이트 → 0.5바이트, 정확히 4분의 1. 대신 눈금 사이로 오차가 생깁니다.
자의 눈금이 성길수록 표현은 거칠어지지만 자리는 덜 차지합니다. 이 맞바꿈이 양자화의 본질입니다.

🔍 같은 값을 서로 다른 자로 재면

방식눈금0.0731을 저장하면크기
FP1665,536개0.0731 그대로2바이트
4비트16개가장 가까운 눈금 → 0.0745로 반올림0.5바이트
값 하나당 오차 ≤ 눈금 간격의 절반 · 파일은 4분의 1로
⚠️ 직관적으로는 위험해 보입니다 — 70억 개 전부에 오차를 심는 셈이니까요. 그런데 실제로는 잘 버팁니다. 왜?
0.0731이 16개 눈금 중 하나(0.0745)로 끌려가고, 그 차이가 오차입니다. 다음 장에서 왜 이 오차를 견디는지 봅니다.

🛡️ 왜 깎아도 잘 버틸까 — 이유 둘

①
오차 상쇄
신경망 출력은 수많은 곱셈·덧셈의 합 → 개별 오차가 서로 상쇄되는 경향
②
softmax
점수를 확률(합=1)로 바꿈 → 절대값이 아니라 누가 더 큰가가 좌우
🎯
그래서
점수가 소수점에서 조금 흔들려도 1등 토큰은 좀처럼 안 바뀐다
🔑 모델이 마지막에 하는 일은 "다음 토큰 순위 매기기"입니다. 순위만 유지되면 약간의 오차는 결과를 바꾸지 않습니다.
softmax는 후보 토큰마다 매긴 점수를 전부 더하면 1이 되는 확률로 바꿔 줍니다. 절대값이 아니라 상대 순위가 중요하다는 점이 핵심입니다.
2

모든 층을 똑같이 깎지 않는다

두 가지 영리한 장치 → Q4_K_M

K-quant · 자리별 차등
단순 반올림에서 한 걸음 더. 어디를 얼마나 깎을지 영리하게 고릅니다.

🧩 장치 ① — 블록마다 자기만의 자 (K-quant)

  • 70억 개 전체에 하나의 자를 대지 않습니다
  • 가중치를 256개짜리 슈퍼블록으로 나누고, 다시 32개짜리 블록으로 쪼갬
  • 블록마다 자기만의 스케일 값 → 값 범위가 좁은 블록은 그 안에서 눈금 16개를 촘촘하게 사용
  • 스케일 값들 자체도 다시 양자화해 메타데이터 부담을 축소
🔧 이 방식을 K-quant라 부릅니다. llama.cpp(개인 컴퓨터용 오픈소스 실행 엔진) 커뮤니티가 만들었고, 오늘 보는 파일 이름·표기 대부분이 여기서 나왔습니다.
같은 4비트라도, 블록마다 자를 새로 대면 좁은 범위에서는 훨씬 정밀해집니다. '적응형 자'라고 생각하면 됩니다.

🎚️ 장치 ② — 깎아도 덜 아픈 곳을 골라 깎기

트랜스포머 블록의 두 부분

어텐션 — 토큰들이 서로를 참고
피드포워드(FFN) — 토큰마다 따로 부풀렸다 줄임
파라미터의 2/3~3/4가 FFN

거칠게 깎으면 손해 큰 자리

① 어텐션의 Value 행렬
② FFN의 아래쪽 사영 행렬
이 두 곳은 전체 레이어 절반에 한해 6비트

나머지 어텐션 행렬·FFN 위쪽 행렬은 그대로 4비트. 깎아도 덜 아픈 곳을 골라 깎으니 용량은 크게 줄고 품질은 덜 상합니다.
피드포워드 = 토큰끼리 정보를 주고받지 않고 각자 앞으로만 통과한다는 뜻. 이 중 '다시 원래 크기로 줄이는' 아래쪽 사영과 어텐션의 Value가 민감합니다.

🏷️ 그래서 Q4_K_M은 이렇게 읽힙니다

Q4기본 4비트
KK-quant 방식
M = medium두 자리 6비트
섞여 있으므로 실효 비트 = 정수가 아니라 파라미터당 약 4.8비트

📁 GGUF 형식

가중치·메타데이터·토크나이저 어휘·텐서 데이터를 파일 하나에 전부 담은 포맷. 곁다리 파일 없이 로드, 메모리 매핑을 염두에 둔 정렬로 로딩도 빠름.

이제 허깅페이스에서 ...Q4_K_M.gguf로 끝나는 파일 이름을 전부 읽을 수 있습니다. 😎
M은 medium. S(small)·L(large)도 있고, 어느 자리를 얼마나 올리느냐의 강도 차이입니다.

내 기계에 들어갈지 계산하는 법

가중치는 시작일 뿐, 세 번째 항이 함정

메모리 계산 · KV cache
여기서 처음 로컬 모델을 돌리는 사람들이 가장 자주 넘어집니다. 이유는 세 번째 항입니다.

🧮 손으로 계산하는 메모리 공식

필요 메모리 ≈ 파라미터 수(B) × 0.5GB
+ KV cache + 런타임 오버헤드(약 0.75GB)

8B

4GB + 오버헤드
≈ 5GB (실측 4.57)

30B

≈ 15GB

70B

≈ 35~40GB

⚠️ 여기까지만 보면 8GB 카드에 8B 모델이 여유로워 보입니다. 바로 이 지점에서 초심자가 넘어집니다 — 세 번째 항(KV cache)이 남아 있으니까요.
4비트는 파라미터당 0.5바이트. 그래서 파라미터 수(B) × 0.5GB가 가중치 몫입니다. 문제는 그다음입니다.

🧾 속도를 위해 저장한 것이 청구서로

  • 모델은 한 토큰씩 생성 — 매번 앞 토큰 전부를 다시 훑으면 절망적으로 느려짐
  • 그래서 이미 계산한 Key·Value 두 벌을 저장해 재사용 → 이것이 KV cache (속도는 순이득)
  • 청구서: 저장 = 메모리 사용, 그 양은 컨텍스트 길이에 정비례
KV cache = 2 × 레이어 수 × KV 헤드 수 × 헤드 차원 × 토큰 수 × 자료형 바이트
(맨 앞 2 = Key와 Value 두 벌)
컨텍스트KV cache가중치 4.6GB와 합치면
4K0.52 GB약 5.1 GB
32K4.19 GB약 8.8 GB
128K16.78 GB약 21.4 GB
8B급 GQA 모델을 BF16 캐시로 돌릴 때의 실제 값입니다. 컨텍스트가 길어질수록 캐시가 가중치를 압도합니다.

🪤 오해 하나와 구조 함정 하나

❓ 흔한 오해

위 표는 컨텍스트를 가득 채웠을 때의 상한. "창을 크게 열어두기만 하면 그만큼 문다"는 뜻이 아님 (뒤에서 실측)

🕳️ 구조 함정 (GQA vs MHA)

GQA: 질문 머리는 여럿, K·V는 그룹으로 공유 → 캐시 작음
MHA(구형): 머리마다 K·V 따로 → 같은 7B라도 캐시 4배, 128K에서 64GB

🔑 가중치 파일 크기만 보고 계산하면 반드시 틀립니다. 긴 문서를 통째로 붙여 넣는 습관이 곧 청구서(→ OOM, 메모리 부족 종료). 모델 카드에서 KV 헤드 수 확인이 여기서 값어치를 합니다.
OOM = Out Of Memory. 자리가 모자라면 일부가 CPU 메모리로 밀려나거나 아예 종료됩니다.

🧯 캐시 부담 완화 수단

  • 가중치를 양자화했듯 캐시도 양자화할 수 있음
  • llama.cpp에서 --cache-type-k q8_0 --cache-type-v q8_0 → 캐시 절반
  • 4비트로 내리면 4분의 1 — 검색·요약처럼 긴 문맥 훑는 작업은 품질 저하 거의 없음
💡 가장 확실한 방법은 필요 없는 컨텍스트를 애초에 열지 않는 것.
긴 컨텍스트가 꼭 필요한 게 아니라면, 캐시 양자화와 짧은 컨텍스트 유지가 8GB 카드를 살립니다.

내 하드웨어는 어느 칸에 있나

4비트 양자화 기준 메모리 사다리

VRAM 티어
VRAM = 그래픽카드가 자기 안에 따로 단 전용 메모리. 본체 RAM과는 다른 물건이고, 가중치는 원칙적으로 여기에 다 들어가야 제 속도가 납니다.

🪜 VRAM 사다리 (4비트 기준)

메모리실행 가능한 범위
8 GB8B급 Q4_K_M을 짧은 컨텍스트로 겨우. 늘릴 여유 없음
12 GB14B급까지, 컨텍스트도 넉넉하게
16 GB20B급, 또는 8B를 긴 컨텍스트로
24 GB30~35B급(약 21.7GB) — 소비자용 하드웨어의 단맛 구간
32 GB35B를 250K 컨텍스트로, 또는 70B 진입
48 GB+70B급을 무거운 컨텍스트와 함께 편안하게
🔑 이 칸은 가중치만 들어가는 자리가 아니라 가중치 + 캐시가 함께 들어가야 하는 자리입니다. (8GB: 가중치 4.6 + 32K 캐시 4.2 = 8.8GB → 이미 초과)
8GB에서 8B를 쓰려면 컨텍스트를 4~8K로 유지하거나 캐시 양자화로 그 4.2GB를 절반으로 눌러야 합니다.

🍎 애플 실리콘 & 칸을 넘치면

Apple Silicon 맥

CPU·GPU가 통합 메모리 공유 → 장착 RAM 자체가 예산. Metal 권장은 대략 2/3~3/4. 64GB면 40GB대 중반이 현실적 상한

CPU 오프로딩

칸을 넘친 층은 CPU·시스템 RAM으로. 속도는 대역폭·PCIe에 묶임 → 수십~100 토큰/s가 한 자릿수로 추락

⚠️ 대화는 가능해도, 에이전트가 도구를 여러 번 호출하며 도는 상황에서는 치명적입니다. 대역폭 = 초당 읽어올 수 있는 데이터 양, 토큰마다 가중치를 전부 읽으니 이 값이 사실상 속도를 정합니다.
맥은 sudo sysctl iogpu.wired_limit_mb=값 으로 조정 가능하되 macOS 몫으로 8GB 이상은 남겨두는 게 안전합니다.

예: OpenAI gpt-oss-20b

총 21B인데 토큰당 활성 3.6B · 층마다 전문가 32개 중 상위 4개 · MXFP4(4.25비트) 배포 · OpenAI가 "16GB 안에서 돌아간다"고 명시

🔑 메모리 요구는 21B, 생성 속도는 3.6B — 이 비대칭이 매력. 통합 메모리 큰 맥이 로컬 LLM에 강한 이유도 같음(용량은 넉넉, 계산은 적게).
단, KV cache는 MoE라고 깎아주지 않습니다 — 어텐션 구조는 그대로라 컨텍스트 계산은 동일 (8K 0.4GB / 32K 1.6GB / 128K 6.4GB, 단 절반이 슬라이딩 윈도라 실제로는 덜 씀).
MoE는 '다 올려야 하지만 다 계산하지는 않는' 구조입니다. 메모리 예산은 총 파라미터, 속도는 활성 파라미터로 계산하세요.

📌 이것만은 꼭 — 핵심 7문장

1양자화 = 실수값을 성긴 눈금으로 반올림. 4비트면 저장 공간이 1/4
2깎아도 버티는 이유: 오차 상쇄 + softmax는 절대값이 아닌 순위
3K-quant(블록별 자) + 자리별 차등(민감한 곳만 6비트) → Q4_K_M(실효 ~4.8비트)
4Q4_K_M: 파일 1/3, 품질 손실 0.5% 미만 → 사실상 표준. 배포 형식은 GGUF
5메모리 ≈ 파라미터(B)×0.5GB + KV cache + 오버헤드 — 세 번째 항이 함정
6KV cache는 컨텍스트 길이에 비례. GQA는 작고 MHA는 4배. 캐시 양자화로 완화
7MoE: 메모리는 총 파라미터, 속도는 활성 파라미터 — 단 KV cache는 그대로
이 7문장이면 "이 모델이 내 카드에 들어갈까?"에 스스로 답할 수 있습니다.

🎯 이해도 확인 질문

Q1. 양자화란 한 문장으로? 16비트를 4비트로 내리면 저장 공간은 어떻게 되나?
Q2. 70억 개 전부에 오차가 생기는데도 모델이 잘 버티는 이유 2가지는?
Q3. Q4_K_M의 Q4·K·M은 각각 무슨 뜻인가? 실효 비트 수는 대략?
Q4. "가중치 4.6GB니까 8GB 카드면 충분"이라는 계산이 틀리는 이유는?
Q5. 같은 7B인데 GQA와 MHA의 KV cache가 크게 다른 이유는?
Q6. MoE에서 메모리 요구량과 생성 속도는 각각 무엇으로 정해지나?
Q4·Q5가 실전에서 가장 자주 넘어지는 지점입니다.

✅ 정답 & 해설

A1. 연속 실수를 미리 정한 몇 개 눈금 중 가장 가까운 곳으로 반올림해 저장하는 것. 2바이트 → 0.5바이트, 정확히 1/4.
A2. ① 출력이 수많은 곱셈·덧셈의 합이라 개별 오차가 상쇄 ② softmax는 절대값이 아니라 순위로 결정 → 1등이 잘 안 바뀜.
A3. Q4 = 기본 4비트, K = K-quant 방식, M = medium(민감한 두 자리를 6비트로). 실효 ≈ 4.8비트.
A4. KV cache를 빼먹었기 때문. 컨텍스트에 비례해 늘어(32K면 +4.2GB) 8.8GB로 8GB를 넘겨 OOM.
A5. MHA는 머리마다 K·V를 따로 들지만, GQA는 그룹으로 공유. 그래서 MHA 캐시가 약 4배.
A6. 메모리 = 총 파라미터(21B), 속도 = 토큰당 활성 파라미터(3.6B). 단 KV cache는 어텐션 구조 그대로라 안 줄어듦.
A4는 "가중치 + 캐시가 함께 들어가야 한다"가 핵심입니다.
