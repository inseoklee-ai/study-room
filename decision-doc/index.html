1

오늘의 산출물

챗봇이 아니라 결정문 한 장

하이브리드도 정답
거대한 모델을 노트북에 밀어 넣어봤고, 어떤 조건에서 쓸 만한지 겪었습니다. 이제 그 경험을 문장으로 굳힙니다.

📝 산출물은 "이건 여기서 돌린다"

챗봇을 완성하는 게 아니라
도메인 업무 하나에 대해
실행 위치 + 그 이유를 댈 수 있는 결정문
  • 이후 모델 선택·라우팅, AI 위험 점검, 도메인 에이전트 설계 때 계속 다시 꺼내 씀
  • 오늘의 Learning by Doing = 설치 명령을 많이 친 게 아니라, 직접 돌려본 경험 위에 판단문을 세우고 동료 검토로 흔들어 본 것
이 문서는 한 번 쓰고 버리는 게 아니라 이후 여러 단계에서 재사용되는 기준 문서입니다.

🤝 하이브리드도 정당한 답 (오히려 가장 흔함)

  • 식별자 제거 전처리는 내부에서, 익명화된 텍스트 요약은 API로
  • 민감한 문서군만 로컬 모델, 나머지는 API로 라우팅
  • 업무를 단계로 쪼개면 단계마다 답이 다를 수 있고, 그 편이 대개 더 정확
🔑 "전부 로컬" 또는 "전부 API"로 좁히지 마세요. 관리형 프라이빗 배포도 이 칸에 들어갑니다 — 로컬은 품질이 모자라고 공개 API는 데이터가 걸리는 업무(민감도 워크북에서 3열·4열이 동시에 채워졌던 그 행)가 대개 여기로 갑니다.
가장 흥미로운 행(조건부로 밖에 보낼 수도, 안에서 처리할 수도 있는 데이터)이 하이브리드·관리형으로 가는 경우가 많습니다.

결정문 템플릿

자기 노트에 옮겨 채우세요

세 근거 + 재검토 조건
마지막 다섯 줄(재검토)이 이 문서를 살아 있게 만듭니다.

🧾 템플릿 (1) 본문

입력 데이터와 출처____

비용 근거월 요청 수 __, API 월비용 __, 로컬 월비용 __, 가장 큰 항목 __
주권 근거버전 고정 필요? __, 멈췄을 때 대체 경로 __, 감사 때 낼 자료 __
결정공개 API / 관리형 프라이빗 / 로컬 / 하이브리드(단계별 __)
감수하는 것____
보완책식별자 제거 / 사람 검토 / 로그 제한 / 회귀 테스트 / 비용 알림 / 기타
세 근거(데이터·비용·주권)를 각각 채운 뒤 '결정'을 적습니다. 근거 없이 결정부터 적으면 안 됩니다.

🔁 템플릿 (2) 재검토 조건

아래 중 하나라도 발생하면 이 결정문을 다시 씁니다
트리거 1월 사용량이 ____를 넘을 때
트리거 2다루는 데이터의 민감도 등급이 바뀔 때
트리거 3쓰는 모델의 종료 예고가 뜨거나 가격이 __% 이상 바뀔 때
트리거 4규정·사내 정책이 바뀔 때
다음 재검토 예정일____
🔑 재검토 조건이 없는 결정문은 반년 뒤 아무도 믿지 않는 문서가 됩니다. 조건이 적혀 있으면, 그 조건이 걸렸을 때 누구든 이 문서를 다시 열게 됩니다.
재검토 조건은 '감지 가능한' 형태여야 합니다. 숫자와 사건으로 적어야 누군가 알아챌 수 있습니다.
3

페어 검토

혼자 읽으면 빈틈이 보이지 않는다

다른 도메인 동료와 7분씩
자기가 쓴 근거는 자기 머릿속에서 항상 말이 됩니다. 그래서 남의 눈이 필요합니다.

🤝 상대가 내 분야를 모를수록 좋다

모르는 사람에게 설명이 통하면 근거가 정리된 것, 설명하다 막히면 거기가 아직 판단이 아니라 느낌으로 남은 자리입니다. 페어는 세 줄만 남깁니다(칭찬은 필요 없음).

페어에게 받을 질문본다
데이터 근거에 확인 날짜와 출처가 적혀 있는가__
비용 가정 중 빠진 항목이 보이는가__
재검토 조건이 실제로 감지 가능한 조건인가__
🔑 세 번째가 특히 중요합니다. "상황이 크게 바뀌면"처럼 적으면 아무도 감지 못 함. "월 요청이 5만 건을 넘으면"처럼 적어야 누군가 대시보드를 보다 알아챕니다.
감지 가능한 조건 = 숫자 + 관측 지점. 이게 있어야 결정문이 실제로 작동합니다.

단원 종합 — 가져갈 판단

🎯 핵심 정리 (1/2)

오늘의 질문가져갈 판단
데이터를 밖으로 보내도 되나"학습 안 씀"과 "안 남음"은 다른 통제 장치 — 학습·로그·리전·하위처리자·계약·삭제를 따로 확인
ZDR을 켜면 끝인가승인 필요한 계약, 적용 안 되는 기능·모델 존재, 법·안전은 여전히 예외
로컬이면 안전한가통제 지점이 안으로 옴 — 분실·내부 노출·백업·프롬프트 기록이 새 관리 대상
로컬이 더 싼가사용량·모델 급·가동률·운영 인력에 따라 뒤집힘 — 자기 숫자를 넣어야
비용은 무엇부터 줄이나병목을 먼저 — 캐싱·배치·소형 모델 라우팅으로 인프라 없이 줄기도
앞 강의들의 핵심을 한 줄씩 압축했습니다. 각 판단의 근거는 해당 강의에서 확인하세요.

🎯 핵심 정리 (2/2)

오늘의 질문가져갈 판단
통제권은 어떻게 확인하나누가 바꾸고·멈추고·설명하는지 각각 답 — 회귀 테스트는 어느 쪽이든 필요
로컬의 주권은 공짜인가보안 패치·모델 업데이트·성능 튜닝·접근 권한 관리가 함께 넘어옴
반드시 한쪽을 골라야 하나아니오 — 단계로 쪼개면 답이 다를 수 있고 하이브리드가 가장 흔한 실무 답
오늘의 산출물은재검토 조건이 붙은 실행 위치 결정문 한 장
🔑 도메인이 결론을 정하지 않습니다. 그 업무가 다루는 데이터·비용·통제 요구가 정합니다.
이 표 전체가 단원 3의 요약본입니다. 결정문을 쓸 때 옆에 두세요.

🎯 이해도 확인 질문

Q1. 오늘의 산출물은 무엇인가? (챗봇이 아니라면?)
Q2. "전부 로컬/전부 API"로 좁히면 안 되는 이유는? 하이브리드는 왜 흔한가?
Q3. 결정문의 마지막 다섯 줄(재검토 조건)이 왜 중요한가?
Q4. 페어 검토의 세 질문 중 "감지 가능한 조건"이 왜 특히 중요한가? 좋은 예/나쁜 예는?
Q5. "모델을 고르는 일"과 "실행 위치를 정하는 일"은 어떻게 다른 문제인가?
Q3와 Q4가 이 강의에서 가장 실무적인 지점입니다.

✅ 정답 & 해설

A1. 도메인 업무 하나에 대해 "이건 여기서 돌린다" + 이유(데이터·비용·주권)를 댈 수 있는, 재검토 조건이 붙은 결정문 한 장.
A2. 업무를 단계로 쪼개면 단계마다 답이 다를 수 있어서. 전처리는 로컬·요약은 API처럼 나누는 게 더 정확 → 하이브리드(+관리형)가 가장 흔한 실무 답.
A3. 재검토 조건이 없으면 반년 뒤 아무도 안 믿는 문서가 됨. 조건이 있으면 그게 걸렸을 때 누구든 다시 열게 됨.
A4. 감지 못 하는 조건은 없는 것과 같음. 나쁜 예 "상황이 크게 바뀌면", 좋은 예 "월 요청 5만 건을 넘으면"(숫자+관측 지점).
A5. 모델 선택 = "어떤 모델이 잘하나". 실행 위치 = "그 일을 어디서 돌릴까"(데이터·비용·주권). 좋은 모델이라도 실행 위치가 안 맞으면 못 씀.
A5가 단원 3 전체의 출발 질문이자 도착 질문입니다.
