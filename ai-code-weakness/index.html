화면은 금방 사는데, 왜 거기서 막힐까

바이브 코딩으로 화면은 하루 만에 만들어지지만, 그다음 벽에 부딪힙니다. AI는 '돌아가는 코드'는 잘 만들어도 '안전하고 튼튼한 코드'는 명시적으로 요구하지 않으면 챙기지 않기 때문입니다. 이 소단원은 비전공자가 반드시 챙겨야 할 세 약점을 다룹니다.

😵 화면은 금방 사는데 — 그다음 벽

첫날 🎉

"우와, 하루 만에 화면이 다 만들어졌어!"

다음 주 😰

"로그인이 자꾸 풀려… 저장한 게 사라져… 클라우드 요금이 왜 이렇게?"

AI는 "돌아가는 코드"는 잘 만들지만 "안전하고 튼튼한 코드"는 놓친다. 문법은 좋아졌지만 안전은 그대로다.
이것이 프로토타입과 프로덕트 사이의 간극입니다. AI는 아주 빠른 신입 개발자와 같아서, 속도는 놀랍지만 보안·비밀 관리·권한 확인에는 감독이 필요합니다.
1

보안 — AI 코드의 최대 약점

가장 흔한 구멍은 "입력을 그대로 믿는" 실수

Veracode 45% · 입력 검증 · 유출 사고의 역사
보안은 AI 생성 코드에서 가장 두드러지는 약점입니다. 규칙 하나만 기억하면 됩니다 — 사용자가 보낸 값은 일단 의심하고 검사한다.

📊 AI 코드의 약 45%에 보안 결함

Veracode가 100개 넘는 AI 모델로 실험
AI 생성 코드의 약 45%에 보안 결함모델이 더 똑똑해져도 이 비율은 거의 줄지 않았다
문법은 좋아졌지만 안전은 그대로. 더 똑똑한 모델을 기다린다고 저절로 해결되지 않는다.
Veracode는 100개가 넘는 AI 모델을 대상으로 실험했고, 생성된 코드의 약 45퍼센트에서 보안 결함을 발견했습니다. 모델 성능이 올라가도 이 비율은 거의 개선되지 않았다는 점이 핵심입니다.

🚪 가장 흔한 구멍 — 입력을 그대로 믿기

보통 사용자검색창에
"김민준"을 친다
vs
나쁜 사람명령어처럼 생긴
문자열을 넣는다

서버가 그걸 그대로 믿고 실행하면 데이터베이스가 통째로 털리거나 지워질 수 있다.

🔑 규칙 하나 — "사용자가 보낸 값은 일단 의심하고 검사한다."
입력값 주입(인젝션) 공격의 원리입니다. 검색창이나 입력칸은 데이터를 받는 곳인데, 공격자는 여기에 명령어를 심습니다. 서버가 데이터와 명령을 구분하지 못하고 실행하면 사고가 납니다.

🗣️ 프롬프트로 요구하면 된다

"사용자 입력을 검증하고, 비밀번호는 해시로 저장하고, 모든 통신은 HTTPS로 해줘. 흔한 보안 취약점(입력값 주입, XSS)을 막아줘."

문법을 외울 필요 없다 — AI에게 무엇을 요구할지만 알면 된다.
비전공자가 할 수 있는 가장 강력한 품질 관리는, 이렇게 보안 요구사항을 명시적으로 프롬프트에 넣고 결과를 한 번 더 되묻는 것입니다. XSS는 다른 사용자의 화면에 악성 스크립트를 심는 공격입니다.

💥 역사에 남은 데이터 유출 사고

사고규모교훈
에퀴팩스 (2017)약 1억 4,300만 명 주민번호·생일·주소알려진 취약점을 방치하지 말 것
소니 PSN (2011)약 7,700만 명, 서비스 장기 중단기본 보안의 중요성
야후 보이스 (2012)비밀번호를 평문으로 저장했다 유출비밀번호는 반드시 해시로
마이스페이스 (2008)약 3억 6천만 계정사이트마다 다른 비밀번호
MOVEit (2023)2,700개 이상 기관, 9천만 명 이상파일 전송 허점도 방치 금물
공통점 — 입력을 함부로 믿지 않기 · 비밀번호는 해시로 · 알려진 취약점 방치 금지. 큰 회사도 기본을 놓쳐 뚫린다.
대부분 막을 수 있었던 사고들입니다. 화려한 신기술이 아니라 기본기를 놓쳐서 뚫렸다는 점이 공통점입니다. 야후 사례는 '비밀번호는 해시로'라는 원칙의 산 증거입니다.
2

환경변수 — 비밀은 코드에 안 적는다

코드에 적은 비밀키는 몇 분 만에 봇이 훔쳐 간다

GitGuardian · .env · .gitignore
비밀값을 코드에 그대로 적는 것은 가장 흔하고 값비싼 실수입니다. 공개 저장소에 올라간 키는 사람이 아니라 자동 봇이 순식간에 발견합니다.

🤖 몇 분 만에 봇이 훔쳐 간다

한 개발자가 API 키를 코드에 그대로 적어 GitHub에 올렸다. 몇 분 만에 봇이 발견해 훔쳐 가, 클라우드에서 비싼 작업을 잔뜩 돌려 수백만 원 요금이 청구됐다.

2025년 유출약 2,865만 개비밀키·비밀번호 (역대 최대)
전년 대비+34%
AI 서비스 키+81%1년 새 급증
GitGuardian 집계 — 과거 유출된 키의 상당수가 아직 살아 있어 지금도 악용된다.
과장이 아닙니다. 2025년 공개 GitHub에 유출된 비밀키·비밀번호가 약 2,865만 개로 역대 최대였고, 전년 대비 34퍼센트 늘었습니다. 특히 AI 서비스 키 유출이 1년 새 81퍼센트 급증했습니다.

🔐 해결책 — 환경변수

비밀값을 코드 바깥에 따로 두고, 실행할 때만 꺼내 쓴다.

나쁜 예: apiKey = "sk-a1b2c3d4e5f6..."   ← 이대로 올라가면 순식간에 유출
좋은 예: apiKey = 환경변수에서 불러오기    ← 실제 값은 코드 밖 .env 파일에
        (.env는 .gitignore로 깃에 안 올라가게)
한 줄 정리 — 코드 = 공개해도 되는 것 / 환경변수 = 절대 공개하면 안 되는 것.
AI에게 이렇게 요구하세요 — "API 키·DB 접속 정보는 코드에 넣지 말고 환경변수로 빼줘. .env는 깃에 안 올라가게." .gitignore는 특정 파일을 깃 추적에서 제외하는 설정 파일입니다.
3

인증 vs 인가

표 검사원과 VIP 바운서 — 로그인엔 두 단계가 숨어 있다

401 · 403 · 토큰 · 해시 · 세션
로그인은 하나의 동작처럼 보이지만 사실 두 단계입니다. '누구세요?'를 확인하는 인증과, '들어갈 권한이 있나요?'를 확인하는 인가입니다. 콘서트장 비유로 풀어 봅니다.

🎫 두 단계 — 인증과 인가

구분비유 (콘서트장)확인하는 것실패 코드
인증
Authentication		입구의 표 검사원"표 주인 맞아요?" (로그인 확인)401 "누구세요?"
인가
Authorization		VIP 구역의 바운서"이 방에 들어갈 권한 있어요?"403 "안 돼요"
🖐 로그인 성공 시 서버가 토큰을 준다 = 클럽 입구의 손목 밴드. 브라우저는 요청마다 이 밴드를 함께 보낸다.
한 번 확인받고 손목 밴드를 차면 이후엔 밴드만 보이면 통과합니다. 토큰이 바로 이 손목 밴드입니다. AI가 만든 코드라도 '권한 확인(인가)이 되어 있나?'는 꼭 되물어야 합니다.

🍳 비밀번호는 해시로 — 되돌릴 수 없는 지문

해해시 — 비밀번호를 '되돌릴 수 없는 지문'으로. 달걀→프라이는 되지만 프라이→달걀은 안 되듯, 원문으로 되돌릴 수 없다
솔솔트(salt) — 흔한 123456은 지문도 뻔하니, 사람마다 다른 무작위 값을 섞는다. 같은 비번이라도 지문이 달라진다
느bcrypt — 일부러 느리게 계산되는 방식. 느린 게 장점 — 도둑이 수억 개를 대입해 보기 어려워진다
서버는 원문 대신 지문만 저장하고 로그인 때 지문끼리 비교 → 데이터가 새어도 원문은 안전.
외울 것은 없습니다. AI에게 "비밀번호는 솔트를 섞어 bcrypt로 해시해서 저장해줘"라고 요구할 줄만 알면 됩니다. 같은 비밀번호는 같은 지문이 나오기 때문에 로그인 때 지문끼리 비교할 수 있습니다.

🍪 쿠키와 세션 — 웹은 건망증이 심하다

초창기 HTTP는 요청 하나하나를 매번 처음 보는 손님처럼 대했다(무상태). 이 건망증을 고치려고 나온 것이 쿠키와 세션.

🪪 쿠키

내 지갑 속 작은 카드. 사이트가 번호를 적어 주면 브라우저가 보관했다 방문 때마다 보여준다.

🗄️ 세션

사이트 금고 속 내 서류철. 카드 번호를 보고 "아, 이 사람!" 하며 정보를 꺼낸다.

⚠️ 진짜 정보는 브라우저(쿠키)에 두면 안 된다 — 사용자가 이름=관리자로 조작 가능. 브라우저엔 의미 없는 번호만, 진짜 정보는 서버 금고에.
손목 밴드와 같은 원리입니다. 세션 ID라는 의미 없는 번호만 브라우저에 두고, 진짜 정보는 서버 금고에 둡니다. 쿠키에 이름=일반사용자 같은 걸 그대로 두면 관리자로 바꿔치기 당할 수 있습니다.

🧐 이 습관, 안전할까?

XAPI 키를 코드에 적어 GitHub에 올린다 — 유출! 환경변수로
X사용자 입력을 그대로 믿고 처리 — 주입 공격의 문
O비밀번호를 솔트 섞어 해시로 저장 — 안전
X모든 사이트에 같은 비밀번호 — 한 곳 털리면 다 위험
O로그인 뒤 권한(인가)까지 확인 — 인증 + 인가
다섯 습관을 스스로 O/X로 판단해 보세요. 세 개의 X는 각각 환경변수·입력 검증·비밀번호 관리로 연결됩니다. 로그인 확인만으로는 부족하고 인가까지 확인해야 합니다.

📌 이것만은 꼭 — 핵심 3문장

1입력 검증 — 사용자가 보낸 값은 일단 의심하고 검사한다(AI 코드 약 45%에 보안 결함).
2비밀은 환경변수 — API 키는 코드 밖 .env에. 코드=공개 OK / 환경변수=공개 절대 금지.
3권한 확인 + 해시 — 인가(403)까지 확인하고, 비밀번호는 솔트+bcrypt로 해시해 저장한다.
AI는 아주 빠른 신입 개발자
속도는 놀랍지만 보안·비밀·권한은 감독이 필요세 가지를 프롬프트로 요구하고 결과를 한 번 더 되묻기 — 비전공자의 가장 강력한 품질 관리
문법 암기가 아니라, 무엇을 요구하고 무엇을 되물을지가 핵심입니다. 세 가지를 프롬프트로 요구하고 결과를 한 번 더 확인하는 습관이 프로토타입을 프로덕트로 만듭니다.

✅ 정답 & 해설

A1. 보안(특히 입력을 그대로 믿는 실수). AI 생성 코드의 약 45%에 보안 결함, 모델이 똑똑해져도 거의 안 줄었다.
A2. 공개 저장소에 올리면 봇이 몇 분 만에 훔쳐 간다. 대신 환경변수로 코드 밖 .env에 두고 .gitignore로 제외한다.
A3. 인증=본인 맞는지(로그인 확인, 실패 401) · 인가=권한 있는지(실패 403).
A4. 솔트 + bcrypt + 해시 — 되돌릴 수 없는 지문으로 저장하면 데이터가 새어도 원문은 안전.
A5. 사용자가 조작할 수 있기 때문(이름=일반사용자 → 관리자). 브라우저엔 의미 없는 번호만, 진짜 정보는 서버 금고에.
A3과 A4를 자기 말로 설명할 수 있으면 오늘 목표는 달성입니다. 더 읽기 출처는 Veracode, GitGuardian의 유출 통계 보고서입니다.
