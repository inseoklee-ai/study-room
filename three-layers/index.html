이름과 생김새 · 겹별 검토 질문

① 개념
문법을 외울 필요는 없습니다. "아, 이렇게 생겼구나" 정도만 보고 넘어갑니다.

🧱 세 겹의 생김새

🟢 HTML — 무엇이 담기나 (태그로 의미를 붙임: h1=제목, button=버튼)
<h1>내 첫 웹페이지</h1>
<button>시작하기</button>
🔵 CSS — 어떻게 보일지 (색·간격·크기·배치)
h1 { color: blue; text-align: center; }
🟣 JS — 무엇이 바뀔지 (누르면 화면이 달라지는 반응)
button.addEventListener('click', () => {
  alert('안녕하세요!');
});
지금은 "세 겹은 각자 맡은 일이 다르다"는 감각만 챙기면 충분. 내력은 다음 파트에서.
HTML은 제목·문단·버튼 같은 정보에 의미를 붙이고, CSS는 그것이 어떻게 보일지, JavaScript는 사용자가 무언가 했을 때 무엇이 바뀔지를 정합니다.

🔧 겹을 지정해 지시하고 판단한다

겹AI에게 시킬 때결과 판단 질문
HTML"제목·안내 카드·버튼을 의미에 맞게 배치해줘"필요한 정보·업무 용어가 빠지지 않았나
CSS"모바일에서도 읽히게 간격·색·글자 크기 조정"눈이 어디로 가나, 깨지는 구간은 없나
JS"버튼을 누르면 화면 내용이 바뀌게"클릭·입력·상태 변화가 기대대로인가
🤔 세 문제를 어느 겹으로? — ①안내 문구가 업무 말과 안 맞음 = HTML ②카드가 모바일에서 글자 겹침 = CSS ③버튼 눌러도 반응 없음 = JS. 현장선 섞이지만 첫 진단을 나누면 다음 지시가 구체화된다.
"페이지를 고쳐줘"는 어디를 고칠지 안 정한 요청, "카드 정보는 그대로 두고 모바일 간격만 조정해줘"는 겹을 지정한 요청입니다.

이름에 담긴 사연

HTML·CSS·JS의 역사 · 박스모델 · 프론트/백엔드

② 내력
각 겹이 왜 따로 존재하는지를 알면 AI 출력에서 어디를 봐야 하는지가 분명해집니다. 세 겹은 각각 다른 시기에 다른 문제를 풀기 위해 태어났습니다.

📄 HTML — 잃어버린 문서에서 시작

  • 1980년대 말 CERN — 수천 연구자가 다른 컴퓨터·프로그램으로 문서를 만들어, 사람이 떠나면 자료 위치도 사라졌다. 팀 버너스리가 1989년 제안 — 문서 속 단어에서 다른 문서로 바로 건너뛰게 연결하자(하이퍼텍스트). 상사의 메모: "막연하지만 흥미롭다"
  • 1993년 CERN이 웹 기술을 로열티 없이 공개 — 그래서 웹은 특정 회사 제품이 아니라 모두의 기반이 됐다(오늘 HTML을 공짜로 쓰는 이유)
HyperText Markup Language — '마크업'은 편집자가 원고 여백에 "여기는 제목"이라 표시하던 관행. <h1>=가장 높은 제목, <button>=누르는 버튼처럼 정보의 의미를 표시한다. 검토 기준은 꾸밈이 아니라 정보.
병원 안내 페이지에 '진료 안내'·'예약'은 있는데 창구에서 하루에도 수십 번 답하는 '진단서 발급'이 빠졌다면 — 이 누락은 코딩이 아니라 현장을 아는 눈에만 보입니다. 그래서 이 겹의 최종 검토자는 여러분입니다. 최초 웹사이트 http://info.cern.ch 는 지금도 접속됩니다.

🎨 CSS — "제목 색을 전부 바꿔주세요"의 악몽

  • 초기엔 꾸밈 태그를 본문 곳곳에 직접 끼웠다 — 문서 수백 개에서 "제목 색을 전부 바꿔주세요"가 오면 모든 문서를 하나하나 고쳐야 했다(내용과 꾸밈이 한 덩어리)
  • 1994년 호콘 비움 리가 인쇄에서 힌트 — 기사와 조판 규칙을 따로 관리하듯, 꾸밈 규칙을 문서 밖 스타일시트로 분리. 1996년 표준
Cascading(폭포처럼 층층이) Style Sheets — 기본·사이트·페이지 규칙이 겹칠 때 어느 쪽이 이기는지 우선순위가 폭포처럼 정해져 있다는 뜻. 2003 CSS Zen Garden이 상징 — 같은 HTML에 CSS만 바꿔 일본 정원도, 잡지 표지도(내용은 한 글자도 안 바뀜).
검토 기준은 정보가 아니라 읽히는 방식 — 눈이 어디로 먼저 가나, 모바일 폭에서 깨지나. AI에겐 "예쁘게"보다 "모바일 390px에서도 카드가 한 열로 읽히게"처럼 관찰 가능한 조건이 낫습니다.

📦 CSS를 말로 고치는 최소 지도 — 박스모델

content실제 내용
글·이미지·버튼
→
padding안쪽 여백
내용↔테두리
→
border테두리
→
margin바깥 여백
다른 상자와
지금은 안쪽 여백은 padding, 바깥쪽 여백은 margin이라는 차이만. gap은 flex·grid로 나란히 놓은 요소 사이 간격. 카드 폭엔 box-sizing: border-box를 함께 쓰면 지정한 width 안에 padding·border까지 포함돼 예상보다 넓어지는 일이 준다.

단어장 대신 일상어로 — "카드 바깥에 여백이 필요해"(margin)·"버튼 글자가 테두리에 너무 붙어"(padding)·"버튼들이 서로 너무 붙어"(gap)·"카드에 테두리를"(border). "어느 요소"와 "모바일에서도"를 함께 말하면 확인하기 좋다

속성명을 암기할 필요 없습니다 — 눈에 보이는 문제를 일상어로 말하면 AI가 CSS 속성으로 번역합니다. "카드 내용은 바꾸지 말고 바깥 간격만 조정하고, 어떤 CSS를 바꿨는지 알려줘"처럼.

⚡ JavaScript — 열흘 만에 태어난 언어

  • 1995 넷스케이프가 페이지가 사용자 행동에 그 자리에서 반응할 언어를 원했다 — 브렌던 아이크가 첫 버전을 열흘 남짓에. Mocha→LiveScript→JavaScript(마지막 개명은 Java 인기에 올라탄 마케팅, 둘은 이름만 닮은 남남 = "햄과 햄스터")
  • 첫 임무는 폼 검증 — 느린 모뎀 시절 제출 버튼 누르기 전에 브라우저가 "이메일 형식이 아닙니다"라고 그 자리에서. JS가 처음 쓸모를 증명한 장면
JS가 맡는 건 시간에 따라 변하는 것 — 클릭·입력·필터·토글. 검토 기준 하나: "무엇을 누르면 무엇이 바뀌어야 하는가"가 기대대로인가. 2005 구글 지도가 결정적 — 페이지를 새로 고치지 않고 데이터를 주고받는 AJAX로 웹이 '문서'에서 '애플리케이션'으로.
겉모습은 Java를 닮았지만(경영진 요구) 속은 학술 언어 Scheme 계열 — 이 어색한 동거가 오해의 뿌리. 지도를 끄는 손을 따라가며 동시에 데이터를 받는 게 어떻게 가능한지는 다음 덱(CS)에서 답합니다.

🧩 세 겹의 내력이 지시의 언어가 된다

겹태어난 문제검토 기준
HTML흩어진 정보를 의미 있게 연결하기정보·용어가 빠지지 않았나
CSS내용과 꾸밈이 붙어 수정이 번지는 문제읽히나, 깨지는 폭은 없나
JS눌러도 반응 없는 정적 문서행동 뒤 변화가 기대대로인가
웹은 처음부터 세 겹으로 설계된 게 아니라 30년에 걸쳐 문제를 하나씩 풀며 지금 모양이 됐다. 각 겹이 태어난 이유가 다르니 맡은 일·검토 기준도 다르다 — 겹을 지정하면 AI가 손댈 범위가 좁아지고 괜찮은 부분이 덜 흔들린다.
내용·표현·동작을 나누는 발상은 웹만의 것이 아닙니다 — 데이크스트라가 1974년 부른 관심사의 분리(separation of concerns). 측면을 나누면 측면마다 판단 기준이 생깁니다.

🧠 CS 교양 — 관심사의 분리

  • 데이크스트라(1974) — 복잡한 문제는 한 번에 한 측면에만 집중하고 나머지는 접어두는 태도가 관심사의 분리. 통째로 붙들면 어디부터 손댈지 모르지만, 나누면 측면마다 판단 기준이 생긴다
  • 협업에도 이어진다 — 콘텐츠 담당자는 문구, 디자이너는 표현, 개발자는 동작. AI와 일할 때도 관심사를 나눠 말하면 AI도 한 측면에 집중한다

🔍 모바일에서 버튼 둘이 겹칠 때, 어느 요청이 나은가?
A. ".nav-button에 flex-wrap: wrap이랑 min-width: 120px를 줘"
B. "버튼 두 개가 겹쳐 누르기 어려워. 글자는 그대로 두고 버튼이 줄바꿈되게 고쳐줘"

B를 권한다 — A는 해법(속성명)을 사람이 지정했는데, 추측한 명세는 틀려도 AI가 따른다. B는 관찰(겹침)·기대(줄바꿈)·지킬 것(글자)을 나눠 말했다. 해법 고르기는 AI의 몫으로 남긴다.
고칠 관심사와 건드리지 말 관심사를 분리한 것입니다.

🍽️ CS 교양 — 프론트엔드와 백엔드

프론트엔드 (홀·메뉴판)

사용자가 브라우저에서 직접 만나는 쪽 — HTML·CSS·JS. 무엇을 보고, 누르고, 입력하나

백엔드 (주방·창고·장부)

화면 뒤 처리 — 서버·API·데이터 저장·권한. 입력이 어디 저장되고 누가 다시 보나(뒤 강의)

홀만 있으면 음식이 안 나오고, 주방만 있으면 뭘 주문할지 모른다 — 두 쪽이 함께 움직일 때 경험이 이어진다. 웹은 로그인·결제·검색이 늘며 보이는 쪽과 처리하는 쪽을 나눠 설계하게 됐다.
  • 바이브 코딩에서도 — "업무 카드가 모바일에서 한 열로"는 프론트엔드, "상담 기록을 저장하고 작성자만 수정하게"는 백엔드. 섞어 던지면 화면은 됐는데 저장이 빠지기도
오늘은 프론트엔드의 세 겹을 먼저 익히고, 백엔드·API는 뒤 강의에서 다룹니다.

🎯 이 덱의 핵심 정리

개념한 문장
세 겹구조(HTML)·표현(CSS)·동작(JS) — 겹을 지정하면 지시가 좁아진다
HTML잃어버린 문서를 연결(하이퍼텍스트) — 검토는 꾸밈 아닌 정보
CSS내용과 꾸밈의 분리(폭포처럼 우선순위) — 검토는 읽히는 방식
박스모델안쪽=padding, 바깥=margin, 사이=gap. 일상어로 말하면 AI가 번역
JavaScript행동 뒤 변화 — 검토는 "무엇을 누르면 무엇이 바뀌나"
관심사 분리·프론트/백측면을 나눠 말한다 / 화면은 프론트, 저장은 백엔드
다음 덱에서 "지도를 끄면서 동시에 데이터를 받는" 게 어떻게 가능한지 — 동기·비동기·프로세스·스레드·코어를 봅니다.

✅ 정답 & 해설

A1. HTML=구조(무엇이), CSS=표현(어떻게 보일지), JS=동작(무엇이 바뀔지). 겹을 지정하면 AI가 손댈 범위가 좁아져 괜찮은 부분이 덜 흔들린다.
A2. HTML은 정보에 의미를 표시하는 마크업이라 — 필요한 정보·업무 용어(예: 진단서 발급)가 빠졌는지는 현장을 아는 눈에만 보인다.
A3. 여러 규칙이 겹칠 때 우선순위가 폭포처럼 정해져 이긴다는 뜻. Zen Garden은 같은 HTML에 CSS만 바꿔 전혀 다른 화면(내용은 그대로)을 보여줬다.
A4. padding = 안쪽 여백(내용↔테두리), margin = 바깥쪽 여백(다른 상자와). gap은 나란히 놓은 요소 사이.
A5. 프론트: "업무 카드가 모바일에서 한 열로". 백엔드: "상담 기록을 저장하고 작성자만 수정하게". 섞어 던지면 한쪽이 빠질 수 있다.
세 겹을 나눠 말하는 습관이 AI 협업의 정확도를 올립니다.
