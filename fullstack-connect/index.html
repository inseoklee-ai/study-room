화면과 서버를 AI로 짜서 — '연결'하기

이제 조각이 다 모였습니다. 지난 시간에 화면을, 이번 시간에 네트워크·백엔드·보안·배포를 배웠습니다. 이 소단원은 그 조각들을 AI로 어떻게 잇는지, 특히 초보가 가장 많이 헤매는 지점을 다룹니다.

🎯 오늘의 한 문장 — 목업으로 화면을 잘 만들어 두면, 백엔드는 "한 겹 덧입히기"입니다.
홀만 있던 가게에 드디어 주방이 생기는 순간을 상상해 보세요. 화면(홀)과 서버(주방)를 잇는 것이 오늘의 목표입니다. 네 파트를 지나면 '연결'이 막연한 두려움이 아니라 순서와 전략의 문제로 바뀝니다.
1

가장 안정적인 순서

어디서부터 손대야 덜 헤매는가

목업 → API → 교체
풀스택을 만들 때 순서가 결과를 좌우합니다. 화면과 서버를 동시에 붙잡으면 초보는 길을 잃습니다. 이 파트는 실패를 일찍 잡는 순서를 세웁니다.

🧱 세 단계로 잇는다

1목업 화면 먼저 — 지난 시간에 만든 '가짜 데이터로 도는 화면'이 출발점이다
2백엔드 API 붙이기 — 그 화면이 부를 창구(엔드포인트)를 만든다
3가짜 데이터를 실제 호출로 교체 — 목업 자리를 진짜 서버 응답으로 바꾼다
화면이 먼저 서 있어야, 서버는 그 화면이 필요로 하는 모양에 맞춰 만들 수 있다.
이 순서의 핵심은 화면이 '무엇을 필요로 하는지'가 먼저 정해진다는 점입니다. 그 필요를 기준으로 API를 만들면, 마지막 교체 단계에서 어긋남이 줄어듭니다.

✂️ 한 가지 결정 — 통째로? 나눠서?

통째로 한 프롬프트앱 전체를 한 번에
→ 초보에겐 거의 항상 실패
→
작게 쪼개서데이터 모양 → API → 화면
→ 실수를 일찍 잡음
통째로 다 시키는 건 AI의 집중력·기억 한계 때문에 무너진다. 작게 쪼개 시키면 각 단계에서 검증할 수 있다.
AI는 한 프롬프트에 담긴 요구가 많을수록 앞의 결정을 잊거나 뒤와 어긋나게 만듭니다. "데이터 모양 먼저, 그다음 API, 그다음 화면"처럼 작은 단위로 나눠 시키면 문제가 커지기 전에 잡힙니다.
2

연결에서 겪는 문제

증상을 알아보고 처방을 익힌다

계약 불일치 · 로딩/에러 · CORS
연결 단계에서 초보가 실제로 부딪히는 문제는 몇 가지로 정해져 있습니다. 증상을 미리 알아 두면, 화면이 이상할 때 어디를 봐야 할지 바로 압니다.

🔌 가장 큰 원흉 — 계약 불일치

  • 프론트가 기대하는 데이터 모양 ≠ 백엔드가 주는 모양
  • AI를 쓰면 오히려 심해진다 — 양쪽에 '얼추 맞는' 걸 따로 만들어 서서히 어긋남

증상

화면에 undefined가 뜨거나, 한 겹 더 감싸인 응답이 온다

처방

'나중에 맞추기'가 아니라, 주고받을 데이터를 처음부터 문서로 적어 두고(API 명세) 그걸 기준으로 양쪽을 짠다

계약 불일치는 코드가 각자 '거의 맞게' 돌아가기 때문에 눈에 잘 안 띕니다. AI는 프론트와 백엔드를 따로 그럴듯하게 만들어 이 어긋남을 키우기 쉽습니다. 그래서 문서(명세)가 근본 처방이 됩니다.

⏳ 나머지 둘 — 상태와 주소

문제증상처방
로딩·에러 상태 누락데이터 오기 전 화면이 깜빡, 서버 오류 시 앱이 멈춘 듯모든 호출을 로딩 / 성공 / 에러 세 상태로 나눠 각각 화면 준비
CORS·주소·환경변수다른 주소 간 차단, "로컬에선 됐는데"백엔드가 내 프론트 주소를 허용, 주소는 환경변수로
'배포'에서 본 CORS·주소 문제는 사실 프론트-백엔드 연결 문제이기도 하다. 그래서 처방도 같다.
로딩과 에러는 '언젠가 넣을 것'이 아니라 호출을 만들 때 함께 설계해야 합니다. CORS는 앞 배포 시간에 본 개념과 같은 문제로, 다른 주소 사이의 요청을 서버가 허용하도록 설정하면 됩니다.
3

연결을 매끄럽게 하는 프롬프트 전략

주고받을 데이터를 '문서'로 남기고 시작한다

명세 · 수직 슬라이스 · 목업→실제 · 커밋
가장 강력한 전략은 주고받을 데이터를 문서로 남기는 것입니다. 이 파트의 다섯 전략은 모두 AI가 프론트와 백엔드의 모양을 맞추기 쉽게 만드는 장치입니다.

📄 근본 해결 — API 명세를 문서로

어떤 창구가 있고, 각 요청·응답이 어떤 JSON 모양인지 적은 문서.

AI에게 이렇게

"엔드포인트 목록과 각 요청/응답 예시(JSON)를 명세 문서로 만들어 줘. 앞으로 이 문서를 기준으로 프론트와 백엔드를 짜자."

기능이 바뀌면 코드보다 이 문서를 먼저 고친다. OpenAPI 같은 표준도 있지만, '이름표-값' 예시 메모라도 충분하다.
명세 문서는 프론트와 백엔드가 공유하는 하나의 '진실'입니다. 양쪽이 각자 추측하는 대신 같은 문서를 참고하므로 계약 불일치가 근본적으로 줄어듭니다. 거창한 표준이 아니어도, 요청과 응답의 JSON 예시를 적어 둔 메모면 됩니다.

🧭 함께 쓰는 네 전략

1한 기능씩 끝까지(수직 슬라이스) — "화면 전부→서버 전부"로 층을 나누면 AI가 다른 층을 몰라 추측하다 틀린다. 대신 "회원가입 한 기능"을 화면-API-저장까지 하나로 완성하고 바로 테스트
2양쪽을 함께 보게 — 프론트·백엔드 코드를 같은 대화·같은 저장소에 두면 AI가 양쪽 모양을 맞추기 수월
3목업→실제 전환 — "지금 화면이 쓰는 가짜 데이터를 방금 만든 실제 API 호출로 바꿔 줘. 명세의 모양은 유지하고, 로딩과 에러 처리도 함께 넣어 줘."
4매 단계 커밋 — 되돌아갈 체크포인트. AI는 확신에 차서 멀쩡한 걸 망가뜨리기도 한다
수직 슬라이스는 한 기능을 화면부터 저장까지 통째로 완성하는 방식으로, 층을 나눌 때 생기는 추측을 없앱니다. 매 단계 커밋은 AI가 잘못 건드렸을 때 안전하게 되돌아갈 지점을 남겨 줍니다.
4

AI의 단골 실수와 검증

'일단 돌아가는' 코드가 안전한 건 아니다

서버 검증 · 하드코딩 · 스타터
AI는 보안이 나빠서가 아니라 프롬프트에 보안이 없었기 때문에 '일단 돌아가는' 코드를 만듭니다. 목표가 '작동'이지 '안전'이 아니기 때문입니다. 내보내기 전 점검이 필요합니다.

⚠️ 단골 실수 둘

1프론트에만 검증, 백엔드 검증 누락 — 공격자는 화면을 안 거치고 API를 직접 부를 수 있다 → 서버에서 입력을 다시 검증("프론트는 못 믿는다")
2하드코딩된 주소 / 키 노출 — localhost 주소를 박으면 배포에서 깨지고, API 키를 프론트 코드에 넣으면 개발자도구로 다 보인다
NEXT_PUBLIC_ · VITE_ 접두사가 붙은 값은 "브라우저에 공개"라는 뜻 → 비밀값엔 절대 쓰지 말 것.
화면 쪽 검증은 사용자 편의일 뿐, 방어선이 아닙니다. 공격자는 화면을 건너뛰고 API를 직접 호출할 수 있으니 서버가 입력을 다시 검증해야 합니다. 프론트 코드는 브라우저에서 누구나 열어 볼 수 있으므로 비밀값을 넣으면 안 됩니다.

🔍 검증 팁 & 부담 줄이기

배포 전 AI에게

"이 코드 전체를 하드코딩된 비밀값 · 서버 입력 검증 누락 · CORS 설정 · 인증 취약점 관점으로 점검해 줘."

스타터로 부담 줄이기 — 프론트·백엔드·DB를 한 묶음으로 다루는 스타터(예: Next.js 풀스택 + Supabase)를 쓰면 둘이 한 프로젝트 안에 있어 CORS·주소 불일치가 애초에 줄어든다.

⚠️ 다만 만능은 아니다 — 접근 규칙 같은 보안 설정을 안 켜면 남의 데이터가 노출될 수 있다. 점검은 여전히 사람의 몫.

스타터는 연결의 물리적 거리를 없애 CORS·주소 문제를 줄여 줍니다. 그러나 접근 규칙 같은 보안 설정을 켜지 않으면 데이터가 노출될 수 있으므로, 점검 책임은 사람에게 남습니다.

백엔드는 정말 "한 겹 덧입히기"화면 코드는 거의 그대로 — 부르는 한 줄만 바뀐다
오늘 배운 네트워크(연결)·보안(안전)·배포(공개)는 그 한 겹을 안전하게, 세상에 열어 두기 위한 준비다.
맨 처음의 장면 — 친구가 링크를 열 수 있고, 새로고침해도 데이터가 남는 것 — 이 이 과정의 끝에서 이뤄집니다. 홀만 있던 가게에 드디어 주방이 생기는 순간입니다.

🎯 이해도 확인 질문

Q1. 풀스택을 만드는 가장 안정적인 세 단계 순서는?
Q2. 앱 전체를 한 프롬프트에 통째로 시키면 왜 초보에겐 거의 실패하나?
Q3. 연결의 가장 큰 원흉인 계약 불일치의 근본 처방은?
Q4. 프론트에만 검증을 두면 왜 위험하며, 처방은 무엇인가?
Q5. 목업으로 화면을 잘 만들어 두면 백엔드 연결이 왜 "한 겹"이 되나?
답이 바로 떠오르지 않으면 앞 장으로 돌아가 확인해 보세요. Q3와 Q5가 오늘의 핵심을 가장 잘 가립니다.

✅ 정답 & 해설

A1. ① 목업 화면 먼저 → ② 백엔드 API 붙이기 → ③ 가짜 데이터를 실제 호출로 교체.
A2. AI의 집중력·기억 한계 때문. "데이터 모양 → API → 화면"으로 작게 쪼개 시켜야 실수를 일찍 잡는다.
A3. 주고받을 데이터를 처음부터 문서로(API 명세) 적어 두고 그걸 기준으로 양쪽을 짠다.
A4. 공격자가 화면을 안 거치고 API를 직접 부를 수 있으므로 → 서버에서 입력을 다시 검증("프론트는 못 믿는다").
A5. "가짜 데이터를 불러오던 한 줄"을 "진짜 서버에 요청하는 한 줄"로 바꾸기만 하면 되고, 화면 코드는 거의 그대로이기 때문.
A3와 A5를 자기 말로 설명할 수 있으면 오늘 목표는 달성입니다.
