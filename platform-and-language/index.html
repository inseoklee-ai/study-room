플랫폼과 언어 선택

화면, 하네스 실행 위치, 모델 실행 위치는 서로 다른 결정입니다

혼자 코드를 점검하는 도구와 동료에게 문서를 정리해 주는 도구는 같은 모델을 써도 필요한 화면이 다를 수 있습니다.

고를 기준

내 사용자가 실제로 사용할 수 있고
내가 AI와 함께 코드를 읽고 검증할 수 있는 조합
  • 모든 조합을 시험할 필요는 없습니다
  • 특별한 이유가 없다면 내 컴퓨터에서 실행하는 Python CLI를 기본안으로 권합니다 — 웹 화면을 만드는 일보다 모델과 도구 사이의 실행 흐름을 먼저 관찰하기 좋기 때문
  • 이미 익숙한 언어나 분명한 화면 요구가 있다면 그쪽을 선택해도 됩니다
여기서 정할 것은 플랫폼과 구현 언어입니다.
1

실행 위치와 화면 형태 구분

"웹으로 만든다"만으로는 정해지지 않습니다

③ 플랫폼과 언어
CLI는 터미널에서 글자로 요청하고 결과를 받는 방식, UI는 사용자가 프로그램과 상호작용하는 화면이나 조작 방식입니다.

서로 다른 세 결정

①화면
②하네스 실행 위치
③모델 실행 위치
  • CLI도 UI의 한 종류이며, 버튼과 입력란을 둔 웹 화면도 UI입니다
  • 로컬 웹 앱 — 내 컴퓨터에서 서버 프로그램을 실행하고 같은 컴퓨터의 브라우저로 접속. 여기서 서버는 브라우저의 요청을 받아 작업을 처리하는 프로그램이며 꼭 멀리 있는 컴퓨터를 뜻하지 않습니다
  • CLI든 웹이든 실제 파일 읽기와 테스트 실행은 하네스가 동작하는 컴퓨터에서 처리하도록 설계할 수 있습니다 — 반대로 원격 서버에 하네스를 올리면 파일 작업의 기준도 그 서버가 됩니다. 내 노트북의 폴더가 자동으로 서버에 연결되지는 않습니다
  • 하네스가 로컬에서 실행된다고 모델까지 반드시 로컬에서 실행되는 것도 아닙니다 — 로컬 하네스가 외부 모델 API를 호출할 수도, 로컬 모델 서버를 호출할 수도 있습니다
모델 연결은 다음 절에서 선택합니다. 지금은 세 가지가 서로 다른 결정이라는 점을 구별하면 됩니다.

사용자에게 맞는 첫 화면

지금의 사용 상황권할 첫 선택함께 고려할 점
내가 자료 정리와 코드 점검에 사용로컬 CLI실행 기록과 승인 내용을 터미널에서 읽기 쉽게 구성
터미널에 익숙하지 않은 사람이 사용로컬 웹입력·진행·결과·승인을 화면에서 구별
여러 기기나 여러 사람이 접속접속 요구를 먼저 구체화실행 위치, 인증, 사용자별 파일 접근 범위가 추가로 필요
  • 웹을 고르면 입력 화면뿐 아니라 작업 중 표시, 완료·실패 상태, 승인 버튼과 처리 중 중복 요청도 설계해야 합니다 — 화면이 있다는 사실만으로 이런 동작이 갖춰지는 것은 아닙니다
  • CLI를 먼저 골라도 핵심 처리와 터미널 입출력을 분리해 두면 나중에 웹 화면을 붙일 여지가 생깁니다 — 그렇다고 웹 전환이 자동으로 끝나는 것은 아닙니다
오늘 필요한 화면을 고르고, 미래의 화면은 실제 필요가 생길 때 별도 설계합니다.

읽고 고칠 수 있는 구현 언어

언어를 바꾼다고 모델이 더 정확해지지 않습니다

③ 플랫폼과 언어
파일 작업, 모델 요청, 응답 해석, 도구 실행, 기록을 어떤 코드와 개발 환경으로 다룰지 선택하는 것입니다.

세 언어와 붙는 조건

언어적합한 경우함께 알아 둘 것
Python간결한 문법으로 파일 처리와 API 연결 코드를 읽어 가고 싶은 경우의 기본안이미 학습했다면 아는 자료 구조와 함수로 하네스 흐름을 설명하기 좋음
TypeScriptJavaScript 경험이 있거나 웹 화면과 서버 코드를 같은 언어 계열로타입으로 실행 전에 일부 불일치를 발견 — 외부 API에서 받은 값이 올바른지는 실행 중에도 검사해야 하며, TypeScript를 쓴다는 이유만으로 잘못된 모델 응답이 차단되지 않습니다
Rust이미 경험이 있거나 컴파일된 CLI의 구조와 자원 관리를 깊게소유권 규칙 등 새로 익힐 개념이 늘어날 수 있음 — 학습의 중심이 하네스 설계라면 그 규칙까지 함께 배우고 싶은지 판단
📌 세 언어를 모두 설치하거나 같은 기능을 세 번 구현할 필요는 없습니다. Python으로도 웹 앱을, TypeScript로도 CLI를 만들 수 있으므로 — "웹이므로 반드시 TypeScript"보다 "내가 TypeScript를 알고 있고 화면과 서버를 함께 다루고 싶다"가 더 구체적인 선택 이유입니다
컴파일은 소스코드를 실행 가능한 형태로 변환하는 과정입니다. 화면과 언어를 하나의 고정된 묶음으로 생각하지 않습니다.

내 선택을 설계 문서에 남기기

나는 Python을 배웠고, 내 컴퓨터에서 문서 정리와 코드 점검에 쓸 거야.
CLI와 로컬 웹 중 맞는 구성과 이유를 설명해 줘.
내가 고른 뒤 PRD와 결정 기록에 남기자. 구현은 아직 하지 마.
항목기록 예 (정답이 아닌 예시)
D02 플랫폼내 컴퓨터에서 실행하는 CLI. 요청·진행·결과와 파일 변경 승인을 터미널에서 확인
D03 언어Python. 기존에 배운 함수와 파일 처리 코드를 활용해 실행 흐름을 읽고 검증
DECISIONS.md선택 이유와 받아들이는 불편 — "현재 사용자는 터미널에 익숙한 나 자신이다. 이미지나 표를 나란히 보는 화면은 첫 요구에 없으며, 필요해지면 웹 화면을 추가로 설계한다"
⚠️ 문서의 기존 형식을 유지하고 — 아직 결정하지 않은 모델 제공자나 권한까지 임의로 확정하지 않습니다
AI가 기록한 내용을 읽고 내 상황과 맞는지 확인합니다.

요구가 달라졌는지 확인

  • 로컬 웹을 골랐는데 공개 서버 배포가 구현 계획에 들어가 있거나, Python을 골랐는데 완성된 다른 에이전트 CLI에 모든 작업을 넘기도록 되어 있다면 — 요구가 달라진 것입니다
  • Claude Code와 OpenCode는 여기서 소스를 함께 만드는 개발 도우미입니다 — 우리가 만드는 제품의 모델 요청과 도구 실행 반복은 제품의 소스에서 구현합니다
이번 선택의 결과는 D02와 D03에 남습니다
아직 모든 설계가 끝난 것은 아니므로 설치와 구현을 서두르지 않습니다
다음 절에서는 이 환경에서 처음 제공할 작업 범위와 모델 제공자를 정해, 실제로 무엇을 실행하는 제품인지 구체화합니다.

❓ 이해도 확인

Q1. "웹으로 만든다"가 정해 주지 않는 것은?
A1. 프로그램이 어디에서 실행되는지. 로컬 웹 앱도 있고, 원격 서버에 올리면 파일 작업의 기준도 그 서버가 된다.
Q2. TypeScript를 쓰면 잘못된 모델 응답이 차단되나?
A2. 아니다. 타입은 실행 전 일부 불일치를 잡을 뿐 — 외부 API 값은 실행 중에도 검사해야 한다.
Q3. 화면과 언어는 한 묶음인가?
A3. 아니다. Python으로 웹 앱을, TypeScript로 CLI를 만들 수 있다. "내가 아는 언어이고 이런 이유로 필요하다"가 더 구체적인 이유.
Q1이 실행 위치를 흐리게 만드는 대표적 표현입니다.
