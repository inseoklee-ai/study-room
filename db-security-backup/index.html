"Little Bobby Tables" — SQL 주입

25년 넘게 보안 위협 1위권

⑤ 보안과 백업
프로그래머 사이에서 전설적인 xkcd 만화(2007)로 시작합니다.

학교에서 전화가 왔습니다

🏫 학교

"아드님 이름을 데이터베이스에 넣었더니 학생 기록이 전부 지워졌어요."

👩 엄마

"아, 우리 아들 이름이 좀 특이하죠."

Robert'); DROP TABLE Students;--
👩 엄마 — "앞으로는 입력값을 꼭 소독(검증) 하시길 바라요."
출처: xkcd "Exploits of a Mom" (https://xkcd.com/327/). 언어별로 막는 법을 정리한 곳: https://bobby-tables.com/ — 발표 때 화면에 띄워 주면 좋습니다.

무슨 일이 벌어진 걸까요

1아들 이름에 DB 명령어처럼 생긴 문자가 들어 있었다
2학교 프로그램이 그걸 이름이 아니라 명령으로 실행했다
3학생(Students) 표를 통째로 삭제(DROP)해 버렸다
  • 이것이 그 유명한 SQL 주입(SQL Injection) — 25년 넘게 보안 위협 1위권을 지키는 공격입니다
  • 로그인 창에 특정 문자를 넣어 비밀번호 없이 로그인하는 것도 같은 원리입니다
출처: Malwarebytes, "What is SQL injection". "명령과 데이터의 경계가 무너진다"가 이 공격의 본질입니다. 다음 슬라이드의 방어법이 정확히 그 경계를 세웁니다.

방어법 — 레시피와 재료를 섞지 않는다

❌ 위험

사용자가 친 글자를 명령 문장에 그대로 이어 붙이기 → DB가 "어디까지가 명령이고 어디부터가 데이터"인지 헷갈린다

✅ 안전

자리표(?)를 미리 비워 둔 명령을 만들고 사용자 입력은 따로 건넨다 → DB가 입력을 무조건 '그냥 데이터'로만 취급

  • 그러면 Robert'); DROP...을 넣어도 그런 이름을 가진 사람을 찾을 뿐 명령으로 실행하지 않습니다
  • 이 방식을 파라미터화 쿼리(prepared statement)라고 합니다 — 보안 전문가들이 꼽는 표준 방어법
🗣️ AI에게 이렇게 — "DB에 넣는 값은 문자열로 이어 붙이지 말고, 파라미터화 쿼리로 처리해줘. 사용자 입력을 그대로 신뢰하지 마."
출처: OWASP, "SQL Injection Prevention Cheat Sheet". 한 문장이 학생 기록을 지키는 셈입니다. SQL 주입은 무서워 보여도 정해진 방어법이 확실합니다.

실화 — 옛날이야기가 아닙니다

TalkTalk 2015 · Heartland 2008

⑤ 보안과 백업
"기본을 안 지켜서" 벌어진 사고들입니다.

알려진 구멍을 안 막아 십대에게 뚫린 통신사

2015년, 영국의 대형 통신사 TalkTalk이 SQL 주입으로 뚫렸습니다. 놀라운 건 공격자가 대단한 조직이 아니라 십대들이었다는 점입니다.

항목사실
이용된 구멍3년 반 전에 이미 패치가 나와 있던 것 — 회사가 방치
유출 규모고객 약 15만 7천 명 (그중 1만 5천여 명은 계좌 정보까지)
체포된 이들모두 21세 미만
사고 비용규제기관 당시 최고액 벌금 · 총 약 4,200만 파운드
🗯️ 규제기관 총평 — "가장 기본적인 보안 조치조차 하지 않았다."
출처: 영국 정보위원회(ICO) 공식 발표; BBC, "TalkTalk hack costs reach £42m", 2016 (https://www.bbc.co.uk/news/business-38262235). 비용은 BBC와 TalkTalk 결산 기준입니다.

규모로는 더 큰 사고도 — 카드 1억 3천만 장

2008년 미국 결제회사 Heartland는 같은 SQL 주입으로 카드번호 약 1억 3천만 장이 털렸습니다 — 당시 사상 최대 규모였죠.

대부분의 큰 사고는 새로운 마법이 아니라
오래전에 답이 나온 기본을 안 지켜서 벌어집니다
  • 다행히 요즘 AI와 최신 도구는 이 방어를 기본으로 해 줍니다
  • 하지만 "내 서비스도 이게 되어 있나?" 묻는 습관은 사람의 몫입니다
출처: Wikipedia, "Albert Gonzalez". 교훈은 앞의 'Bobby Tables'와 똑같습니다 — 방어법은 이미 있습니다.

개인정보 다루기 — 모을수록 무거워진다

자산이자 책임

⑤ 보안과 백업
이름·이메일·비밀번호가 쌓이면 그건 자산이자 책임입니다. 새면 사용자가 다칩니다.

비전공자가 지킬 세 가지

1비밀번호는 절대 그대로 저장하지 않는다 — 되돌릴 수 없는 해시(+솔트)로. 야후 보이스(2012)가 평문으로 저장했다 크게 데인 그 이야기
2꼭 필요한 것만 모은다 — 안 받아도 되는 정보는 처음부터 안 받는 게 가장 안전한 보관. 없는 데이터는 샐 수도 없으니까요
3민감 정보는 특히 조심 — 주민번호·카드번호 같은 건 되도록 직접 저장하지 말고 전문 서비스(결제사 등)에 맡긴다
🗣️ AI에게 — "비밀번호는 솔트 섞어 해시로 저장하고, 민감한 개인정보는 최소한만 수집하게 설계해줘."
2번이 CERN 슬라이드('무엇을 저장할지 고르는 일')와 같은 결입니다. 저장하지 않는 것도 설계입니다.

사용자 정보를 저장하는 순간의 기본 네 가지

1필요한 것만 모은다(최소 수집) — 한국 개인정보보호법도 "목적에 필요한 최소한만" 모으도록 정한다. "이메일 하나면 되는데 전화번호·생년월일까지 받고 있진 않나?"
2비밀번호는 해시로 — 그것도 빠른 해시가 아니라 bcrypt·Argon2 같은 비밀번호 전용을 쓴다
3민감정보(주민번호·카드번호)는 직접 다루지 않는 게 최선 — 결제는 PG에, 본인확인은 인증 서비스에. 내 DB엔 저장하지 않는다
4모을 때 밝힌 목적에만 쓴다(목적 제한) — 다른 데 쓰거나 남에게 넘기려면 별도 동의가 필요하다
🎯 한 줄 — "덜 모으고, 비밀번호는 해시하고, 민감정보는 남에게 맡기고, 목적 밖으로 쓰지 않는다."
출처: 국가법령정보센터 개인정보 보호법 제3·16조; OWASP Password Storage Cheat Sheet. 가장 안전한 데이터는 애초에 안 가진 데이터입니다.

실제 사용자를 받는다면 — 최소한 이건

1가입 때 '수집·이용 동의'를 받는다 — 무엇을·왜 모으는지 알리고 동의(필수/선택 구분)
2개인정보처리방침 한 장을 둔다 — 무엇을·왜 모으고 얼마나 보관하는지 (AI에게 초안을 요청해도 된다)
3제3자에게 넘길 때는 미리 알리고 동의를 받되 다섯 가지를 밝힌다 — ① 제공받는 자 ② 이용 목적 ③ 제공 항목 ④ 보유·이용 기간 ⑤ 동의 거부권과 거부 시 불이익
🧭 그리고 — 되도록 안 넘기는 게 최선입니다
근거·자세한 내용은 개인정보 보호법(국가법령정보센터)에서 볼 수 있습니다. 이 슬라이드는 '취미 프로젝트'와 '실제 사용자를 받는 서비스'의 경계를 알려 줍니다.

데이터를 잃지 않기 — 백업, 그리고 유명한 참사들

토이 스토리 2 · GitLab · Ma.gnolia

⑤ 보안과 백업
해커가 없어도 데이터는 사라집니다 — 실수 한 번으로요.

🎬 「토이 스토리 2」가 눈앞에서 지워지던 날

픽사, 1998년 제작 중(1999년 개봉). 누군가 잘못된 명령을 실행해 영화 파일이 눈앞에서 지워지기 시작했습니다. 설상가상 백업 시스템도 한 달째 고장나 있었죠.

🏠 영화를 살린 건 — 출산 후 재택근무하던 한 기술 총괄(TD)이 집 컴퓨터에 두었던 2주 전 사본이었습니다
  • 하마터면 영화가 통째로 날아갈 뻔했습니다
  • 주목할 점 — 백업이 '있다고 믿었지만' 고장 나 있었다는 것
이 이야기는 소단원 ③의 미니 퀴즈 "정기 백업 → O"의 근거입니다. 우연히 살아난 것이지 대비된 게 아니었다는 점을 강조하세요.

같은 실수, 다른 결말

GitLab (2017)

엔지니어가 실수로 잘못된 서버의 데이터를 지웠고, 여러 겹의 백업이 모두 조용히 고장나 있어 6시간치 데이터를 잃었다

Ma.gnolia (2009)

백업은 있었지만 원본과 같은 시스템에 뒀다가, 그 시스템이 망가지자 백업도 함께 사라져 서비스가 문을 닫았다

1백업이 '진짜 되는지' 가끔 확인한다 — 픽사·GitLab 둘 다 '있다고 믿었지만' 고장 나 있었다
2사본은 다른 곳에 둔다 — 원본과 같은 곳이면 함께 사라진다
3여러 벌을 둔다
출처: EnvisionIT, "Six Horror Stories of Data Loss". 세 교훈이 다음 슬라이드의 3-2-1 규칙으로 정리됩니다.

백업의 황금률 — 3-2-1

백업은 "했다"가 아니라 "복구된다"가 중요합니다. 미국 사이버보안기관(CISA)이 권하는 표준입니다.

33벌 — 원본 1 + 사본 2, 최소 세 벌을 둔다
22종 — 서로 다른 매체 두 곳에(예: 노트북 디스크 + 클라우드). 한 종류가 통째로 망가져도 다른 쪽은 살아남게
11벌은 다른 장소에(off-site) — 화재·도난·랜섬웨어처럼 한 장소를 통째로 잃는 사고에 대비
  • 개인 실천 예 — ① 노트북의 원본 ② 외장하드 사본 ③ 클라우드(구글 드라이브나 DB 자동 백업) → 자연히 3벌·2종·off-site 1벌
🔎 CISA가 특히 강조하는 것 — 복구가 진짜 되는지 가끔 확인하세요. 열어본 적 없는 백업은 백업이 아닙니다
출처: CISA, "Data Backup Options". 참고로 요즘 클라우드 DB는 백업을 도와주지만 무료 요금제에는 자동 백업이 없는 경우가 많습니다(예: Supabase 무료는 직접 백업 필요, 자동 일일 백업은 Pro부터). 내 요금제에 자동 백업이 포함되는지 꼭 확인하세요. (출처: Supabase Docs, "Database Backups")

❓ 이해도 확인

Q1. SQL 주입은 왜 일어나는가?
A1. 사용자 입력을 명령 문장에 그대로 이어 붙여 DB가 "어디까지 명령, 어디부터 데이터"인지 구분하지 못하기 때문. 방어는 파라미터화 쿼리.
Q2. TalkTalk 사고에서 가장 뼈아픈 사실은?
A2. 이용된 구멍이 3년 반 전에 이미 패치가 나와 있던 것이었다. 규제기관 총평 — "가장 기본적인 보안 조치조차 하지 않았다".
Q3. "가장 안전한 데이터"는 무엇인가?
A3. 애초에 안 가진 데이터. 없는 데이터는 샐 수도 없다 — 그래서 최소 수집이 원칙.
Q4. 3-2-1 규칙과 CISA의 추가 당부는?
A4. 3벌·2종·off-site 1벌. 그리고 복구가 진짜 되는지 확인할 것 — 열어본 적 없는 백업은 백업이 아니다.
Q3은 이 소단원의 태도를 묻는 문제입니다. 기술이 아니라 판단입니다.
