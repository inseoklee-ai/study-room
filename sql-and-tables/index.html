SQL 한 줄 구경하기

SELECT · FROM · WHERE · 그리고 CRUD

③ SQL 구경과 데이터의 모양
딱 한 줄만 봅니다. 외우게 하지 않습니다.

한 줄만 읽어 봅시다

SELECT 이름, 가격 FROM 상품 WHERE 분류 = '케이크';

풀어 읽으면 이렇습니다 — "상품 표에서(FROM 상품) 분류가 '케이크'인 것들의(WHERE) 이름과 가격을 줘(SELECT)."

구조

SELECT 무엇을 · FROM 어디서 · WHERE 어떤 조건으로

느낌

정말 영어 문장에 가깝습니다. 그래서 원래 이름이 "Structured English Query Language"였죠

소단원 ②에서 본 SEQUEL의 'English'가 여기서 실감됩니다. 사장님의 요청 문장과 SQL 한 줄을 나란히 읽어 주면 좋습니다.

넣고·고치고·지우기 — 단어만 바뀝니다

RSELECT — 꺼내 보기 (조회)
CINSERT — 새로 넣기
UUPDATE — 고치기
DDELETE — 지우기
🔁 이 네 가지를 묶어 CRUD(만들기·읽기·고치기·지우기) — 대부분의 서비스는 결국 이 네 동작의 반복입니다
  • 외울 필요는 없습니다. 실제 SQL은 AI가 써 줍니다
  • 목업 데이터의 "이름표-값"을 알아봤던 것처럼, "이 표에서 뭘 꺼내는(넣는) 거구나"를 알아보는 정도면 충분합니다
CRUD는 뒤 실습(Todo 앱)의 뼈대가 됩니다. Todo 앱이 교과서인 이유가 정확히 CRUD 네 동작을 다 쓰기 때문입니다.

표로 생각하기 — 행, 열, 그리고 관계

쇼핑몰 데이터를 표 몇 개로 쪼개면

③ SQL 구경과 데이터의 모양
이 파트가 오늘의 산출물(데이터 설계도)과 직접 연결됩니다.

관계형 데이터베이스는 결국 표입니다

표표 하나 = 한 종류 (예: 상품 표)
행행(row) = 한 건 (예: 딸기 케이크 하나)
열열(column) = 항목 (예: 이름, 가격, 분류)

그리고 표끼리 관계로 잇습니다. 주문 표는 "어떤 상품을 샀는지"를 상품 표를 가리키는 방식으로 적습니다 — 정확히는 각 상품에 붙은 고유 번호(ID)로 가리킵니다.

🔗 이 "표로 나누고 관계로 잇기"가 바로 관계형(relational)이라는 이름의 뜻입니다
엑셀을 떠올리게 하면 대부분 바로 이해합니다. '가리킨다'는 말이 핵심 — 베끼지 않고 번호로 참조합니다.

해 보기 — 쇼핑몰 데이터를 표 셋으로

한 덩어리로 뭉치면 이렇게 됩니다 — "홍길동이 3월 2일에 초코케이크 2개를 12,000원에 샀고, 홍길동의 주소는 …". 주문이 100건이면 홍길동 주소가 100번 적힙니다.

표담는 것예시 한 줄
회원사람 정보1번 · 홍길동 · 서울…
상품파는 것7번 · 초코케이크 · 12,000원
주문언제 누가 무엇을55번 · 1번 회원 · 7번 상품 · 2개 · 3/2
  • 핵심은 주문 표가 이름·주소를 다시 적지 않고 "1번 회원"이라고만 가리키는 것 — 주소가 바뀌면 회원 표 한 곳만 고치면 끝
  • 표를 잇는 이 '번호'를 키(key)라고 부릅니다 — 표와 표를 잇는 고리
직접 설계할 필요는 없습니다. AI에게 "쇼핑몰에 필요한 표들과 그 관계를 그려줘"라고 하면 이런 그림을 만들어 줍니다. 여러분이 할 일은 그 그림을 읽고 "내 서비스엔 어떤 표가 더 필요하지?"를 판단하는 것입니다.

① 일대다(1:N) — 한쪽이 여러 개를 가진다

회원 1명은 주문을 여러 건 남기지만, 주문 1건은 한 회원의 것입니다. 이럴 땐 '주문' 표에 "누구의 주문인지"를 가리키는 칸(회원 번호) 하나만 넣으면 끝입니다.

같은 모양의 예

블로그 글 1개 ↔ 댓글 여러 개 · 유튜브 채널 1개 ↔ 영상 여러 개

구현

'여러 개' 쪽 표에 상대를 가리키는 칸 하나를 둔다. 그게 전부다

🧩 1:N은 칸 하나로 해결됩니다 — 새 표가 필요 없습니다
초보가 자주 하는 실수는 '여러 개'를 한 칸에 콤마로 욱여넣는 것입니다. 다음 슬라이드에서 왜 안 되는지 나옵니다.

② 다대다(N:M) — 연결 표가 필요합니다

학생 1명은 여러 수업을 듣고, 수업 1개도 여러 학생이 듣습니다. 이건 양쪽 표 어디에도 상대를 다 적을 수 없습니다 — 한 칸에 여러 개를 욱여넣으면 검색이 깨집니다.

표학생
→
연결 표수강신청
학생번호 · 수업번호
→
표수업
  • '누가 어떤 수업을 듣는다'는 연결 표를 하나 새로 만들어, 학생 번호와 수업 번호를 짝지어 한 줄씩 적습니다
  • 그러면 N:M이 '연결 표를 사이에 둔 두 개의 1:N'으로 깔끔하게 풀립니다
🧭 판단 감각 하나 — "A 하나가 B 여럿을, 동시에 B 하나도 A 여럿을 갖나?" 그렇다면 N:M이라 중간 표가 필요하고, 한쪽만 여러 개면 1:N
이 판단만 해 주면 표를 만드는 SQL은 AI가 씁니다. 뒤 실습에서 Todo 앱에 '태그'를 넣으면 정확히 이 N:M이 등장합니다.

DB는 왜 그렇게 빠를까 — 색인

책 뒤 '찾아보기'와 같은 트릭

③ SQL 구경과 데이터의 모양
도서관 비유가 여기서 다시 쓰입니다.

책 뒤 '찾아보기'가 정답입니다

두꺼운 전공책 맨 뒤에는 '찾아보기'가 있죠. "삼투압 → 245쪽"처럼요. 그 덕에 처음부터 한 장씩 넘기지 않고 바로 원하는 곳으로 갑니다. DB의 색인(index)이 정확히 이겁니다.

✅ 색인이 있으면

자주 찾는 항목(이메일·상품명)에 색인을 만들어 두면 수백만 건에서도 순식간에 찾는다

❌ 색인이 없으면

처음부터 전부 뒤집니다 — 그래서 느려지죠

  • 비전공자가 외울 건 없습니다. "검색이 느려요" 싶을 때 AI에게 "자주 검색하는 항목에 색인을 넣어줘"라고 하면 됩니다
"왜 느리지?"의 가장 흔한 답이 색인 부재입니다. 개념만 알아 두면 원인을 짚을 수 있습니다.

그런데 색인은 공짜가 아닙니다

색인은 '값 → 행 위치'를 미리 정리해 둔 구조라 수백만 행에서도 몇 단계만에 원하는 행에 닿습니다. 대신 넣고 고칠 때마다 색인도 갱신해야 하고 공간도 듭니다.

⚖️ 빠른 DB는 색인이 많은 DB가 아니라, 실제로 자주 쓰는 검색·정렬에 맞게 최소한만 거는 DB입니다

비전공자 실전 — AI에게 "색인 넣어줘"만 하지 말고, 먼저 실제 화면의 질문을 문장으로 주세요.

"사용자는 자기 주문만 최근순 20개 본다"
→ 이 화면에 맞는 색인을 제안해 줘
개발자로 더 갈 사람만: 많은 관계형 DB의 기본 색인은 B-트리 계열로, 한 노드에 수십~수백 갈래를 둬 세 층만 내려가도 수백만 범위를 가릅니다(O(log n)). DB는 행이 아니라 '페이지' 단위로 읽으므로 실제 속도는 페이지 수·캐시 적중에도 달렸습니다. (user_id, created_at) 같은 복합 인덱스는 순서가 중요하고, WHERE name LIKE '%민수'(앞 와일드카드)나 WHERE LOWER(email)=...(열에 함수)처럼 색인을 못 타는 경우도 있습니다. AI가 제안한 SQL은 실제와 비슷한 데이터로 EXPLAIN을 돌려 어느 색인을 탔는지 확인하는 게 안전합니다.

계좌 이체가 '반쪽만' 되면 — 트랜잭션과 ACID

전부 되거나, 전부 안 되거나

③ SQL 구경과 데이터의 모양
돈·재고·예약을 다룰 때 반드시 필요한 감각입니다.

만 원이 증발하는 순간

은행에서 A가 B에게 만 원을 보냅니다. 컴퓨터가 할 일은 둘입니다.

①A에서
만 원 빼기
→
정전!여기서 멈추면
→
②B에
만 원 넣기
  • ①을 하고 ②를 하기 직전에 정전이 나면? A 돈은 사라졌는데 B는 못 받았습니다
  • 데이터베이스는 이걸 막으려고 여러 동작을 하나의 묶음(트랜잭션)으로 처리합니다
🎯 원칙은 딱 하나 — "전부 되거나, 전부 안 되거나." 중간에 반쪽만 남는 일은 없습니다
이 예는 1983년에 이름 붙은 ACID의 A(원자성)를 그대로 보여 줍니다.

네 가지 약속 — ACID

A원자성 — 반쪽 실행은 없다. 전부 아니면 전부 취소
C일관성 — 규칙에 어긋난 상태로는 안 끝난다
I고립성 — 동시에 여러 명이 만져도 서로 꼬이지 않는다
D지속성 — 한번 됐다고 하면, 정전이 나도 남아 있다
🧭 외울 건 없습니다 — 돈·주문·예약처럼 "틀리면 큰일"인 데이터는 이 성질이 강한 SQL DB가 안전하다, 이 감만 있으면 충분
출처: Wikipedia, "ACID"; Härder & Reuter, 1983. 소단원 ②의 SQL/NoSQL 표에서 SQL의 강점이 '정확성(돈·주문)'이었던 이유가 바로 이것입니다.

마지막 티켓 한 장을 동시에 눌렀다면

친구 둘이 마지막 티켓 한 장을 거의 동시에 누르면? 아무 규칙이 없으면 둘 다에게 팔릴 수 있습니다. 트랜잭션(여러 작업을 '전부 되거나 전부 안 되거나'로 묶기)이 이걸 막습니다.

🗣️ 실전 요구 한 줄 — "동시에 두 명이 마지막 하나를 요청하는 상황도 테스트하고 안전하게 처리해 줘"

어디에 필요한가

돈 · 재고 · 예약처럼 '동시에 두 번' 눌릴 수 있는 곳

⚠️ 착각 금지

ACID는 백업이 아닙니다 — 실수로 지운 걸 되돌려 주진 않습니다. 백업은 따로 챙겨야 합니다

개발자로 더 갈 사람만: '고립' 수준에 따라 더러운 읽기·반복 불가 읽기·유령 읽기가 생길 수 있고 실제 동작은 DB마다 다릅니다(PostgreSQL은 표준 표와 차이가 있어 이름 암기보다 공식 문서와 동시성 테스트로 확인). 재고 차감은 '읽고 → 앱에서 계산 → 쓰기'보다 UPDATE ... SET stock=stock-1 WHERE id=? AND stock>0 처럼 조건을 DB에서 함께 확인하고 영향받은 행 수를 검사하는 게 경쟁에 강합니다(앱 메모리에서만 검사하면 lost update 위험). 초보 프로젝트 최소 기준: 짧은 트랜잭션 하나로 묶기, DB 제약조건 선언, 실패를 정직하게 안내, 백업 복구를 문서로 남기기.
5

정규화와 마이그레이션 — 정리정돈, 그리고 구조 바꾸기

같은 걸 두 번 적지 않기

③ SQL 구경과 데이터의 모양
코드가 1970년에 꿈꿨던 "중복 없이"가 여기서 이름을 얻습니다.

주소를 100군데 고쳐야 한다면

단골 손님의 주소가 바뀌었습니다. 그 손님의 주문 100건에 주소를 매번 따로 적어 뒀다면? 100군데를 다 고쳐야 하고, 하나라도 놓치면 데이터가 서로 안 맞게 됩니다.

🧹 그래서 관계형 DB는 "같은 정보는 한 곳에만 적고, 나머지는 그걸 가리키게" 합니다
  • 손님 정보는 '회원 표'에 한 번만 두고, 주문 표에는 '몇 번 회원'이라고만 적습니다
  • 주소가 바뀌면 회원 표 한 곳만 고치면 끝
  • 이렇게 중복을 걷어내는 정리정돈을 정규화(normalization)라고 부릅니다
🧭 과제에서 데이터의 '모양'을 그릴 때 — "이 정보, 여기저기 똑같이 적히고 있진 않나?" 한 번만 의심해 보세요
출처: Wikipedia, "Database normalization". 이것도 AI가 알아서 해 줍니다. 사람이 할 일은 의심 한 번입니다.

데이터가 커지면 생기는 일 — 색인과 마이그레이션

🐢 조회가 느려졌다

원하는 줄을 찾느라 수백만 줄을 처음부터 훑기 때문. 해법은 앞서 본 색인(인덱스)

🔧 표 구조를 바꿔야 한다

칸 추가·표 분리 등. 이미 데이터가 든 DB의 구조를 안전하게 바꾸는 작업이 마이그레이션(migration)

  • 마이그레이션은 "DB 구조 변경을 Git처럼 이력으로 관리하는 것"이라 생각하면 됩니다 — 되돌리기도 됩니다
⚠️ 딱 하나만 기억 — 칸을 삭제하는 변경은 그 안의 데이터가 영구히 사라질 수 있습니다. 구조를 바꾸기 전엔 반드시 백업
출처: Prisma, "What are database migrations". 비전공자는 "느려지면 색인, 구조를 바꾸면 마이그레이션이라는 게 있다"는 감만 있으면 충분합니다.

네 갈래 — 성격과 쓰는 곳

종류한 줄 설명대표어떤 곳에
문서
Document		JSON처럼 자유로운 덩어리로 저장MongoDB형태가 자주 바뀌는 데이터, 프로필·카탈로그
키-값
Key-Value		"이름표 → 값" 아주 단순·초고속Redis, DynamoDB장바구니·세션·캐시(빠른 임시 저장)
컬럼
Column		대량 분석에 강한 열 중심Cassandra, HBase로그·대규모 통계 분석
그래프
Graph		점과 선으로 '관계'를 저장Neo4j소셜 네트워크("친구의 친구")
  • 그래프 DB는 "친구의 친구의 친구"처럼 연결을 따라가는 데 최적이라 소셜 네트워크가 즐겨 씁니다
  • 키-값은 너무 단순해서 오히려 엄청나게 빠르고, 그래서 쇼핑몰 장바구니 같은 데 쓰입니다
출처: MongoDB, "NoSQL Databases Explained"; AltexSoft. 키-값(Redis)은 소단원 ④에서 세션 저장소로 다시 등장합니다.

그래서 나는 뭘 쓰나 — 한 줄 기준

표로 잘 정리되고 관계가 분명하면

(사용자·주문·상품처럼) → SQL(관계형)

형태가 자주 바뀌고 아주 대규모면

→ NoSQL

비전공자의 첫 서비스 기본값은 SQL
그중에서도 PostgreSQL이 무난합니다 — 자료가 가장 많고, 필요하면 유연한 형식도 지원해서 나중에 곤란해질 일이 적습니다
  • 물론 정답은 내 데이터의 모양에 달려 있습니다
출처: TheLinuxCode, "SQL vs NoSQL in 2026"; DEV, "When to Use SQL vs NoSQL 2026". 소단원 ⑥의 무료 DB 비교에서 Supabase(Postgres)가 첫 후보로 나오는 근거입니다.

❓ 미니 퀴즈 — 이 데이터, 어떻게 다룰까

Q1. 사용자·주문·상품이 서로 관계로 얽힌 쇼핑몰
A1. SQL(관계형) — 관계가 분명하고 정확성이 중요하다
Q2. "친구의 친구"를 따라가는 소셜 관계
A2. 그래프 NoSQL (예: Neo4j)
Q3. 잠깐 쓰고 버리는 장바구니(초고속·단순)
A3. 키-값 NoSQL (예: Redis)
세 문제 모두 앞 표에서 그대로 나옵니다. 정답을 맞히는 것보다 "왜 그 성격인가"를 말로 설명하게 하는 게 좋습니다.

❓ 미니 퀴즈 — 이 습관, 안전할까

Q4. 사용자가 친 값을 명령문에 그대로 이어 붙인다
A4. X — SQL 주입! 파라미터화로 처리해야 한다 (소단원 ⑤)
Q5. 비밀번호를 그대로(평문) 저장한다
A5. X — 해시로. 야후 보이스의 교훈 (소단원 ④·⑤)
Q6. 정기적으로 백업(자동 또는 직접)을 해 둔다
A6. O — 토이 스토리 2의 교훈 (소단원 ⑤)
세 습관의 근거는 소단원 ⑤에서 실화로 나옵니다. 여기서는 "이건 위험하다"는 감만 심어 두고 넘어갑니다.
