모두콘 문서를 검색 재료로 바꾸는 단계입니다. 여기서 가장 흔한 사고는 성능이 아니라 '공간이 다른 벡터'입니다.

과거 스크립트를 그대로 돌리면 384차원이 남습니다

과거에 쓰던 경로는 BGE 384차원 벡터를 남깁니다. 화면에서 숫자 배열은 정상처럼 보이지만, 질문이 다른 공간에서 만들어진다면 '가까움'이라는 판단 자체가 성립하지 않습니다.

모델onnx-community/embeddinggemma-300m-ONNX

첫 방문모델 파일 약 200MB · 첫 로드 실측 5~15초

1

캐시는 재방문 경험의 계약입니다

성능 장식이 아닙니다

④ 임베딩과 벡터스토어
모델 파일을 매 질문마다 다시 내려받으면 검색을 시작하기도 전에 사용자를 기다리게 만듭니다.

HTTP 캐시만 믿기 어려운 이유

  • Hugging Face의 resolve URL이 서명된 CDN URL로 리다이렉트되며 캐시 적중이 불안정할 수 있습니다
  • 따라서 원래 URL을 키로 삼아 Cache Storage에 직접 보관하고, 캐시 적중 때에는 완료 상태와 캐시 사용 여부를 즉시 알리는 편이 낫습니다
  • Cache Storage가 실패할 수 있으므로 한 번의 재시도 뒤에도 실패하면 다운로드를 계속하는 경로를 남겨 두고, 브라우저 환경에 따라 저장을 보장한다고 단정하지 않아야 합니다
🎯 캐시 전략의 목적은 — 사용자가 다시 방문했을 때 모델 준비가 아니라 질문 자체에 집중하게 만드는 것
캐시를 "빠르게 하는 기술"이 아니라 "재방문 경험의 약속"으로 보는 관점이 이 슬라이드의 요지입니다.
2

기본 파이프라인이 멈추는 지점을 우회합니다

토크나이저와 세션을 분리

④ 임베딩과 벡터스토어
브라우저에서 pipeline()을 곧바로 호출하는 방식은 간결해 보이지만 실패할 수 있습니다.

no_gather_q4 경로로 역할을 분리합니다

기본 q4 또는 q8 경로가 선택되면 WASM ONNX Runtime이 GatherBlockQuantized 연산을 지원하지 않아 실패할 수 있습니다. 해결은 모델 전체를 포기하는 일이 아니라 역할을 분리하는 일입니다.

1토크나이저는 transformers.js의 AutoTokenizer로 사용
2추론 세션은 model_no_gather_q4.onnx와 데이터 파일을 ONNX Runtime에 직접 넘긴 뒤 WASM 실행 공급자를 지정
// rag.ts의 핵심 경로를 짧게 확인합니다.
const tokenizer = await AutoTokenizer.from_pretrained(modelId);
const session = await ort.InferenceSession.create(modelUrl, {
  executionProviders: ["wasm"],
});
🗣️ 에이전트에게는 오류 문구만 전달하지 말고 — 토크나이저와 ORT 세션을 분리해야 하는 이유와 no_gather_q4 파일을 써야 하는 조건을 함께 요구해야 합니다
이 우회는 문서 임베딩과 브라우저 질문 임베딩이 같은 모델 계열의 계산을 거치게 하는 조건이기도 합니다.

평균을 만들고 길이를 맞춰야 비교가 공정해집니다

모델 출력의 last_hidden_state는 토큰마다 하나씩 생기므로, 문장 하나를 대표하는 벡터로 줄이는 규칙이 필요합니다.

1mean pooling
attention_mask가 가리키는 실제 토큰만 평균
→
2L2 정규화
벡터 길이를 1로
  • 이 순서가 없으면 패딩 토큰이 문장 표현에 섞이거나, 문장 길이 차이가 점수에 과도하게 영향을 줄 수 있습니다
  • 정규화된 벡터끼리는 내적이 곧 코사인 유사도로 읽히므로, 검색 단계가 별도 길이 보정을 반복하지 않아도 됩니다
🗣️ 에이전트에게 명시할 것 — 출력 텐서의 첫 값만 사용하지 말 것 · 마스크를 분모와 분자에 함께 반영할 것 · 0으로 나누는 경우를 방어할 것
숫자로 바꾸는 과정의 작은 생략이 검색 결과 전체의 편향으로 이어질 수 있습니다.

차원이 같다고 비교가 되는 것은 아닙니다

  • 과거 BGE 경로는 384차원, 현재 모두콘 코퍼스는 Gemma의 768차원 — 두 결과를 섞으면 계산이 실패하거나 의미 없는 거리를 만듭니다
  • 더 위험한 경우는 차원이 우연히 같아도 서로 다른 모델의 공간을 섞는 경우입니다 — 숫자는 나오지만 가까움의 뜻이 보장되지 않습니다
문서 벡터를 만들 때 쓴 모델 · pooling 방식 · 정규화 규칙을
질문 임베딩에도 똑같이 적용합니다
🧭 기존 스크립트가 있다는 이유만으로 재실행하지 말고, 현재 코퍼스의 차원과 생성 모델을 먼저 확인하는 태도가 필요합니다
벡터스토어에 이 사실을 확인할 수 있는 생성 경로를 남겨 두어야 합니다.
3

실습 3 — 문서 벡터스토어를 만듭니다

그리고 검색으로 되짚어 확인합니다

④ 임베딩과 벡터스토어
현재 경로는 embed-docs-browser-path.mjs 입니다.

생성 조건을 고정합니다

embed-docs-browser-path.mjs는 Node 환경에서 같은 모델의 feature-extraction pipeline을 사용하고, dtype:"q4", pooling:"mean", normalize:true 조건으로 문서 벡터를 만들며 결과를 app/public/moducon-docs.json에 둡니다.

모두콘 공개 문서 청크 배열을 읽어 브라우저 RAG용 벡터스토어를 만드는
embed-docs-browser-path.mjs를 작성합니다. onnx-community/embeddinggemma-300m-ONNX를
사용하고 dtype은 q4, pooling은 mean, normalize는 true로 고정합니다.
각 청크의 id, text, url, section을 보존하고 vector를 추가하여
app/public/moducon-docs.json에 저장합니다. 기존 BGE 384차원 경로는 사용하지 말고,
생성 후 모든 vector가 768차원인지 검사하는 검증도 포함합니다.
✅ 생성된 스크립트의 모델 ID, q4 설정, mean pooling, 정규화, 출력 필드를 한 줄씩 대조합니다
확인은 차원 수만 대조하는 데서 멈추지 않고, 모델 ID와 pooling·정규화 규칙까지 문서 생성과 질문 처리 양쪽에서 같은지 점검합니다. 그래야 상위 결과가 우연히 익숙한 표현을 골랐는지, 실제로 비교 가능한 좌표에서 가까운 청크를 골랐는지 분리해 읽을 수 있습니다.

스팟체크 — 검색 결과를 거꾸로 읽습니다

생성 명령이 성공했다는 메시지만으로 벡터스토어가 올바르다고 판단할 수 없습니다.

python3 check_retrieval.py
1예상 질문을 넣고 top-1과 top-3에 어떤 청크가 놓이는지 읽습니다
2문서에 근거가 있는 질문(모두콘이 무엇인지·참가 방법·발표 신청)은 관련 청크가 상위에 나타나는지 확인
3문서 범위 밖 질문은 억지로 관련 청크가 정답처럼 보이지 않는지도 관찰
⚠️ top-1이 기대와 다를 때 곧바로 임계값을 바꾸기보다 — 질문과 문서가 같은 임베딩 경로를 지나갔는지, 청크의 사실 경계가 적절한지부터 역순으로 점검합니다
여기서 확인하는 대상은 모델의 지능이 아니라 문서 청크·생성 모델·정규화·검색 점수의 연결입니다.

더 깊이 갈 사람을 위한 길

WebGPU 백엔드

WASM 대신 WebGPU를 executionProviders에 지정해 보면, 지원 브라우저에서 임베딩 준비와 계산이 어떻게 달라지는지 관찰할 수 있습니다

양자화 비교

모델 파일의 양자화를 q4와 q8로 바꿔 가며 검색 상위 결과의 순서 변화를 기록해 보는 것도 같은 코퍼스로 할 수 있는 실험입니다

❓ 이해도 확인

Q1. 문서 384차원, 질문 768차원이면 무슨 일이 생기나?
A1. 배열이 있어도 비교 계약이 성립하지 않는다. 계산이 실패하거나 의미 없는 거리가 나온다. 차원이 우연히 같아도 다른 모델의 공간이면 마찬가지.
Q2. 기본 pipeline() 호출이 실패할 수 있는 이유와 우회는?
A2. WASM ONNX Runtime이 GatherBlockQuantized를 지원하지 않는다. 토크나이저(AutoTokenizer)와 ORT 세션(model_no_gather_q4.onnx)을 분리해 WASM 공급자를 지정한다.
Q3. mean pooling과 L2 정규화를 하는 이유는?
A3. 패딩 토큰이 섞이거나 문장 길이가 점수에 과도하게 영향을 주는 것을 막는다. 정규화 뒤에는 내적이 곧 코사인 유사도가 된다.
Q4. top-1이 기대와 다를 때 먼저 할 일은?
A4. 임계값 조정이 아니라 같은 임베딩 경로를 지났는지, 청크의 사실 경계가 적절한지 역순 점검.
Q4의 습관이 소단원 ⑤·⑧에서 반복됩니다.
