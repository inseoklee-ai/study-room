미완성 PRD와
설계 대화

AI가 코드를 작성할 수 있다고 선택들이 내 의도와 같아지지는 않습니다

"내 파일을 정리하고 코드를 고치는 에이전트를 만들어 줘"에는 방향이 있지만 구현에 필요한 선택은 아직 많습니다.

일부가 비어 있는 설계 자료로

  • 아직 정하지 않은 것 — 터미널에서 쓸지 웹 화면에서 쓸지, 어떤 폴더까지 읽을지, 파일을 바꾸기 전에 어떻게 확인받을지
  • 완성 코드를 따라 실행하는 대신 — AI와 대화하며 미결정 사항을 구체화하고, 합의한 내용을 문서에 남긴 뒤 자기 하네스를 구현합니다
README와 설계 문서를 읽고, 아직 정하지 않은 것부터 같이 정하자.
코드는 아직 만들지 마.
앞 절에서 열어 둔 harness-design-kit 폴더를 Claude Code 또는 OpenCode의 작업 폴더로 그대로 사용합니다.
1

문서의 역할

각 문서의 역할에 맞춰 연결합니다

② 설계 대화
PRD는 코드의 클래스 이름을 모두 정하는 문서가 아니라, 구현이 해결해야 할 문제와 범위를 설명하는 기준입니다.

일곱 문서

문서대화에서 맡는 역할
README.md자료를 사용하는 순서와 시작점
AGENTS.md, CLAUDE.md개발 도우미가 따를 협업 지침
PRD.md사용자·업무·제품 요구사항과 미결정 선택
DECISIONS.md선택한 내용과 선택 이유
INTERFACES.md구성요소가 주고받을 입력·출력 약속

📌 처음부터 모든 문서를 완벽하게 채울 필요는 없습니다 — 사용자와 작업을 정하면 PRD가, 그 결정을 구현하려고 입력·출력을 정하면 인터페이스 문서가 구체화됩니다. 같은 설명을 여러 파일에 길게 복제하기보다 각 문서의 역할에 맞춰 연결합니다
PRD는 Product Requirements Document의 약자입니다.

질문·기록·합의의 반복

선택을 숨은 가정으로 남기지 않기

② 설계 대화
PRD에는 선택을 추적할 ID가 있습니다.

결정 ID와 상태

구분뜻
D01 · D02 · D03 …사용자와 업무 · 플랫폼 · 언어처럼 하나의 결정 대상을 가리킴
OPEN아직 결정하지 않음
CHOSEN선택을 합의함
DEFERRED필요 없다는 뜻이 아니라 나중에 다루기로 함
학생: 우선 내가 터미널에서 쓸 거야. 실습 폴더의 자료를 찾아보고,
      나중에는 코드도 고치고 싶어.
AI:   첫 동작은 파일을 읽고 요약하는 작업으로 잡고,
      쓰기와 테스트 실행은 그다음 단계로 확장할 수 있습니다.
학생: 좋아. 읽기는 실습 폴더 안으로 제한하자. 이 선택과 이유를 기록해 줘.
🎯 이 대화는 최종 정답이 아니라 범위를 좁히는 예입니다 — 중요한 것은 선택을 숨은 가정으로 남기지 않는 것
AI가 선택지를 제시해도 곧바로 추천안을 받아들일 필요는 없습니다. 다른 학생은 웹 화면이 필요할 수 있고 익숙한 언어도 다를 수 있습니다.

AI가 맡을 일과 학생이 판단할 일

🤖 AI에게 맡길 수 있는 일

대안을 설명하고, 결정의 영향을 짚고, 합의한 내용을 문서로 작성하는 일

🧑‍🎓 학생이 판단할 일

사용할 장면, 허용할 행동, 감수할 불편

💬 기술적 차이가 낯설다면 "추천해 줘"에 이어 "내 작업에서는 왜 그 선택이 나은지 설명해 줘"라고 요청할 수 있습니다
선택한 이유를 남기는 것이 이 절의 습관입니다.
3

지침 파일과 실제 행동

지침은 유도이지 강제 장치가 아닙니다

② 설계 대화
도구마다 파일 탐색과 적용 규칙이 다릅니다.

같은 폴더 이름이 같은 행동을 보장하지 않습니다

  • Claude Code는 CLAUDE.md를 프로젝트 지침으로 읽으며 다른 파일을 가져오는 문법도 제공합니다 — AGENTS.md를 자동으로 같은 방식으로 읽는다고 가정하지 말고 자료의 CLAUDE.md가 공통 지침을 어떻게 연결하는지 확인
  • OpenCode는 AGENTS.md를 통해 프로젝트 지침을 제공하는 방식을 안내합니다
  • "미결정 사항을 먼저 질문하라"는 문장은 AI의 행동을 유도하는 지침입니다 — 제품에 구현한 필수 입력 검사처럼 강제로 실행을 막는 장치는 아닙니다
내가 답하지 않은 선택은 OPEN으로 남겨 줘.
합의한 내용만 기록하고 다음 질문을 해 줘.
🔍 문서를 읽었다고 말하는지만 보지 말고 — PRD의 미결정 항목을 실제로 짚는지 확인합니다. 질문이 너무 많으면 지금 결정할 것과 미룰 것을 나누되 중요한 결정을 AI가 조용히 대신 정하게 두지는 않습니다
AI가 질문 없이 선택을 채우거나 구현을 시작하려 하면 위 문장으로 바로잡으세요.

구현으로 넘어가는 기준

첫 구현 전 합의D01~D07
미뤄도 됨D08 추가 제공자
D09 확장 기능
  • D01~D07 — 사용자·업무, 플랫폼, 언어, 첫 모델 제공자, 최초 도구와 작업 범위, 승인 방식, 세션
  • 합의가 끝나면 학생이 명시적으로 구현을 요청합니다
합의한 설계로 첫 읽기 작업부터 구현하자. 실행 결과를 보고 다음 기능으로 넓히자.
📌 지금 단계에서는 아직 그 요청을 서두르지 않습니다. 설계 문서는 처음의 빈칸을 채우고 끝나는 제출물이 아니라 — 구현 중 발견한 문제와 선택 변경을 반영하며 계속 사용하는 작업 기준입니다
다음부터 플랫폼과 언어, 기능 범위, 실행 흐름을 차례로 검토합니다.

❓ 이해도 확인

Q1. DEFERRED는 무슨 뜻인가?
A1. 필요 없다는 뜻이 아니라 나중에 다루기로 했다는 뜻.
Q2. "미결정은 먼저 질문하라"는 지침의 한계는?
A2. 행동을 유도하는 지침일 뿐 강제로 실행을 막는 장치가 아니다. AI가 선택을 채우면 바로잡아야 한다.
Q3. 첫 구현 전에 합의할 범위는?
A3. D01~D07. 추가 제공자(D08)와 확장 기능(D09)은 미뤄도 된다.
Q2가 문서 기반 협업에서 가장 오해하기 쉬운 지점입니다.
