네트워크 기본기

주소를 넣으면 화면이 뜨기까지 — 인터넷의 뼈대

백엔드를 이해하려면 인터넷이 어떻게 연결되는지 최소한만 알면 됩니다. 네트워크 엔지니어가 될 필요는 없습니다. 이 흐름을 알면 AI가 만든 것을 이해하고, 문제가 생기면 어디를 볼지 알고, AI에게 제대로 요청할 수 있습니다.

  • 여기에 자물쇠의 원리·패킷의 여행·요청 한 번의 여정·상태 코드를 더한다
🎯 오늘의 한 문장 — 주소를 넣으면 화면이 뜨는 그 1초 안에서 무슨 일이 벌어지는지 본다.
네 조각은 순서대로 이어집니다. 이름을 번호로 바꾸고, 그 번호의 컴퓨터에 닿고, 알맞은 문으로 들어가, 공통 언어로 대화합니다. 이 뼈대만 잡으면 나머지는 살을 붙이는 일입니다.
1

이름을 주소로

사람이 외우는 이름을, 컴퓨터가 아는 번호로

도메인 · DNS · IP 주소
모든 컴퓨터에는 번호가 있지만 사람은 번호를 외우지 못합니다. 그 사이를 이어 주는 것이 도메인과 DNS입니다. 이 첫 조각이 나머지 세 조각의 출발점입니다.

📖 도메인은 이름, DNS는 전화번호부

사람이 외우는도메인
mysite.com
→ DNS →
컴퓨터가 아는IP 주소
142.250.72.14
  • 모든 컴퓨터엔 번호(IP 주소)가 있다 — 외우기 불편하고(IPv6는 더 길다) 수시로 바뀌기도
  • 도메인 = 사람이 외우는 가게 이름 · DNS = 이름을 번호로 바꿔 주는 전화번호부
  • 도메인은 사는 것(1년 만 원 안팎) — 등록 후 "이 도메인은 저 서버(IP)를 가리켜라"라고 연결
⚠️ 흔한 함정 — 왜 바로 안 바뀌지? DNS는 답을 한동안 기억(캐시)하므로, 가리키는 곳을 바꿔도 즉시 반영 안 됨(전파에 몇 분~몇 시간).
도메인은 등록 기관에서 빌리는 이름입니다. DNS 설정이란 그 이름 옆에 "실제 서버의 번호"를 적어 두는 일입니다. 캐시 때문에 변경이 늦게 보이는 것은 고장이 아니라 정상 동작입니다.

🧱 도메인은 '별칭' 그 이상 — 다섯 가지 힘

이름과 실제 서버 사이에 '한 겹'을 두는 추상화. 앞(도메인)은 그대로, 뒤(서버·IP)는 바꿀 수 있다.

힘무엇을 할 수 있나
① 이사 자유서버를 옮겨도 주소는 그대로 (DNS 한 줄만 고침)
② 여러 서버하나의 이름 → 여러 서버 (부하 분산·CDN)
③ 구조화서브도메인으로 나눔 (api.·blog.·shop.)
④ 신뢰의 증표이메일 @ 뒤·HTTPS 인증서가 도메인에 발급됨
⑤ 보유·이동내 이름으로 보유 — 호스팅을 바꿔도 그대로
🔒 오해 — 자물쇠(HTTPS)는 '믿을 만한 회사'라는 증명이 아니라 '이 도메인의 주인과 암호를 걸어 통신 중'이라는 뜻일 뿐. 피싱도 자물쇠를 붙일 수 있다 → 도메인 철자 자체를 확인.
도메인이 별칭에 불과하다면 이 다섯 가지 힘이 안 나옵니다. 이름과 실체 사이에 한 겹을 둔 덕분에 뒤를 자유롭게 갈아 끼울 수 있습니다. 자물쇠는 신뢰의 보증이 아니라 암호화의 표시라는 점을 꼭 기억하세요.
2

그 주소엔 무엇이

늘 켜진 컴퓨터, 그리고 안과 밖의 경계

서버 · 호스팅 · 클라우드 · 내부망/외부망
주소가 가리키는 곳에는 24시간 켜진 컴퓨터가 있어야 합니다. 그리고 그 컴퓨터가 우리 집 안에 있는지 세상에 열려 있는지가 '왜 내 링크가 안 열리지?'를 가릅니다.

🖥️ 서버 = 24시간 켜진 컴퓨터

  • 서버 = 내 서비스 파일·데이터를 올려 두고 24시간 켜진 컴퓨터
  • "노트북을 닫으니 꺼진" 이유가 여기 — 노트북은 24시간 켜 두는 물건이 아님
  • 그래서 호스팅(늘 켜진 컴퓨터를 빌려 씀)을 쓴다
예전회사가 서버를 직접 구입
전원·냉방·보안·고장까지
→
지금 · 클라우드거대 서버 창고에서
필요한 만큼만 빌림
클라우드(아마존·구글) — 고장·보안·전원은 그쪽이 맡는다. 비전공자가 할 일은 "어디에 올릴지"만 고르는 것.
서버는 특별한 기계가 아니라 그저 늘 켜져 있는 컴퓨터입니다. 클라우드는 그 컴퓨터를 필요한 만큼만 빌려 쓰는 방식이고, 관리의 번거로움을 대신 맡아 줍니다.

🚪 내부망과 외부망 — 문지기는 공유기

내내부망(LAN) — 집·회사 안 공유기로 묶인 '우리끼리' 네트워크. 192.168.0.5 같은 집 안 전용 주소(사설 IP)
외외부망(WAN=인터넷) — 그 바깥의 전 세계. 밖에서 볼 때 우리 집은 공유기 하나(공인 IP 하나)로만 보임
문문지기 = 공유기(NAT) — 안→바깥은 자유롭지만 바깥→안은 기본적으로 못 들어옴(그래서 평소 안전)
localhost:3000이 나한테만 보이고 친구에겐 안 보이는 이유 = '내부망의 내 컴퓨터'에만 있으니까. 서비스를 '세상에 연다' = 내부망의 무언가를 외부망에서 닿게 만드는 일.
맨 처음 만나는 '안 열리는 링크'는 대부분 이 경계 때문입니다. 클라우드 서버에 올리거나 터널로 이어야 바깥에서 닿을 수 있습니다. 안전과 불편이 같은 원리에서 나옵니다.
3

어느 문으로

한 서버, 여러 일 — 요청을 알맞은 창구로

포트 · 방화벽
서버 한 대는 웹·메일·데이터베이스를 동시에 처리합니다. 어떤 요청을 어느 창구로 보낼지 정하는 번호가 포트이고, 그 문을 지키는 경비가 방화벽입니다.

🔢 포트 = 호실 번호, 방화벽 = 경비

  • 서버 한 대는 여러 일을 동시에 (웹·메일·DB…) — "이 요청은 어느 창구로"를 정하는 게 포트
  • IP가 '건물 주소'라면 포트는 '호실 번호'(0~65535번). 웹은 보통 80(HTTP)·443(HTTPS)
  • localhost:3000의 3000이 포트 번호
  • 방화벽 = 그 문을 지키는 경비 (필요 없는 문은 닫아 둠)
"내 컴퓨터에선 되는데 밖에선 안 열려요"의 흔한 원인 — 열려야 할 문(포트)이 방화벽에 막힘. 배포 플랫폼을 쓰면 대개 알아서 열어 줌.
포트는 같은 주소 안의 여러 창구를 구분하는 번호입니다. 방화벽은 쓰지 않는 창구를 닫아 위험을 줄입니다. 배포 도구는 이 설정을 대신해 주므로 비전공자가 직접 만질 일은 드뭅니다.
4

무슨 말로

브라우저와 서버가 대화하는 공통 언어

HTTP · HTTPS · API
주소를 찾고 문으로 들어갔으면 이제 대화할 차례입니다. 그 공통 언어가 HTTP이고, 대화를 암호로 감싼 것이 HTTPS입니다.

💬 HTTP — "이 페이지 줘" → "여기 있어"

[브라우저의 요청]
GET  /products      ← "products 목록 페이지를 줘(GET)"
Host: mysite.com

[서버의 응답]
200 OK              ← "성공! 여기 있어"
(그리고 화면 내용이나 데이터가 따라옴)
  • HTTPS = 이 대화를 암호로 감싼 안전한 버전 — 주소창 자물쇠 아이콘
  • HTTP는 엽서처럼 훔쳐볼 수 있지만 HTTPS는 밀봉된 봉투 — 로그인·결제엔 필수
  • 참고 — 프로그램끼리 정해진 창구로 요청·응답을 주고받는 약속 = API. "AI야, 지도 API 붙여줘"의 그 API
없으면 "안전하지 않음" 경고가 뜬다. 요즘 배포 플랫폼은 자물쇠(SSL 인증서)를 자동으로 붙여 준다.
HTTP는 사람이 읽을 수 있을 만큼 단순한 텍스트 대화입니다. HTTPS는 그 대화를 봉투에 넣어 밀봉합니다. API는 사람 화면 대신 프로그램끼리 이 대화를 나누는 창구입니다.

🔐 자물쇠의 원리 — 우편함과 열쇠

공개키 = 우편함 투입구누구나 편지를 넣을 수 있음
(공개해도 됨)
↔
개인키 = 유일한 열쇠우편함을 여는
서버만의 열쇠
  • 누구나 공개키로 잠글 수는 있지만 열 수 있는 건 개인키를 가진 서버뿐 → 중간에서 엿봐도 못 읽음
  • 실제론 이 방식이 느려서, 접속 초반에 공개키로 '오늘만 쓸 임시 열쇠(세션 키)'를 안전하게 주고받고 그다음부턴 빠른 방식으로 대화 — 첫 인사 = TLS 핸드셰이크
  • 진짜 사이트인지는 인증기관(CA)이 서명한 인증서로 보증
이 복잡한 과정을 배포 플랫폼이 자동으로 처리해 준다.
공개키로 잠그고 개인키로만 여는 비대칭 구조가 핵심입니다. 다만 느리기 때문에 처음에만 이 방식으로 임시 열쇠를 나누고, 이후엔 빠른 대칭 방식으로 대화합니다. 인증서는 그 상대가 진짜인지 보증하는 신분증입니다.

📦 패킷 — 데이터는 잘게 쪼개져 여행한다

데이터는 통째로가 아니라 작은 조각(패킷)으로 쪼개져 각자 여행 후 도착지에서 다시 조립된다.

✉️우편 비유 — 긴 편지를 인덱스카드 여러 장에 나눠 적고 '보낸이·받는이·몇 번째'를 표시 (패킷도 머리표+내용)
🍕피자 비유 — 조각으로 나눠 보내면 한 조각만 없어져도 그 조각만 다시 보내면 됨
🧭내비 비유 — 패킷들은 서로 다른 길로 감(한 길이 막히면 우회) → 인터넷 일부가 고장 나도 전체가 안 멈춤
이 공통 규칙이 TCP/IP. 덕분에 수십억 대 기기가 같은 회선을 동시에 나눠 쓴다.
큰 데이터를 조각으로 나누면 손실에 강하고 회선을 함께 쓰기 좋습니다. 세 비유는 각각 조각의 표시, 재전송, 우회를 설명합니다. 이 약속이 TCP/IP이고 인터넷 전체가 이 위에서 돌아갑니다.

🚚 요청 한 번의 여정 — 엔터를 치면, 1초 안에

1브라우저가 DNS에 물음 — "mysite.com IP가 어디죠?" (택배: 배송지 검색)
2IP를 받아 서버에 연결 (443번 문, HTTPS 자물쇠) (택배: 차량 이동)
3"이 페이지 줘"라고 HTTP 요청 → 서버가 화면·데이터를 응답 (택배: 요청·수령)
4브라우저가 그 응답을 화면으로 그림 (택배: 포장 풀기)
목업 데이터는 이 여정 없이 화면에 미리 넣어 둔 것. 진짜 서비스는 매번 이 왕복이고, 백엔드는 그 왕복의 반대편 끝에서 대답하는 쪽.
네 조각이 여기서 하나로 이어집니다. 이름을 번호로, 번호의 서버에 연결, 공통 언어로 요청·응답, 마지막으로 화면 렌더링. 이 왕복의 반대편이 다음 소단원의 주제인 백엔드입니다.

🚦 HTTP 상태 코드 — 인터넷의 신호등

맨 앞 숫자만 보면 됨 — 2xx 성공 / 3xx 다른 데로 / 4xx 요청(나)의 잘못 / 5xx 서버의 잘못.

코드뜻한마디
200 OK성공"다 잘됐어"
301/302주소 이동"그 페이지 저쪽으로 옮겼어"
401 Unauthorized로그인 필요"누구세요?"
403 Forbidden권한 없음"누군지 알지만 넌 안 돼" (VIP 바운서)
404 Not Found없는 페이지"그런 페이지 없어"
429 Too Many Requests너무 많은 요청"천천히 좀"
500 Internal Server Error서버 오류"네 잘못 아냐, 내가 터졌어"
실전 팁 — 4xx면 내 요청을 고치고, 5xx면 서버(만든 사람) 문제. AI에게 "500 에러가 나"라며 화면 에러를 그대로 붙이면 원인을 훨씬 잘 찾음.
재미로 418 "I'm a teapot"은 1998년 만우절 농담이고, 451은 소설 제목에서 따온 "법적 이유로 막힌 콘텐츠"입니다. 앞자리 하나만 봐도 방향이 잡힙니다. 4로 시작하면 내 쪽, 5로 시작하면 서버 쪽입니다.

🧠 미니 퀴즈 — 이 상황엔 몇 번?

없는 페이지에 들어감 → 404 Not Found
로그인 안 하고 진입 → 401 Unauthorized
로그인했지만 권한 없음 → 403 Forbidden
서버가 터짐 → 500 Internal Server Error
정상 → 200 OK
401과 403의 차이가 핵심 — 401은 "누구세요?"(신원 미확인), 403은 "넌 안 돼"(신원은 알지만 권한 없음).
401과 403을 헷갈리기 쉽습니다. 401은 아직 누구인지 모르니 로그인하라는 뜻이고, 403은 누구인지 알지만 그 사람에겐 권한이 없다는 뜻입니다. VIP 바운서 비유가 403입니다.

🔍 직접 해보기 — 검사 → 네트워크 탭

1아무 웹사이트에서 우클릭 → '검사(Inspect)'
2'네트워크(Network)' 탭을 연다
3새로고침 → 맨 위 줄 Status에 200 등이 보임
4화면이 안 뜰 땐 여기서 빨간 줄(4xx·5xx)을 찾으면 단서
AI에게 도움 청할 때 이 화면을 함께 주면 정확한 답을 받는다. 문제의 위치가 데이터로 보이기 때문.
네트워크 탭은 브라우저가 실제로 주고받은 요청·응답을 그대로 보여 줍니다. 빨간 줄 하나가 문제의 위치를 정확히 가리키므로, 막연히 "안 돼요" 대신 상태 코드를 함께 전달하면 훨씬 빨리 해결됩니다.

🎯 이해도 확인 질문

Q1. 도메인과 DNS는 각각 무엇에 비유되었나?
Q2. localhost:3000이 나한테만 보이는 이유는? (내부망/외부망으로 설명)
Q3. IP가 '건물 주소'라면 포트는 무엇에 해당하는가?
Q4. HTTPS의 자물쇠에서 공개키와 개인키는 각각 어떤 역할인가?
Q5. 4xx 오류와 5xx 오류는 각각 누구의 잘못인가?
답이 바로 떠오르지 않으면 앞 장으로 돌아가 확인해 보세요. Q4의 공개키·개인키와 Q5의 4xx/5xx 구분이 오늘의 핵심을 가장 잘 가립니다.

✅ 정답 & 해설

A1. 도메인 = 사람이 외우는 가게 이름, DNS = 이름을 번호(IP)로 바꿔 주는 전화번호부.
A2. 그 서비스가 내부망의 내 컴퓨터에만 있어서. 공유기(NAT)가 바깥→안을 막으므로, 세상에 열려면 외부망에서 닿게 만들어야 함.
A3. 호실 번호 — 한 서버(건물)의 여러 창구를 구분. 웹은 보통 80·443, localhost:3000의 3000이 포트.
A4. 공개키 = 누구나 넣는 우편함 투입구(잠그기), 개인키 = 서버만 가진 유일한 열쇠(열기).
A5. 4xx = 요청(나)의 잘못, 5xx = 서버(만든 사람)의 잘못.
A2와 A4를 자기 말로 설명할 수 있으면 오늘 목표는 달성입니다. 특히 A5의 구분은 문제가 생겼을 때 어디부터 봐야 할지 바로 알려 줍니다.
