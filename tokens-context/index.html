🔙 강의를 열었던 질문으로

"문서를 더 많이 넣었는데 왜 답은 더 좋아지지 않았을까?" — 역사는 여기서 활용가의 책상 위로 내려옵니다.

  • 어텐션 = 한 토큰이 다른 모든 토큰을 참고 → 비교 수 ≈ n × n (토큰 수의 제곱)
  • 입력을 2배로 늘리면 계산은 2배가 아니라 4배 가까이 불어난다
  • 앞서 본 KV cache가 그 비용이 쌓이는 자리 — 대화가 길수록 Key·Value를 계속 들고 있어야 함
긴 입력 = 긴 계산 = 비용 + 대기 시간트랜스포머를 강하게 만든 구조가, 동시에 우리가 치르는 비용·한계의 정체
그래서 프롬프트를 다르게 봅니다. "글자를 몇 자 썼는가"가 아니라 "토큰을 몇 개 썼고 어디에 배치했는가". 이 두 가지가 이 강의가 향하던 실용의 목적지입니다.
1

토큰 — 비용과 문맥의 단위

비용은 글자 수가 아니라 토큰 수에 가깝게 움직인다

Token · 한국어의 함정
토큰은 모델이 글을 다루는 가장 작은 단위이자, 우리가 비용과 문맥을 세는 단위입니다. 문장이 토큰으로 쪼개지는 과정은 앞서 봤고, 여기서는 그 쪼개짐이 왜 비용과 한계가 되는지를 봅니다.

🔤 사람의 "한 문장"이 모델에겐 다르다

  • 사람에겐 한 문장이 자연스러운 단위지만 모델에겐 그렇지 않다
  • 한국어는 조사·어미·띄어쓰기·희귀 전문용어 때문에 체감보다 토큰이 늘어난다
  • "10쪽이라 별로 안 길다"는 감각이 API 비용·응답 지연에선 맞지 않을 수 있다
비용은 글자 수가 아니라 토큰 수에 가깝게 움직이고
긴 입력은 곧 긴 계산이다
모델별 토큰화·한도·가격은 제공사·시점마다 다르다. 숫자를 외우는 대신 요청 직전에 공식 문서·토큰 도구에서 다시 확인하는 습관을. (예: OpenAI Tokenizer·Models 문서)
토큰이 어떻게 쪼개지는지 눈으로 보여 주는 Tokenizer, 모델별 한도를 정리한 Models 문서가 확인 지점의 예입니다.

🔍 토큰이 만드는 세 가지 판단

판단 질문왜 중요한가업무 예시
입력 토큰이 많은가비용·대기 시간이 늘어난다120쪽 회의록 전체를 매번 넣는 챗봇
출력 토큰이 긴가생성 비용·검토 시간이 늘어난다"상세히 설명"만 반복하는 보고서 생성기
같은 내용을 더 짧게 줄일 수 있나더 중요한 근거를 컨텍스트에 넣을 수 있다계약서 원문 대신 조항 번호·쟁점·근거 표를 먼저
목표는 무조건 짧게가 아니다. 짧게 만들다 판단 근거를 빼면 더 위험하다. 토큰을 아끼되 책임 있는 판단에 필요한 근거는 남기는 균형이 활용가의 일.
비용 절감과 판단 품질 사이의 균형이 핵심입니다. 줄이는 것 자체가 목적이 아닙니다.

🧪 손으로 돌려보기 — 내 문장이 몇 토큰?

!pip install transformers tiktoken

import tiktoken
from transformers import AutoTokenizer

gpt_tok = tiktoken.get_encoding("o200k_base")   # 최근 OpenAI 모델 계열 방식
ko_tok  = AutoTokenizer.from_pretrained(
            "monologg/koelectra-small-v3-discriminator")

PAIRS = [
  ("계약 기간은 체결일로부터 1년으로 하며, 자동 갱신됩니다.",
   "The contract term is one year from the date of execution, ..."),
  ("환불은 결제일로부터 7일 이내에만 가능합니다.",
   "Refunds are available only within 7 days of payment."),
]
for ko, en in PAIRS:
    for s in (ko, en):
        n = len(gpt_tok.encode(s))
        print(f"{len(s):>3}자 → {n:>3}토큰  (글자당 {len(s)/n:.2f})  {s}")
모델 가중치는 필요 없고 토크나이저만 있으면 됩니다. tiktoken은 OpenAI 방식, AutoTokenizer로 한국어 특화 토크나이저도 함께 비교합니다.

같은 문장을 두 토크나이저가 어떻게 쪼개는지:

                 '으로',' 하','며',',',' 자동',' �','�','신','됩니다','.']
  한국어 모델 방식 ['계약','기간','##은','체결','##일로','##부터','1','##년',

한국어 문장은 글자당 1.45토큰인데 영어는 5.06토큰 — 같은 뜻인데 글자당 토큰이 3.5배 차이. GPT 방식은 '갱'을 두 조각으로 깨뜨렸고, 한국어 모델은 '계약·기간'처럼 뜻을 살려 17개로 더 적게 잘랐습니다.

👀 여기서 볼 것 세 가지

1같은 뜻인데 글자당 토큰 3.5배 차이 — 컨텍스트 128K라도 한국어로 채우면 훨씬 적게 들어가고, 요금도 같은 비율로 불어난다
2'갱'이 두 조각으로 깨짐(바이트 단위) vs 한국어 토크나이저는 뜻을 살려 17개 — 토크나이저가 어떤 언어를 많이 봤나가 갈린다
3앞의 어텐션 n² 비용과 직결 — 조각이 2배면 계산은 4배. 한국어라 토큰이 더 나온다는 사실은 요금·속도·한계를 함께 밀어 올린다
후보 문장을 여러분 도메인 문서로 바꿔 이 표를 다시 만들어 보면 예산 감각이 확 잡힙니다.
세 번째가 핵심 — 토큰 수는 요금표 한 줄로 끝나지 않고 속도와 한계까지 함께 결정합니다.
2

컨텍스트 윈도우 — 한 번에 펼치는 작업대

클수록 좋은 게 아니라, 근거를 배치하는 설계 공간

Context Window · 배치 · Lost in the Middle
토큰이 낱장의 종이라면, 컨텍스트 윈도우는 그 종이를 한 번에 펼쳐 놓는 작업대입니다. 정확히는 모델이 한 요청에서 참고할 수 있는 토큰의 범위입니다.

🧭 큰 작업대라고 검토가 쉬워지진 않는다

컨텍스트 윈도우 = 검토자가 책상 위에 한 번에 올려놓을 수 있는 자료의 크기. 지원 길이는 모델·모드·시점마다 다르니 공식 사양에서 확인합니다.

1자료를 많이 올릴수록 검토 비용·시간이 늘어난다
2중요한 종이가 어디 있는지 찾기 어려워진다
3충돌하는 자료를 함께 올리면 어떤 기준을 우선할지 모델이 흔들린다
그래서 컨텍스트 윈도우는 "클수록 좋다"가 아니라 근거를 배치하는 설계 공간. 모델마다 다룰 수 있는 길이가 다른 이유 하나가 위치 인코딩 방식(RoPE·ALiBi는 학습보다 긴 입력에 유리).
이미지 비유: 서류와 메모가 잔뜩 널린 책상. 책상이 넓다고 검토가 쉬워지지 않듯, 컨텍스트도 그렇습니다. (사진은 저작권 고려해 비유로 대체)

🧱 컨텍스트는 네 칸으로 나눠 설계

무엇을 하는가역할 / 목표
무엇을 우선하나판단 기준
무엇을 보고 답하나근거 자료
어떻게 내놓나출력 형식

🚫 흔한 실패 — 근거 자료만 잔뜩 넣고 판단 기준을 비워 둔다. 고객 불만 300건 넣고 "분석해줘"만 하면, 환불 위험·법적 리스크·제품 결함·교육 필요 중 무엇을 우선할지 안 줬으니 산출물을 검토하기 어렵다.

트랜스포머는 문맥을 볼 수 있지만, 여러분의 업무 우선순위를 스스로 책임지진 않는다. 그 우선순위는 컨텍스트 안에 직접 넣어야 한다.
역할·판단기준·근거·출력형식 네 칸으로 나누면 무엇을 넣고 뺄지가 분명해집니다. 특히 '판단 기준'을 빠뜨리지 않는 게 핵심입니다.

📌 큰 작업대의 함정 — 중간에서 길을 잃는다

  • 80쪽을 통째로 넣으면 앞부분은 잘 반영되는데 중간이 뭉개진다 — 착각이 아니었다
  • "Lost in the Middle"(Liu 등, 2023): 중요 정보가 맨 앞·맨 뒤일 때 성능 최고, 중간일 때 뚝 떨어지는 U자 곡선
  • 긴 컨텍스트를 표방하는 모델에서도 이 경향이 나타났다 (arXiv:2307.03172)
처방프롬프트 설계 예
중요한 기준을 앞쪽에"우선순위: 안전 → 법규 준수 → 비용 순으로 판단합니다."
근거 자료에 제목·번호를[자료 A: 2026-05 고객 불만], [자료 B: 내부 정책]
답변에 근거 위치를 요구"각 결론마다 인용한 자료 번호를 붙이세요."
긴 컨텍스트는 자료를 많이 넣게 해주지만, 자료를 구조화하는 일까지 대신해 주지는 않는다.
처방은 논문을 외우는 게 아니라 이 세 가지를 습관으로 만드는 것입니다. 위치가 성능을 가른다는 사실을 배치로 활용합니다.

🔬 긴 컨텍스트에 직접 넣기 vs RAG

RAG(검색 증강 생성) = 필요한 조각을 먼저 검색해 그 조각만 컨텍스트에 넣는 방식(Lewis 등, 2020). "긴 컨텍스트면 RAG 불필요?"의 답은 업무에 따라 다르다.

선택어울리는 상황주의
긴 컨텍스트 직접자료가 한 번성·전체 맥락 중요·비용 감당 가능길수록 비용·지연·누락 위험 점검
RAG로 조각 검색문서 많음·반복 질의·최신성·근거 추적 중요검색이 틀리면 좋은 모델도 틀린 근거로 답함
요약 후 투입긴 회의록·리포트를 여러 단계 판단에 쓸 때요약에서 빠진 정보는 뒤에서 복구 어려움
지금 구현하진 않는다. 다만 큰 모델을 고르는 판단과 좋은 컨텍스트를 설계하는 판단은 서로 다른 일이라는 점만 기억. 이후 RAG·컨텍스트 엔지니어링으로 이어진다.
RAG: arXiv:2005.11401. 검색이 틀리면 모델도 틀리므로, 모델 선택과 컨텍스트 설계는 별개의 책임입니다.

📌 이것만은 꼭 — 핵심 5문장

1어텐션은 모든 토큰이 서로를 참고 → 계산이 토큰 수의 제곱(n²). 입력 2배면 계산 4배, 곧 비용·지연.
2비용은 글자 수가 아니라 토큰 수로 움직인다. 한국어는 영어보다 글자당 토큰이 몇 배 더 든다.
3컨텍스트 윈도우는 작업대 — 클수록 좋은 게 아니라 근거를 배치하는 설계 공간.
4컨텍스트는 역할·판단기준·근거·출력형식 네 칸. '판단 기준'을 비우면 산출물을 검토하기 어렵다.
5중간은 뭉개진다(Lost in the Middle) — 중요 기준은 앞쪽에, 자료엔 번호를, 답엔 근거 위치를.
토큰과 컨텍스트, 이 두 단어가 트랜스포머 강의가 처음부터 향하던 실용의 목적지였습니다.

🎯 이해도 확인 질문

Q2. "비용은 글자 수가 아니라 토큰 수"라는 말이 한국어 사용자에게 특히 중요한 이유는?
Q3. 컨텍스트 윈도우가 "클수록 좋다"가 아닌 이유 세 가지는?

Q5. Lost in the Middle이 무엇이며, 활용가의 처방 세 가지는?

✅ 정답 & 해설

A1. 어텐션은 각 토큰이 나머지 모든 토큰과 비교되므로 비교 수 ≈ n×n. 토큰이 2배면 비교는 약 4배 → 비용·대기 시간도 함께.
