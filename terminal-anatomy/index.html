터미널 vs 셸 vs
커널 vs 프롬프트

이름의 역사부터 명령이 움직이는 길까지

처음 터미널을 열면 검은 창·커서·낯선 기호가 한 덩어리처럼 보여 "터미널에 명령어를 쳤다"고 말하게 됩니다. 이 한 문장 안에는 서로 다른 네 역할이 섞여 있습니다.

🎯 이 구분은 command not found가 왜 나왔는지, 설치한 도구를 왜 못 찾는지, Claude Code가 어느 층에서 멈췄는지를 더 정확하게 읽기 위한 지도다.
세 층(터미널·셸·명령)을 분리해 말하면 문제를 훨씬 빨리 설명할 수 있습니다.

📜 이름의 역사 — 끝·껍데기·알맹이·재촉

이름뜻과 유래
터미널통신에서 선로의 끝단(말단 장치). 1960~70년대 대형 컴퓨터에 연결하던 키보드·화면·텔레타이프. 오늘 macOS Terminal 등은 그 입출력을 재현하는 에뮬레이터 — 명령의 뜻은 보통 해석하지 않는다
셸커널을 감싼 바깥 껍데기. 사람이 쓴 글을 해석해 프로그램을 실행. Thompson(1971)·Bourne(/bin/sh, 1977)·bash(1989)·zsh
커널알맹이·핵심. CPU·메모리·파일·네트워크 자원을 프로그램이 쓰게 중개하는 운영체제의 중심. 보통 직접 문장을 쓰지 않는다
프롬프트'재촉' — 셸이 "입력을 기다린다"고 내보내는 표시($ % user@computer:~$). 명령어가 아니라 복사 대상이 아니다
셸은 한 앱 이름이 아니라 명령을 해석하는 프로그램의 계열. 문서에 % pwd라면 %는 예시 프롬프트이고 실제 입력할 것은 pwd.
달걀의 알맹이(커널)와 껍데기(셸)를 떠올리면 됩니다. 셸이 사람 글을 해석해 프로그램을 실행하고, 그 프로그램과 커널이 만나는 길을 마련합니다.

🔌 층 사이엔 PTY가 있다

창터미널 앱
(master 쪽)
↔
가상 문자 장치PTY
master·slave
↔
해석셸
(slave 쪽)
  • 터미널과 셸은 직접 손을 잡지 않는다 — master·slave로 짝을 이룬 PTY(pseudoterminal, 의사 터미널)를 통해 글자를 주고받는다
  • 이 구조 덕분에 창 속 프로그램은 여전히 전통적인 물리 터미널에 연결된 것처럼 동작한다
터미널과 셸은 같은 것이 아니며, 프롬프트는 셸이 터미널에 그려 달라고 한 작은 안내문이다.
터미널 앱은 보통 master 쪽, 셸은 옛 물리 터미널처럼 보이는 slave 쪽을 사용합니다.

⚙️ pwd 한 줄이 거치는 일곱 단계

1터미널이 키 입력을 받는다 — p·w·d·Enter를 화면에 보이고 PTY master로 전달('창'의 일)
2PTY가 셸에 글자를 넘긴다 — 화면에 보인다고 아직 실행된 건 아니다
3셸이 문장을 파싱한다 — 공백·따옴표·변수·파이프(|)·리디렉션(>) 문법 해석
4명령의 위치를 찾는다 — 외부 프로그램이면 $PATH를 앞에서부터. 단 pwd는 내장 명령(builtin)이기도
5fork와 exec로 새 프로그램 시작 — 자기 복제(fork) 뒤 실행 파일 올리기(exec). 셸은 남고 새 프로그램은 독립
6시스템 콜로 커널에 요청 — 파일 읽기·현재 디렉터리 확인은 커널에. 커널이 권한 확인 후 자원 중개
7stdout이 화면에 돌아온다 — 결과가 PTY를 거쳐 터미널로. pwd의 경로 한 줄이 이렇게 온 결과
모든 명령이 똑같이 복제되는 건 아니다(내장/외부/파이프에 따라 다름). 그러나 "창이 곧 명령어"보다 훨씬 정확한 기본 모형.
pwd가 내장 명령일 수 있어 which pwd의 결과와 실제 실행 방식이 언제나 같다고 단정하면 안 됩니다.

🙅 흔한 오해 — 검은 창 하나가 전부

  • 가장 흔한 오해 = "터미널 = 검은 창 = 명령어". 검은색은 꾸미기일 뿐 — 밝은 테마 Windows Terminal도, VS Code 아래 패널도 터미널이 될 수 있다
  • 세 층은 다르다 — 터미널은 글자 입출력 인터페이스, 셸은 그 글자로 된 명령을 해석하는 프로그램, 명령은 실제로 실행되는 내장 기능 또는 별도 프로그램
오류도 이 지도로 나눈다 — 창이 안 열리면 터미널 앱 문제, command not found는 셸의 명령 탐색 또는 설치 문제, Permission denied는 커널이 관리하는 권한 규칙.
세 층을 분리해 말하면 문제를 더 빨리 설명할 수 있습니다.

🔄 터미널과 셸은 서로 바꿀 수 있다

  • 같은 macOS Terminal 창에서도 bash를 실행하면 bash 세션을 시작할 수 있고, 같은 zsh를 iTerm2·macOS Terminal·VS Code 터미널에서 쓸 수 있다
  • 그래서 "iTerm2를 설치했으니 bash가 설치됐다"거나 "VS Code를 열었으니 셸이 바뀌었다"는 결론은 틀리다 — 조합이 자유롭다(iTerm2+zsh, VS Code 터미널+bash 모두 가능)
또 하나의 오해 — 프롬프트 기호를 명령에 포함하는 것. $ npm --version에서 $는 설명 표시일 수 있으니 복사할 땐 npm --version만. 프롬프트는 사용자 이름·폴더·Git 브랜치까지 보이게 바꿀 수 있어 사람마다 다르게 보이는 게 정상.
기본 로그인 셸을 바꾸는 설정도 있습니다.

🔬 실습 관찰 — 각 층을 직접 찾기

echo $SHELL     # 로그인 셸로 설정된 경로 (지금 실행 중과 반드시 같진 않음)
echo $0         # 현재 실행 중인 셸 이름
tty             # 현재 세션이 연결된 터미널 장치 경로 (예: /dev/ttys001)
which pwd       # $PATH를 따라 찾은 pwd 위치 (type pwd 도 함께)
echo $PATH      # 외부 명령을 찾을 때 순서대로 보는 디렉터리 목록
🪟 Windows PowerShell은 위가 그대로 안 돈다 — $PSVersionTable(지금 셸 확인)·Get-Command pwd(어디서 찾았나)·$env:Path(탐색 경로). 관찰 포인트는 같다 — 지금 내 셸이 무엇이고, 명령을 어디서 찾는가.
  • Node·Claude Code를 설치했는데 command not found가 나오면, 설치 실패뿐 아니라 실행 파일이 $PATH 목록에 없는 경우도 살핀다
이 명령들은 컴퓨터를 바꾸지 않고 정보만 출력합니다. echo $SHELL과 echo $0이 다르거나 답이 달라도 정상일 수 있습니다. 출력 원문과 "무엇을 기대했는지"를 함께 AI에게 보여 주면 추측 명령을 줄입니다.

📍 Claude Code는 어디에 있는가

터미널도, 셸도, 커널도 아니다일반적으로 셸 위에서 실행되는 프로그램
  • 터미널 창에서 claude를 입력하면 셸이 $PATH에서 claude를 찾아 새 프로세스를 실행한다. Claude Code는 그 셸 환경과 권한 안에서 파일을 읽고 명령 실행을 요청하고 결과·오류를 보여준다
  • AI가 "명령을 실행했다"고 말할 때도, 실제로는 이 여러 층을 지나는 것
AI가 강력해도 권한과 현재 작업 폴더를 초월하지는 않는다 — 그래서 오류 한 줄·pwd·echo $SHELL·실행한 명령을 함께 주는 습관이 안전하고 재현 가능한 도움을 요청하는 방법.
이 구분이 협업에서 특히 유용합니다.

🩺 오류를 층으로 나눠 본다

증상먼저 의심할 층
claude: command not found설치 또는 $PATH(셸의 명령 탐색)
EACCES·Permission denied운영체제가 관리하는 파일 권한(커널)
글자가 깨지거나 창 자체가 멈춤터미널 앱·인코딩·PTY 연결
한 줄의 오류가 어느 층의 문제인지 갈린다세 층을 분리해 설명하면 AI도 다음 행동을 좁힌다
오류 한 줄, pwd, echo $SHELL, 실행한 명령을 함께 주는 습관이 재현 가능한 도움을 부릅니다.

🎯 이 덱의 핵심 정리

층한 문장
터미널글자 입출력 창(에뮬레이터) — 명령의 뜻은 보통 해석하지 않는다
셸사람 글을 해석해 프로그램을 실행하는 프로그램 계열(zsh·bash)
커널자원을 중개하는 알맹이 — 시스템 콜로 요청받는다
프롬프트입력 대기 표시 — 복사 대상이 아니다($ %)
PTY·7단계창≠셸, 그 사이 PTY. pwd 한 줄이 일곱 단계를 거친다
Claude Code셸 위 프로그램 — 권한·작업 폴더를 초월하지 않는다
다음 덱에서 이 지도를 손으로 — 터미널로 폴더를 탐험·생성하고, AI에게 정리를 맡기고, 직접 한 것과 비교합니다.

🎯 이해도 확인 질문

Q1. 터미널·셸·커널·프롬프트의 역할을 한 줄씩 구분하면?
Q2. 터미널과 셸 사이의 PTY는 무엇을 하나?
Q3. $ npm --version에서 $를 복사하면 안 되는 이유는?
Q4. command not found와 Permission denied는 각각 어느 층을 의심하나?
Q5. Claude Code는 이 층들 중 어디에 있나?
Q4가 오류를 층으로 나눠 읽는 실전 감각입니다.

✅ 정답 & 해설

A1. 터미널=글자 입출력 창, 셸=명령을 해석·실행, 커널=자원 중개(알맹이), 프롬프트=입력 대기 표시(명령어 아님).
A2. 터미널과 셸은 직접 안 잡고 master·slave 짝의 가상 문자 장치(PTY)로 글자를 주고받아, 창 속 프로그램이 물리 터미널에 연결된 것처럼 동작하게 한다.
A3. $는 입력 대기 프롬프트(설명 표시)일 뿐 명령의 일부가 아니다 — 실제 입력할 것은 npm --version.
A4. command not found는 셸의 명령 탐색($PATH)·설치, Permission denied는 커널이 관리하는 파일 권한.
A5. 셸 위에서 실행되는 프로그램 — 셸이 $PATH에서 claude를 찾아 실행하며, 셸의 권한·작업 폴더 안에서 동작한다.
A5를 이해하면 AI가 "실행했다"고 할 때도 여러 층을 지난다는 것이 보입니다.
