실제로 이어지는 모델·도구 반복

타입 표기만으로 실행 검사가 끝나지 않습니다

⑨ Python 하네스
Agent.run의 중심에서 모델을 호출합니다.

세 발췌

reply = await self.provider.complete(messages, self.backend.definitions)

@dataclass(frozen=True)
class ToolRequest:
    id: str
    name: str
    arguments: dict[str, Any] | str

validated = ToolRequest(request.id, request.name, arguments)
async with asyncio.timeout(self.limits.tool_timeout_seconds):
    result = await self.backend.execute(validated)
  • messages는 현재 대화, definitions는 사용할 수 있는 도구 설명. await는 모델 응답을 기다리는 지점 — 비동기 실행을 사용하면 기다리는 작업에 취소와 시간 제한을 적용할 수 있습니다. Python 안의 반복과 도구 실행을 다른 에이전트 제품에 맡기는 호출은 아닙니다
  • id는 요청과 결과를 연결, name은 도구 선택, arguments는 입력 — 타입 표기만으로 실행 검사가 끝나는 것은 아니므로 루프에서는 JSON을 해석하고 도구의 JSON Schema로 인수를 검사합니다
  • 백엔드는 요청을 받아 실제 작업을 수행하는 부분 — 일상 사용에서는 승인받은 파일·명령 실행, 로컬 평가에서는 별도 작업 복사본의 파일 처리와 Python 실행. 작업 복사본은 운영체제 격리를 뜻하지 않습니다
📌 결과를 대화에 추가하면 바깥 반복이 다시 모델을 호출합니다. 위 발췌만 복사해 전체 구현이라고 생각하지 않습니다 — 실제 함수에는 인수 오류, 결과 ID 검사, 기록, 중단 처리가 있습니다
도구 요청이 없는 텍스트를 받으면 반환하고, 한도나 오류에 도달하면 다른 상태로 끝납니다.

제공자별 차이를 처리하는 위치

어댑터처리 내용
OpenAIProviderResponses API 사용. 모델의 function_call과 실제 결과의 function_call_output을 call_id로 연결. store=False로 요청하면서 다음 요청에 필요한 출력 항목과 추론 관련 항목도 보존 — 텍스트만 남기고 나머지 응답을 버리지 않습니다
OllamaProviderOpenAI 호환 경로를 가정하지 않고 네이티브 /api/chat 사용. 호출 ID가 없는 응답에는 내부 ID를 붙이며 — 이는 Ollama 서버가 발급한 ID라고 설명하지 않습니다. 모델의 도구 지원과 답변 품질은 별도로 확인
📌 두 어댑터가 모두 구현되어 있어도 학생의 첫 검증은 선택한 제공자 하나부터 할 수 있습니다 — 추가 제공자를 평가할지는 D08에 맞춥니다
같은 실행 의도를 서로 다른 형식으로 표현하는 지점입니다.

로컬 읽기와 코딩 실행

개발 도우미가 아니라 실행한 하네스에 요청

⑨ Python 하네스
work/meeting.txt는 수업용 가상 독서 모임 자료입니다 — 시작 시각은 오후 3시, 준비물은 책 한 권과 필기구.

두 실행

uv run run.py --provider openai --model gpt-4.1-mini --workspace work \
  --session reading --prompt "meeting.txt를 읽고 모임 시각과 준비물을 알려 줘."

uv run run.py --provider ollama --model qwen3.5:2b --workspace work \
  --session local-reading --prompt "meeting.txt를 읽고 모임 시각과 준비물을 알려 줘."
uv run run.py --provider openai --model gpt-4.1-mini --workspace work \
  --session receipt-fix \
  --prompt "영수증 계산의 테스트를 실행하고 잘못된 부분을 고쳐 줘. 테스트는 바꾸지 말고 다시 확인해 줘."

uv run python -m unittest discover -s work -p test_receipt.py -v
  • receipt.py는 할인액을 영수증 전체에서 한 번 차감하고 결과가 음수가 되지 않아야 하는 예제. 저장과 명령 실행은 터미널의 승인 내용을 읽고 y를 입력해야 진행
  • 변경 전 실패와 변경 후 결과를 구별합니다. 직접 검사를 실행한 사실과 에이전트가 스스로 수정에 성공한 사실도 따로 기록
  • Ollama 기본 주소는 http://localhost:11434 — 소형 모델의 정확성을 보장된 것으로 취급하지 않습니다
⚠️ LocalTools는 상대 경로·숨김 경로·링크를 검사하고 쓰기를 승인받습니다. run_command는 명령 인수 목록을 받아 셸 해석 없이 실행하지만 — 승인한 코드 자체는 사용자 권한을 가집니다. 작업 폴더를 지정했다고 운영체제 격리가 생긴 것은 아닙니다
모델은 해당 계정에서 이용할 수 있는 도구 호출 지원 모델로 선택합니다.

한도 · 저장 · 지표

구분내용
기본 한도모델 호출 12회, 도구 호출 30회, 전체 300초, 도구당 30초. 도구 출력 16,000자, 대화 JSON 200,000자 초과 시 context_limit로 중단
세션.harness/sessions/에 저장. 도구 요청과 각 결과를 중간 저장하고 임시 파일을 완성한 뒤 교체. 재개 시 제공자·모델·주소·작업 폴더가 다르면 새 이름을 요구
복구중단되어 결과가 없는 요청은 repair_pending이 오류 결과로 종결
지표모델·도구 호출 수, 도구 오류 수, 경과 시간, 보고된 입력·출력 토큰
⚠️ 문자 한도는 모델의 토큰 한도와 같지 않으며 대화를 자동 요약하는 기능도 아닙니다. 같은 세션을 여러 프로세스에서 동시에 사용하는 설계가 아니며, 파일 변경과 세션 저장이 하나의 거래처럼 묶인 것도 아니므로 실행 여부가 불확실한 작업을 자동 반복하지 않고 실제 파일을 확인합니다
📌 usage_known=False라면 숫자 0을 무료 사용이나 실제 무사용으로 해석하지 않습니다. completed도 모델이 텍스트를 반환했다는 상태이며 업무 정답이나 벤치마크 통과가 아닙니다
대화 파일에는 자료 내용이 남을 수 있어 공개 저장소에 포함하지 않습니다.

같은 루프를 로컬 평가에

모델의 판단 루프는 기존 Agent가 맡습니다

⑨ Python 하네스
평가 경로에서는 local_agent.py의 LocalBenchmarkTools를 같은 Agent에 연결합니다.

평가용 백엔드

result = await Agent(
    provider,
    LocalBenchmarkTools(workspace, options["command_timeout"]),
    limits, trace, SYSTEM,
).run(instruction + "\n\nLocal task working directory (relative to workspace): "
      + options.get("task_cwd", "."))
  • 읽기·쓰기 도구와 run_python을 제공하고 일반 CLI의 run_command는 제외 — 모델이 Python 코드를 실행하려면 먼저 작업 폴더에 .py 파일을 만든 뒤 파일 경로와 인수 목록으로 요청. 임의 셸 명령을 받는 방식과 구별됩니다
  • 모델의 판단 루프는 기존 Agent가 맡고, 실행 범위와 도구 목록은 평가용 백엔드가 정합니다
  • 평가 작업 복사본 안의 변경은 사전 허용된 동작으로 다루지만 — 그 허용이 사용자 컴퓨터의 다른 파일 접근까지 뜻하지는 않습니다. 로컬 CLI의 매번 확인하는 승인 방식과 평가의 자동 실행 정책을 구별
  • execution.py는 실행할 파일 경로를 검사하고 출력·시간을 제한. 출력이 상한을 넘으면 프로세스를 종료하면서 파이프를 계속 비워 무한 대기를 줄임 — POSIX는 프로세스 그룹, Windows는 자식 프로세스를 종료. 별도 세션으로 벗어난 자식까지 가두는 운영체제 샌드박스는 아닙니다
이 평가 경로에서는 원본 과제와 작업 복사본만 허용된 범위로 사용합니다.

원본 문제와 로컬 경로의 계약

  • 이번 평가 문제는 자체 작성한 연습문제가 아닙니다 — Terminal-Bench Pro의 고정 커밋에서 원본 난이도 쉬움 2·중간 4·어려움 4를 선정하고 원래 컨테이너의 절대 경로를 로컬 작업 폴더로 옮겨 실행. 난이도는 원본 메타데이터의 분류이며 이 로컬 환경에서 새로 측정한 난도가 아닙니다
  • benchmark_source.py는 manifest의 저장소 커밋과 파일별 크기·SHA256을 확인. SHA256은 파일 내용에서 계산한 식별값
  • 준비 단계는 원본 Dockerfile의 파일 복사와 필요한 초기화 작업을 명시적으로 옮깁니다 — Dockerfile 전체를 자동으로 해석하는 범용 도구는 아닙니다
  • 원본의 /app, /protected, /home/user는 작업 폴더 안의 대응 위치로. 작업 지시와 채점 코드도 같은 경로 계약을 적용해야 합니다 — 경로 하나만 바꾸고 원본 환경과 같다고 주장하면 입력 위치나 작업 디렉터리가 달라져 엉뚱한 실패가 생길 수 있습니다
⚠️ 실행 위치와 도구·의존성이 원본 컨테이너와 다르므로 — 공식 컨테이너 점수와 동일한 평가라고 표현하지 않습니다. 실제 로컬 실행의 재현 여부와 한계를 따로 기록합니다
자격정보 복구 문제의 정답 목록은 모델 작업 폴더에 노출하지 않고 평가자 전용 캐시에서 읽도록 옮긴 예외가 있으며, 이 변경은 manifest에 기록합니다.

모델과 분리된 채점

uv sync --locked --extra dev
uv run python -m pytest -q
  • grading.py는 원본 tests/test_outputs.py의 경로를 작업 복사본에 맞추고 pytest로 실행. 결과는 JUnit XML과 표준 출력·오류로
  • 모델이 "완료했다"고 말한 문장을 점수로 사용하지 않습니다 — 원본 테스트가 실제 산출물을 확인한 결과를 수집. 테스트 실행 오류나 시간·출력 한도 초과도 기록
  • 테스트를 작업 폴더 밖에 두는 것은 일반 파일 도구에 노출하지 않기 위한 구조이며 — 호스트에서 실행되는 Python 코드가 다른 파일을 읽을 수 없게 보장하는 장치는 아닙니다
  • 원본 정답과 채점 파일을 학생 하네스의 입력이나 개선 프롬프트에 넣지 않는 평가 규칙도 지킵니다
  • 위 검사는 호출 연결, 잘못된 인수, 한도, 승인 거절, 실행 정리를 확인 — 모의 응답 검사 성공을 실제 OpenAI·Ollama의 열 문제 성능으로 기록하지 않습니다
여기까지 읽었다면 제품의 요청·실행 루프와 평가의 문제 준비·채점 경로를 구별할 수 있습니다. 경로 이식 코드가 존재한다는 사실만으로 모든 원본 과제가 로컬에서 검증되었다고 단정하지 않습니다.
