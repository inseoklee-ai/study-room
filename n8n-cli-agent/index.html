1

API 키와 CLI 준비

Settings → n8n API

④ CLI와 에이전트
API 키는 워크플로 목록 조회와 생성, 삭제, 실행 기록 조회에 사용됩니다.

세 줄로 연결합니다

n8n 화면의 Settings → n8n API에서 API 키를 발급합니다. 터미널에서는 npx로 설치 없이 CLI를 실행합니다.

npx @n8n/cli config set-url https://n8n.vibemakers.kr
npx @n8n/cli config set-api-key <발급한 API 키>
npx @n8n/cli workflow list
  • API 키의 쓰임 — 워크플로 목록 조회 · 생성 · 삭제 · 실행 기록 조회
키를 요청문이나 공유 화면에 그대로 남기지 않도록 주의합니다.

공식 스킬로 작업 범위를 알립니다

npx @n8n/cli skill install --global
구분내용
공식 스킬이 지원하는 일워크플로 조회 · 생성 · 활성화, 실행 기록 확인, 연결 정보 관리, --jq로 값 고르기
공식 스킬 설치를 지원Claude Code · Cursor · Windsurf
같은 CLI를 도구로 사용opencode · Antigravity
📌 스킬을 전역 설치하면 코딩 에이전트가 CLI의 작업 범위를 알 수 있습니다
하네스 중단원 ⑤에서 본 "SKILL.md를 추가한 사실만으로 끝이 아니다"라는 원칙이 여기에도 적용됩니다.
2

요청문에 검토 지점을 넣습니다

연결 확인 → 정의 검토 → 생성 → 기록 조회

④ CLI와 에이전트
요청에는 생성 전에 검토할 내용을 분명히 적습니다.

한 요청에 담는 네 단계

먼저 workflow list로 이 인스턴스의 연결 상태를 확인해 줍니다.
이어서 Manual Trigger → HTTP Request
(https://en.wikipedia.org/api/rest_v1/page/summary/N8n)
워크플로 정의를 wf.json으로 만들고,
생성 명령을 실행하기 전에 JSON의 노드와 연결을 보여 줍니다.
확인했다는 답을 받은 뒤 생성합니다.
생성 뒤에는 실행 기록을 찾아 상태코드와 원 응답을 보여 줍니다.
🎯 핵심은 "확인했다는 답을 받은 뒤 생성합니다" — 승인 지점을 요청문 안에 미리 박아 둡니다
이 문장이 소단원 ①에서 말한 "어디에서 멈추게 할지"의 구체적 실행입니다.

wf.json의 구조

에이전트는 workflow create --file=wf.json으로 워크플로를 생성할 수 있습니다.

키내용
name워크플로 이름
nodes노드의 id · 이름 · 종류 · 버전 · 위치
connections노드 사이의 연결
settings워크플로 설정
✅ 검토할 것 — 두 노드의 이름과 URL, 그리고 연결. 확인한 뒤에만 생성을 승인합니다
에이전트가 보여 준 JSON을 검토하는 순간에는, 짧은 JSON 한 줄이 외부 요청으로 이어진다는 긴장감이 생깁니다.

생성 뒤에는 화면과 대조합니다

1에이전트가 보여 준
JSON 검토
→
2생성 승인
→
3화면에서 같은 이름의 워크플로와
실행 기록을 열어 다시 대조
  • 대조 대상 — 노드와 연결이 JSON에서 본 것과 같은지
CLI의 응답과 화면의 노드가 같아 보여도, 실제로 같은지는 두 곳을 나란히 열어야 알 수 있습니다.

실행 기록 조회와 CLI의 한계

방금 실행을 찾아 상태코드와 원 응답을 보여 줍니다.
  • 에이전트는 execution list와 execution get <실행 ID>로 기록을 찾아 상태코드와 원 응답을 보여 줄 수 있습니다
  • CLI에는 새 수동 실행을 시작하는 명령이 없습니다 — 그래서 Manual Trigger 워크플로의 첫 실행은 n8n 화면에서 수행하고, 이후 실행 기록을 조회합니다
  • 상태코드와 원 응답이 어느 노드 출력에 보이는지는 화면에서 다시 확인합니다
이 한계가 다음 절 MCP의 execute_workflow와 대비됩니다.

3

한 걸음 더 — MCP로 실행까지

CLI의 한계와 대비되는 지점

④ CLI와 에이전트
MCP 활성화와 연결의 구체적인 절차는 이 강의 범위에서 다루지 않습니다.

MCP 네 가지 도구

도구하는 일실측
validate_workflowSDK 코드를 먼저 검증두 노드 워크플로 코드가 valid: true 반환
create_workflow_from_code코드로 워크플로 생성 
execute_workflowmanual 모드로 실행실행 기록이 success로 남음
get_workflow_execution실행 기록 조회각 노드의 실행 상태와 HTTP Request가 돌려준 JSON 확인
📌 MCP로는 워크플로 실행까지 맡길 수 있습니다 — CLI에 새 수동 실행 명령이 없다는 앞의 한계와 대비됩니다. 다만 MCP가 보여 준 JSON도 원 응답과 대조해 확인합니다
인스턴스 설정에서 MCP 서버를 활성화하면 코딩 에이전트에게 n8n의 작업을 더 넓게 맡길 수 있습니다.

❓ 이해도 확인

Q1. 요청문에 반드시 넣을 문장은?
A1. "생성 명령을 실행하기 전에 JSON의 노드와 연결을 보여 주고, 확인했다는 답을 받은 뒤 생성합니다." 승인 지점을 요청문에 미리 박는다.
Q2. Manual Trigger 워크플로의 첫 실행을 화면에서 해야 하는 이유는?
A2. CLI에 새 수동 실행을 시작하는 명령이 없기 때문. MCP의 execute_workflow는 이 한계를 넘는다.
Q3. 에이전트와 학생의 역할 구분은?
A3. 에이전트는 CLI 호출과 생성·조회, 학생은 생성 결과와 실행 근거의 확인.
Q1은 앞으로 어떤 도구를 쓰든 쓸 수 있는 요청문 패턴입니다.
