결과의 좋고 나쁨을 평가하는 시간이 아니라, 요청의 입구와 실행 경계를 화면에서 찾는 시간입니다.

범위를 작게 정합니다

Claude Code

Anthropic이 만든 터미널용 코딩 에이전트. 터미널 안에서 저장소를 읽고 파일을 고치고 명령을 실행

opencode

오픈소스 터미널 코딩 에이전트. 여러 모델 제공자를 설정에서 골라 쓸 수 있음

  • 이번 관찰은 둘 중 이미 사용하는 하나에서만 합니다
  • 설치, 로그인 변경, 확장 연결, 파일 수정은 이번 범위에 넣지 않습니다
  • 읽기 전용 과업 하나면 충분 — 현재 작업 폴더의 파일 목록을 읽는 요청이나 공개 문서 한 건을 요약하는 요청
범위를 좁히는 것이 관찰의 조건입니다. 여러 도구를 동시에 열면 무엇이 도구 차이인지 알 수 없습니다.

fixture — 매번 같은 재료

fixture는 개발자들이 오래전부터 써 온 테스트 용어입니다. 뜻은 "무엇을 시험할 때마다 결과가 똑같이 나오도록 미리 준비해 둔 고정된 자료"입니다.

🍳 요리 교실에서 매번 같은 재료를 미리 다져 두는 것과 비슷합니다 — 재료가 그때그때 다르면 어떤 차이가 실력이고 어떤 차이가 재료 탓인지 구분할 수 없습니다
  • 관찰도 마찬가지입니다 — 자료가 늘 같아야 달라진 것이 자료가 아니라 도구라는 말을 할 수 있습니다
  • 공개 문서 한 건 또는 내용이 알려진 작은 텍스트 파일 한 건이면 충분합니다
  • 비밀값·개인 자료·실제 저장소·수정이 필요한 파일은 이 관찰의 대상이 아닙니다
관찰 메모에는 도구 이름과 버전, 작업 폴더의 위치, fixture의 종류를 먼저 남깁니다. 나중에 같은 화면을 다시 볼 때 관찰 조건을 구분하게 합니다.

시범 — 한 바퀴를 처음부터 끝까지

Claude Code CLI 2.1.220 · ~/obs-lab · notes.txt

② 화면 관찰
실제 실행 기록입니다. 버전 번호는 화면에 표시된 값을 그대로 관찰 조건으로 남깁니다.

첫 걸음 요청 · 둘째 걸음 도구 호출

이 폴더의 파일 목록을 보여 줘

요청 문장은 대화 흐름 안에 남고, 응답 본문과 구분되어 표시됩니다. 결과 목록의 내용보다 요청이 들어간 화면의 위치를 먼저 봅니다. 요청을 넣으면 응답이 만들어지는 동안 도구 호출 영역이 표시됩니다.

● Bash(ls -la /Users/admin/obs-lab)
    List files in obs-lab
🔎 공식 문서는 파일 탐색에 Glob, 파일 읽기에 Read를 안내하지만 — 이 요청에서 모델은 Bash의 ls -la를 골랐습니다. 도구를 고른 주체가 모델의 판단이었다는 점이 첫 번째 관찰
화면에 나타난 도구 이름과 명령이 이번 실행의 사실입니다. 문서가 안내하는 것과 실제로 고른 것이 다를 수 있다는 관찰이 이 시범의 핵심입니다.

셋째 걸음 결과 · 넷째 걸음 최종 응답

total 8
  drwxr-xr-x   4 admin  staff   128 Sep  2 01:36 .
  drwxr-xr-x@ 171 admin  staff  5472 Sep  2 01:38 ..
  drwxr-xr-x   4 admin  staff   128 Sep  2 01:37 .omc
  -rw-r--r--   1 admin  staff    32 Sep  2 01:36 notes.txt
`/Users/admin/obs-lab` 내용:

  - `notes.txt` — 32바이트 파일
  - `.omc/` — OMC 상태 디렉터리 (숨김)
  • 원본 명령의 출력이 그대로 돌아옵니다 — 이 원본이 세션 기록에 남는다는 사실이 컨텍스트 관리의 재료가 됩니다
  • 지금은 네 줄이라 그대로 두지만, 출력이 길어지면 관측 축약이 개입할 자리입니다
🧱 실행의 네 층 — 요청 → 도구 호출 → 도구 결과(원본) → 사람을 위한 요약이 한 세션에 순서대로 남습니다
이 네 층이 하네스가 화면에 보여 주는 실행의 흔적입니다.

완성된 관찰 메모

조건: Claude Code CLI 2.1.220 · 작업 폴더 ~/obs-lab
      fixture는 공개 문서를 받아 둔 notes.txt 한 건

입력    — 요청은 대화창에 들어가고 응답과 구분되어 남았습니다.
도구 호출 — Bash(ls -la)가 화면에 표시되었습니다.
           공식 문서가 안내하는 Glob/Read가 아니라 모델이 Bash를 골랐습니다.
관측    — 원본 ls 출력 네 줄이 그대로 돌아왔습니다.
           축약 표시는 이 실행에서 확인하지 못했습니다.
승인    — 이 읽기 요청에는 승인 창이 없었습니다. 설정의 허용 규칙은 미확인입니다.
기록    — 세션에 요청부터 요약까지 순서대로 남았습니다.
🚫 아직 쓰지 않는 문장 — "이 도구는 읽기가 안전하다". 안전 판정에는 권한 규칙 확인이 필요한데 이번 관찰은 그 규칙을 열어 보지 않았습니다
이 시범 기록의 뼈대는 뒤의 비교표와 실험에서 쓰는 관찰 로그 형식에도 그대로 이어집니다.

관찰 기록은 사실과 해석을 나눕니다

같은 내용도 어떻게 적느냐에 따라 갈립니다

② 화면 관찰
기록에는 화면이나 로그에서 확인한 내용만 넣습니다.

한 줄로 이렇게 남깁니다

✅ 사실로 남기는 문장

"파일 목록 요청에 승인 없이 읽기가 실행되었습니다. 관측한 사실: 화면의 파일 목록. 미확인: 설정 파일의 권한 규칙"

❌ 아직 쓰지 않는 문장

"이 도구는 읽기가 안전하다" — 이 관찰만으로 안전을 단정할 수 없습니다

  • 도구와 버전, 작업 폴더와 fixture는 관찰 조건으로 남깁니다
  • 요청이 들어간 곳과 화면의 도구 호출 → 행동 포맷 · 세션·로그 위치와 축약 표시 → 컨텍스트 관리·경험·반성 · 실행 전 승인 신호 → 권한과 보안
  • 화면에 보인 연결·설정 단서는 확인한 사실로, 이번 실행에서 보이지 않은 기능은 한계로 구분합니다
🎯 이 기록은 도구 전체를 판정하는 증명이 아니라 — 짧은 실행 하나에서 보인 경계와 보이지 않은 경계를 구분하는 출발점
해석은 뒤의 기능 절들이 근거를 모아 줍니다.

❓ 이해도 확인

Q1. fixture를 쓰는 이유는?
A1. 자료가 늘 같아야 달라진 것이 자료가 아니라 도구라고 말할 수 있기 때문. 매번 같은 재료를 미리 다져 두는 것과 같다.
Q2. 시범에서 가장 중요한 관찰은?
A2. 공식 문서는 Glob/Read를 안내하지만 모델이 Bash(ls -la)를 골랐다 → 도구를 고른 주체는 모델의 판단이고, 화면에 나타난 것이 그 실행의 사실.
Q3. 승인 창이 뜨지 않았을 때 어떻게 적나?
A3. "승인 없이 읽기가 실행됨. 관측: 화면의 파일 목록. 미확인: 설정 파일의 권한 규칙" — "읽기가 안전하다"고 쓰지 않는다.
Q4. 실행의 네 층은?
A4. 요청 → 도구 호출 → 도구 결과(원본) → 사람용 요약. 한 세션에 순서대로 남는다.
