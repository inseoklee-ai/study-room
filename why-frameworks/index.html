프레임워크는
왜 이렇게 많을까

뼈대라는 뜻 · 반복·변화·연결이라는 세 문제

검색창에 "프론트엔드 프레임워크 추천"을 넣으면 React·Vue·Svelte·Angular·Next.js가 쏟아집니다. "이걸 다 알아야 하나요?"의 답은 아니요 — 다만 왜 많아졌는지 알아야 AI 추천도 판단할 수 있습니다.

🗺️ 문법이 아니라 뜻과 판단

  • 건축의 철골·비계처럼 프레임워크(framework) = 뼈대·틀. 웹서비스에서 반복되는 일을 미리 정리해 둔 개발 골조
  • 부품 상자(라이브러리)와 다르다 — 프레임워크는 "이렇게 화면을 나누고 연결하자"는 약속까지 준다(제어의 역전: 프레임워크가 흐름을 쥐고 내 코드를 불러 준다)
🎯 핵심 한 문장 — 종류가 수십 개지만 비전공자가 다 배울 필요는 없다. 큰 그림을 잡고, 내 상황을 AI에게 설명해 추천받고, 그 근거를 판단하는 것이 선택법.
💡 오늘의 산출물은 코드가 아니다"내 조건에서 어떤 게 맞는지"를 AI에게 제대로 물을 선택 프롬프트와 평가표
혼자 빠르게 만드는 데도 도움이 되지만, 여러 사람이 오래 고칠 때 더 큰 힘을 냅니다 — 누가 들어와도 어느 폴더를 봐야 하는지 짐작할 수 있으니까요. 의사의 EMR, 변호사의 사건관리 SaaS처럼 검증된 틀 위에 우리 절차를 얹는 것과 같습니다.

반복·변화·연결 · 컴포넌트·상태·라우팅

② 세 문제
프레임워크는 개발자를 괴롭히려는 이름표가 아니라, 화면이 커질 때 반복해서 터지는 문제를 줄이려고 생겼습니다.

📜 반복을 덜어내는 20년

시기도구 · 풀려던 문제
2006 jQuery브라우저마다 다른 JS를 덮어줌("적게 쓰고 더 많이") — 화면이 늘면 여전히 뒤엉킴
2010 AngularJS·Backbone화면을 구조적으로 나누자 — 데이터가 바뀌면 화면도 규칙적으로
2013 React화면을 컴포넌트로 나눔 · "어떻게"가 아니라 "무엇이어야"를 선언(선언형 UI)
2014 Vue컴포넌트 사고를 받되 점진적으로 배우게
2016~ Svelte·Solid·Qwik각자 다른 병목(컴파일러·반응형 성능·서버 상태 이어받기)
여기까진 다 프론트엔드(화면) 프레임워크. 백엔드에도 같은 이유로 Django·FastAPI·Spring·Express·Rails가 있다. 공통 질문은 하나 — "규모가 커질 때 반복되는 일을 어떻게 줄일 것인가?" (오늘은 프론트엔드로 좁힘)
이름이 바뀌어도 풀려는 문제는 같았습니다.

🧩 커질 때 생기는 세 문제

문제순수 웹 코드에서개발자 말
반복비슷한 카드·폼·버튼을 여러 곳에 복사컴포넌트 — 재사용 조각
변화선택값·로딩·실패·완료를 여러 코드가 따로 바꿈상태 — 지금의 현재값
연결화면이 늘수록 어느 주소에 어떤 화면인지 헷갈림라우팅 — 주소별 화면
  • 컴포넌트 — 같은 카드 30개면, 복사해 두면 배지 하나 추가에 30곳을 고쳐야. 컴포넌트는 설계를 한 곳에 두고 데이터만 바꿔 부른다
  • 상태 — 필터를 바꾸면 목록·결과 수·안내 문구가 함께 바뀌어야. 손으로 흩어 놓으면 한 곳은 바뀌고 한 곳은 예전 값인 버그
  • 라우팅 — /search·/profile처럼 주소와 화면을 연결. 커지면 주소 체계가 길 찾기이자 작업 지도
낯선 말 같아도 방금 표의 문제를 다른 이름으로 부르는 것에 가깝습니다.

👀 눈으로 — 순수 JS는 복사 30번, 수정 30번

<!-- 카드 하나를 직접 적고, 같은 구조를 30번 복사... -->
<div class="expert-card">
  <h3>김민준 변호사</h3>
  <p class="badge">형사전문 15년</p>
</div>

// 동적으로 만들어도 구조를 문자열로 직접 조립
experts.forEach(expert => {
  card.innerHTML = `<h3>${expert.name}</h3>
    <p class="badge">${expert.badge}</p>`;
});
// 배지에 아이콘을 추가하려면? 이 코드를 다시 찾아 고쳐야
배지 디자인을 바꾸려면 30곳을 모두 찾아 고쳐야 한다. "어떤 요소를 찾아 → 어떻게 바꿀지"를 개발자가 일일이 적는다.
도메인에 맞게 환자 카드·사건 카드·광고 성과 박스로 바꿔 생각해도 됩니다.

🧩 React — 한 번 만들고, 데이터만 바꿔

// ExpertCard.jsx: 카드 설계를 "한 번" 만든다
function ExpertCard({ name, badge, bio }) {
  return (
    <div className="expert-card">
      <h3>{name}</h3>
      <p className="badge">{badge}</p>
    </div>
  );
}

// 데이터만 바꿔 여러 번 부른다
{experts.map(expert => (
  <ExpertCard key={expert.name} {...expert} />
))}
배지에 아이콘을 추가하려면? ExpertCard 한 곳만30개 카드가 모두 바뀐다 — 이것이 모듈화·재사용의 힘
💡 오늘 외울 필요 없다 — 핵심은 순수 JS는 30번 복사, 컴포넌트는 한 번 만들고 데이터만 바꿔 쓴다. 이 차이가 "프레임워크가 왜 생겼는가"의 가장 직접적인 답.
코드를 당장 이해하지 않아도 괜찮습니다.

💥 상태 — 필터를 바꾸면 함께 바뀌어야

"형사전문" 필터를 고르면 한 곳이 아니라 다섯 곳이 바뀌어야 한다 — 필터 버튼 표시·결과 목록·결과 수·빈 결과 안내·페이지 제목.

순수 JS 위험상태가 있으면
목록만 바꾸고 카운트를 안 바꿈같은 상태를 공유해 일관됨
빈 결과 문구 조건을 빠뜨림상태가 비면 자동 표시
const [selectedFilter, setSelectedFilter] = useState('all');
// 상태에서 파생 — 개발자가 따로 안 바꿈
const filtered = selectedFilter === 'all'
  ? experts
  : experts.filter(e => e.specialty === selectedFilter);
// 결과 수, 빈 안내, 목록이 filtered에서 모두 자동으로
개발자는 selectedFilter를 바꾸는 한 줄만 적는다 — 한 곳을 바꾸면 연결된 곳이 모두 일관되게 바뀌는 것이 상태 관리의 가장 큰 이점.
도메인으로 — 환자 목록에서 "당뇨" 필터를 고르면 목록·결과 수·차트·문구가 다 바뀌어야. 이런 "한 값이 여러 곳을 당겨 바꾸는" 상황이 많을수록 상태 관리의 이점이 커집니다.

🧠 CS 교양 — 추상화와 모듈화

추상화 (abstraction)

복잡한 속을 감추고 필요한 조작만 밖으로. 자동차는 엔진을 몰라도 페달·핸들만. 프레임워크는 손 많이 가는 DOM 조작을 손잡이 뒤로 — "무엇이어야 한다"만 적는 선언형 UI

모듈화 (modularity)

큰 덩어리를 갈아 끼울 수 있는 조각으로. 레고처럼 — 컴포넌트가 이것. 조각 사이 약속만 지키면 한 조각을 고쳐도 다른 게 안 무너진다

💡 AI에게 좋은 지시는 이 두 언어로 된다 — "카드를 컴포넌트로 만들어 재사용해"(모듈화), "검색 결과가 바뀌면 목록이 따라 바뀌게"(상태=추상화). 무엇을 조각으로 나누고 무엇을 상태로 둘지는 여러분이 판단 — 이 판단이 문법보다 오래 쓸모 있다.
📖 1972년 데이비드 파나스 — "서로 관련된 것끼리가 아니라 바뀌어야 할 이유가 같은 것끼리 모아라". 50년 뒤 React 컴포넌트·Vue 파일 구조·Svelte 컴파일 단위에 살아 있습니다. 도구는 바뀌어도 복잡함을 조각으로 나누는 생각은 그대로.

🏗️ 가상 DOM — 설계도를 먼저, 차이만 칠하기

직접 칠하기 (실제 DOM)

벽 하나하나 붓을 들고 — 벽이 100개면 손이 100번

설계도에 먼저 (가상 DOM)

리모델링 뒤를 설계도에 그리고, 지금 집과 나란히 놓아 다른 점만 — 바뀐 벽이 3개면 붓은 3번

  • React — ①메모리 위 가상 DOM(설계도)을 그리고 ②실제 DOM과 비교 ③바뀐 부분만 적용(이 과정이 재조정)
⚠️ 오해 — 가상 DOM이 항상 가장 빠른 건 아니다. Svelte처럼 컴파일 때 미리 알아내면 비교가 필요 없어 더 빠를 수도. 가상 DOM의 강점은 "가장 빠르다"가 아니라 "개발자가 직접 DOM을 안 만져도 된다"는 편의성(일관성·개발 효율).
📖 2000년대 브라우저는 DOM을 연속으로 건드리면 매번 화면을 다시 계산하는 레이아웃 스래싱을 겪었습니다. 가상 DOM은 "한 번에 모아서 바꾸자"는 해결책이었습니다.

🎯 이 덱의 핵심 정리

개념한 문장
프레임워크반복되는 일을 미리 정리한 개발 골조(약속까지 준다)
세 문제반복·변화·연결 = 컴포넌트·상태·라우팅
컴포넌트설계를 한 곳에 두고 데이터만 바꿔 재사용 — 한 곳 고치면 다 바뀜
상태한 값을 바꾸면 연결된 곳이 모두 일관되게 바뀐다
추상화·모듈화복잡함을 감추고(추상화) 조각으로 나눠(모듈화) 반복을 줄인다
가상 DOM설계도와 현실의 차이만 칠하기 — 편의성이 강점(항상 최속은 아님)
다음 덱에서 이 눈으로 프레임워크를 고르는 법 — 판단 축·AI 친화도·AI와 PRD 대화를 봅니다.

✅ 정답 & 해설

A1. 라이브러리는 내가 필요할 때 불러 쓰지만, 프레임워크는 전체 흐름을 쥐고 있다가 내 코드를 불러 준다(제어의 역전) — "이렇게 나누고 연결하자"는 약속까지.
A2. 반복·변화·연결 = 컴포넌트(재사용 조각)·상태(현재값)·라우팅(주소별 화면).
A3. 설계를 한 곳에 두고 데이터만 바꿔 부르므로, 배지 하나 추가에 컴포넌트 한 곳만 고치면 30개가 다 바뀐다.
A4. 한 상태에서 목록·결과 수·빈 안내·제목이 파생돼, 한 곳을 바꾸면 연결된 곳이 모두 일관되게 바뀐다(한쪽만 예전 값인 버그 방지).
A5. Svelte처럼 컴파일 때 미리 알아내면 비교가 필요 없어 더 빠를 수도. 진짜 강점은 개발자가 직접 DOM을 안 만져도 되는 편의성(일관성·효율).
A2를 쥐면 프레임워크를 문법 묶음이 아니라 문제 해결 도구로 볼 수 있습니다.
