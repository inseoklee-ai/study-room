핵심은 인원수가 아니라 연결된 책임입니다

멀티 에이전트는 여러 에이전트가 참여한다는 뜻일 뿐입니다.

"여러 명"이라는 말이 말해 주지 않는 것

  • 멀티 에이전트는 누가 일을 나누고 누가 다음 행동을 정하는지를 말해 주지 않습니다
  • 같은 수의 워커도 연결 방식에 따라 — 중복 조사 · 대기 · 잘못된 인계처럼 다른 실패를 만듭니다
🎯 구조를 고를 때 먼저 확인할 두 가지 — 결과가 어디로 모이는지와 틀린 결과를 누가 되돌리는지
작업 보드의 카드를 역할별로 나누어 맡는 모습은 핵심이 인원수가 아니라 연결된 책임임을 보여 줍니다.

소통 경로 — 허브형과 직접형

🔵 허브형

모든 소통이 리드를 경유합니다. 오케스트레이터-워커와 팬아웃·합성이 여기 속하며, 리드가 일을 나누고 결과를 받거나 합성합니다

🟣 직접형

에이전트끼리 결과와 제어권을 바로 주고받습니다. 비평-수정과 인계가 여기 속하며, 비평자는 초안 작성자에게 의견을 돌려주고 앞 담당은 다음 담당에게 맥락을 넘깁니다

  • 도식에서 파란 화살표는 제어권 또는 위임의 방향, 회색 화살표는 탐색 결과나 검토 결과가 모이는 방향입니다
두 경로가 책임과 제어권을 어떻게 다르게 움직이는지가 네 구조의 차이입니다.
1

허브형 두 구조

오케스트레이터-워커 · 팬아웃·합성

② 네 가지 구조
모든 소통이 리드를 지나는 구조입니다.

오케스트레이터-워커 — 리드가 나누고 합칩니다

리드는 전략을 세우고 과업을 위임합니다. 워커는 병렬로 탐색하고, 리드는 결과를 받아 합성합니다. Anthropic은 이 구조를 orchestrator-worker라고 부릅니다.

  • 맞는 과업 — 독립된 조사 질문이 여럿인 열린 과업
  • 위험은 모호한 위임입니다 — 워커가 같은 범위를 찾거나, 결과만 전달하고 근거를 남기지 않을 수 있습니다
  • 의존성이 큰 과업에서 워커를 동기 실행하면 — 가장 늦게 끝나는 워커 때문에 전체가 기다립니다
✅ 위험을 낮추는 방법 — 목표 · 출력 포맷 · 도구·출처 지침 · 과업 경계를 먼저 적습니다
소단원 ⑥의 오케스트레이션 실행(C)이 이 구조입니다.

팬아웃·합성 — 독립 결과를 모아 비교

같은 출발점에서 여러 워커가 독립적으로 조사한 뒤 리드가 결과를 비교해 합칩니다. 팬아웃은 일을 여러 갈래로 펼친다는 뜻입니다.

  • 맞는 과업 — 자료 수집과 관점 비교처럼 중간 결과를 기다리지 않고 시작할 수 있는 과업
  • 주요 위험은 독립성만 믿고 결과를 그대로 이어 붙이는 일입니다 — 서로 다른 결과가 같은 근거를 반복하거나 중요한 관점 하나를 빠뜨릴 수 있습니다
🔍 리드가 확인할 것 — 결과의 수보다 근거가 얼마나 겹치는지, 어떤 관점이 비어 있는지
소단원 ①의 "분리는 결과 수가 아니라 증거의 독립성을 만든다"가 여기서 실무 지침이 됩니다.

직접형 두 구조

비평-수정 · 인계

② 네 가지 구조
에이전트끼리 결과와 제어권을 바로 주고받는 구조입니다.

비평-수정 — 비평을 되돌립니다

1초안
→
2비평이 문제를 찾아
작성자에게 돌려줌
→
3수정
  • 맞는 과업 — 반례 점검이나 설계안 검토처럼 한 결과의 약점을 찾아야 하는 과업
  • 비평은 새 답을 많이 만드는 역할이 아니라 — 초안의 근거, 누락, 과도한 일반화를 점검하는 역할
  • 주요 위험은 비평과 수정이 끝없이 반복되는 일입니다. 확인할 항목과 되돌릴 횟수를 정하지 않으면 결론을 늦출 수 있습니다
⚠️ 비평 결과가 초안보다 항상 더 정확하다고 해석해서도 안 됩니다
하네스 중단원 ⑥(반성)의 "틀린 교훈" 문제와 같은 구조의 위험입니다.

인계 — 제어권을 넘깁니다

한 담당이 다음 담당에게 제어권을 넘깁니다. 문의의 성격에 따라 다른 전문 역할로 대화를 이어 가야 하는 과업에 맞습니다.

  • 다음 담당은 이미 확인한 사실과 아직 답하지 못한 질문을 받아야 합니다
  • 주요 위험은 잘못된 인계와 반복 인계입니다 — 인계 기준이 흐리면 같은 설명을 다시 묻게 됩니다
  • 어떤 조건에서 넘기고 어떤 조건에서 앞 담당에게 되돌릴지 기록해야 합니다
고객 지원처럼 역할 전환이 잦은 흐름에서 자주 쓰이는 구조입니다.

패턴-과업 매칭표

패턴소통 경로와 구조맞는 과업주요 위험
오케스트레이터-워커허브형: 리드가 전략·위임·합성독립 조사가 여럿인 열린 과업중복 조사와 대기 병목
팬아웃·합성허브형: 독립 워커 결과를 리드가 비교자료 수집과 관점 비교근거 반복과 누락
비평-수정직접형: 작성자와 비평자가 의견을 주고받음반례 점검과 설계안 검토끝없는 되돌림
인계직접형: 앞 담당이 다음 담당에게 제어권역할 전환이 필요한 대화잘못된 인계와 반복
네 구조 모두 한 실행 환경 안의 에이전트들이었습니다.

오늘 실습에서는 만들지 않는 개념 지도

② 네 가지 구조
오늘 실습에서는 A2A나 Agent Card를 직접 만들지 않습니다. 외부 에이전트 연동을 검토할 때 찾아볼 개념 지도입니다.

같은 환경 안과 밖

🏠 같은 실행 환경 안

환경이 누가 어떤 도구를 쓸 수 있는지, 결과를 어디에 남길지 이미 알고 있었기에 — 내부 호출과 정해진 메시지 포맷만으로 협업

🌐 소유자·프레임워크가 다른 외부

어느 주소로 요청하는지, 상대가 어떤 일을 받을 수 있는지, 일이 끝났는지, 결과물은 어디 있는지가 합의되지 않으면 — "검토를 맡긴다"는 문장만으로는 연결할 수 없습니다

📖 A2A(Agent2Agent Protocol) — 서로 다른 프레임워크나 공급자가 만든 에이전트 애플리케이션 사이의 통신과 상호운용을 목표로 하는 공개 프로토콜. Google이 2025년 4월 발표, 공식 문서는 Linux Foundation 산하 컨소시엄으로 이관되어 TSC가 유지
서로 다른 기관이 같은 표준 서식으로 요청과 확인을 주고받듯, 통신 규격은 참여자 모두가 알아보는 서식을 정하는 일입니다.

약속의 세 층

층내용
발견상대 에이전트가 Agent Card라는 JSON 문서로 이름·접근 URL·인증 방식·수행 가능 기능을 선언. 카드는 이력서에 가깝고, 실제 권한과 품질 검증은 별도로
작업의뢰하는 쪽이 task를 보내고 requested(submitted)·working·완료·실패 상태를 추적. 오래 걸리는 일은 한 번의 응답으로 끝나지 않으므로 상태 조회가 연결의 일부
결과물답변 문장 대신 파일과 구조화 데이터를 담는 artifact로 반환 — "완료"라는 상태와 "무엇이 만들어졌는가"를 구분하는 장치
흐름: 카드 확인 → task 전송 → submitted·working·input-required 상태 갱신 → artifact 반환 → 의뢰자가 검증하고 다음 작업 결정.

Agent Card 초안

{"name":"curriculum-review-agent",
 "description":"교안 초안의 사실 인용과 표현 위험을 검토한다",
 "url":"https://example.org/a2a",
 "skills":[{"id":"citation-review","name":"인용 검토",
            "description":"출처와 주장 연결을 점검한다"}]}
📌 이 한 줄은 구현 완료 선언이 아니라 기능 선언의 초안입니다 — 기능마다 입력 범위 · 반환 artifact · 사람이 승인해야 할 지점 · 허용하지 않는 권한을 덧붙이면 "연결할 수 있는 agent"와 "맡겨도 되는 agent"를 구분하는 설계가 시작됩니다
위 endpoint는 도달하지 않는 자리표시자 값입니다. 실제 배포에서는 환경에 맞게 바꿉니다.

우리 실습과의 관계

  • claude-agent-sdk 0.2.151에서 options.agents의 AgentDefinition은 리드가 워커에 프롬프트·도구·모델을 맡기는 정의입니다. 워커는 자신의 결과를 리드에게 돌려주고 끝납니다
  • 이 SDK 버전에서 서브에이전트끼리 직접 소통하는 방법은 공개 인터페이스로 제공되지 않습니다 — 오늘 실습의 모든 소통은 리드를 경유하는 허브형
  • 스트림 기록에는 같은 세션의 백그라운드 서브에이전트가 보낸 메시지를 구분하는 정보가 남습니다. Claude Code 에이전트 팀 실험 기능과 이어지는 흔적이지만 — 직접 메시지를 보내는 공개 호출은 이 버전에 없고 안정적인 기능도 아닙니다
🎯 도입 판단은 "A2A를 지원하는가"가 아니라 — "우리 과업에 독립된 외부 에이전트가 실제로 있는가"에서 시작합니다
같은 하네스 안의 짧은 서브에이전트 호출이라면 기존 실행 구조가 더 단순할 수 있습니다. 반대로 부서·공급자가 다르고 각자 내부 구현을 감춘 채 반복적으로 과업을 주고받아야 한다면 카드·task·artifact가 설계의 언어가 됩니다. 출처: Google Developers Blog, 「Announcing the Agent2Agent Protocol (A2A)」(2025-04), A2A Project 공식 문서.

❓ 이해도 확인

Q1. 구조를 고를 때 먼저 확인할 두 가지는?
A1. 결과가 어디로 모이는지와 틀린 결과를 누가 되돌리는지.
Q2. 팬아웃·합성에서 리드가 볼 것은?
A2. 결과의 수가 아니라 — 근거가 얼마나 겹치는지, 어떤 관점이 비어 있는지.
Q3. Agent Card는 무엇을 보장하나?
A3. 아무것도 보장하지 않는다. 이력서에 가까운 기능 선언이며 실제 권한과 품질 검증은 별도.
Q3은 이 강의 전체를 관통하는 "문서가 곧 증거는 아니다"라는 원칙입니다.
