1

과제 — 두 갈래 중 하나로 제출

나에게 맞는 쪽을 고른다. 목표는 같다.

A 튜토리얼 · B 내 서비스
두 갈래는 난이도 등급이 아니라 출발점의 차이입니다. 만들 주제가 아직 없으면 A, 지난 시간의 PRD·목업으로 이어갈 주제가 있으면 B를 고릅니다. 어느 쪽이든 '백엔드가 실제로 도는 것'을 경험한다는 목표는 동일합니다.

🔀 나에게 맞는 한 갈래를 고른다

갈래 A — 튜토리얼로 한 바퀴

아직 만들 주제가 없다면. 잘 만든 튜토리얼을 따라 데이터가 진짜로 저장되는 작은 앱(방명록·할 일 목록 등)을 만든다.

갈래 B — 내 서비스에 붙여 배포

만들 주제가 있다면. 지난 PRD·목업을 이어 내 서비스에 백엔드 기능 한 겹을 붙이고 화면까지 배포한다.

공통 목표 — '백엔드가 실제로 도는 것'을 내 손으로 경험. 백엔드가 필요한 기능은 하나면 충분하다.
B의 "기능 하나면 충분"은 예를 들어 글이 저장되어 새로고침해도, 다른 기기에서도 남는 것 정도입니다. 크게 만들 필요가 없습니다. 한 겹이라도 실제로 도는 것이 핵심입니다.

🅰️ 갈래 A — 따라하기 → 내 손으로 바꿔보기

1추천 출발점 — Supabase 공식 퀵스타트. 무료로 DB·로그인·배포까지 한 바퀴를 돈다
2AI와 함께 — "이 튜토리얼을 함께 따라가며 각 단계가 무엇을 하는지 설명해줘"라고 하면 훨씬 남는다
3개선 한 가지 — 그냥 따라만 말고 기능 하나를 더하거나(항목 삭제·검색) 보안 체크를 직접 적용
📤 제출 — 작동 링크(또는 시연) + 내가 바꾸거나 개선한 부분 한 줄.
'따라하기 → 내 손으로 바꿔보기'가 진짜 학습입니다. 튜토리얼을 그대로 끝내면 손끝에 남는 게 적지만, 작은 기능 하나라도 스스로 바꿔보면 각 단계가 무엇을 하는지 몸으로 이해하게 됩니다.

🅱️ 갈래 B — 먼저 설계 한 장(코드가 아니라 지도)

항목내가 채울 것
백엔드가 꼭 필요한 기능저장 / 로그인 / 검색 중 무엇?
화면만으로 되는 기능서버 없이 되는 것은? ('먼저 예측' 표를 다시 보며)
필요한 창구(엔드포인트)예: 목록 주기 / 하나 저장하기 (CRUD 중 무엇?)
다뤄야 할 비밀값API 키·비밀번호 등 환경변수로 뺄 것
호스팅뒤에 나올 '세 가지 길' 중 무엇?
📤 제출 — 작동 링크(또는 3분 시연) '새로고침해도 데이터가 남는' 장면 + 설계 한 장 + 고른 호스팅과 그 이유 한 줄.
설계 한 장은 코드가 아니라 지도입니다. 무엇을 서버에 맡기고 무엇을 화면만으로 처리할지, 어떤 창구가 필요하고 어떤 비밀값을 빼야 할지를 먼저 그려두면, 만드는 도중 길을 잃지 않습니다.
2

공통 — 제출 전 보안 체크

A든 B든, 내기 전에 반드시 지나는 관문

환경변수 · 백엔드 검증 · RLS · 인가 · 요금 한도
보안 체크는 두 갈래 공통입니다. 루브릭의 첫 학습목표가 '보안을 스스로 점검할 수 있다'인 만큼, 이 다섯 항목은 제출 전 반드시 스스로 확인해야 합니다.

✅ 제출 전 보안 체크 다섯

1. 비밀값(키·비밀번호)을 코드에 직접 안 적고 환경변수로 뺐는가?
2. 가격·수량·권한 같은 검증을 백엔드에서 하는가? (프론트만 믿지 않기)
3. (Supabase면) RLS를 켜고 정책을 넣었는가?
4. 로그인이 필요한 데이터에 권한 확인(인가)이 들어가는가?
5. 사용하는 무료 티어의 한도와 요금 알림을 아는가?
이 다섯은 AI가 자주 놓치는 지점이다. 만들 때 프롬프트로 요구하고, 낸 결과를 다시 되물어 확인한다.
프론트만 믿지 않기가 특히 중요합니다. 가격이나 수량, 권한 같은 값은 화면에서 얼마든지 조작될 수 있으므로, 최종 판단은 반드시 백엔드에서 다시 검증해야 합니다.
3

백엔드를 어디에 둘까 — 세 가지 길

상황에 맞게 고른다. 정답은 하나가 아니다.

집+터널 · 무료 클라우드 · Supabase
세 가지 길은 각각 '언제 쓰면 좋은지'와 '한계'가 다릅니다. 원리를 만지고 싶은지, 내 로직을 안정적으로 열고 싶은지, 데이터 저장·조회가 대부분인지에 따라 고르면 됩니다.

🏠☁️🧰 세 가지 길, 언제 · 한계

길무엇언제한계
① 집 컴퓨터 + 터널내 노트북에서 서버를 돌리고 Tailscale Funnel 같은 무료 터널로 공개(포트포워딩 없이·CGNAT 통과)원리를 직접 만지거나 잠깐 시연·공유컴퓨터 꺼지면 멈춤·대역폭/포트 제한 → 상시 서비스엔 부적합
② 무료 클라우드 서버Render처럼 서버 코드를 올려 24시간 돌리는 무료 티어내가 짠 백엔드 로직(엔드포인트·검증)을 안정적으로 열 때안 쓰면 잠들고(첫 요청 ~1분), 무료 DB는 기한이 있을 수 있음
③ Supabase (BaaS)서버 없이 DB·로그인·저장·자동 API를 '빌려' 씀. Postgres 중심백엔드 대부분이 '저장·조회·로그인'이면 가장 빠름내부 함수(Edge Functions)는 Deno+TypeScript로 제한, 장시간 복잡 로직엔 별도 서버
호스팅은 '무엇이 가장 좋은가'가 아니라 내 서비스가 무엇을 필요로 하는가로 고른다.
Supabase는 앱 코드 자체는 여러 언어로 붙일 수 있지만, Supabase 안에서 도는 함수는 Deno와 TypeScript로 제한됩니다. 대부분 기능이 DB에서 파생되는 Postgres 중심 구조라는 점을 기억하면 어떤 일에 맞는지 판단하기 쉽습니다.

⚠️ Supabase 보안은 '자동'이 아니다

  • 브라우저가 공개 키로 DB에 직접 접근하는 구조 → RLS(행 수준 보안)를 켜고 규칙을 짜야만 안전
  • 안 켜면 그 공개 키로 누구나 데이터를 읽고 고치고 지울 수 있다
  • 특히 AI 코딩 툴로 만든 테이블은 RLS가 꺼진 채 시작되는 경우가 많다
공개 키 + RLS 켜짐안전
↔
RLS 꺼짐열린 DB
CVE-2025-48757 — 실제로 수백 개 앱이 데이터를 통째로 노출한 사고. AI에게 "RLS 켜고 정책 넣어줘"라고 반드시 요구·확인.
이 슬라이드는 강의 전체에서 가장 실무적인 경고입니다. Supabase가 편리한 만큼, 기본이 안전한 것은 아니라는 점을 반드시 기억해야 합니다. AI가 만든 테이블일수록 RLS 상태를 직접 확인하세요.

💭 오늘의 회고 — 스스로 답해보기

회고 1. 내 화면이 '세상과 끊겨 있던' 이유를 손님·주방 비유로 한 문장으로?
회고 2. 404와 500 중, 내 서비스에서 더 자주 만나고 싶지 않은 것은? 왜?
회고 3. '먼저 예측' 표에서 틀리게 예측했던 항목이 있나? 지금은 왜 그런지 설명할 수 있나?
회고 4. AI에게 보안을 맡길 때 반드시 되물어야 할 질문 하나는?
회고는 정답을 맞히는 시험이 아니라, 배운 개념이 내 안에서 연결되는지 확인하는 시간입니다. 특히 회고 4는 방금 본 RLS 경고와 곧바로 이어집니다.

📋 프로젝트 제출 루브릭

학습목표평가기준
보안을 스스로 점검할 수 있다제출물에 보안상의 문제가 없는지 잘 검토되어 있고, 실제로 문제가 없어야 한다
실제 동작하는 백엔드 동작을 포함시킬 수 있다실제로 동작하는 백엔드 동작이 의도한 것과 일치한다
프론트엔드와 백엔드가 적절하게 만들어져 동작한다서비스가 직관적이고 의도한 대로 잘 동작한다
📦 제출 — 파일 또는 URL 중 한 방식(ZIP·PDF·이미지, 최대 5MB). 제출 후 수정 불가.
제출 후 수정이 불가하므로, 내기 전에 보안 체크 다섯 항목을 한 번 더 확인하세요. 링크로 제출한다면 실제로 접속되는지, 새로고침해도 데이터가 남는지도 마지막으로 점검합니다.

📌 핵심 정리 — 이 강의가 남긴 다섯

오늘 배운 것한 문장 정리내가 할 수 있는 행동
백엔드의 역할화면 뒤에서 저장·확인·연결을 맡는 '주방'새로고침해도 남아야 할 데이터를 구분
네트워크 네 조각도메인·DNS·HTTP(S)·포트·호스팅이 주소를 화면으로 잇는다안 열릴 때 어디를 볼지 감이 온다
요청의 여정·상태 코드요청→응답 왕복, 맨 앞 숫자가 신호등(4=내 잘못, 5=서버 잘못)에러 번호를 AI에게 그대로 붙여 물어본다
AI 코드의 약점보안·비밀 관리·권한 확인은 AI가 자주 놓친다프롬프트로 요구하고 결과를 되묻는다
배포와 비용화면·서버·데이터를 나눠 올리고 GitHub로 자동 배포환경변수를 넣고 요금 알림을 켜 둔다
이 표는 강의 전체의 한 장 요약입니다. 왼쪽은 개념, 가운데는 한 문장 정의, 오른쪽은 실제로 손을 움직이는 행동입니다. 개념이 행동으로 이어질 때 비로소 배운 것이 됩니다.

✅ 정답 & 해설

A1. A: 튜토리얼로 작은 앱을 한 바퀴 / B: 내 서비스에 백엔드 한 겹 붙여 배포. 공통 목표는 '백엔드가 실제로 도는 것'을 내 손으로 경험.
A2. 꼭 필요한 기능 · 화면만으로 되는 기능 · 필요한 창구(엔드포인트) · 다룰 비밀값 · 호스팅 다섯 항목.
A3. RLS: 공개 키로 DB에 직접 접근하는 구조라 켜야만 데이터가 안전. 백엔드 검증: 가격·수량·권한은 프론트만 믿을 수 없어 서버에서 다시 확인.
A4. ① 집+터널(원리 체험·잠깐 시연) ② 무료 클라우드(내 로직 안정적으로) ③ Supabase(저장·조회·로그인 대부분일 때 가장 빠름).
A5. "공개 키 + RLS 켜짐 = 안전 / RLS 꺼짐 = 열린 DB". 꺼져 있으면 누구나 읽고·고치고·지울 수 있다.
A3와 A5를 자기 말로 설명할 수 있으면 이번 프로젝트의 보안 목표는 달성입니다. AI가 만든 테이블일수록 RLS 상태를 직접 확인하는 습관이 남으면 충분합니다.

백엔드 소단원 종료 · 배운 것을 내 손으로 도는 것으로

백엔드는 화면 뒤의 주방입니다. 저장하고 확인하고 연결하는 그 일들을, 이제 개념이 아니라 내가 만든 서비스에서 볼 수 있습니다. 여기까지가 이 강의입니다 — 배운 것을 도는 것으로 만든 여러분, 수고하셨습니다.
