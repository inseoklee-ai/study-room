1

binding — 채널 계정을 역할에 연결

라우터가 갈 길을 정합니다

⑦ 멀티에이전트
채널 계정은 슬랙 작업공간 하나, 와츠앱 번호 하나 같이 채널이 구분하는 단위입니다.

가장 짧은 형태

{
  agents: {
    entries: {
      main: {
        default: true,
        workspace: "~/.openclaw/workspace",
      },
      support: {
        workspace: "~/.openclaw/workspace-support",
      },
    },
  },
  bindings: [
    { channel: "discord", account: "support", agent: "support" },
  ],
}
  • 예 — 디스코드의 support 계정에서 온 메시지는 항상 support 에이전트로 가게 만드는 규칙이 binding
출처: docs/concepts/agent-bindings

default: true를 반드시 둡니다

기본 에이전트를 정하지 않으면
갈 곳이 없어진 메시지가 조용히 사라지는 사고가 날 수 있습니다
  • 어떤 binding에도 해당하지 않는 대화가 도착하면 기본 에이전트가 받습니다
  • 여러 역할을 두기로 했다면 어느 에이전트가 남은 대화를 받을지 반드시 정해 둡니다
📌 binding이 하는 일은 메시지를 받을 에이전트를 고르는 것까지입니다 — 앞 절의 페어링 승인이나 허용 목록처럼 "누가 말을 걸 수 있는지"를 정하는 규칙은 채널 설정이 따로 가집니다. 라우터가 갈 길을 정할 뿐, 문지방의 기준을 대신 정하지 않습니다
출처: docs/concepts/agent-bindings
2

에이전트마다 분리되는 것

페르소나 하나의 전체

⑦ 멀티에이전트
에이전트 하나가 감싸는 범위를 페르소나 하나의 전체라고 부릅니다.

세 가지가 에이전트마다 따로입니다

항목내용
workspace (작업 폴더)에이전트가 기본으로 일하는 폴더. main과 support가 각자 다른 폴더를 쓰므로 만지는 파일이 처음부터 갈립니다
상태 폴더인증 프로필과 에이전트별 설정이 사는 곳
대화 기록에이전트마다 따로인 SQLite 파일 — ~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite
  • 기억과 기록은 기본으로 섞이지 않습니다 — 한 에이전트의 기본 메모리는 다른 에이전트의 기록을 검색하지 않습니다. 함께 써야 하는 자료는 두 에이전트가 모두 읽는 공유 문서를 명시적으로 둡니다
연구 담당과 코딩 담당이 한 테이블에서 일하면 서류가 섞입니다. 폴더를 나누고 필요한 문서만 복사해 두는 규칙이 있어야 합니다. 출처: docs/concepts/multi-agent

문서가 분명히 적은 경계

⚠️ 상태 폴더 재사용

에이전트끼리 재사용하면 인증과 세션 상태가 충돌합니다

⚠️ 작업 폴더의 성격

기본 작업 경로일 뿐 단단한 격리 장치가 아닙니다 — 폴더 밖의 경로를 막아야 한다면 sandbox를 따로 두어야 합니다

폴더를 나눈 것과
폴더 밖을 막은 것은 다른 일입니다
출처: docs/concepts/multi-agent, docs/concepts/agent-workspace

delegate — 자기 계정으로 대신 행동

사람으로 가장하지 않습니다

⑦ 멀티에이전트
역할이 늘어나면 사람을 대신해 일하는 에이전트가 필요해집니다.

정체성을 한 문장으로 못 박습니다

사람으로 가장하지 않고, 자기 자격 증명으로,
정해진 권한 안에서 대신 행동합니다
  • delegate는 조직 안에서 자기 이메일 주소와 표시 이름을 가지고 일하는 에이전트입니다
  • 내 계정을 빌려주는 자동화가 아니라 — 권한 범위를 정해 둔 보조 구성원을 추가하는 설계
🪜 권한은 작은 것에서 시작합니다 — 첫 단계는 읽고 초안만 만들고 사람의 검토를 받는 등급. 아무것도 승인 없이는 밖으로 나가지 않습니다. 발송과 일정 생성처럼 밖으로 나가는 행동은 다음 등급에서 delegate 자신의 이름으로. 넓힐 때는 도구 제한 · sandbox · 감사 기록을 먼저 갖추는 순서
delegate 문서가 다루는 권한은 조직의 이메일과 캘린더입니다. 넓은 위임 열쇠 하나가 새면 모든 사서함과 캘린더가 열리는 구조라 공식 문서 스스로 최소 권한을 권합니다. 수업에서는 실제 메일 권한을 연결하지 않고 역할과 승인 규칙 설계까지만 다룹니다. 출처: docs/concepts/delegate-architecture

standing orders와 전문가 레인

병렬 작업은 역할 설계가 먼저

⑦ 멀티에이전트
역할이 여럿이면 맡긴 일을 언제 어떻게 하는지 규칙이 필요합니다.

standing orders — 항상 적용되는 지시

칸 1허용
칸 2승인
칸 3중단
  • 무엇을 해도 되는지, 무엇은 승인을 받아야 하는지, 무엇이 보이면 멈추는지를 에이전트에게 미리 적어 두는 규칙
  • 앞 절에서 만든 권한 기준 메모와 같은 문양입니다
출처: docs/automation/standing-orders

전문가 레인과 용량

{
  agents: {
    defaults: {
      maxConcurrent: 4,
      subagents: { maxConcurrent: 8, delegationMode: "prefer" },
    },
  },
  messages: {
    queue: { mode: "collect", cap: 20, drop: "summarize" },
  },
}
  • 공식 문서의 병렬 전문가 레인 — 연구·제작·검토처럼 역할이 겹치지 않게 나누고, 동시에 돌릴 개수를 정해 두는 구성
  • 동시 실행 수에 한도를 두고, 몰리는 메시지는 모아 두었다가 요약해 넘기는 규칙까지가 설계 대상
  • 에이전트를 늘리는 일보다 역할 겹침과 용량을 먼저 정하는 편이 사고를 줄입니다
출처: docs/concepts/parallel-specialist-lanes

에이전트끼리 직접 대화는 기본으로 닫혀 있습니다

{
  tools: {
    agentToAgent: {
      enabled: false,
      allow: ["home", "work"],
    },
  },
}
  • 켜려면 명시적 활성화와 허용 목록이 필요합니다 — 필요한 상대만, 필요한 범위만 지정하는 설계
  • 명령줄의 openclaw agent는 별개의 도구입니다. --agent, --session-id처럼 대상을 지정해 한 번의 실행을 요청할 뿐 — 에이전트 사이의 대화를 여는 장치가 아닙니다
  • 역할 간 전달은 서로의 대화를 모두 보는 것이 아니라, 누구에게 무엇을 넘길지 명시하는 작업입니다
출처: docs/concepts/multi-agent, docs/tools/agent-send

Gateway가 문을 지키고
binding이 대화를 역할에게 나르고
각 에이전트는 자기 폴더와 자기 기록 안에서
정해진 권한만 움직입니다
  • 역할이 이렇게 나뉘면 다음 질문이 따라옵니다 — 역할마다 토큰을 얼마나 쓰는지, 비용이 어떻게 쌓이는지, 지금 연결이 살아 있는지를 어디서 보는지
다음 절에서 이 질문을 직접 확인합니다.

❓ 이해도 확인

Q1. default: true가 없으면?
A1. 어떤 binding에도 맞지 않는 대화가 갈 곳이 없어 조용히 사라지는 사고가 날 수 있다.
Q2. binding과 페어링의 역할 차이는?
A2. binding은 메시지를 받을 에이전트를 고르는 것까지, 페어링·허용 목록은 누가 말을 걸 수 있는지를 정하는 채널 설정. 라우터가 문지방 기준을 대신 정하지 않는다.
Q3. 작업 폴더가 격리 장치인가?
A3. 아니다. 기본 작업 경로일 뿐이며 폴더 밖을 막아야 한다면 sandbox를 따로 둔다. 상태 폴더 재사용은 인증·세션 충돌을 낸다.
Q2와 Q3이 이 절에서 가장 자주 오해되는 지점입니다.
