1

왜 내 노트북으론 벅찰까

학습되는 숫자(파라미터)와 연산량이 문제마다 천차만별

파라미터 · 행렬곱 · GPU
파인튜닝쯤 오면 "내 노트북으론 벅차다"가 느껴집니다. 왜일까요? 학습되는 숫자(파라미터)의 개수와 그에 따르는 연산량 때문입니다.

📏 파라미터 규모의 천차만별

오늘의 학습파라미터(학습되는 숫자)어디서 도나
카페 선형모델2개 (w, b)노트북에서 즉시
MNIST 분류기수만 ~ 수십만노트북 CPU로도 몇 분
ResNet18 파인튜닝약 1,100만GPU 권장(Colab 등)
대형 언어모델(LLM)수십억 ~ 수천억GPU 수백~수천 대, 데이터센터
학습은 매 스텝 "예측→오차→조정"을 하는데, 그 계산의 대부분이 방대한 행렬 곱셈. 파라미터·데이터가 많을수록 곱셈 횟수가 폭발적으로 는다.
LLM의 수천억 파라미터를 1초에 하나씩 세기만 해도 수천 년이 걸립니다. 학습은 이 숫자 전부를 수없이 조정하는 일이니, 데이터센터급 장비가 필요한 이유가 짐작됩니다.

⚙️ 그래서 GPU를 쓴다

CPU

복잡한 일을 순서대로 빠르게 처리하는 큰 코어 몇 개. 다재다능하지만 같은 계산을 대량 병렬로 하는 덴 불리.

GPU

단순한 계산을 동시에 처리하는 작은 코어 수천 개. 행렬 곱셈처럼 "같은 계산을 엄청 많이 병렬로"에 딱.

행렬 곱셈이 병렬에 잘 맞는 건 그 안 수많은 곱셈이 서로 독립이라 순서 없이 한꺼번에 계산되기 때문. 그래서 GPU가 학습을 CPU보다 수십~수백 배 빠르게 끝낸다.
개인 노트북엔 이런 GPU가 없으니 Colab 무료 GPU나 클라우드를 빌려 씁니다. 코딩 에이전트에게 "GPU 런타임에서 돌려 줘"라고 부탁하는 것도 이 때문.

💸 규모를 끝까지 밀면

LLM을 처음부터 학습(사전학습)하려면
고성능 GPU 수천 대 · 수 주 · 수백만~수억 달러
  • 그래서 현실의 실무는 대부분 직접 훈련하지 않는다
  • 이미 학습된 모델을 가져와(파인튜닝) 쓰거나 API로 부른다
  • 오늘 파인튜닝을 체험한 이유 — "남이 배운 것을 물려받는" 감각 + 그 아래 규모·비용의 현실을 함께 알기
원리를 아는 사람이 "무엇을·어디서·어떻게 돌릴지"만 지시하면 되는 시대 — 직접 훈련 코드를 쓰지 않아도.
이 감각이 강의 1의 실용적 목적지입니다. 훈련하는 사람이 아니라, 훈련을 판단·지시하는 사람이 되는 것.

🖥️ Colab CLI로 GPU 손에 넣기

GPU 없는 내 노트북에서 실습을 돌리는 가장 손쉬운 길이 구글 코랩. 2026년 6월, 브라우저 탭 없이 명령어로 쓰는 Colab CLI(google-colab-cli)가 나왔습니다.

pip install google-colab-cli        # 설치 (uv tool install 도 가능)
colab run --gpu T4 train.py          # GPU VM 띄움 → 실행 → 자동 반납
  • 무료는 보통 T4, 더 강한 A100·H100·TPU는 유료(Pro/Pro+)
  • 핵심 — Colab CLI는 AI 에이전트가 직접 쓰도록 설계됨 → Claude Code·Codex 같은 에이전트가 이 명령을 대신 실행
그래서 앞 덱의 "에이전트에게 프롬프트로 시킨다"가 말뿐이 아니라, 에이전트가 실제 GPU에서 코드를 돌리고 정확도를 받아오는 데까지 이어진다.
원리를 아는 사람이 무엇을·어디서·어떻게 돌릴지만 지시하면 됩니다. 훈련 코드를 손으로 쓰지 않아도.

결국 데이터가 전부다

모델 구조보다 데이터가 결과를 가른다

강의 1 정리
오늘 우리는 인공지능이 "배운다"는 것을 세 번 직접 봤습니다 — 회귀·분류·파인튜닝.

🧵 세 실습을 관통하는 한 문장

회귀카페 매출
연속값 예측
분류MNIST
softmax 확률
파인튜닝개/고양이
물려받기
모델 구조보다 데이터가 결과를 가른다데이터 10%↓ → 정확도↓ · 사전학습 특징 물려받기 → 적은 데이터로도 잘 됨
그래서 AI를 다루는 사람의 진짜 일은 "좋은 모델 고르기"보다 좋은 데이터를 모으고 검증하는 것에 가깝습니다.
세 실습 모두 같은 "예측→오차→조정"이었고, 성능을 가른 건 언제나 데이터였습니다.

🧭 그래서 활용가의 일은

  • 앞으로 직접 학습을 돌릴 일은 많지 않다
  • 하지만 원리를 봤기에 — 코딩 에이전트에게 무엇을 시킬지(무슨 데이터로·어떤 학습)
  • 그리고 나온 결과의 무엇을 의심할지(데이터가 충분한가·정확도가 왜 이런가) 판단할 수 있다
다음 — 오늘 잠깐 스친 언어모델의 속
토큰과 컨텍스트, 그리고 트랜스포머
강의 1에서 잡은 "학습=예측·오차·조정 / 데이터가 전부"라는 감각이, 강의 2 트랜스포머로 이어집니다.

🎯 강의 1 핵심 정리

핵심 질문오늘의 답
"배운다"는 무엇인가규칙을 손으로 짜는 대신, 데이터에서 예측→오차→조정을 반복해 패턴을 찾는 것
회귀와 분류의 차이회귀는 연속값(매출), 분류는 어느 범주인지(softmax 확률)
softmax가 하는 일여러 후보 점수를 합이 1인 확률로 바꿔 확신 정도와 함께 고르게
파인튜닝은 왜 쓰나사전학습 특징을 물려받아 적은 데이터·계산으로 내 문제에
왜 GPU가 필요한가학습은 방대한 행렬 곱셈, GPU가 대규모 병렬로 CPU보다 훨씬 빠름
활용가의 진짜 일은모델 고르기보다 좋은 데이터를 모으고 결과를 의심·검증하는 것
강의 1(AI는 어떻게 배우나) 7개 소단원의 결론입니다.

🎯 이해도 확인 질문

Q1. 카페(2개)와 LLM(수천억)의 파라미터 규모 차이가 왜 "노트북으론 벅차다"로 이어지나?
Q2. 학습에 GPU가 CPU보다 유리한 이유는? (행렬 곱셈의 어떤 성질 때문)
Q3. LLM을 처음부터 학습하는 비용은? 그래서 실무는 대개 어떻게 하나?
Q4. 강의 1 전체를 관통하는 한 문장은?
Q5. "활용가의 진짜 일"은 무엇인가?
Q4가 강의 1의 결론입니다 — 데이터가 결과를 가른다.

✅ 정답 & 해설

A1. 학습은 파라미터·데이터에 비례해 행렬 곱셈이 폭발한다. 수천억 파라미터를 수없이 조정하려면 노트북 연산·메모리로는 감당이 안 된다.
A2. 행렬 곱셈 안 수많은 곱셈이 서로 독립이라 한꺼번에 계산 가능 → 작은 코어 수천 개의 GPU가 대규모 병렬로 처리.
A3. GPU 수천 대·수 주·수백만~수억 달러. 그래서 실무는 직접 훈련 대신 파인튜닝하거나 API로 부른다.
A4. 모델 구조보다 데이터가 결과를 가른다(데이터 10%↓ 정확도↓, 사전학습 물려받기 적은 데이터로도↑).
A5. 모델 고르기보다 좋은 데이터를 모으고, 결과를 의심·검증하는 것. 원리를 알기에 무엇을 시키고 무엇을 의심할지 판단한다.
A4·A5가 강의 1의 결론이자 실용적 태도입니다.
