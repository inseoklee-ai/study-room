스킬 너머
— 확장과 요즘 흐름

지금 당장 필요하진 않습니다 — '한 걸음 더' 나가는 이야기

여기부터는 당장 필요하진 않습니다. 스킬·MCP에 익숙해지면 만나게 될 이야기예요. 지금은 이런 게 있다는 감만 잡아도 충분하고, 이 중 끌리는 것만 골라 읽어도 됩니다.

여섯 갈래 — 쌓아 올린 결과들

1플러그인 — 스킬·MCP·명령을 한 꾸러미로 나누기
2에이전트 팀 — 여러 전문 에이전트를 통째로 얹기
3명세 주도 개발 — '먼저 적고 시키기'를 프로젝트 전체로
4컴파운드 엔지니어링 — 일할 때마다 규칙·스킬로 남겨 쌓기
5루프 엔지니어링(Ralph) — 프롬프트가 아니라 루프를 설계하기
6MCP → 스킬 + CLI — 가벼운 쪽으로 도는 요즘 흐름
여섯 갈래 모두 앞서 배운 스킬·MCP·규칙 파일 위에 쌓인 것들입니다. 순서대로 볼 필요는 없습니다.
1

스킬·도구를 통째로 나누기 — 플러그인

한 꾸러미, 명령 한 줄

⑤ 스킬 너머
낱개로 쌓다 보면 남한테 "내 세팅 그대로 써 봐"라고 넘기기가 번거롭습니다.

다섯 가지를 한 꾸러미로

  • 스킬
  • 서브에이전트 — 큰 일을 나눠 맡는 보조 AI
  • 슬래시 명령 — /로 시작하는 단축 명령
  • 자동화 훅 — 정해진 순간에 자동 실행되는 동작
  • MCP 연결
# 마켓플레이스(플러그인 모음)를 하나 등록하고
/plugin marketplace add anthropics/claude-plugins-community
# 거기서 원하는 플러그인을 설치
/plugin install <플러그인이름>@claude-community
⚖️ 필요할 때 켜고 안 쓸 때 끄면 됩니다 — 많이 켤수록 AI가 읽어야 할 맥락이 늘어 느려지니 '지금 쓸 것만'
Anthropic이 직접 고른 공식 모음(claude-plugins-official)과 사람들이 올린 커뮤니티 모음(claude-plugins-community)이 있고, 깃허브 주소나 내 폴더에서 바로 설치할 수도 있습니다.

진짜 빛나는 건 팀에서입니다

보통 좋은 세팅은 잘하는 한 사람 머릿속(이나 노트북)에만 있죠. 그걸 플러그인으로 묶어 두면 —

"우리 팀 코드 리뷰는 이렇게", "배포는 이 순서로" 같은 노하우가
설치 한 번으로 모두의 것이 됩니다
  • 버전이 붙어 있어 만든 사람이 고치면 다 같이 업데이트됩니다
  • 문제가 생기면 이전 버전으로 되돌리기도 됩니다
출처: Anthropic, "Claude Code plugins" 공식 문서, 2026. 이 강의의 과제(스킬 하나를 GitHub에 올리기)가 그 첫걸음입니다.

oh-my-claudecode · omo

⑤ 스킬 너머
서브에이전트를 아예 '팀' 규모로 키운 오픈소스 레이어들입니다.

지휘자가 나눠 맡기고 병렬로

큰 일이 들어오면 지휘자가 알아서 조사·구현·검증 담당에게 나눠 맡기고 병렬로 굴리는 식입니다.

oh-my-claudecode

Claude Code에 플러그인으로 얹는 '팀 우선' 오케스트레이션 레이어. 설치하면 수십 개의 전문 에이전트와 스킬이 한 번에 딸려 온다

oh-my-openagent (omo)

한발 더 나아가 모델을 가리지 않는다. Claude든 GPT든 Gemini든 한 인터페이스 뒤에 묶어 "잔일엔 값싼 모델, 판단엔 제일 똑똑한 모델"처럼 골라 쓴다

/plugin marketplace add https://github.com/Yeachan-Heo/oh-my-claudecode
/plugin install oh-my-claudecode
🧭 omo는 특정 회사 도구에 묶이고 싶지 않을 때의 선택입니다 — 소단원 ④의 "모델은 갈아 끼우는 부품"과 이어집니다
첫날부터 손댈 도구는 아닙니다. 그래도 알아 둘 값어치가 있어요 — "AI 하나에게 다 시키기"에서 "여러 전문 AI를 지휘하기"로 넘어가는 흐름의 끝에 이런 레이어가 있고, 이게 오늘 배운 스킬·플러그인·서브에이전트를 차곡차곡 쌓아 올린 결과라는 것. (출처: oh-my-claudecode·oh-my-openagent 공식 저장소, 2026)

프롬프트를 넘어 루프로 — 'Ralph'

루프 엔지니어링

⑤ 스킬 너머
이름은 심슨 캐릭터 랠프 위검에서 땄습니다. '단순해 보이는데 진짜 되더라'는 뜻으로 붙였고, 유래와 실전 방법은 헌틀리의 원문 https://ghuntley.com/ralph 에 정리돼 있습니다.

방법은 놀랄 만큼 단순합니다

1같은 지시(스펙 = 앞서 본 명세 파일)를 계속 다시 준다
2한 번에 한 가지만 하고 커밋하기를 목표를 이룰 때까지 반복
3진행 상황은 대화 기억이 아니라 파일과 git에 쌓아 둔다
  • 헌틀리의 원래 방식은 명령줄에서 에이전트를 매번 새로 호출하는 bash 루프라, 한 바퀴가 새 프로세스로 시작됩니다
  • 단, '깨끗한 대화 리셋'이 Ralph의 정해진 기능은 아니고 같은 세션에 지시만 다시 넣는 구현도 많습니다
개발자 제프리 헌틀리가 퍼뜨렸습니다. 단순한데 되는 이유가 다음 슬라이드입니다.

왜 하나의 긴 대화 대신 이렇게 할까

앞서 본 '컨텍스트 부패'를 떠올리면 됩니다. 대화가 길어질수록 AI가 헤매니, 상태를 대화 기억에 쌓지 않고 스펙·AGENTS.md 같은 고정 파일과 git에 둡니다.

🔁 그러면 어느 바퀴에서 시작하든 AI가 같은 안내 파일을 근거로 삼습니다

2023 AutoGPT

'무한 반복'으로 실패

Ralph

'멈출 기준(스펙) + 파일에 쌓는 진행'으로 다시 풀었다

  • 헌틀리는 이 방식으로 프로그래밍 언어 하나를 약 300달러어치 호출로 만들어 화제가 됐습니다
소단원 ①의 AutoGPT 소동과 소단원 ④의 컨텍스트 부패가 여기서 합쳐집니다. 강의 전체에서 가장 잘 맞물리는 대목입니다.

이제 도구에 아예 들어왔습니다

  • Claude Code에는 목표만 주면 알아서 도는 /goal 명령이 생겼습니다
  • Anthropic과 OpenAI가 '루프 만드는 법'을 공식 문서로 냈습니다
  • Claude Code를 만든 보리스 체르니는 이렇게까지 말합니다 —
"나는 이제 프롬프트하지 않는다
루프를 돌리고, 그 루프가 대신 프롬프트한다"
⚠️ 다만 안전장치가 없으면 무한 반복·엉뚱한 목표·요금 폭발이 흔하니, 멈출 기준과 검토는 여전히 사람 몫입니다
출처: Geoffrey Huntley, "ralph"; Anthropic, "Getting started with loops", 2026; Pragmatic Engineer, "What is loop engineering".

요즘 흐름 — MCP에서 '스킬 + CLI'로

가벼운 쪽으로 도는 반작용

⑤ 스킬 너머
MCP는 편하지만 공짜가 아니라는 이야기입니다. 이 흐름이 소단원 ⑥ 실습의 설계 근거입니다.

MCP는 공짜가 아닙니다

연결해 두면 AI가 그 도구 설명서를 미리 통째로 읽어 두는데, 이게 앞서 본 컨텍스트(기억 공간)를 꽤 잡아먹습니다.

⚠️ 서버 몇 개만 붙여도 대화를 시작하기도 전에 수만 토큰이 날아가곤 합니다

그래서 2026년 들어 재미있는 반작용이 생겼습니다 — 무거운 MCP 서버 대신, AI가 원래 알고 있는 명령줄 도구(CLI)를 그냥 쓰게 하자는 흐름이죠.

  • 예 — 깃허브 작업은 gh라는 공식 CLI가 이미 있고, AI는 이 명령을 학습으로 알고 있습니다
  • 그러니 GitHub용 MCP 서버를 따로 세우는 대신 "gh로 이슈 목록 가져와"라고 시키면 됩니다
출처: Anthropic, "Code execution with MCP", 2025. 다음 슬라이드에 실측 수치가 나옵니다.

같은 일을 하는데 — 1천 vs 4만 토큰

비교가벼운 쪽무거운 쪽
같은 작업 수행CLI 약 1,000 토큰MCP 약 40,000 토큰
도구 설명 방식800토큰짜리 스킬 파일28,000토큰짜리 MCP 설명서
  • 여기에 "이럴 땐 이 명령을 써" 정도를 담은 짧은 스킬 파일 하나만 얹으면 더 빠르고 정확해집니다
  • 800토큰짜리 스킬 파일이 2만 8천 토큰짜리 MCP 설명서보다 나았다는 결과도 있습니다
출처: MCP·CLI 벤치마크 및 실무자 비교, 2026. 수치는 특정 작업 기준이라 상황에 따라 다릅니다.

그런데 이 문제도 도구 쪽에서 손보고 있습니다

요즘 Claude Code는 연결된 MCP 도구를 처음부터 다 읽지 않고, 필요할 때 검색해서 그때그때 불러오는 방식(툴 서치)을 기본으로 씁니다.

🎯 그래서 MCP를 잔뜩 붙여 둬도 예전처럼 대화를 시작하자마자 컨텍스트가 꽉 차진 않습니다
  • 즉 'MCP는 무거우니 무조건 피하라'가 아니라, 무거운 부분은 도구가 알아서 덜어 주는 쪽으로 가고 있는 겁니다
출처: Anthropic, "Advanced tool use"; Claude Code MCP 문서. 기술 비교는 반년이면 뒤집힌다는 걸 보여 주는 좋은 예입니다.

요즘 정리 — 셋 중 하나가 아니라 함께

내 상황가벼운 선택
혼자 작은 걸 만들 때이미 있는 CLI + 짧은 스킬 — 가볍고 빠르다
여럿이 쓰고 접근 권한·기록이 중요할 때MCP — 표준화된 관리가 여전히 강하다
MCP가 한물간 건 아닙니다
스킬 · MCP · CLI를 상황에 따라 함께 씁니다
회사 환경에서는 MCP의 표준화된 관리(권한·감사 기록)가 강점입니다. 이 판단이 소단원 ⑥ 실습의 마지막 결론으로 다시 나옵니다.

Q1. 플러그인이 팀에서 특히 값진 이유는?
A1. 잘하는 한 사람 머릿속에만 있던 세팅(스킬·MCP·명령·훅)을 설치 한 번으로 모두의 것으로 만들고, 버전·롤백이 된다.
Q2. Ralph 루프가 상태를 '대화 기억'이 아니라 파일·git에 쌓는 이유는?
A2. 컨텍스트 부패 — 대화가 길어지면 AI가 헤매기 때문. 파일에 두면 어느 바퀴에서 시작하든 같은 안내 파일을 근거로 삼는다.
Q3. 2023년 AutoGPT와 Ralph의 결정적 차이는?
A3. Ralph에는 멈출 기준(스펙)과 파일에 쌓는 진행이 있다. AutoGPT는 언제 멈출지 몰라 무한 반복했다.
Q4. "MCP는 무거우니 무조건 피하라"가 왜 틀린 결론인가?
A4. 툴 서치처럼 도구가 무거운 부분을 덜어 주는 쪽으로 발전하고 있고, 여럿이 쓰며 권한·기록이 중요한 환경에서는 MCP의 표준화된 관리가 여전히 강하다.
Q4는 "새로운 게 항상 옳다"는 성급한 결론을 막습니다.
