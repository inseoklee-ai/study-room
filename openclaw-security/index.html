1

파일과 명령의 범위

도구 목록이 곧 권한입니다

⑤ 보안
세션의 sessionRoot는 파일 접근을 판단하는 작업 폴더 경계입니다.

권한 모드가 정하는 것

  • 세션의 sessionRoot는 파일 접근을 판단하는 작업 폴더 경계입니다
  • 권한 모드(permission mode)는 그 경계 안팎에서 파일을 읽고 쓰는 범위와 명령 실행을 누가 검토하는지 정합니다
🎯 도구 목록이 곧 권한이라는 말은 — 에이전트가 할 수 있는 행동이 보이는 도구에 한정된다는 뜻입니다
출처: docs/gateway/permission-modes

모드파일 읽기파일 쓰기명령 실행

2

채널 입구에서 계정을 구분합니다

앞 절 페어링 승인의 이유

⑤ 보안
페어링은 승인 대기 계정을 확인한 뒤 대화를 허용하는 입구의 신원 확인입니다.

입구를 더 좁게

  • 앞 절에서 Telegram 첫 메시지에 페어링 승인을 한 까닭 — 봇에게 말을 거는 계정을 구분하기 위해서
  • 소유 계정 하나만 쓰는 봇이라면 numeric Telegram ID를 허용 목록에 넣어 입구를 더 좁게 제한할 수 있습니다
  • open 정책은 공개 봇에만 맞고, 그 경우에도 도구를 강하게 제한해야 합니다
⚠️ 그룹 대화에서는 누가 메시지를 보냈는지 따로 제한할 수 있으며 — 직접 메시지의 페어링 승인이 그룹 발신자 허용 목록으로 자동 확대되지는 않습니다
출처: docs/channels/telegram. 승인의 범위가 자동으로 넓어지지 않는다는 점이 핵심입니다.

읽은 내용과 실행 요청을 분리합니다

프롬프트 인젝션

⑤ 보안
웹 문서, 이메일, 채팅 메시지에는 사람에게 명령처럼 보이는 문장이 섞일 수 있습니다.

읽어 온 문서는 실행 허가가 아닙니다

📖 프롬프트 인젝션 — 외부 내용에 섞인 문장이 에이전트의 원래 과업보다 앞서 행동하게 유도하는 일
읽어 온 문서는 판단 재료일 뿐
실행 허가가 아닙니다
  • 외부 내용을 읽는 역할에는 읽기 전용 도구를 두고 — 명령 실행이나 파일 변경이 필요한 과업은 별도 승인 뒤에 진행합니다
  • OpenClaw 보안 문서의 안내 — 신뢰하기 어려운 내용을 요약하는 읽기 전용 에이전트를 따로 두고, 검색·웹 읽기·브라우저 도구는 필요한 경우에만 켜기
출처: docs/gateway/security/index.md

음성 환경에서도 다시 확인합니다

  • 파일을 바꾸거나 외부로 보내는 행동을 시작하기 전에 — 요청 내용을 말로 다시 읽고, 승인 의사를 발화로 받는 규칙을 둡니다
말한 요청과 실제 실행은
다른 권한이라는 원칙을 유지합니다
소단원 ⑩의 Talk mode에서 같은 원칙이 다시 나옵니다.

❓ 이해도 확인

Q1. 요약 과업은 어느 모드에서 시작하나?
A1. read-only. 파일 쓰기 도구가 아예 없고 명령 실행은 거부된다. 파일을 고칠 때만 guarded를 검토한다.
Q2. DM 페어링 승인이 그룹 대화까지 확대되나?
A2. 아니다. 그룹 발신자 허용 목록은 따로 제한해야 한다.
Q3. 명령 허용 목록 우회 권고가 보여 준 것은?
A3. 명령 이름을 제한하는 일과 인자를 제한하는 일은 다른 일이라는 점.
Q3은 허용 목록을 만들 때 반드시 기억해야 하는 교훈입니다.
