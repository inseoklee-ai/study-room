연결을 맡는 세 역할

호스트 · 클라이언트 · 서버

② MCP 구조
'서버'라는 말이 나오면 인터넷 어딘가의 큰 컴퓨터를 떠올릴 수 있습니다.

세 역할

역할구체적인 대상학생이 확인할 것
호스트Claude Code 또는 OpenCode — 대화와 모델 사용을 관리하고 어떤 서버를 연결할지, 도구 실행을 어떻게 허용할지 다룸내가 대화하는 앱과 서버 연결 상태
클라이언트호스트 안에서 각 MCP 서버와 메시지를 주고받는 구성 요소어떤 서버에 메시지를 전달하는 연결인지
서버weekly_records_server.py로 제공하는 weekly-records — 요청에 기능이나 자료를 제공하는 프로그램의 역할어떤 기능이 공개되어 있고 어떤 자료를 반환하는지
📌 학생이 클라이언트 프로그램을 별도로 작성하거나 설치하지 않습니다 — 사용하는 앱이 이 역할을 담당합니다. 이번 실습의 서버는 내 컴퓨터에서 실행하는 작은 Python 프로그램입니다
클라이언트와 서버가 같은 컴퓨터에서 실행되어도 이 구분은 그대로입니다 — '어디에서 실행되는가'와 '어떤 역할을 하는가'는 서로 다른 질문입니다.

사용자의 말이 이동하는 경로

1사용자가 호스트에 "첫 주 기록을 읽어 줘"라고 말합니다
2모델이 사용할 도구와 입력을 선택해 호출을 요청합니다
3호스트가 필요한 실행 허용을 처리하고, 클라이언트를 통해 서버에 메시지를 전달합니다
4서버의 Python 코드가 기록을 읽어 결과를 돌려주면 호스트가 모델에게 전달해 답변을 이어 갑니다
🎯 도구 선택을 요청하는 모델과 파일을 실제로 읽는 서버는 서로 다른 역할입니다
Claude Code와 OpenCode를 함께 켜서 같은 로컬 서버 코드를 등록하면 각 앱이 자기 서버 프로세스를 시작할 수 있습니다 — 같은 소스 파일을 쓴다는 말이 실행 중인 프로그램 하나를 공유한다는 뜻은 아닙니다.

도구의 안내와 업무 데이터

모든 업무 기록을 곧바로 보낼 필요는 없습니다

② MCP 구조
우선 무슨 도구가 있으며 어떻게 호출하는지를 알려 줄 수 있습니다.

안내와 인자

안내 항목내용
이름get_weekly_records
설명week-one 또는 week-two의 업무 기록을 읽습니다. 보고서 작성이나 완료·진행·위험 판정은 하지 않습니다
필요한 입력week: 조회할 주차를 나타내는 문자열
반환할 자료주차 · 팀 이름 · 기간 시작일 · 보고 기준일 · 업무 기록 목록
{"week":"week-one"}
  • 왼쪽 week는 입력 항목의 이름, 오른쪽 week-one은 이번 호출에서 선택한 값. { }는 이름과 값을 묶는 객체(object)
  • 이것은 JSON — 서로 다른 언어로 만든 프로그램도 같은 데이터를 읽도록 텍스트로 표현. Python 딕셔너리와 겉모습은 비슷하지만 완전히 같은 문법은 아닙니다 (문자열은 큰따옴표, 값 없음은 None 대신 null)
인자(argument)는 함수를 실제 호출할 때 넣는 값입니다.

입력 스키마

{
  "type": "object",
  "properties": {
    "week": { "type": "string" }
  },
  "required": ["week"]
}
  • type: object는 입력 전체가 객체라는 뜻, properties 아래에는 항목의 규칙, required는 반드시 들어가야 하는 항목
  • {}를 보내면 week가 빠져 있고, {"week": 1}은 항목은 있지만 자료형이 다릅니다
⚠️ "week-three"도 문자열이므로 자료형 규칙만 보면 맞습니다. 하지만 실습 자료에는 첫째·둘째 주만 있습니다 — 자료형 검사와 우리 업무에서 허용하는 값 검사는 구분됩니다
실제 SDK가 만드는 안내에는 제목 등 다른 정보도 포함될 수 있어 필요한 부분만 발췌했습니다. 두 번째 검사는 다음 절의 Python 함수가 담당합니다.

도구를 연결했다고 읽은 것은 아닙니다

데이터를 받은 상태

JSON-RPC 메시지 읽기

도착 순서 대신 식별자로 짝짓기

② MCP 구조
JSON이 데이터를 적는 형식이라면, JSON-RPC는 그 형식으로 요청과 응답을 주고받는 약속입니다. RPC는 Remote Procedure Call입니다.

목록 요청과 호출 메시지

{ "jsonrpc": "2.0", "id": 1, "method": "tools/list" }

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_weekly_records",
    "arguments": { "week": "week-one" }
  }
}
  • jsonrpc의 2.0은 JSON-RPC의 버전 — Python SDK의 2.1.1이나 날짜로 적는 MCP 명세 버전과 서로 다릅니다
  • params는 메서드에 전달하는 입력을 묶습니다. 바깥의 tools/call은 '도구 실행'이라는 공통 작업, 안쪽의 get_weekly_records는 '주간 기록 조회'라는 구체적 기능
수업 서버는 MCP Python SDK 2.1.1로 제작하고 실제 stdio 검증에서 2025-11-25로 통신했습니다. 처음의 initialize 요청과 준비 완료 알림은 호스트와 SDK가 담당하므로 학생이 직접 작성할 필요는 없습니다.

이름이 같은 두 id

{
  "id": "TASK-102",
  "title": "로그인 안내 문구 개선",
  "owner": "지우",
  "status": "개발 완료",
  "due_date": "2026-09-07",
  "deployed_at": null,
  "verification": "미실시",
  "blocker": null,
  "note": "코드 작성은 끝났으며 다음 배포를 기다린다."
}
위치목적
id: "TASK-102"업무의 식별자
id: 2 (호출 메시지)통신 요청의 식별자
📌 앱이 첫 주를 id: 2, 둘째 주를 id: 3으로 보냈는데 둘째 주가 먼저 읽혔다면 — 먼저 도착했다는 이유로 첫 주의 답장으로 처리하면 잘못된 보고서가 됩니다. 도착 순서 대신 식별자로 요청과 응답을 짝짓습니다
업무 자료는 result 안의 structuredContent에서 구조를 유지한 객체로 읽을 수 있습니다. JSON-RPC에는 응답을 기대하지 않는 알림도 있으며, 그런 알림은 요청 ID를 붙이지 않습니다.

tools · resources · prompts

작업 동사 하나로 정답을 정하지 않습니다

② MCP 구조
MCP 서버가 공개할 수 있는 것은 도구만이 아닙니다.

세 종류

종류성격이 팀 업무의 예
Tool입력을 받아 실행하는 기능. 검색·계산·조회도 도구가 될 수 있음 — '도구는 수정 작업만 한다'고 이해하면 읽기 전용 MCP의 역할을 놓칩니다주차를 받아 업무 기록 조회
Resource식별자(URI)로 가리켜 읽는 자료. team://guide/terms처럼 해당 서버에서 해석하는 식별자도 있어 브라우저에 붙여 넣어 열리는 것은 아님팀 용어 안내 자료
Prompt서버가 제공하는 대화 템플릿. 값이 들어간 대화 메시지 묶음을 호스트가 받아 사용주차가 들어간 보고 시작 대화
🎯 "기록을 읽으니까 무조건 resource"처럼 작업 동사 하나로 정답을 정하지 않습니다 — 앱이 실행할 기능으로 제공할지, 읽을 자료로 제공할지가 설계의 차이입니다. 세 종류를 모두 구현해야 MCP 서버가 되는 것은 아닙니다
뒤에서 작성할 Agent Skill과 MCP Prompt도 이름만 보고 같은 것으로 생각하지 마세요. MCP Prompt는 서버에서 발견하고 가져오는 대화 템플릿이고, Skill은 과업 수행에 필요한 지식·절차·자료를 묶는 방식이며 MCP 없이도 사용할 수 있습니다.

메시지가 오가는 통로

stdio와 Streamable HTTP

② MCP 구조
지금까지는 '무슨 말을 주고받는지'를 읽었습니다. 이제 '어떤 통로로 주고받는지'를 봅니다.

stdio — 표준 입력과 표준 출력

호스트의 클라이언트 ── 요청 ──▶ 서버의 stdin
호스트의 클라이언트 ◀─ 응답 ─── 서버의 stdout
  • 이번에는 호스트가 서버용 명령을 실행해 로컬 서버 프로세스를 시작합니다 — 학생이 별도 창에 서버를 항상 띄워 두고 기다리는 구조로 시작하지 않습니다
  • 그래서 첫 서버에는 웹 주소가 없어도 됩니다. 호스트는 서버를 시작할 실행 파일과 인자를 알아야 합니다
⚠️ 익숙한 print()가 문제를 만듭니다 — stdio 서버의 표준 출력은 이미 MCP 메시지용 통로입니다. 일반 문장을 섞으면 받는 쪽이 MCP 메시지로 해석하려다 실패할 수 있습니다
서버가 시작되었습니다!
{"jsonrpc":"2.0","id":2,"result":{"content":[]}}
위는 문제가 있는 출력의 설명용 예입니다. 로그는 별도의 표준 오류(stderr)로 보내면 통신 출력과 구분할 수 있습니다 — print("...", file=sys.stderr). 이름에 '오류'가 들어 있어도 정상 시작 같은 진단 정보를 기록할 수 있습니다.

두 통로의 시작점

연결 방식호스트가 알아야 하는 시작점이해하기
stdio실행할 프로그램과 인자내 앱이 내 컴퓨터에서 업무 기록 서버를 시작하고 입출력 연결
Streamable HTTPMCP 서버의 URL (https://.../mcp)실행 중인 팀 서버의 주소로 메시지를 보내 기록 조회
⚠️ 이 차이를 '인터넷 사용 여부'로 외우면 예외가 생깁니다 — HTTP 서버도 내 컴퓨터에서 띄울 수 있고, stdio로 연결한 로컬 서버가 내부에서 Google API를 호출할 수도 있습니다
  • 따로 그려 볼 것 — 호스트와 MCP 서버 사이의 통로, 그리고 MCP 서버가 업무 자료에 접근하는 방식
Google 자료가 있다면 '호스트 ↔ 로컬 MCP 서버'는 stdio이고 '로컬 MCP 서버 ↔ Google 서비스'는 인터넷 요청일 수 있습니다. 공통 메시지 형식을 쓴다고 계정 자료를 자동으로 읽을 수 있게 되는 것은 아닙니다.

내부 구현을 서버에 두고 기능만 제공

호스트와 주고받는 것제공자 서버에 둘 수 있는 것
도구 이름·설명·입력 스키마도구를 구현한 소스 코드와 내부 알고리즘
조회할 주차 같은 호출 인자원본 데이터베이스와 조회·가공 과정
서버가 반환하도록 정한 업무 기록응답에 포함하지 않은 다른 팀·다른 기간의 자료
⚠️ 오른쪽이 자동으로 비공개가 되는 것은 아닙니다. 서버가 원본 자료를 응답에 넣으면 그 자료는 호스트로 전달됩니다. API 키나 접근 토큰도 도구 설명이나 결과에 포함하지 않아야 합니다 — 인증과 접근 권한도 별도로 구현
  • MCP가 더하는 이점은 — 여러 호스트가 같은 방식으로 도구를 발견하고 호출할 수 있다는 것. 소스 코드를 배포하지 않는 구조 자체는 일반 원격 API에서도 가능합니다
  • 서버를 원격으로 옮겨도 모델마다 다른 호출 표현이나 파서의 차이까지 해결되지는 않습니다
예시 주소 https://reports.example.com/mcp는 설명용이며 접속·등록 대상이 아닙니다. /mcp라는 글자가 필수는 아니고, 제공자가 정한 실제 엔드포인트 URL을 사용합니다.

❓ 이해도 확인

Q1. 호스트·클라이언트·서버 중 학생이 직접 만드는 것은?
A1. 서버뿐이다. 호스트는 쓰는 앱이고 클라이언트는 그 앱 안의 연결 구성 요소다.
Q2. tools/call과 get_weekly_records의 관계는?
A2. 앞은 MCP가 정한 메서드 이름(도구 실행), 뒤는 우리가 만든 업무 도구의 이름. 도구가 늘어도 메서드는 그대로다.
Q3. stdio 서버에서 print()를 조심해야 하는 이유는?
A3. 표준 출력이 이미 MCP 메시지용 통로라서. 진단은 표준 오류로 보내고 실제 반환값은 return으로 돌려준다.
