1

실행 환경 세 갈래

같은 역할 이름이어도 코드는 서로 바꿔 쓸 수 없다

Claude Agent SDK · LangChain+Gemini · Ollama
system·user·assistant라는 역할 구분은 어디서나 같은 개념이지만, 라이브러리마다 자료형도 호출 방식도 다릅니다. 이 차이는 감출 결함이 아니라 실행 환경을 고를 때 확인할 조건입니다.

🧩 같은 역할, 다른 인터페이스

  • system·user·assistant 역할 구분은 모든 라이브러리에서 같은 자료형·호출 방식으로 나타나지 않는다
  • 인터페이스 차이는 감출 결함이 아니라 실행 환경을 고를 때 확인할 조건 — 인증·자료형·호출 메서드·비용·모델 한계가 다르다
  • 같은 역할 이름을 봤다고 코드를 서로 바꿔 쓸 수 없다
세 경로 모두 system을 바꾸거나 이력을 제공했을 때 응답이 어떻게 달라지는지 관찰할 수 있다. 다만 만드는 방법은 같지 않다 — 한쪽 입력 모양을 다른 쪽에 억지로 옮기지 않는다.
비교 질문은 어느 경로든 같습니다. user 요청을 고정한 뒤 system만 바꾸면 문체·구조·추가 정보 요청이 무엇이 달라지는가, 이력을 넣으면 새 응답이 실제로 반영하는가. 오류가 나면 전문도 남겨 인증·혼잡·모델 출력 문제를 프롬프트 변경과 구별합니다.

📋 세 실행 환경 비교

경로되는 것주의할 점
Claude Agent SDK구독 로그인 인증. ClaudeAgentOptions(system_prompt=...) + query()의 비동기 user 메시지 생성기로 에이전트 실행 구성범용 chat completions식 messages 배열 API가 아님. 토큰당 과금이 아니라 구독 로그인 안에서 동작
LangChain + GeminiAPI 키 인증. SystemMessage·HumanMessage·AIMessage 목록을 invoke()에 전달. 같은 추상화로 공급자 교체추상화가 공급자 고유 기능을 감출 수 있음. 재실측 시 고수요로 503 UNAVAILABLE 발생 → 키가 있어도 성공 보장 아님
Ollama인증 없이 로컬 실행. system·user·assistant role 딕셔너리 목록을 chat()에 전달. 사용료 없이 반복 관찰로컬이라는 사실이 품질 보장 아님. 소형 모델의 지시 이행·한국어 품질 자체가 관찰 대상
세 코드를 같은 모양으로 만드는 게 아니라 — 구독 로그인으로 에이전트 실행을 볼지, API 키+범용 메시지 추상화를 쓸지, 로컬 모델의 조건·한계를 시험할지 결정한다.
세 경로의 선택 기준은 표의 두 열에 있습니다. 되는 것과 주의할 점을 함께 읽어야, 실습에서 나온 결과를 인증 문제인지·혼잡 문제인지·모델 출력 문제인지 구별할 수 있습니다.

🅰️ Claude Agent SDK — system A/B 비교

도구 없이 한 턴. 이력은 assistant 배열로 넣지 않고, 비동기 user 생성기로 질문을 전달한다.

QUESTION  = "배송일은 언제인가요?"
SYSTEM_A  = "고객 문의에 정중하게 답한다"
SYSTEM_B  = "기술 문서 톤으로 답한다"

async def user_messages(text):
    yield {"type":"user","message":{"role":"user","content":text}}

async def save_run(filename, system_prompt):
    options = ClaudeAgentOptions(system_prompt=system_prompt, max_turns=1, tools=[])
    async for event in query(prompt=user_messages(QUESTION), options=options):
        ...  # event!r 를 원문으로 기록
    # claude-system-a.txt / claude-system-b.txt 로 저장
max_turns=1은 턴 수만 제한(답변 길이 아님), tools=[]는 도구 호출 제외. assistant 이력을 범용 배열로 주입하는 실험은 이 예제 범위가 아니다.
Claude Agent SDK는 범용 chat completions API가 아니라 에이전트 실행을 구성하는 방식입니다. 생성기에 assistant 역할 태그를 문자열로 조립해 배열 API를 흉내 내는 것은 부자연스럽습니다. 멀티턴 효과는 LangChain·Ollama 경로에서 봅니다.

🅱️ LangChain + Gemini — 메시지 객체 목록

SystemMessage·HumanMessage·AIMessage 목록을 invoke()에 전달. 같은 추상화로 이력까지 한 번에.

model = ChatGoogleGenerativeAI(model="gemini-3.7-flash")

def save_run(filename, messages):
    Path(filename).write_text(str(model.invoke(messages).content), ...)

save_run("gemini-system-a.txt", [SystemMessage(SYSTEM_A), HumanMessage(QUESTION)])
save_run("gemini-system-b.txt", [SystemMessage(SYSTEM_B), HumanMessage(QUESTION)])
save_run("gemini-with-history.txt", [
    SystemMessage(SYSTEM_A), HumanMessage(QUESTION),
    AIMessage("정확한 안내를 위해 주문번호 또는 운송장 번호를 알려 주세요."),
    HumanMessage("주문번호가 없으면 무엇을 확인해야 하나요?"),
])
GEMINI_API_KEY를 셸 환경 변수로 설정한 뒤 사용. 여기서는 AIMessage로 이력을 명시해 멀티턴 효과를 관찰할 수 있다.
LangChain은 세 종류 메시지 객체를 목록으로 넘기는 통일된 추상화를 제공합니다. 편리하지만 공급자 고유 설정을 감출 수 있고, 재실측에서 503 UNAVAILABLE 같은 일시적 혼잡을 만날 수 있어 프롬프트 변경과 구별해 기록해야 합니다.

©️ Ollama — role 딕셔너리 목록

인증 없이 로컬 모델 실행. system·user·assistant를 그대로 딕셔너리로 쌓는다.

def save_run(filename, messages):
    Path(filename).write_text(
        chat(model="qwen3.5:2b", messages=messages).message.content, ...)

save_run("ollama-with-history.txt", [
    {"role":"system",   "content":"고객 문의에 정중하게 답한다"},
    {"role":"user",     "content":"배송일은 언제인가요?"},
    {"role":"assistant","content":"정확한 안내를 위해 주문번호 또는 운송장 번호를 알려 주세요."},
    {"role":"user",     "content":"주문번호가 없으면 무엇을 확인해야 하나요?"},
])
사용료 없이 반복 관찰이 가능하다. 단 로컬이라는 사실이 품질 보장은 아니며, 소형 모델의 지시 이행·한국어 응답 품질 자체가 관찰 대상이다.
Ollama는 system·user·assistant를 가장 날것 그대로 role 딕셔너리로 쌓는 방식입니다. 세 라이브러리의 이력 표현이 서로 얼마나 다른지 — 문자열 조립, 메시지 객체, role 딕셔너리 — 를 비교하면 "같은 개념, 다른 인터페이스"가 분명해집니다.

messages 세 번 실행

무엇을 고정하고, 무엇을 바꾸고, 무엇을 더하는가

기본 호출 · system 교체 · 이력 추가
이제 실제로 세 번 실행합니다. 목적은 모델에 건넨 입력을 분리해 보고, 바꾼 입력과 응답의 차이를 원문으로 확인하는 것입니다. 응답이 마음에 드는지부터 판단하지 않습니다.

🔁 세 실행 — 고정 · 변경 · 추가

1기본 호출 — system A + user 질문 고정 → 01-customer-service.txt
2system 교체 — 질문은 그대로, system A→B로 변경 → 02-technical-documentation.txt
3이력 추가 — system B 유지, user 입력에 앞선 문답 요약+새 요청 추가 → 03-with-history.txt
무엇을 고정/변경했고 어떤 문장·구조가 달라졌는지 기록한다. 세 실행 모두 원문 파일로 남기고, 오류로 끝나면 오류 유형·전문도 보관한다.
파랑=유지, 주황=변경, 초록=추가로 생각하면 한 번에 하나씩만 바꾸는 비교가 됩니다. 한 실행에서 여러 조건을 동시에 바꾸면, 응답 차이가 무엇 때문인지 설명할 수 없게 됩니다.

👀 강사 미리 실행 — 같은 질문, system만 다름

🙂 고객 문의 톤 (정중하게 답한다)

"문의해 주셔서 감사합니다. 다만 지금 확인할 수 있는 주문·배송 정보가 없어 배송일을 바로 안내드리기 어렵습니다. 정확한 안내를 위해 주문번호/이메일·연락처, 어떤 상품, 주문 일자를 알려주시면 도움이 됩니다…"

🛠️ 기술 문서 톤 (기술 문서 톤으로 답한다)

"질문에 필요한 컨텍스트가 없습니다. 현재 세션에 주문·배송 정보가 없고 연결된 도구에도 조회용 데이터 소스가 없습니다. 확인이 필요한 항목: 어떤 배송인가 / 조회 경로(주문번호·운송장·URL) / 대체 소스."

둘 다 배송일을 단정하지 않는다. 고객 톤은 감사·사과로 시작해 주문자·상품·주문일을 요청, 기술 톤은 컨텍스트 부재·연결 도구를 먼저 설명하고 조회 경로·대체 소스로 분류한다.
"더 좋다"를 판정하는 게 아니라 "system 변경으로 무엇이 달라졌다"를 한 문장으로 쓰는 것이 핵심입니다. 두 응답 모두 없는 사실을 지어내지 않았다는 공통점도 함께 관찰하세요.

📎 세 번째 호출 — 이력을 넣으면

  • Claude Agent SDK에서는 이력을 assistant role 배열로 전달하지 않고, 앞선 대화를 한 user 요청에 명시해 재호출한다
  • 03-with-history.txt에서 "주문번호 또는 운송장 번호"라는 앞선 제안이 마지막 답에서 어떻게 이어지는지 확인한다
  • 참조가 안 보이면 — "이력을 user 입력에 포함했으나 응답에서 분명한 참조를 확인하지 못했다"라고 기록한다
⚠️ 이력이 입력이라는 사실과, 모델이 매번 이력을 원하는 방식으로 활용한다는 보장은 구분한다. (assistant-role 이력 실험은 LangChain·Ollama에서.)
이력을 넣었다고 모델이 반드시 그것을 반영하는 것은 아닙니다. 입력에 넣었다는 사실과 출력이 그것을 활용했다는 사실은 별개이므로, 원문에서 참조 여부를 직접 확인하고 없으면 없다고 기록해야 합니다.

✅ 완주 확인 4가지

1세 실행 원문 파일 모두 보관 (오류로 끝났다면 오류 유형·전문도)
2첫·둘째는 같은 질문·system만 다름을 파일에서 확인 가능
3셋째엔 앞선 대화를 명시한 user 입력과 응답이 함께 들어 있음
4system 변경이 바꾼 점과 이력 추가 점을 원문 근거로 한 문장씩 작성
이 네 가지가 채워지면 실습 완주다 — 결과의 우열이 아니라 입력과 출력의 차이를 원문으로 설명했는지가 기준.
이 4가지가 이번 실습의 채점표입니다. 특히 4번 — 무엇이 달라졌는지 원문 근거로 한 문장씩 쓰는 것이 프롬프트를 "감"이 아니라 "관찰"로 다루는 훈련의 핵심입니다.

📌 이것만은 꼭 — 핵심 4문장

1system·user·assistant는 같은 개념이지만 라이브러리마다 자료형·호출 방식이 다르다.
2세 환경 — Claude Agent SDK(에이전트 실행) · LangChain+Gemini(메시지 객체) · Ollama(role 딕셔너리).
3질문을 고정하고 system만 바꾸면 문체·구조·추가 정보 요청이 달라진다.
4이력은 입력이지만, 모델이 원하는 방식으로 활용한다는 보장은 아니다 — 원문으로 확인한다.
네 문장이 이번 실습의 뼈대입니다. 더 읽기: Claude Agent SDK·LangChain·Ollama 각 라이브러리의 메시지 전달 방식 문서를 함께 보면 인터페이스 차이가 더 분명해집니다.

✅ 정답 & 해설

A1. Claude Agent SDK = 비동기 user 생성기(범용 배열 아님) · LangChain = 메시지 객체 목록(System/Human/AIMessage) · Ollama = role 딕셔너리 목록.
A2. max_turns=1은 턴 수만 제한(답변 길이 아님), tools=[]는 도구 호출 제외.
A3. 공통 — 둘 다 배송일을 단정하지 않음. 차이 — 고객 톤은 감사·사과 뒤 주문자·상품·주문일 요청, 기술 톤은 컨텍스트 부재·조회 경로·대체 소스로 분류.
A4. assistant role 배열이 아니라, 앞선 대화를 한 user 요청에 명시해 재호출.
A5. 앞선 대화를 명시한 user 입력과 그에 대한 응답이 함께.
A4와 A5를 자기 말로 설명할 수 있으면 이번 실습의 목표는 달성입니다. A1의 세 표현 방식 대비가 "같은 개념, 다른 인터페이스"의 요점입니다.
