먼저 회원 표 하나가 필요합니다

회원(users) 표예시 한 줄
id · email · password_hash · created_at(가입일)1 · hong@example.com · (해시값) · 2026-03-02
C회원가입 = 회원 표에 행 하나 넣기(Create) — 사용자가 입력한 이메일로 새 줄을 만든다
R로그인 = 그 이메일로 행을 찾아(Read) 비밀번호를 대조 — 맞으면 통과, 틀리면 거절
🔁 결국 앞서 본 CRUD의 조합입니다 — 새로운 마법이 아닙니다
칸 이름을 password가 아니라 password_hash로 두면 "원문 금지"를 스스로 상기하기 좋습니다. 이 작은 명명 습관이 사고를 막습니다.

여기서 꼭 지킬 세 가지

1비밀번호는 절대 원문으로 저장하지 않는다 — 칸에 원문이 아니라 해시(솔트 + bcrypt)를 저장한다
2이메일은 '유일'하게 — 같은 이메일로 두 번 가입되지 않도록 email 칸에 유일(unique) 제약을 건다. 없으면 중복 계정·로그인 혼란이 생긴다
3필요한 것만 모은다 — 가입에 꼭 필요한 것 외엔 받지 않는다 (최소 수집)
⚠️ 인증은 직접 만들지 마세요. 로그인·비밀번호 재설정·소셜 로그인은 함정이 많아 자작하면 사고로 이어지기 십상입니다
  • 검증된 Auth 서비스·라이브러리(예: Supabase Auth)를 씁니다
  • AI에게 — "인증은 처음부터 만들지 말고 검증된 Auth를 붙여줘. 비밀번호는 해시로, 이메일은 유일하게."
출처: OWASP Authentication Cheat Sheet. 세 원칙 모두 소단원 ⑤(보안)에서 실화와 함께 다시 나옵니다.

로그인 상태는 어떻게 유지되나

무상태 · 쿠키 · 세션 vs 토큰(JWT)

④ 사용자를 다루기
"한 번 로그인하면 페이지를 넘겨도 왜 계속 로그인 상태일까"에 답하는 파트입니다.

HTTP는 무상태 — 매 요청이 남남입니다

지난 시간에 봤듯 HTTP는 '무상태'라 매번 '나 아까 그 사람'을 다시 증명해야 합니다. 그 증명을 실어 나르는 게 쿠키입니다.

🍪 쿠키란

사이트가 브라우저에 건네는 작은 메모. 브라우저가 보관했다가 요청할 때마다 자동으로 함께 보낸다 (지난 시간의 '지갑 속 카드')

❓ 그래서 갈림길

이 쿠키(또는 그 자리)에 무엇을 담느냐 — 여기서 세션과 토큰으로 갈린다

🔑 로그인이 계속 유지되는 건 이 쿠키 덕분입니다
지난 시간 내용을 한 슬라이드로 복습하고 바로 두 갈래로 넘어갑니다.

갈래 1 — 세션: 서버가 기억한다

로그인서버가 상태를
세션 저장소에 적음
→
브라우저에번호표
(세션 ID)만
→
요청마다번호표 제시
  • 서버가 상태를 쥐고 있어서 로그아웃·강제 차단을 바로 할 수 있습니다 — 저장소에서 지우면 번호표는 즉시 휴지 조각
  • 단점 — 서버가 여러 대로 늘면 그 저장소를 함께 나눠 써야 합니다
✅ 단순한 웹앱 + 즉시 로그아웃·차단이 중요하면 세션이 더 단순하고 안전합니다
출처: MDN, "Session management". '저장소를 함께 나눠 쓰는 문제'는 파트 3의 Redis로 해결됩니다.

갈래 2 — 토큰(JWT): 서버가 기억하지 않는다

로그인하면 서버가 사용자 정보와 만료 시각을 담아 위조 못 하게 서명(도장)한 증명서(JWT)를 통째로 내줍니다. 이후 브라우저는 요청마다 이 토큰을 내밀고, 서버는 저장소를 뒤질 필요 없이 서명만 확인합니다.

✅ 강한 곳

서버 확장·여러 서비스 연동·모바일. 저장소 조회가 없어 '무상태'

⚠️ 꼭 알 것

토큰 내용은 암호가 아니라 그냥 인코딩이라 가진 사람은 누구나 열어 봅니다. 서명이 막는 건 '못 바꾸게'이지 '못 보게'가 아닙니다 → 민감정보를 토큰에 넣으면 안 됩니다

  • 단점 — 한 번 내준 토큰은 즉시 무효화가 어렵습니다(서버에 지울 기록이 없으니)
  • 그래서 보통 만료를 짧게 두고 '리프레시 토큰'으로 조용히 갱신하는 방식을 씁니다
출처: Auth0, "JSON Web Tokens". JWT를 '암호화'로 오해하는 사람이 아주 많습니다. 이 슬라이드에서 반드시 짚어 주세요.

그래서 뭘 쓰나 — 그리고 직접 만들지 마세요

내 상황유리한 쪽왜
단순한 웹앱, 즉시 로그아웃·차단 필요세션서버가 상태를 쥐고 있어 지우면 끝
여러 서비스·모바일·큰 확장토큰저장소 조회 없이 서명만 확인 → 확장에 강함
MDN조차 "세션 관리를 직접 구현하지 말고 검증된 라이브러리를 쓰라"고 못 박습니다
  • Auth 서비스(Supabase Auth · Clerk · Auth0 등)가 세션이든 토큰이든 발급·만료·갱신·저장까지 알아서 안전하게 처리합니다
  • 우리 몫은 "무슨 방식인지 이해하고, 믿을 만한 도구에 맡기는" 판단까지
출처: MDN, "Session management". 이 강의에서 가장 실용적인 결론입니다. 두 갈래를 배운 이유도 '고르기 위해서'가 아니라 '맡긴 것을 이해하기 위해서'입니다.

캐시와 Redis — 로그인이 빠른 비결

계산대 옆 바구니 · TTL · 저장 위치

④ 사용자를 다루기
소단원 ③에서 본 키-값 NoSQL이 여기서 실제 역할을 얻습니다.

캐시 — 자주 쓰는 걸 가까이 둔다

캐시(cache)는 자주 쓰는 데이터를 메모리에 잠깐 두어 빠르게 꺼내 쓰는 것입니다. 매번 창고(디스크·DB) 깊숙이 다녀오는 대신, 자주 찾는 물건을 계산대 옆 바구니에 올려 두는 셈이죠.

얻는 것

속도가 크게 오른다

대신 감당할 것

원본과 잠깐 어긋날 수 있다 → '언제까지 신선한 걸로 볼지'(수명, TTL)를 정해 둔다

⚖️ 캐시는 속도와 신선함의 거래입니다 — 공짜가 아니라는 점이 색인과 같습니다
출처: MDN, "HTTP caching". 색인도, 캐시도 "빠르게 만드는 대신 무엇을 내주는가"를 묻습니다. 이 감각이 성능 이야기의 기본입니다.

세션 저장소에 Redis가 딱 맞는 이유

로그인에서 캐시가 등장하는 자리가 바로 세션 저장소입니다. 세션 확인은 거의 모든 요청마다 일어나 '빠름'이 생명인데, 소단원 ③에서 본 Redis(키-값, 메모리 기반)가 딱 맞습니다.

1조회가 매우 빠르다 — 메모리 기반 키-값
2키마다 자동 만료(TTL)를 걸 수 있다 → "30분 활동 없으면 자동 로그아웃"을 손쉽게 만든다
3여러 서버가 같은 저장소를 나눠 쓴다 → 앞서 본 세션의 단점이 해결된다
🤝 "세션을 여러 서버가 나눠 쓰는 문제"와 "캐시로 속도를 얻는 것"이 같은 도구(Redis) 하나로 만납니다
출처: Redis 공식, "Session management". 소단원 ③의 NoSQL 4갈래 표를 다시 띄워 키-값 줄을 짚어 주면 연결이 잘 됩니다.

❓ 이해도 확인

Q1. 회원가입과 로그인을 CRUD로 말하면?
A1. 회원가입 = 회원 표에 행 하나 넣기(Create), 로그인 = 이메일로 행을 찾아(Read) 비밀번호 대조.
Q2. 세션과 토큰의 결정적 차이는?
A2. 서버가 상태를 기억하는가. 세션은 서버가 기억해 즉시 로그아웃·차단이 되고, 토큰은 기억하지 않아 확장에 강하지만 즉시 무효화가 어렵다.
Q3. JWT에 비밀번호를 넣으면 안 되는 이유는?
A3. 토큰 내용은 암호화가 아니라 인코딩이라 가진 사람은 누구나 열어 볼 수 있다. 서명은 '못 바꾸게' 할 뿐 '못 보게' 하지 않는다.
Q4. Redis가 세션 저장소로 적합한 두 가지 이유는?
A4. ① 메모리 기반이라 조회가 매우 빠르다 ② 키마다 자동 만료(TTL)를 걸 수 있어 자동 로그아웃을 쉽게 만든다.
Q3이 이 소단원의 핵심 오해입니다. 여기서 막히면 토큰 슬라이드로 되돌아가세요.
