Skill 재사용하기

재사용할 것은 지난주 답이 아니라 판단 기준입니다

둘째 주 기록에는 낯익은 업무가 하나 있습니다 — TASK-102, 로그인 안내 문구 개선입니다.

왜 새 대화를 여는가

  • 지금까지의 대화에는 직접 설명한 팀 규칙과 완성한 첫 주 보고서가 들어 있습니다 — 이 상태에서 요청하면 Skill을 읽지 않고도 앞 대화의 내용으로 잘 작성할 수 있습니다
  • 그러면 결과는 좋더라도 Skill이 준비한 지식을 실제로 사용했는지 알기 어렵습니다
  • 새 대화는 앞서 주고받은 메시지의 영향을 줄이는 방법입니다 — 설치한 Skill이나 프로젝트 파일까지 지우는 기능은 아닙니다
  • 프로젝트 지침에 팀 규칙을 따로 써 두었다면 새 대화에서도 전달될 수 있으므로 — 어떤 자료가 함께 제공되는지는 결과를 해석할 때 기억해 둡니다
둘째 주 업무 기록을 우리 팀 주간 보고서로 정리해 줘.
📌 이번 요청에는 Skill 이름이나 업무별 정답을 넣지 않았습니다 — 자료 위치를 안내하는 것과 완료·위험의 판정을 대신해 주는 것은 다른 도움입니다
자료를 찾지 못하면 data/week-two.json을 알려 주세요. MCP 환경이라면 weekly-records에서 둘째 주를 조회할 수 있다고 알려 줄 수 있습니다.

사용한 입력을 확인합니다

  • MCP를 썼다면 get_weekly_records의 입력이 {"week":"week-two"}인지, 파일을 읽었다면 data/week-two.json인지
  • 반환된 자료의 report_date는 2026-09-11 — 보고서는 이 기준일의 현황을 담아야 합니다. 실습하는 날의 실제 날짜로 바꾸면 같은 기록도 다른 결과가 됩니다
  • 완성 결과는 첫 주 파일을 덮어쓰지 않고 second-week-report.md로 — 두 보고서가 있으면 같은 업무의 상태가 어떻게 바뀌었는지 나중에 다시 살펴볼 수 있습니다
앞에서 만든 first-week-report.md와 report-work-notes.md도 그대로 둡니다.

near-miss 사례

⑪ Skill 재사용
보고서 작성이 잘되면, 이번에는 보고서와 관련 있지만 해야 할 일이 다른 요청을 해 봅니다.

가까운 다른 요청

둘째 주 업무 제목만 알려 줘.

팀 보고서 양식을 영어로 번역해 줘.
  • 두 요청에는 업무나 보고서라는 익숙한 단어가 들어 있습니다. 하지만 첫 번째는 제목 조회, 두 번째는 번역
  • 제목 네 개를 부탁했는데 완료·진행·위험으로 나눈 보고서 전체를 만들었다면 — 사용자의 요청보다 작업 범위를 넓힌 것
  • 이를 가까운 다른 요청, 영어로는 near-miss 사례라 부릅니다 — 적절한 요청에서 Skill을 쓰는지만 보면 Skill이 너무 넓게 적용되는 현상을 놓칠 수 있어 함께 살펴봅니다
  • 번역 과정에서 팀 용어를 확인하려고 규칙 파일을 읽었다면 그것만으로 실패는 아닙니다 — 확인할 것은 "파일을 읽었는가" 자체보다 사용자가 요청한 일을 유지했는가
Skill 선택 기록과 최종 작업 범위를 함께 보고 판단합니다.

관찰에 맞춰 개선하기

관찰한 현상먼저 확인할 곳가능한 개선
Skill을 찾지 못함저장 위치, 호스트의 인식, description의 사용 조건실제 업무 요청에서 쓰는 표현으로 사용 시점을 명확히
본문만 보고 팀 규칙을 읽지 못함참조 경로와 파일 존재 여부, 본문의 안내경로를 바로잡거나 언제 그 규칙을 읽는지 설명
첫 주 기록이나 실제 오늘 날짜를 사용입력 선택 과정과 기준일 처리지정한 주의 기록과 그 안의 report_date를 사용하도록
배포 상태만으로 완료 처리완료 조건과 위험 조건의 우선순위혼동하는 조건을 구분하고 일반화 가능한 사례 추가
분류는 맞고 합계가 틀림업무의 중복·누락과 집계분류한 항목을 기준으로 수를 다시 확인하도록
제목 조회를 보고서 작성으로Skill의 적용 범위 설명보고서 작성과 단순 조회를 구분하도록
📌 규칙 파일의 경로를 잘못 써서 읽지 못한 상황이라면 완료 조건을 더 강하게 반복해도 해결되지 않습니다. TASK-202는 위험이다처럼 이번 정답을 넣기보다 "배포했더라도 운영 확인이 통과하지 않았으면 위험"이라는 재사용 가능한 기준을 분명하게
수정한 뒤에는 같은 둘째 주 입력으로 다시 확인합니다. 입력까지 동시에 바꾸면 결과가 달라진 이유를 구분하기 어렵습니다. 해결되었다면 첫 주 기록도 다시 적용해 이전에 잘 처리하던 사례에 영향을 주지 않았는지 확인하세요.

비교에서 알 수 있는 것

두 주는 입력 자체가 다릅니다

⑪ Skill 재사용
첫 보고서보다 이번 보고서가 더 정확했다는 사실 하나만으로 Skill 때문에 성능이 향상되었다고 결론 내리기는 어렵습니다.

질문을 구체적으로 나눕니다

알고 싶은 것비교할 조건
팀 지식을 제공하면 어떤 차이가 생기는지같은 기록에 팀 규칙을 제공하지 않은 결과와 제공한 결과
같은 지식을 Skill로 묶으면 어떤 가치가 있는지같은 기록·규칙을 일반 요청으로 전달한 결과와 Skill로 제공한 결과
Skill 수정이 도움이 되었는지같은 입력에 수정 전과 수정 후
  • 두 번째 비교에서는 양쪽이 모두 정확할 수도 있습니다 — 그때도 새 대화마다 무엇을 다시 설명해야 했는지, 자료를 어느 위치에서 유지할 수 있었는지, 다른 사람이 같은 업무를 요청하기 쉬워졌는지는 관찰할 수 있습니다
  • Skill의 가치를 보여 주기 위해 일반 요청이 반드시 실패해야 하는 것은 아닙니다
  • 비교의 출발점으로 남겨 둔 결과를 기준선이라 합니다 — 합격해야 하는 점수선을 뜻하지 않습니다
  • 직접 비교한다면 입력·모델·사용할 수 있는 자료를 가능한 한 같게 두고 대화를 분리. "Skill을 쓰지 않는 조건"이라 이름 붙였더라도 설치된 Skill이 자동 적용되었다면 그 비교는 다시 해석해야 합니다
공식 Agent Skills 평가 안내도 실제 요청과 입력을 남기고 Skill이 없는 경우 또는 이전 버전과 비교하며 관찰 가능한 근거로 확인하는 방식을 제시합니다. 조건이 분리되지 않았다면 "같은 대화에서 적용 전후를 관찰했다"처럼 실제 범위로 기록하면 됩니다.

📖 사용한 입력과 조건을 남겨 다른 사람이 같은 확인을 다시 해 볼 수 있게 하는 것을 재현이라 합니다 — AI가 매번 글자 하나까지 똑같은 보고서를 써야 한다는 뜻은 아닙니다. 표현이 달라도 같은 자료에서 팀 기준에 맞게 판정하고 그 근거를 다시 확인할 수 있으면 이 과업에서 중요한 부분을 재현한 것
더 살펴보고 싶다면 별도 연습용 복사본에서 운영 확인 상태나 기한 하나를 바꾸고 예상 분류를 먼저 적어 볼 수 있습니다. 원본 자료는 유지하고 바꾼 조건을 기록해 두세요.
