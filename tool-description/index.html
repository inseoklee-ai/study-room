계약을 쓰는 일은 곧 프롬프트를 쓰는 일

부산 창고 재고를 물었는데 모델이 주문 조회 도구를 골랐다면, 잘못은 어느 문장에서 시작됐을까요? 도구는 함수 이름만 등록하는 기능이 아니라 설명·인자 스키마·반환/실패를 묶은 계약이며, 모델은 그 계약을 읽고 행동을 고릅니다. 이 소단원은 그 계약이 결국 프롬프트임을 코드로 확인합니다.

1

도구는 계약이다 — 세 자리를 함께 쓴다

함수 이름 등록이 아니라, 모델이 읽고 선택하는 계약

설명 · 인자 스키마 · 반환/실패
고칠 자리를 찾으려면 모델이 실제로 읽은 도구 설명을 펼쳐야 합니다. 도구는 설명(description)과 인자 스키마, 그리고 반환 형식과 실패 뒤 행동을 묶은 계약이며, 이 세 자리는 각자 다른 일을 맡습니다.

📑 계약의 세 자리, 각자 맡는 일

설설명 — 도구의 목적과 사용할 조건을 문장으로. "허용된 창고의 현재 재고를 조회하며 수량은 바꾸지 않는다"는 선택의 경계를 준다
인인자 스키마 — 호출의 빈칸을 기계적으로 제한. 식별자의 의미·필수 여부·허용값을 규격화해 형식 오류가 실행 경계를 넘지 못하게 한다
반반환/실패 — 성공엔 식별자·상태·기준 시각처럼 필요한 값만, 실패엔 재입력·권한 요청·재조회 중 다음 행동을 드러낸다
실패 조건을 빼면 모델은 빈자리를 추측으로 메운다. 정상값뿐 아니라 인자 누락·범위 밖 값·일시적 서버 실패로도 계약을 확인한다.
설명은 목적과 맥락을, 스키마는 형식을 맡습니다. 둘은 겹치지 않고 서로를 보완합니다. 반환 형식은 다음 판단을 정하므로, 실패 응답이 무엇을 하라고 말하는지가 정상 응답만큼 중요합니다.

🔍 목적 · 형식 · 다음 판단으로 나눠 쓴다

자리맡는 일빠지면 생기는 일
설명목적·맥락·사용 조건을 문장으로실패 조건이 없으면 추측으로 메움
인자 스키마입력·출력의 구조·자료형·필수값 규격형식 오류가 실행 경계를 넘음
반환 형식성공 시 필요한 값만(식별자·상태·시각)다음 판단의 근거가 흐려짐
실패 뒤 행동재입력·권한 요청·재조회 중 무엇을오류에서 다음 행동을 못 고름
설명은 목적·맥락을, 스키마는 형식을 맡는다. 계약은 정상값과 실패 경로를 모두 적어야 완성된다.
표의 각 행은 계약의 한 자리입니다. 도구를 설계할 때 이 네 항목을 체크리스트처럼 확인하면, 나중에 모델이 이상하게 행동할 때 어느 문장을 고쳐야 할지가 분명해집니다.

도구를 주는 방식의 계보

텍스트 규약에서 표준 프로토콜까지, 무엇이 달라졌나

텍스트 규약 · function calling · M×N · MCP
도구를 모델에 건네는 방식은 개발자가 문장을 파싱하던 데서 API가 호출 구조를 보장하는 방식으로, 다시 표준 프로토콜로 진화했습니다. 각 단계가 앞 단계의 어떤 문제를 풀었는지를 따라가면 MCP가 왜 등장했는지 보입니다.

🧬 네 단계로 본 계보

각 단계는 앞 단계의 문제를 푼다 — 표기법의 불일치 → 호출 구조 보장 → 연결의 폭증 → 표준 프로토콜.
이 네 칸이 파트 2의 지도입니다. 이어지는 두 슬라이드에서 ①→②, ③→④를 각각 자세히 봅니다. 뒤로 갈수록 "모델의 요청을 다른 실행기가 그대로 읽는다"는 보장이 강해집니다.

① 텍스트 규약 → ② 네이티브 툴 호출

1초기 텍스트 규약 — 시스템 프롬프트에 도구 이름·인자·규칙을 텍스트로 적고, 모델이 만든 Action: 검색 같은 문장을 개발자가 직접 파싱(ReAct 계열). 표기법이 벤더·구현마다 달라 호환 보장이 약함
2네이티브 툴 호출 API — OpenAI가 2023년 6월 function calling 도입: JSON 스키마로 함수를 선언하고 구조화된 함수 호출을 받음. Anthropic의 tool use도 이름·설명·입력 스키마를 보내고 tool_use 블록을 받음
모델이 실행용 문장을 지어내고 개발자가 해석하던 방식 → API가 호출 구조를 보장하는 방식으로.
ReAct 계열은 Yao 외의 연구에서 정리된 접근입니다. 텍스트 규약은 유연하지만, 한 모델의 요청을 다른 실행기가 그대로 읽는다는 보장이 약했습니다. 네이티브 API는 그 호출 구조를 계약으로 고정했습니다.

③ M×N 문제 → ④ MCP

3M×N 문제 — 애플리케이션 M개·도구 N개면 각 조합을 따로 연결하는 M×N개의 작업. API마다 도구 선언·인증·반환값 해석 규칙도 다름. 개별 호출 구조는 갖췄지만 여러 제품이 연결을 함께 쓰는 문제는 남음
4MCP(Model Context Protocol) — Anthropic이 2024년 11월 25일 공개 표준으로 발표. 서버는 도구·리소스·프롬프트를 표준 형식으로 내놓고, 클라이언트는 공통 규약으로 소비. stdio·HTTP 같은 표준 전송 계층 사용
벤더별 연동을 표준 연결로 — M×N개의 개별 작업이 하나의 공통 규약으로 수렴한다.
function calling은 한 호출의 구조는 보장했지만, 제품마다 도구를 다시 연결하는 M×N 부담은 남았습니다. MCP는 그 연결 자체를 표준화해, 서버가 한 번 공개한 도구를 여러 클라이언트가 공통 규약으로 소비하게 합니다.

🚪 능력을 건네는 세 경로

경로주로 맡는 것좋은 점 / 주의
시스템 프롬프트규칙모든 요청에 적용되는 짧고 안정적인 규칙엔 알맞음 / 드문 절차까지 넣으면 매번 문맥 비용
Skill(불러오는 안내 문서)절차과업별 절차·참고자료·완료 기준 재사용 / 언제 불러오고 누가 갱신할지 관리 필요
MCP연결서버의 도구·스키마를 표준 방식으로 연결 / 인증·권한·서버 운영을 대신 해결하지 않음
세 경로는 각각 규칙·절차·연결을 맡는다. 어느 것도 인증·권한·운영을 마법처럼 없애 주지는 않는다.
세 경로는 배타적이지 않고 역할이 다릅니다. 규칙은 시스템 프롬프트에, 재사용할 절차는 Skill에, 외부 도구 연결은 MCP에 두는 식으로 나눠 쓰면 각자의 비용과 관리 지점이 분명해집니다.

🧠 그러나 모델의 관점에서는…

시스템 프롬프트도 · Skill도 · MCP도
결국 모델이 읽는 문장으로 환원된다능력을 어떤 경로로 건네든, 모델 입장에서는 하나의 프롬프트 안 텍스트가 된다
경로는 개발자에게 다르지만, 모델에게는 같은 자리다. 그래서 도구를 설계하는 일과 프롬프트를 쓰는 일은 나뉘지 않는다.
이것이 파트 3으로 넘어가는 다리입니다. 경로가 셋이어도 모델이 실제로 받는 것은 하나의 텍스트입니다. 다음 랩에서 그 텍스트를 직접 꺼내 눈으로 확인합니다.
3

실측 랩 — 주입된 문장을 꺼내기

클라이언트가 실제로 보내는 JSON과 렌더된 프롬프트를 펼친다

2026-08-27 · colab-mcp · qwen3.5:2b
MCP 도구를 로드하고 클라이언트가 주입할 JSON을 직접 출력해, 도구 설명이 어디에 어떤 형태로 들어가는지 확인합니다. 이어 채팅 템플릿으로 같은 입력을 직접 렌더해 두 입력이 사실상 같은 텍스트임을 대조합니다.

🧪 랩 ① — MCP 도구를 JSON으로 꺼내기

client = MultiServerMCPClient({"colab": {"transport": "stdio",
    "command": "uv", "args": ["run", "--directory",
    "colab-mcp 설치 경로", "colab-mcp"]}})
tools = await client.get_tools()
print(json.dumps([convert_to_openai_tool(t) for t in tools],
      ensure_ascii=False, indent=1))
  • MultiServerMCPClient — 이름별 MCP 서버 접속 설정을 받는 클라이언트
  • get_tools() — 서버가 공개한 도구 목록을 비동기로 가져옴
  • convert_to_openai_tool() — 각 도구를 함수 호출 형식으로 변환
이 코드는 실행하지 않고, 클라이언트가 모델에 보낼 도구 정의 JSON을 그대로 출력하기만 합니다. 다음 슬라이드에서 그 JSON 안에 무엇이 들어있는지 봅니다.

📤 출력 — description 문장이 그대로

도구 정의 JSON에 사람이 쓴 설명 문장이 손대지 않은 채 들어간다:

open_colab_browser_connection —
  "Opens a connection to a Google Colab browser
   session and unlocks notebook editing tools…"
우리가 도구에 적은 description 문장이 JSON에 그대로 실린다. 즉 도구 설명을 쓰는 순간 모델이 읽을 지시를 쓴 것이다.
여기서 계약의 첫 자리인 설명이 어디로 가는지가 드러납니다. 설명은 별도 메타데이터가 아니라, 모델에게 전달되는 도구 정의 안에 문장 그대로 들어갑니다. 부정확한 설명은 곧 부정확한 지시입니다.

🧪 랩 ② — 호출 요청은 쓰기만 한다

llm = ChatOllama(model="qwen3.5:2b",
                 temperature=0, reasoning=False)
r = await llm.bind_tools(tools).ainvoke(
        "구글 코랩을 브라우저로 연결해 줘")
print("tool_calls:", [(tc["name"], tc["args"])
                      for tc in r.tool_calls])
print("prompt_eval_count:",
      r.response_metadata.get("prompt_eval_count"))
tool_calls[('open_colab_browser_connection', {})]
·
prompt_eval_count289
모델은 실행하지 않고 요청만 쓴다. 서버는 이 요청 처리에 프롬프트 289토큰을 읽었다.
모델의 출력은 실행 결과가 아니라 "이 도구를 이 인자로 부르겠다"는 요청입니다. 실제 실행과 결과 해석은 클라이언트의 몫입니다. prompt_eval_count 289는 서버가 이 요청을 처리하며 읽은 프롬프트 토큰 수입니다.

🔧 채팅 템플릿을 렌더하면 <tools> 안에

  • GGUF(모델 가중치·설정 파일 형식)에서 공식 채팅 템플릿을 꺼내 같은 입력을 직접 렌더
  • 도구 JSON이 시스템 블록 안 <tools>에 놓이고, 그 아래 <tool_call> 호출 형식 안내·사용자 발화·모델 응답 자리가 이어짐
  • 특수 토큰(<|im_start|> 등)은 서버가 문자가 아니라 토큰으로 취급
서버 처리값prompt_eval_count 289
≈
raw 렌더 입력prompt_eval_count 288
1토큰 차이는 시작 토큰·빈 생각 블록 처리 차이(reasoning=False로 고정해 재현) — 두 입력은 사실상 같은 텍스트다.
렌더한 텍스트를 raw 입력으로 보내면 288토큰이 나옵니다. 서버 처리값 289와의 1토큰 차이는 시작 토큰과 빈 생각 블록 처리 차이에서 오며, reasoning=False로 고정하면 재현됩니다. 도구 설명은 별도 채널이 아니라 시스템 지시와 같은 프롬프트 안에 놓입니다.

📌 이것만은 꼭 — 핵심 4문장

1도구는 설명·인자 스키마·반환/실패를 묶은 계약이며, 모델은 이 계약을 읽고 행동을 고른다.
2도구를 주는 방식은 텍스트 규약 → function calling → M×N → MCP로, 표준 연결을 향해 왔다.
3시스템 프롬프트·Skill·MCP는 규칙·절차·연결을 맡지만, 모델에겐 모두 문장이다.
4랩에서 확인 — description은 JSON에 그대로, 도구 JSON은 <tools> 시스템 블록에 주입된다(289≈288).
4번이 이 소단원의 결론입니다. 도구 설명 문장이 시스템 지시와 같은 프롬프트 안에 놓이는 이상, 계약을 쓰는 일은 곧 프롬프트를 쓰는 일입니다.
