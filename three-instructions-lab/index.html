지시 3안

재고 실행하고 비교하기 — 채점 기준을 결과보다 먼저

이 실습은 같은 고객 문의를 세 지시(A·B·C)로 실행해 비교합니다. 핵심은 순서입니다. 결과를 보기 전에 무엇을 성공으로 셀지 기준표를 먼저 만들고, 세 실행 경로에 지시를 있는 그대로 전달해 원문을 기준표로 대조합니다.

PART 3세 경로로 실행·기록

  • 같은 입력에 다른 계약 세 장(최소·보강·형식)을 놓는다
  • Claude SDK · Gemini · Ollama 세 경로에 같은 지시를 전달한다
  • 원문을 기준표로 대조하고, 무엇이 달랐는지 한 문장으로 남긴다

이 실습은 앞 소단원들의 태도를 손으로 실행합니다. 지시라는 한 부품만 바꿔 세 안을 실행하되, 성공 기준·입력·모델·생성 설정은 고정합니다. 그래야 차이를 능력이 아니라 조건으로 설명할 수 있습니다.
1

결과보다 먼저 놓는 자

무엇을 성공으로 셀지부터 기준표로

이진 판정 · 통과/실패
과업은 주문 정보가 없는 고객의 배송일 질문에 보낼 답변 초안을 쓰는 것입니다. 모델이 실제 주문 시스템을 못 읽는다는 조건도 함께 고정합니다. 실행하기 전에 채점 기준부터 정합니다.

🪤 결과를 본 뒤 기준을 만들면?

  • 마음에 드는 결과의 표현을 성공 조건으로 삼게 된다
  • 그 자는 차이를 재는 도구가 아니라 이미 나온 답을 정당화하는 설명이 된다
결과 → 기준 (함정)답을 보고
자를 맞춘다
vs
기준 → 결과 (실습)자를 먼저 세우고
답을 잰다
실행 전에 성공을 정의해야, 세 안의 결과를 같은 잣대로 통과/실패 판정할 수 있다.
이것이 실습의 뼈대입니다. 좋아 보이는 결과가 나오면 사람은 자기도 모르게 그 결과가 잘한 점을 성공 기준으로 삼습니다. 그러면 비교가 아니라 사후 정당화가 됩니다.

📋 실행 전 채점 기준 — 이진 정의

실행 전 채점 기준통과의 이진 정의확인 위치
근거 없는 날짜 금지입력에 없는 배송일·주문 상태·운송장 번호를 확정적으로 안 씀답변 문장
부족한 정보 처리배송일 확정 불가를 밝히고 확인 정보 한 가지 요청답변 문장
고객용 문체비난·전문 용어 나열 없이 정중한 한국어전체 응답
형식 준수C안은 reply,question 두 키 JSON 객체만, 두 값 비지 않음파싱 결과
마지막 행은 형식을 약속한 C안에서만 적용한다. 문체 우열까지 한 점수에 섞지 않는다.
이진 판정을 쓰는 이유는 업무상 반드시 지킬 약속부터 살피기 위해서입니다. 답변이 자연스러워도 없는 배송일을 단정하면 안전 실패, 사실을 조심했어도 약속한 JSON을 깨면 형식 실패로 봅니다.

🔬 판정 규칙의 모호함도 실행 전에

  • '정중함'처럼 해석이 남는 항목은 그대로 두면 사람마다 다르게 판정한다
  • → 문장 끝 존대 · 고객 비난 없음을 확인 규칙으로 미리 적어 둔다
애매"정중한가?" — 판정자의 인상에 맡기면 안전 실패를 놓친다
규칙문장 끝 존대 O · 고객 비난 X — 원문에서 눈으로 확인 가능한 규칙으로 환원
해석이 남는 기준을 실행 전에 규칙으로 못 박아야, 원문을 볼 때 판정이 흔들리지 않는다.
기준을 이진으로 정의한다고 모호함이 사라지는 것은 아닙니다. '정중함' 같은 항목은 확인 가능한 규칙으로 미리 바꿔 두어야, 세 안을 볼 때 같은 잣대가 유지됩니다.
2

같은 문의에 다른 계약 세 장

입력 고정 — 배송일은 언제인가요?

A 최소 · B 보강 · C 형식
같은 사용자 입력 "배송일은 언제인가요?"를 고정하고, 시스템 지시만 세 가지로 바꿉니다. A는 요청의 최소 기준선, B는 예상 위험만 보강, C는 B에 출력 모양을 더한 과잉안입니다.

🧾 지시 세 안 — 무엇을 더했나

A 최소안요청의 가장 작은
기준선
→
B 부품 보강안A에서 예상한
위험만 보강
→
C 과잉안(형식)B의 목표·제약 유지
+ 출력 모양
과잉 = 정보량이 아니다. 이 과업에 비해 형식 계약을 지나치게 세밀히 추가했는지를 관찰한다.
세 안은 지시라는 한 부품을 단계적으로 늘린 것입니다. 입력·모델·생성 설정은 세 안 모두 같게 두어야, 결과 차이를 지시의 차이로 귀속할 수 있습니다.

Ⓐ 최소안 — 기준선

[A] 고객 문의에 답변 초안을 작성하라.
역할·근거 범위·모를 때 행동·산출 형식이 대부분 비었다 → 친절한 답이 나와도 지시가 보장한 게 아니라 학습된 성향일 수 있다.
A안이 좋은 답을 내더라도, 그것을 지시의 성과로 볼 수는 없습니다. 지시가 아무것도 요구하지 않았으므로, 결과가 좋다면 모델의 기본 성향이 우연히 맞은 것일 수 있습니다.

Ⓑ 부품 보강안 — 위험만 보강

[B] 고객 문의에 정중한 한국어 답변 초안을 작성하라.
입력에 없는 배송일, 주문 상태, 운송장 번호는
추정하거나 단정하지 말라.
정보가 부족하면 확인에 필요한 정보 한 가지를 요청하라.
역할고객용 문체 — 정중한 한국어 답변
제약입력 밖 사실 금지 — 배송일·상태·운송장 추정 금지
예외정보 부족 시 질문 — 확인 정보 한 가지 요청
B안은 A안에서 비어 있던 부품 중 이 과업에서 위험한 것만 채웠습니다. 역할·제약·예외 처리 세 가지를 명시했고, 이 셋 중 무엇이 결과 차이를 만드는지가 관찰 대상입니다.

Ⓒ 과잉안 — 형식 보강

[C] B안의 지시를 따른다. 아래 JSON 객체만 출력하라.
{"reply":"고객에게 보낼 답변","question":"추가로 확인할 정보 한 가지"}
두 값은 한국어 문자열이며 비워 둘 수 없다.
형식을 추가하나 JSON이 곧 사실성 보장은 아니다. 자연어를 프로그램용 객체로 바꾸는 비용이 생길 수 있어, 형식이 실제 소비자에게 필요한지 별도 판단한다.
C안은 형식이라는 계약을 더한 것이지 답을 더 사실적으로 만드는 것이 아닙니다. 유효한 JSON이면서도 reply에 잘못된 배송일을 넣으면 형식 통과·안전 실패가 됩니다. 형식과 사실성은 별개 기준입니다.

🔁 한 번씩만 실행해 일반화하지 않는다

  • 같은 모델·입력으로 최소 3회 실행해 변동을 보관한다
  • 기록에 모델명·시각·시스템 지시·사용자 입력·원문 응답을 함께 남긴다
  • 무작위성 설정에선 한 번의 답이 아니라 반복 결과의 범위를 본다
한 번의 좋은 답은 지시의 증거가 아니다. 변동을 함께 기록해야 차이가 부품 때문인지 우연인지 구분된다.
단발 실행은 우연을 실력으로 착각하게 만듭니다. 같은 조건으로 여러 번 실행해 원문을 모두 보관하면, 세 안의 차이가 안정적인지 아니면 실행마다 흔들리는지 볼 수 있습니다.
3

세 실행 경로를 있는 그대로

인터페이스는 지시를 전달하는 그릇

Claude SDK · Gemini · Ollama
같은 지시라도 라이브러리마다 전달 그릇이 다릅니다. Claude Agent SDK는 system_prompt와 비동기 생성기, Gemini는 메시지 객체 목록, Ollama는 role 딕셔너리 목록입니다. 자료형을 잘못 맞추면 비교에 라이브러리 오류가 섞입니다.

🅰 Claude Agent SDK — 비동기 생성기

options = ClaudeAgentOptions(
    system_prompt=system_prompt, max_turns=1, tools=[])
record = [f"variant:{variant}",
          f"system_prompt:{system_prompt}",
          f"user:{QUESTION}"]
async for event in query(
        prompt=user_messages(QUESTION), options=options):
    record.append(f"{type(event).__name__} | {event!r}")
max_turns=1 · tools=[]로 추가 턴·도구를 제외하고, 지시+사용자 입력의 응답만 관찰한다.
구독 로그인으로 인증하고, system_prompt와 query()로 한 턴을 실행합니다. 범용 messages 배열 API가 아니며, 한도는 로그인 계정 상태에 의존합니다. 지시를 system_prompt 위치에 전달하는 것이 핵심입니다.

🅱🅲 Gemini · Ollama

LangChain + Gemini

model = ChatGoogleGenerativeAI(
    model="gemini-3.7-flash")
model.invoke([
    SystemMessage(instruction),
    HumanMessage(QUESTION)])

메시지 객체 전달. API 키가 있어도 공급자 혼잡(503)은 지시와 무관한 실패 → 성공/오류 구별 기록.

Ollama (로컬)

chat(model="qwen3.5:2b", messages=[
  {"role":"system",
   "content":instruction},
  {"role":"user",
   "content":QUESTION}])

role 딕셔너리, 인증 없이 로컬 반복. 작은 모델의 한국어 품질·지시 이행도는 결과로 재야 한다.

A·B·C를 세 경로 모두 동일한 메시지 위치로 전달하고, 모델·입력·생성 설정을 고정합니다. 실패하면 오류 전문도 결과 파일로 남깁니다. 파일명 규칙 경로-안-반복번호.txt로 반복과 경로 차이를 원문에서 분리 확인합니다.

🧭 세 경로 비교 — 되는 것 / 주의

경로되는 것주의
Claude Agent SDK구독 로그인 인증, system_prompt+query()로 한 턴 실행범용 messages 배열 API 아님, 한도는 로그인 계정 상태에 의존
LangChain+GeminiAPI 키, SystemMessage·HumanMessage·AIMessage를 invoke()공급자 고유 설정이 추상화에 가려짐, 503은 지시 실패 아님
Ollama인증 없이 role 딕셔너리, 로컬 반복로컬이 품질 보장 아님, 이행 품질도 관찰 대상
같은 system 이름을 봤다고 입력 자료형까지 바꿔 쓰면 비교에 라이브러리 오류가 섞인다.
세 경로는 지시를 담는 그릇이 다를 뿐 같은 지시를 전달하는 것이 목적입니다. 각 경로의 '주의'는 지시 실패로 오독하기 쉬운 지점들입니다. 특히 503 같은 공급자 오류를 지시 품질과 혼동하면 안 됩니다.

📝 판정 기록 양식 — 원문 읽은 뒤

안날짜 금지정보 처리문체형식차이 만든 부품
A 최소안통과/실패통과/실패통과/실패해당 없음관찰 후 기록
B 보강안통과/실패통과/실패통과/실패해당 없음역할·제약·예외 중 하나
C 형식안통과/실패통과/실패통과/실패통과/실패형식 또는 새 충돌
자리표시자는 실행 전 계약, 실제 통과/실패는 원문을 읽은 뒤 채운다. 한 결과의 좋은 인상으로 모든 기준을 통과시키지 않는다.
예를 들어 C안이 코드 펜스를 붙여 JSON을 냈다면 "객체만 출력" 형식 행은 실패입니다. C안이 유효 JSON이면서 reply에 잘못된 배송일을 넣으면 형식 통과·안전 실패입니다. 각 셀을 독립적으로 판정합니다.

🖊️ 'B가 더 좋다'에서 멈추지 않는다

  • 기록을 마치면 무엇이 달랐는지 한 문장으로 남긴다
  • 그 문장에 지시 부품 · 관측값 · 고정 조건을 함께 담는다

예) "B안은 정보 부족 시 질문 예외를 추가했으며, 세 실행 중 확인 정보 요청이 A안보다 많았다."

차이가 없다면 그 역시 중요한 관측이다 — 부품이 이미 학습된 성향과 겹쳤거나, 시험 입력이 효과를 못 드러낸 것.
비교의 결론은 순위가 아니라 인과의 설명입니다. 실패한 안은 최소 변경 후 같은 조건으로 다시 잽니다. 차이가 없다는 관측도 버리지 말고, 왜 없었는지를 기록해 두어야 다음 시험을 설계할 수 있습니다.

🎯 이해도 확인 질문

Q1. 채점 기준을 결과보다 먼저 세워야 하는 이유는?
Q2. 답변이 자연스러운데 없는 배송일을 단정했다 — 어느 판정인가?
Q3. A·B·C 세 안은 각각 무엇을 더한 것인가?
Q4. Gemini 실행에서 나온 503은 지시의 실패로 세야 하나?
Q5. C안이 코드 펜스를 붙여 JSON을 냈다면 형식 행은?
Q2와 Q5가 이진 판정의 핵심을 가립니다. 인상이 좋다고 안전·형식 기준을 함께 통과시키지 않는 태도를 확인하세요.

✅ 정답 & 해설

A1. 결과를 먼저 보면 마음에 든 결과의 표현을 성공 조건으로 삼아, 자가 차이를 재는 도구가 아니라 이미 나온 답을 정당화하는 설명이 되기 때문.
A2. 안전 실패 — 문체가 자연스러워도 근거 없는 날짜를 확정하면 통과가 아니다.
A3. A=최소 기준선, B=A의 예상 위험 보강(역할·제약·예외), C=B에 출력 형식을 더한 과잉안.
A4. 아니다. 503은 공급자 혼잡으로 지시와 무관한 실패 — 성공/오류를 구별해 기록한다.
