업무 기록 MCP 만들기

도구가 임의로 요약하면 다음 단계에서 필요한 근거가 사라집니다

주 이름을 받으면 해당 주의 기록을 읽어 주는 도구를 만듭니다. 조회 기능의 역할을 작게 잡습니다.

직접 만드는 부분은 가운데입니다

입력: week-one
  ↓
첫째 주 자료 선택 → 파일 읽기 → 기본 모양 확인
  ↓
반환: 주차·팀·기준일·업무 기록 전체
  • MCP 메시지를 받아 함수를 실행하고 결과를 보내는 통신 작업은 SDK가 맡습니다
  • SDK는 특정 기능을 개발할 때 사용하는 도구와 코드의 묶음 — MCP를 처음부터 구현하는 대신 공식 Python SDK에 우리의 조회 함수를 등록합니다
업무가 완료됐는지, 팀장에게 무엇을 강조할지는 뒤에서 다룹니다.

먼저 읽어 볼 원자료

차이를 지우지 않고 그대로 가져오기

③ MCP 만들기
자료를 열어 보면 메모 문장 대신 이름과 값이 짝을 이루고 있습니다.

첫째 주 파일 발췌

{
  "week": "week-one",
  "team": "가상 제품팀",
  "period_start": "2026-08-31",
  "report_date": "2026-09-04",
  "records": [
    {
      "id": "TASK-102",
      "title": "로그인 안내 문구 개선",
      "owner": "지우",
      "status": "개발 완료",
      "due_date": "2026-09-07",
      "deployed_at": null,
      "verification": "미실시",
      "blocker": null,
      "note": "코드 작성은 끝났으며 다음 배포를 기다린다."
    }
  ]
}
  • 이름을 키, 연결된 내용을 값이라 부릅니다. records의 값은 대괄호로 묶인 목록 — 한 주에 업무가 여러 개이므로 업무 하나씩을 객체로 만들어 넣었습니다
  • null은 해당 자리에 값이 없다는 표현. JSON을 Python으로 읽으면 null은 None이 됩니다
실제 파일의 업무는 네 개이며, 실습 파일을 이 한 항목으로 덮어쓰지 않습니다. 날짜는 가상 자료의 기준일이므로 컴퓨터의 오늘 날짜로 바꾸지 않습니다.

흥미로운 기록 하나

TASK-102의 상태는 '개발 완료'인데
배포일은 없고 확인도 '미실시'입니다
  • 보고서에서 이것을 어떻게 표현할지는 팀의 기준을 알아야 정할 수 있습니다
  • 지금 도구가 할 일은 이 차이를 지우지 않고 그대로 가져오는 것
  • 도구가 임의로 '완료 한 건'으로 요약하면 다음 단계에서 필요한 근거가 사라집니다
원본에서 TASK-102를 찾아 상태와 note를 직접 읽어 보세요. 다음 절에서 실제 도구를 호출했을 때 다시 확인할 기준이 됩니다.

실습 폴더의 Python 환경

uv · 세 파일 · 가상환경

③ MCP 만들기
첨부 폴더는 이미 uv 프로젝트로 준비되어 있으므로 uv init이나 uv add를 다시 실행할 필요는 없습니다.

세 파일은 다른 질문에 답합니다

파일답하는 질문담긴 내용
pyproject.toml우리 코드에 무엇이 필요한가mcp[cli]==2.1.1은 직접 의존성(cli는 터미널 mcp 명령 포함, ==는 버전 고정), requires-python = ">=3.10"
uv.lock그 조건을 만족하는 패키지를 어떤 버전으로 조합할까직접·간접 의존성의 확정 버전. 운영체제·Python에 따라 uv가 맞는 항목을 선택 — 손으로 수정하지 않습니다
.python-version이번 실습에서 어떤 Python을 쓸까3.13 — 3.13.x의 마지막 숫자까지 고정한 표기는 아닙니다. 필요한 Python이 없으면 자동 내려받을 수 있음
📌 가상환경은 프로젝트마다 설치할 패키지를 분리하는 공간입니다 — 별도 컴퓨터를 만드는 것은 아닙니다. uv는 pyproject.toml 옆에 .venv를 자동으로 만듭니다. [tool.uv]의 package = false는 이번 실습 코드를 설치 가능한 패키지로 빌드하지 않는다는 설정
다른 프로젝트가 MCP SDK 1.x로 작성되어 있어도, 이번 2.1.1을 별도 환경에 두면 각자 맞는 환경에서 실행할 수 있습니다. data와 .venv는 서로 다른 역할의 폴더입니다.

준비와 확인

uv sync --locked
uv run --locked python --version
uv run --locked python -c "import sys; print(sys.executable)"
uv run --locked python -c "from importlib.metadata import version; print(version('mcp'))"
  • uv sync는 잠금 파일을 기준으로 패키지를 가상환경에 맞추는 명령. --locked는 선언과 잠금 파일이 맞는지 확인하되 잠금 파일은 변경하지 않음 — 맞지 않으면 오류로 멈춥니다
  • uv run은 뒤의 명령을 이 프로젝트 환경에서 실행 — 별도로 가상환경을 활성화하는 명령을 외우지 않아도 됩니다
  • --locked는 설치를 금지하거나 인터넷 연결을 없애는 옵션이 아닙니다
  • 결과 확인 — Python 3.13.x, 실행 경로는 실습 폴더의 .venv 아래, MCP는 2.1.1
⚠️ .venv에 설치해 놓고 호스트가 다른 Python을 실행하면 '설치했는데도 mcp를 찾을 수 없다'는 오류가 납니다 — 재설치를 반복하기보다 설치한 프로젝트와 호스트가 실행하는 프로젝트가 같은지 확인합니다
보통 macOS·Linux는 .venv/bin/python, Windows는 .venv\Scripts\python.exe를 가리킵니다. AI에게 준비를 맡길 때도 이 관계를 알고 있으면 무엇을 확인해 달라고 요청할지 판단할 수 있습니다.

코드 따라가기

주차를 파일로 · 입력 검사 · 원본 반환

③ MCP 만들기
AI가 만든 코드가 글자까지 같을 필요는 없습니다. 대신 주차가 어떤 파일을 가리키는지, 없는 주차를 받으면 어떻게 하는지, 원본 기록이 그대로 돌아오는지를 살펴봅니다.

주차를 파일로 바꾸는 표

import json
from pathlib import Path
from typing import Any

DATA_DIR = Path(__file__).with_name("data")
WEEK_FILES = {
    "week-one": "week-one.json",
    "week-two": "week-two.json",
}
  • WEEK_FILES는 주차와 파일 이름을 연결한 딕셔너리 — 도구를 쓰는 쪽은 실제 폴더 구조를 몰라도 week-one이라고 요청하면 됩니다
  • 두 주차를 표에 적어 두었으므로 아무 파일 경로나 받는 조회 기능이 되지 않습니다 — week-three는 비슷한 이름을 추측해 열지 않고 허용 주차인지 먼저 검사
  • __file__은 이 Python 파일의 경로, .with_name("data")는 마지막 이름을 data로 바꿉니다
🎯 이 기준을 쓰는 이유 — 호스트가 터미널의 현재 폴더와 다른 곳에서 서버를 실행할 수 있기 때문입니다. 코드 파일의 위치를 기준으로 삼으면 시작 위치가 달라도 코드 옆의 자료를 찾습니다
json은 JSON을 Python 자료로 읽는 데, Path는 파일 위치를 다루는 데, Any는 반환값의 자료형 설명에 쓰입니다. 세 기능은 Python에 포함되어 있습니다.

입력을 확인하는 함수

def load_weekly_records(week: str) -> dict[str, Any]:
    selected_week = week.strip().lower()
    if selected_week not in WEEK_FILES:
        raise ValueError("week는 week-one 또는 week-two를 사용하세요.")
  • week: str은 타입 힌트, -> dict[str, Any]는 문자열 키의 딕셔너리를 반환하며 값의 종류는 다양할 수 있다는 설명 (team은 문자열, records는 목록)
  • 일반 Python 함수에 힌트를 적었다고 모든 호출의 타입을 Python이 자동 검사하는 것은 아닙니다
  • strip()과 lower()로 " WEEK-ONE "을 "week-one"으로 — 이런 처리를 정규화라 합니다. week-three를 week-one으로 바꾸는 것처럼 내용을 추측하지는 않습니다
  • 없는 주차면 raise ValueError(...)로 중단 — 기록이 없는 상황을 정상적인 빈 보고서처럼 넘기지 않으므로 호출한 쪽이 입력을 확인해 다시 요청할 수 있습니다
def로 함수를 정의하고 괄호 안의 week로 입력을 받습니다. 콜론 뒤에서 들여쓴 줄들이 함수의 작업입니다.

파일을 읽고 원본을 돌려주기

with (DATA_DIR / WEEK_FILES[selected_week]).open(encoding="utf-8") as file:
    data = json.load(file)

if not isinstance(data, dict) or not isinstance(data.get("records"), list):
    raise ValueError("주간 데이터는 records 목록이 있는 객체여야 합니다.")
if data.get("week") != selected_week:
    raise ValueError("요청한 주차와 데이터의 week가 다릅니다.")
return data
  • DATA_DIR / 파일이름의 /는 숫자를 나누는 연산이 아니라 Path에 파일 이름을 이어 붙이는 연산
  • with ... as file:은 블록을 벗어날 때 파일을 닫도록 처리합니다. json.load(file)은 텍스트를 코드가 키로 값을 찾을 수 있는 자료로 바꿉니다
  • or의 앞 조건이 참이면 뒤는 평가하지 않으므로 — 딕셔너리가 아닌 자료에 .get()을 호출하지도 않습니다
  • 파일의 week와 요청한 주차가 같은지도 확인 — 파일 이름은 첫째 주인데 내부가 둘째 주 자료라면 보고서가 잘못됩니다
📌 return data는 print(data)와 다릅니다 — SDK가 반환 자료를 받아 호스트에 전하려면 함수의 반환값이 필요합니다. 원자료의 네 기록은 여기서 요약되거나 분류되지 않습니다
지금 검사는 바깥 자료 구조와 주차에 집중합니다. 모든 업무의 날짜 형식이나 기록의 사실 여부까지 확인하는 코드는 아닙니다.

Python 함수를 도구로 공개하기

같은 파일에 있다고 모두 공개되지는 않습니다

③ MCP 만들기
도구로 제공할 함수를 SDK에 등록하는 부분을 봅니다.

@mcp.tool()로 등록합니다

from mcp.server import MCPServer

mcp = MCPServer("weekly-records")

@mcp.tool()
def get_weekly_records(week: str) -> dict[str, Any]:
    """week-one 또는 week-two의 가상 팀 업무 기록을 읽습니다.

    반환값은 주차, 팀 이름, 기간 시작일, 보고 기준일, 업무 기록 목록입니다.
    파일을 수정하지 않으며 완료·진행·위험 판정이나 보고서 작성은 하지 않습니다.
    """
    return load_weekly_records(week)
  • weekly-records는 서버 이름, get_weekly_records는 그 서버가 제공하는 도구 이름
  • @mcp.tool()은 데코레이터 문법 — 바로 아래 함수를 서버의 도구로 등록. load_weekly_records에는 이 표시가 없으므로 외부에 공개되지 않습니다
  • 삼중 따옴표 문자열은 docstring. SDK는 함수 이름·설명·타입 힌트를 이용해 호스트에 제공할 도구 정의를 만듭니다
공개 함수는 요청을 받아 실제 파일 읽기를 담당한 함수를 호출합니다. 이렇게 나누면 파일 조회 규칙을 MCP 통신과 별도로 읽고 시험하기 쉽습니다.

모양 검사와 허용 값 검사

MCP에 공개된 get_weekly_records(week)
                 ↓
파일 조회 함수 load_weekly_records(week)
                 ↓
data/week-one.json → Python 딕셔너리 → MCP 응답
입력어디에서 거절되나
{"week": 1} 또는 week 생략MCP SDK의 입력 처리 (스키마 검사)
"week-three"문자열 조건은 맞지만 — 함수 안의 WEEK_FILES 검사에서
🎯 입력의 모양 검사와 우리가 정한 허용 값 검사는 서로 다른 역할입니다. 학생이 스키마 JSON을 따로 작성하는 것이 아니라 SDK가 함수 정보를 바탕으로 만듭니다
  • 도구 설명이 필요한 이유 — 모델에게 week라는 문자열만 알려 주면 어떤 값을 써야 할지 부족합니다. AI가 도구를 엉뚱하게 사용한다면 실행 코드뿐 아니라 모델이 읽는 이 안내도 살펴봅니다
MCP Python SDK 2.1.1의 서버 작성 방식은 공식 SDK 예제를 기준으로 합니다.

실행 방식도 짚어 둡니다

  • 첨부 완성 예제에는 서버를 직접 시작하는 코드가 없으므로 uv run --locked python weekly_records_server.py로 실행하면 함수와 서버 객체를 정의한 뒤 끝납니다
  • 다음 절에서는 mcp run이 이 파일의 서버 객체를 찾아 실행하도록 호스트에 등록합니다 — 별도 터미널에서 서버를 계속 켜 놓는 방식이 아닙니다
  • AI가 생성한 다른 구현에는 실행 진입점이 들어 있을 수 있습니다 — 그런 파일은 Python으로 직접 실행하는 방식이 맞을 수 있습니다
📌 "이 서버는 어떻게 시작하는지 코드에서 찾아 설명해 줘" 정도로 짧게 요청해도 좋습니다
stdio 연결에서는 표준 출력이 MCP 메시지 통로입니다. 진단은 표준 오류로 보냅니다. 환경 준비에서 터미널에 Python 경로를 출력한 것은 서버 통신 밖의 독립 명령이므로 목적과 위치가 다릅니다.

❓ 이해도 확인

Q1. Path(__file__).with_name("data")를 쓰는 이유는?
A1. 호스트가 터미널의 현재 폴더와 다른 곳에서 서버를 실행할 수 있기 때문. 코드 파일 위치를 기준으로 삼으면 코드 옆의 자료를 찾는다.
Q2. {"week": 1}과 "week-three"는 각각 어디에서 거절되나?

A3. @mcp.tool() 표시가 없기 때문. 같은 파일에 있다고 모든 함수가 도구가 되지는 않는다.
