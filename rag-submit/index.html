  • 기능 목록에는 답변이 아니라 사용자의 판단을 돕는 이유를 붙이고, 자료의 갱신 주체와 출처 링크의 책임도 적어 둡니다
갱신 주체를 적어 두면 이후 자료가 바뀌었을 때 무엇을 다시 검토해야 하는지 분명해집니다.

실험 — 내 루브릭으로 한 바퀴

실패한 답도 지우지 않습니다

⑨ 제출
앞에서 정한 자기 루브릭을 새 챗봇에 그대로 적용합니다.

고정 질문 세 종류로 경계를 관찰합니다

1자료를 직접 묻는 것
2여러 청크를 잇는 것
3자료 밖을 묻는 것
  • 확인할 것 — 출처를 인용한 답, 도메인 밖 질문의 거부, 판정 배지의 grounded 여부, 짧은 답변에서도 근거 표시가 남는지
  • 한 번의 실행에서는 프롬프트 문구나 검색 설정처럼 변수 하나만 바꾸고, 나머지 조건과 질문 순서는 유지합니다
📓 README.md에는 실행 날짜 대신 — 실험 이름 · 바꾼 변수 · 고정 질문 · 각 질문의 cited·refusal·grounded 판정 · 관찰한 근거 · 채택 또는 되돌림 결정을 기록합니다
실패한 답도 지우지 않아야 다음 수정이 무엇을 보존해야 하는지 알 수 있습니다. 루브릭의 목표값과 실제 판정값을 나란히 남기면, 개선이라는 말이 어떤 관찰에 근거하는지도 동료와 사용자에게 설명할 수 있습니다.

배포 — 내 주소로 세상에 내놓기

주소가 열리는 것만으로 배포가 끝나지 않습니다

⑨ 제출
정적 페이지가 답변을 대신 실행하는 것은 아닙니다.

빌드와 실행 조건

npm run build     # 정적 결과물 생성 → dist 를 GitHub Pages 에 올림
                  # 프로젝트 설정의 base:'./' 가 배포 주소 아래에서도
                  # 자산 경로를 상대적으로 찾게 합니다
  • 그러나 정적 페이지가 답변을 대신 실행하지 않습니다. 페이지를 연 사용자의 브라우저가 localhost:11434의 Ollama qwen3.5:2b를 직접 호출합니다
  • 따라서 그 사용자 컴퓨터에서 Ollama가 실행 중이어야 하며, Pages 출처의 요청을 허용하도록 OLLAMA_ORIGINS를 설정해야 합니다
✔배포 주소에서 소개 질문과 도메인 밖 질문을 각각 입력해 자산 로드 · 모델 연결 · 출처 표시 · 거부 안내를 확인합니다
✔연결 실패 시 모델이 없다는 안내와 재시도 방법이 보이는지 확인해, 사용자가 페이지 오류와 자신의 실행 조건을 구별할 수 있게 합니다
주소가 열리는 것만으로 배포가 끝났다고 판단하지 않고, 사용 조건을 갖춘 브라우저에서 실제 경로를 따라갑니다.

제출 뒤에 남는 것

오늘 만든 것은 자료를 넣고 답을 내는 화면만이 아닙니다. PRD로 질문의 범위와 거절의 기준을 정하고, 같은 스키마와 임베딩 공간 안에서 자료를 교체하고, 루브릭과 고정 질문으로 답변을 판정하고, 사용 조건까지 안내하는 흐름을 한 번 연결했습니다.

❓ 마지막 확인

Q1. 내 자료로 바꿀 때 그대로 두어야 하는 것은?
A1. 스키마(id·text·url·section·vector) · 검색 순서 · 프롬프트의 출처·거부 규칙. 그래야 바뀐 결과를 '내 자료의 차이'로 읽을 수 있다.
Q2. 자료 벡터만 새 모델로 만들고 질의는 그대로 두면?
A2. 검색 점수가 비교할 자리를 잃는다. 임베딩은 embeddinggemma-300m의 768차원으로 통일한다.
Q3. 배포 주소가 열리면 배포가 끝난 것인가?
A3. 아니다. 사용자의 Ollama 실행과 OLLAMA_ORIGINS 허용이 필요하고, 소개 질문·자료 밖 질문을 각각 넣어 출처 표시와 거부 안내까지 확인해야 한다.
Q4. README의 '사용 조건'에 반드시 들어갈 세 가지는?
A4. Ollama 실행 · 첫 방문 임베딩 다운로드 약 200MB · CORS 설정 필요. 숨기지 않는다.
