검색은 사용법을 준비하고, MCP 호출이 업무 자료를 가져옵니다

일정 생성과 메일 발송의 입력 형식까지 처음부터 모두 읽어야 할까요?

존재를 알리는 정보와 상세 사용법

  • Tool Search는 필요한 도구를 찾은 뒤 그 도구의 상세 정의를 불러오는 기능입니다
  • 연결된 도구의 존재를 알리는 정보와 실제 호출에 필요한 상세 사용법을 나누어 다룹니다
  • 현재 공식 문서는 지원 환경에서 이 방식을 기본으로 안내합니다 — 별도 검색 서버를 새로 만드는 실습이 아닙니다
📌 OpenCode를 사용한다면 이 절에서 검색과 호출의 차이를 이해한 뒤 다음 절로 넘어가면 됩니다 — 두 앱을 모두 설치해야 하는 실습은 아닙니다
지금 사용하는 호스트의 기능을 확인하는 단계입니다.

이해 · 검색 · 로드 · 호출

⑥ Tool Search
사람에게는 짧은 요청이지만 에이전트 안에서는 서로 다른 일이 이어집니다. 아래는 화면 로그를 복제한 예시가 아닙니다.

네 장면

장면일어나는 일이 시점에 아직 아닌 것
① 할 일 이해지금 필요한 능력은 주간 업무 기록 조회모델은 요청을 받았지만 아직 업무 기록을 읽지 않았습니다
② 도구 검색Claude Code에 연결된 도구가 검색 대상. ToolSearch가 한 일은 '조회할 수단 찾기'결과에 get_weekly_records가 등장하더라도 TASK-101~104를 읽었다는 뜻은 아닙니다
③ 상세 정의 로드무엇을 하는 도구인지, 어떤 입력을 받는지 — week: str와 설명문이 의미를 가짐이름만으로는 날짜 범위인지 숫자 1인지 결정하기 어렵습니다
④ 실제 호출{"week":"week-one"} → 서버가 JSON을 읽어 반환그제야 TASK-102의 상태나 TASK-103의 장애 요인을 살펴볼 수 있습니다
🔍 이 차이는 검색어만 보고 판단하면 놓치기 쉽습니다 — 도구를 찾을 때도 '업무 기록', 데이터를 읽을 때도 '업무 기록'이라 말하기 때문. 검색 결과가 도구의 사용법인지, 실제 업무의 내용인지를 보면 구분됩니다
필요한 정의를 문맥에 넣는 일을 흔히 로드(load)한다고 부릅니다. 검색은 필요한 사용법을 준비했고, MCP 호출은 업무 자료를 가져왔습니다.

서버에 쓴 설명은 주석이 아닙니다

어떤 자료를 가져오는 도구인지 분명하게 적어 두어야
모델이 현재 작업에 맞는 도구를 고르고 입력을 구성하는 데 도움이 됩니다
  • 검색 기능이 생겨도 도구의 역할을 잘 설명하는 일은 여전히 우리 몫입니다
공식 SDK 설명에서도 필요한 정의를 검색해 문맥에 넣고 이후 작업에서 사용하는 과정을 구분합니다.

AI와 내 환경 확인하기

지금 세션과 새 세션을 구분합니다

⑥ Tool Search
설정부터 외우기보다 현재 환경에서 기능이 적용되는지 확인해 봅니다.

요청과 읽을 것

내 환경에서 Tool Search를 쓸 수 있는지 확인해 줘.
필요하면 설정하고, MCP로 week-one 기록을 읽어 줘.
  • 읽어 볼 것 — 확인한 설치 버전, 사용 모델과 연결 경로, 적용할 설정. 설정을 바꿨다면 새로 시작해야 하는지도 확인
  • AI가 터미널에서 설정값을 지정했다고 이미 실행 중인 모든 세션이 동시에 바뀌는 것은 아닙니다 — 지금 보고 있는 세션과 새로 실행하는 세션을 구분해야 같은 화면을 반복해서 확인하는 일을 피할 수 있습니다
환경변수는 프로그램을 시작할 때 함께 전달하는 설정값입니다.

ENABLE_TOOL_SEARCH 값

ENABLE_TOOL_SEARCH=true claude          # macOS · Linux

$env:ENABLE_TOOL_SEARCH = "true"        # Windows PowerShell
claude
Remove-Item Env:ENABLE_TOOL_SEARCH      # 임시 설정 제거
값도구 정의를 준비하는 방식
미지정지원 환경에서 필요할 때 불러옵니다
true필요 시 로드를 명시
auto지연 가능한 정의가 문맥의 10% 미만이면 미리 로드, 10%에 도달하면 지연
auto:5같은 기준을 5%로. auto:N의 N은 0–100
false미리 로드
⚠️ auto는 현재 기본값의 다른 이름이 아닙니다 — 도구가 적은 환경과 많은 환경을 같은 기준으로 다루려는 임계값 모드입니다. 서버에 alwaysLoad: true를 지정하면 그 서버의 도구는 미리 로드됩니다
PowerShell에서는 현재 터미널 세션에 값이 남아 이후 실행하는 프로그램에도 전달될 수 있습니다. 다음 실행에도 같은 설정을 쓰려면 프로젝트의 .claude/settings.json의 env에 둘 수 있고, 기존 env가 있다면 같은 이름의 항목을 하나 더 만들지 않고 그 안에 추가합니다.

지원 환경 확인

  • 현재 문서는 Sonnet · Haiku · Opus 4.5 이후의 지원 모델을 안내합니다
  • 사내 중계 서버를 쓰면 tool_reference 전달 지원을 확인해야 합니다 — 검색한 도구를 참조하는 데 필요한 데이터이며, true가 중계 서버에 없는 기능까지 추가하지는 않습니다
  • Azure 호스팅 Microsoft Foundry와 Google Agent Platform의 이전 세대 모델에는 별도 제한이 있습니다. CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS 설정이나 조직의 관리 정책도 확인 대상
📌 이름만 보고 켜졌다고 판단하지 말고 공식 문서의 현재 지원 조건을 확인합니다
개인의 모든 프로젝트에 적용할지, 이번 프로젝트에만 적용할지는 설정 파일의 범위에 따라 달라집니다.

실제 반환값까지 관찰하기

화면이 보여 주는 범위 안에서

⑥ Tool Search
/mcp에서 weekly-records 서버와 도구의 상태를 살펴보고, 대화에 표시되는 검색·호출 항목을 펼쳐 봅니다.

다섯 가지 관찰

관찰한 내용읽을 의미
서버와 도구의 가용 상태업무 기록을 읽을 연결이 준비됐습니다
ToolSearch에서 찾은 도구현재 요청을 처리할 수단을 발견했습니다
실제 MCP 호출의 입력조회 주차가 week-one인지 확인
반환된 week와 records올바른 주차의 업무 데이터가 왔는지 확인
최종 답변답변의 내용이 반환 자료에 근거하는지 확인
📌 상세 정의가 화면에 모두 노출되지 않는다면 그 부분을 직접 봤다고 기록할 필요는 없습니다
  • 원본의 TASK-102 맞춰 보기 — 제목 '로그인 안내 문구 개선', 상태 '개발 완료', note는 다음 배포를 기다린다. 모델이 짧게 '조회했습니다'라고 답했더라도 실제 반환 자료를 보면 무엇을 읽었는지 확인할 수 있습니다
여기서는 TASK-102를 보고서에서 어떤 범주로 분류할지까지 결정하지 않습니다. 자료가 정확하게 도착했는지 확인하는 단계입니다.

검색이 나타나지 않은 경우

  • 같은 대화에서 둘째 주를 요청했는데 ToolSearch가 다시 보이지 않으면 — 앞에서 찾은 정의를 재사용했는지 살펴봅니다. 이미 사용법을 아는 도구를 다시 쓰는 요청이라면 매번 같은 검색을 할 이유가 줄어듭니다
  • 반대로 대화가 압축되어 발견 정보가 정리된 뒤에는 다시 검색할 수 있습니다
  • 설정을 auto로 했다면 정의 분량이 기준에 도달하지 않아 미리 로드했을 수도 있습니다 — 도구가 적은 지금 실습에서 특히 중요한 해석
⚠️ 검색이 보이지 않았다는 관찰과, 기능이 고장 났다는 결론은 다릅니다 — 현재 설정, 새 대화인지 여부, 실제 호출 결과를 함께 살펴보세요
  • 도구는 찾았지만 호출에서 오류가 났다면 오류의 내용을 읽습니다. 주차 입력이 잘못됐다는 응답이면 서버가 요청을 받고 입력을 검사하는 단계까지 도달한 것. 프로그램을 실행하지 못했다면 Python 경로나 환경을 살펴볼 차례
검색 설정만 반복해서 바꾸기보다 마지막으로 성공한 단계 다음을 확인하면 문제를 좁힐 수 있습니다.

절약 효과를 해석하는 기준

핵심 결과는 필요한 도구를 불러와 원본 기록을 읽는 과정을 설명하는 것
  • 도구 하나를 연결한 상태에서 큰 토큰 절약률이 나오도록 만들 필요는 없습니다 — 검색 자체에도 과정이 추가되므로 적은 도구에서는 전체 시간이 더 빨라진다고 단정할 수 없습니다
  • 비교한다면 — 같은 모델·연결 도구·질문을 쓰되 이전 검색 이력이 없는 새 대화에서 각각. 시작할 때의 문맥과 검색·실행을 마친 뒤의 문맥을 따로 기록
  • 앞의 값만 줄었다고 작업 전체 비용도 같은 비율로 줄었다고 결론 내리지 않습니다
🎯 Tool Search는 정의를 언제 읽을지 돕고, 우리는 과업에 필요한 자료의 범위를 설계합니다 — 필요하지 않은 모든 주의 자료까지 가져오면 상세 정의를 아꼈어도 데이터가 문맥을 채웁니다
공식 SDK 문서도 검색의 추가 왕복과 도구 집합 크기에 따른 차이를 설명합니다.

❓ 이해도 확인

Q1. ToolSearch 결과에 도구 이름이 나왔다면 기록을 읽은 것인가?
A1. 아니다. '조회할 수단'을 찾은 것이며 실제 기록은 tools/call 뒤에 온다.
Q2. auto 모드는 무엇인가?
A2. 기본값의 다른 이름이 아니라 — 지연 가능한 정의가 문맥의 10%(또는 auto:N의 N%)에 도달하면 지연하는 임계값 모드.
Q3. 검색이 보이지 않으면 고장인가?
A3. 아니다. 정의 재사용, 도구가 적어 미리 로드, 새 대화 여부를 함께 살핀다.
Q1이 이 소단원의 핵심입니다.
