실습 1:
도구 정의서

실패 사례를 계약 문장 서너 줄로 되돌리기

이 실습은 재고 조회라는 하나의 도구를 예로, 모델이 읽는 지시를 계약 문장으로 직접 씁니다. 도구의 이름·설명·입력 스키마에 반환 형식과 실패 뒤 행동까지 더한 여섯 항목을 한 표에 모으고, 실행 전에 채점 기준을 저장한 뒤, 실패 기록을 다시 정의서로 되돌리는 흐름을 따라갑니다.

1

도구 정의서로 재고 조회를 묶는다

도구 설명 문장이 곧 모델이 읽는 지시다

이름 · 설명 · 입력 스키마 · 반환 · 실패
고객이 '부산 창고의 A-17 재고'를 다시 물었을 때 모델이 창고와 상품을 추측하지 않게 하려면, 조회의 계약부터 직접 써야 합니다. 도구 설명 문장이 모델이 읽는 지시이므로, 재고 조회의 계약을 여섯 항목으로 고정합니다.

📋 도구 정의서란 무엇인가

  • 도구 정의서(tool definition) = 도구의 이름·설명·입력 스키마를 정리한 문서
  • MCP 사양·Anthropic·LangChain이 쓰는 표현이다
  • 여기에 반환 형식과 실패 뒤 행동까지 더해 여섯 항목을 한 표에 모은다
여섯 항목을 한눈에 비교해야 계약의 어느 칸이 비어 실패가 생겼는지 바로 가리킬 수 있다.
정의서를 표 하나로 모으는 이유는 실패를 항목별로 지목하기 위해서입니다. 설명이 흩어져 있으면 어느 칸이 비었는지 보이지 않지만, 여섯 칸을 나란히 두면 빈 칸이 곧 실패의 원인이 됩니다.

🧱 정의서 여섯 항목 — 재고 조회

항목기록할 내용
① 이름동사+대상: get_inventory
② 하는 일 한 문장승인된 창고의 특정 SKU 가용 수량을 읽기 전용으로 조회
③ 언제 쓰고 안 쓰는지수량 질문엔 쓰고, 수량 변경·창고 미지정엔 안 씀
④ 인자 스키마sku 문자열 3~32자, warehouse_id는 SEOUL-01·BUSAN-02
⑤ 반환 형식SKU · 창고 · 가용 수량 · 확인 시각
⑥ 실패 정의와 뒤 행동오류별로 한 번 재시도 · 허용 창고 질문 · 또는 중단
여섯 항목은 뒤에서 실패를 되돌릴 좌표계가 됩니다. 실패가 나면 이 번호 중 어느 것이 비었는지 표시하고, 그 항목을 한 문장으로 보완하게 됩니다.

✂️ 도구 하나는 동작 하나

1과업 단위로 자른다 — 재고 조회와 수량 변경을 한 엔드포인트에 함께 넣지 않는다. 도구 하나는 동작 하나여야 한다
2반환값을 제한한다 — 원본 재고 데이터 덤프가 아니라 답의 근거가 될 available_quantity · checked_at 같은 필드로 한정한다
⚠️ 과한 반환은 컨텍스트를 잠식해 필요한 근거를 흐린다.
도구를 잘게 자르고 반환을 좁히는 것은 절제가 아니라 근거 관리입니다. 필요 없는 필드가 답에 끼어들면 모델이 무엇을 근거로 삼았는지 흐려지고, 뒤에서 볼 원가 인용 같은 실패가 생깁니다.
2

실행 전에 scorecard를 저장한다

결과를 본 뒤 기준을 만들면 마음에 드는 호출을 정당화하게 된다

tool-lab/scorecard.md · 이진 정의
결과를 본 뒤 기준을 만들면, 마음에 드는 호출을 성공이라 사후 정당화하게 됩니다. 그래서 채점 기준을 실행 전에 파일로 저장하고, 각 기준은 통과 여부를 둘로만 가르는 이진 정의로 씁니다.

📝 실행 전 채점 기준 네 줄

채점 기준통과의 이진 정의확인 위치
스키마 준수호출이 sku 문자열과 허용된 warehouse_id만 사용도구 호출 인자
호출 성공유효 입력에서 성공 반환 또는 명시된 오류 코드가 남음도구 응답
결과 사용 가능성최종 답이 available_quantity·checked_at만 근거로 삼음최종 답변
실패 처리오류 뒤 수량을 추정하지 않고 정해진 행동을 택함호출·최종 답변
각 기준은 둘 중 하나로만 판정된다 — 인상이 아니라 위치를 지목해 확인한다.
네 기준은 각각 호출 인자, 도구 응답, 최종 답변이라는 확인 위치를 갖습니다. 위치가 정해져 있어야 나중에 두 실행을 같은 자리에서 비교할 수 있습니다.

🐍 계약을 코드로 고정

ALLOWED_WAREHOUSES = {"SEOUL-01", "BUSAN-02"}
DESCRIPTIONS = {
    "minimal": "상품 재고를 조회합니다.",
    "contextual": ("승인된 창고에서 특정 상품의 현재 가용 재고를 "
        "읽기 전용으로 조회합니다. ... INVALID_SKU이면 SKU를 "
        "확인해 달라고 묻고, WAREHOUSE_NOT_ALLOWED이면 허용된 "
        "창고를 요청하며, TEMPORARY_UNAVAILABLE이면 한 번만 "
        "재시도한 뒤 중단합니다."),
}
INPUT_SCHEMA = {"type": "object", "properties": {
    "sku": {"type": "string", "minLength": 3, "maxLength": 32},
    "warehouse_id": {"type": "string",
        "enum": sorted(ALLOWED_WAREHOUSES)}},
    "required": ["sku", "warehouse_id"],
    "additionalProperties": False}
두 설명 minimal / contextual을 제외한 계약을 코드로 고정한다 — 스키마·허용 범위·실패 코드까지.
설명 두 종류만 변수로 남기고 스키마와 허용 범위는 코드로 못박습니다. contextual 설명은 언제 쓰는지, 어떤 인자를 넣는지, 오류 코드별로 무엇을 할지를 문장으로 담아, 정의서 여섯 항목이 그대로 설명 안에 들어가 있습니다.

🔧 이름 · 스키마 · 문법 검사

1이름은 get_inventory처럼 동사+대상으로
2인자 스키마는 서버도 검사할 수 있도록 형식·허용 범위를 분명히
3ast.parse()로 실행 없이 문법만 검사한다
스키마를 분명히 두면 모델의 설명과 서버의 검사가 같은 계약을 가리킨다.
스키마는 모델에게 주는 지시인 동시에 서버가 실제로 걸러낼 수 있는 규칙입니다. ast.parse는 계약 코드를 실행하지 않고 문법만 확인하므로, 실제 호출 없이도 정의가 깨지지 않았는지 점검할 수 있습니다.
3

설명과 실패를 다시 설계한다

같은 모델·같은 요청·같은 스키마, 설명만 바꾼다

minimal ↔ contextual · 실패 되돌리기
이제 같은 모델, 같은 요청, 같은 스키마에서 설명만 minimal과 contextual로 바꿔 실행합니다. 다른 조건을 고정했기 때문에, 결과 차이는 설명 한 항목의 효과로 읽을 수 있습니다.

🔬 설명만 바꿔 같은 순서로 넣는다

고정모델 · 요청
· 스키마
·
변경설명만
minimal↔contextual
·
같은 순서로 투입정상 요청 → "어느 창고든
SKU A-17 재고"
두 입력을 같은 순서로 넣어 scorecard에 표시한다 — 실패 기록은 정의서 여섯 항목으로 되돌린다.
정상 요청과 창고를 지정하지 않은 요청을 같은 순서로 두 설명에 넣습니다. 창고를 지정하지 않은 요청은 계약의 빈 칸을 드러내려는 의도된 자극이고, scorecard의 네 기준이 어디서 어긋나는지 표시합니다.

♻️ 실패를 비어 있던 항목으로

실패 사례비어 있던 항목보완 문장
존재하지 않는 창고 코드를 임의로 넣어 WAREHOUSE_NOT_ALLOWED를 반복 호출③ 언제 쓰는지
⑥ 실패 뒤 행동		허용되지 않은 창고면 허용 코드를 질문하고 재호출하지 않음
SKU 없이 가장 비슷한 상품을 골라 조회④ 인자 스키마
⑥ 실패 뒤 행동		SKU는 필수이며 없으면 상품 식별자를 질문
응답의 내부 원가까지 최종 답에 인용⑤ 반환 형식가용 수량과 확인 시각만 반환하고 답의 근거로 씀
실패 사례가 계약 문장 서너 줄로 되돌려지는 경험이 기록을 읽는 눈을 만든다.
세 실패는 모두 정의서의 특정 빈 칸을 가리킵니다. 반복 호출은 언제 쓰는지와 실패 뒤 행동이, 유사 상품 조회는 인자 스키마가, 원가 인용은 반환 형식이 비었기 때문입니다. 빈 칸을 한 문장으로 채우면 계약이 다시 닫힙니다.

📌 이것만은 꼭 — 핵심 4문장

1도구 설명 문장이 모델이 읽는 지시 — 이름·설명·스키마에 반환·실패까지 여섯 항목으로 고정한다.
2도구 하나는 동작 하나, 반환은 근거가 될 필드로 제한한다.
3채점 기준은 실행 전에 이진 정의로 저장한다 — 사후 정당화를 막는다.
4실패는 비어 있던 정의서 항목으로 되돌려 한 문장으로 보완한다.
여섯 항목·이진 채점·되돌리기는 하나의 순환입니다. 이 순환이 도구 하나에서 몸에 익으면, 다음의 여러 도구가 얽힌 하네스에서도 실패를 항목으로 지목하는 눈이 이어집니다. 출처: MCP 사양·Anthropic·LangChain의 도구 정의 표현.

✅ 정답 & 해설

A1. 이름 · 하는 일 한 문장 · 언제 쓰고 안 쓰는지 · 인자 스키마 · 반환 형식 · 실패 정의와 뒤 행동.
A2. 도구 하나는 동작 하나여야 하므로 과업 단위로 자른다 — 읽기와 변경을 섞으면 계약과 권한이 흐려진다.
A3. 결과를 본 뒤 기준을 만들면 마음에 드는 호출을 성공으로 정당화하게 되기 때문.
A4. 고정: 모델·요청·스키마. 변경: 설명만(minimal↔contextual).
A5. ⑤ 반환 형식 — 가용 수량과 확인 시각만 반환·근거로 쓰도록 보완한다.
A4와 A5를 자기 말로 설명할 수 있으면 오늘 목표는 달성입니다. 특히 A5처럼 실패를 항목 번호로 지목하는 습관이 계약을 다시 닫는 힘입니다.
