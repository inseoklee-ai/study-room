Skill로 남기기

결과 한 줄과 그 결과를 만든 규칙을 구별하는 것이 출발점입니다

남기려는 것은 'AI가 틀렸다는 증거'가 아니라 다음 보고서에서도 계속 사용할 지식입니다.

다음 금요일에도 필요한 지식

  • 첫째 주 TASK-102는 배포 전이어서 진행으로 분류했습니다. 다음 주에도 같은 업무가 진행일까요? 기록이 바뀌면 판정도 바뀔 수 있습니다
  • 반면 '개발 완료만으로 우리 팀의 완료 성과에 넣지 않는다'는 기준은 다음 주에도 필요합니다
  • 지금 대화에는 팀 규칙과 첫 보고서가 이미 있습니다. 그러나 다음 금요일 새 대화에서도 같은 자료가 자동으로 전달되는 것은 아닙니다
📌 필요한 지식을 파일로 남겨 두면 지원하는 앱이 해당 Skill을 발견하고 작업에 필요한 내용을 읽을 수 있습니다 — 모델을 다시 학습시키는 것이 아니라 작업할 때 참고할 지식을 준비하는 것
first-week-report.md와 report-work-notes.md를 다시 펼쳐 봅니다. 처음부터 잘 작성됐다면 올바른 판단에 어떤 기준이 사용됐는지 찾아봅니다.

# 팀 주간 진행 보고서

입력은 한 주의 업무 기록이다. 결과는 팀의 완료 기준과 위험 분류를 적용한
Markdown 보고서다. 상태 이름만 보고 완료 여부를 결정하지 않는다.

보고서를 작성할 때 팀 규칙을 읽는다. 이 문서에 데이터 필드, 분류 우선순위,
기한 계산, 보고서 형식이 있다. 현재 팀 규칙을 새로 추측하거나 일반적인
프로젝트 관리 기준으로 바꾸지 않는다.
실습 자료의 team-weekly-report/SKILL.md와 비교해 보세요. 본문이 길어 두 슬라이드로 나눴습니다 — 앞부분은 frontmatter와 입력·결과의 범위, 그리고 팀 규칙을 읽는 지점입니다.

SKILL.md 본문 ② — 자료·판단·산출물

사용자가 준 JSON이나 파일이 있으면 그것을 사용한다. 연결된
get_weekly_records로 조회해도 된다. MCP 연결은 필수가 아니며, 보고서를
쓰기 위해 새 서버 설치나 계정 인증을 시작할 필요는 없다. 대상 주차를
알 수 없으면 주차를 확인한다.

입력의 report_date를 기준으로 각 기록을 한 번씩 분류한다. 보고서에는 업무
ID와 판정의 근거가 된 필드를 남긴다. 팀 규칙으로 판정할 수 없거나 기록이
충돌하면 위험 항목으로 분리하고 확인이 필요한 사실을 적는다.

보고서를 파일로 요청받으면 Markdown으로 저장한다. 이 Skill은 기록 자체를
고치거나 메시지를 발송하지 않는다. 사용자가 규칙 변경을 요청하면 해당
요청의 기준을 우선하고 보고서에 달라진 기준을 표시한다.
뒷부분은 자료를 얻는 방법, 재확인 가능한 판단, 그리고 보고서 작성과 원본 변경의 구별입니다. 다음 슬라이드에서 문단마다 맡는 일을 표로 봅니다.

문단마다 맡는 일이 있습니다

문단맡는 일
첫 문단입력과 결과물의 범위. '프로젝트를 관리한다'처럼 넓게 적으면 일정 수정이나 담당자 배정까지 포함한다고 해석할 여지가 있음. '상태 이름만 보고 결정하지 않는다'는 TASK-102 사례와 연결
두 번째판단에 필요한 지식의 위치. '참고 자료도 활용한다'고 적는 대신 어느 파일을 언제 읽을지 지정 — 참조 파일을 비워 두거나 이름만 만들면 핵심이 빠집니다
세 번째자료를 얻는 방법과 업무 지식의 관계. 도구는 통로, Skill은 해석. 이미 JSON을 받았다면 MCP를 새로 연결할 필요가 없고, 기준이 정확해도 엉뚱한 주의 기록을 가져오면 다른 보고서가 됩니다
네 번째재확인 가능한 판단. report_date를 쓰면 지난주 보고서를 다시 생성해도 시간 기준이 바뀌지 않고, 업무 ID와 근거 필드가 있으면 '왜 위험이지?'의 답을 원본에서 찾을 수 있습니다
마지막보고서 작성과 원본 변경의 구별. 파일 저장은 요청한 산출물에 맞추고, 기준 변경 요청이 있으면 바뀐 기준을 드러냄 — 원래 규칙과 새 기준이 섞여 해석하기 어려워지는 일을 줄입니다
기록이 서로 모순될 때는 새로운 사실을 만들어 채우는 대신 무엇을 확인해야 하는지 남깁니다.

앞부분과 본문

  • .md는 Markdown 문서의 확장자 — 평문에 기호를 붙여 제목·목록·링크를 표현. #은 제목, 대괄호 안은 링크에 보이는 문구, 괄호 안은 대상 파일의 위치
  • 맨 위 --- 사이의 구역을 frontmatter라 하며 YAML(속성: 값)로 적습니다 — 본문이 실제 작업 지침이라면 앞부분은 Skill을 발견하고 선택하는 데 쓰는 안내
  • name은 폴더와 함께 다룰 식별자. description에는 '무엇을 하는지'와 '언제 필요한지'를 — 예제의 '주간 업무 보고', '이번 주 진행 상황 정리'는 사용자가 할 법한 요청과 연결
  • '모든 일을 완벽히 처리한다'처럼 넓게 쓰면 선택 기준이 흐려집니다 — 제외 문장을 계속 늘리는 것보다 업무 범위를 먼저 정확하게 표현하세요
📐 형식 규칙 — 파일 이름은 대문자를 포함해 SKILL.md. name은 1~64자, 소문자 영문·숫자·하이픈(앞뒤 하이픈과 연속 하이픈 금지, Skill 폴더명과 일치), description은 1~1024자
따라서 team-weekly-report/SKILL.md 안의 이름은 team-weekly-report입니다. AI가 Team Weekly Report처럼 다른 이름을 넣었다면 폴더와 속성을 함께 확인하세요.

⑩ Skill로 남기기
이번 Skill에 필요한 실제 구조는 두 파일입니다.

두 파일의 관계

team-weekly-report/
├── SKILL.md
└── references/
    └── team-rules.md
  • references/team-rules.md는 Skill 폴더를 기준으로 찾는 상대경로 — 작성자 컴퓨터의 전체 위치를 적지 않았으므로 다른 컴퓨터로 옮겨도 두 파일의 관계를 유지
  • 그래서 공유하거나 설치할 때는 SKILL.md 하나가 아니라 team-weekly-report 폴더 전체를 옮깁니다
각 업무를 위험 → 완료 → 진행 순서로 확인하여 한 범주에만 넣는다.
기한이 보고 기준일과 같으면 지연이 아니다.
🎯 두 문장 모두 실제 판정을 바꿉니다 — 첫 문장은 차단 요인이 남은 '배포 완료' 업무를 어느 범주에 넣을지, 두 번째는 보고 당일이 기한인 업무를 성급하게 지연으로 분류하지 않게. 본문에서 참조 링크를 읽었다는 것과 이런 규칙을 실제로 읽은 것은 다른 상태
Skill에서는 이름과 설명으로 관련성을 판단하고, 선택된 Skill의 본문을 읽고, 필요한 참조 자료를 더 읽는 흐름을 쓸 수 있습니다 — 이를 점진적 공개라고 부릅니다.

사용하지 않는 폴더를 먼저 만들 필요는 없습니다

관례적 이름두는 것
references판단에 필요한 문서
scripts재사용할 실행 코드 — 매번 같은 날짜 계산 코드를 다시 만들고 있다면 묶을 이유가 생깁니다
assets결과물에 적용할 서식이나 이미지 — 정해진 보고서 양식을 배포해야 한다면
⚠️ 파일을 나눴다는 이유만으로 이번 보고서의 문맥이 무조건 작아지는 것은 아닙니다 — 지금의 분리는 작업 지침과 팀 기준을 각각 관리하는 데에도 의미가 있습니다. 이번에는 실제로 쓰는 팀 규칙만 있으면 됩니다
이 예제에서는 주간 보고서를 만들 때마다 팀 규칙이 필요하므로 참조 파일도 읽습니다.

# 최종 파일

  • 앞의 점이 붙은 .claude, .opencode는 파일 탐색기에서 숨겨 보일 수 있는 폴더. ~는 사용자 홈 폴더
  • OpenCode는 .claude/skills도 지원하므로 두 앱에서 함께 쓸 때는 그 위치를 공유할 수 있습니다
  • 같은 이름의 Skill을 여러 위치에 중복 복사하기보다 실제 사용할 위치 하나를 정하세요. 대상 폴더가 이미 있다면 새 복사본을 안에 중첩시키지 말고 내용을 비교한 뒤 수정
이번 팀 규칙은 프로젝트 범위에 둡니다. 현재 프로젝트에만 쓰는 가상 팀 규칙을 모든 프로젝트에 적용할 필요는 없습니다.

이름을 지정하여 불러오기

/team-weekly-report 첫째 주 기록으로 보고서를 만들어 줘.      # Claude Code

team-weekly-report 스킬을 사용해 첫째 주 보고서를 만들어 줘.   # OpenCode
  • OpenCode는 내부 skill 도구로 Skill 내용을 불러옵니다 — 사용자가 그 내부 호출 코드를 직접 입력할 필요는 없고, Claude Code의 슬래시 문법을 OpenCode에서 똑같이 써야 하는 것으로 이해하지 마세요
  • AI의 '스킬을 사용했습니다'라는 말과 함께 실제 파일 읽기 또는 Skill 로드 기록을 살펴보세요 — team-weekly-report를 불러왔는지, 그 뒤 references/team-rules.md를 읽었는지
  • 맞춰 볼 것 — 첫째 주 업무가 네 건인지, 보고 기준일이 2026-09-04인지, 업무 ID별 근거가 붙었는지
🔧 Skill을 찾지 못했다면 — 현재 열어 놓은 프로젝트 위치와 최종 파일 경로 → 파일 이름이 정확히 SKILL.md인지, 앞부분의 이름과 설명이 있는지 → OpenCode는 Skill 접근 권한이나 skill 도구가 꺼져 있는지. Claude Code는 감시 중인 디렉터리 변경을 반영하지만 세션 시작 때 없던 최상위 Skills 디렉터리를 처음 만든 경우에는 재시작이 필요
이 확인은 새로운 정답을 외우는 활동이 아니라, 이번 입력과 실제 팀 기준으로 보고서를 만들었는지 확인하는 활동입니다.

A1. 넣을 것은 다른 기록에도 적용할 기준과 작업 방식. 넣지 않을 것은 특정 주의 정답(TASK-102는 진행)과 "꼼꼼하게 작성한다"류의 문장.
Q2. 공유·설치할 때 무엇을 옮기나?
A2. SKILL.md 하나가 아니라 team-weekly-report 폴더 전체. 참조 경로가 상대경로이기 때문.
Q3. 파일이 폴더에 있으면 Skill로 발견되나?
A3. 아니다. 앱이 찾아보는 위치(.claude/skills/ 등)에 두어야 한다.
