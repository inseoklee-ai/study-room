실습 2:
도구 실행과 MCP

요청·실행·근거를 분리하고, 남이 만든 도구를 붙이기

"재고 7개"라는 답은 누가 만들었을까요? 모델의 요청, 프로그램의 실행, 결과가 답에 쓰인 순간을 실행 원문에서 한 단계씩 가려냅니다. 그 다음 자기 도구 대신 남이 만든 MCP 서버를 붙여 봅니다.

  • 그 원문을 트레이스로 남기고, 경계 사례는 한 곳만 고쳐 다시 실행한다

실습의 목표는 화면의 답이 아니라 그 답이 만들어진 경로입니다. 요청과 실행을 분리해 관찰하고, 그 관찰을 기록으로 보존하고, 남이 만든 도구도 같은 방식으로 주입·호출됨을 확인합니다.
1

요청과 실행을 분리해 관찰한다

모델은 도구를 요청하고, 하네스가 그 함수를 실행한다

qwen3.5:2b · 온도 0 · reasoning=False
로컬 qwen3.5:2b 서버, 온도 0, reasoning=False로 실행합니다. 실행 명령은 uv run --with langchain --with langchain-ollama python 파일명. 모델의 요청과 프로그램의 실행은 서로 다른 소관임을 코드로 확인합니다.

🧰 도구 하나를 계약으로 만든다

@tool
def get_inventory(sku: str, warehouse_id: str) -> dict:
    """승인된 창고에서 특정 상품의 현재 가용 재고를
    읽기 전용으로 조회합니다. warehouse_id에는
    SEOUL-01 또는 BUSAN-02만 넣습니다. 수량을 변경하지
    않습니다. INVALID_SKU이면 SKU를 확인해 물어야 합니다."""
    if warehouse_id not in ("SEOUL-01", "BUSAN-02"):
        return {"error": "WAREHOUSE_NOT_ALLOWED"}
    return {"sku": sku, "warehouse_id": warehouse_id,
            "available_quantity": 7, "checked_at": "..."}
@tool = 함수의 이름·인자·설명을 모델이 호출할 수 있는 도구 계약으로. bind_tools([...]) = 그 계약을 모델에 연결.
docstring이 곧 모델이 읽는 설명 문장입니다. 허용 창고를 enum처럼 못박고, 읽기 전용임과 실패 뒤 행동(SKU를 물어라)을 계약에 적어 둡니다. ToolMessage는 실제 반환값을 이전 호출 id와 함께 모델에 돌려주는 메시지입니다.

고른다

r1 = await llm_with_tools.ainvoke("BUSAN-02 창고의 SKU A-17 재고를 알려 줘")   # [1]
result = get_inventory.invoke(r1.tool_calls[0]["args"])                        # [2]
r2 = await llm_with_tools.ainvoke([r1, ToolMessage(content=...,
        tool_call_id=r1.tool_calls[0]["id"])])                                # [3]
[1]에서 모델은 도구와 인자를 요청할 뿐 함수를 실행하지 않습니다. [2]에서 하네스가 요청 인자를 꺼내 실제 함수를 호출하고 반환값을 받습니다. [3]에서 모델이 그 결과 메시지를 근거로 최종 답을 만듭니다.

🧭 각 단계는 누구의 소관인가

1[1]은 모델의 소관 — 도구·인자를 요청할 뿐, 함수를 실행하지 않는다
2[2]는 하네스의 소관 — 요청 인자를 꺼내 실제 함수를 호출하고 반환값을 받는다
3[3]은 다시 모델의 소관 — 도구 결과를 메시지로 받은 모델이 그 값에 근거해 답한다
[1]의 호출이 그럴듯해도 [2]가 없으면 재고를 읽었다 말할 수 없고, [2]가 성공해도 [3]이 수량을 바꾸면 결과 사용은 실패다.
세 단계를 하나로 뭉뚱그리면 "도구를 잘 썼다"는 인상만 남습니다. 요청·실행·근거 사용을 나눠 봐야 어디서 어긋났는지 지목할 수 있습니다.

📄 실측 출력을 그대로 본다

[1] 모델의 요청: [('get_inventory', {'sku': 'A-17', 'warehouse_id': 'BUSAN-02'})]

[2] 하네스의 실행 결과: {"sku": "A-17", "warehouse_id": "BUSAN-02",
    "available_quantity": 7, "checked_at": "2026-08-27T01:55:00+09:00"}

[3] 결과를 읽은 최종 답:
    승인된 창고(BUSAN-02)에서 상품 A-17의 현재 가용 재고는 7개입니다.
"재고 7개"는 모델이 지어낸 값이 아니라 [2]의 반환값을 [3]이 읽어 만든 답이다.
출력 원문을 보면 7이라는 숫자가 [2]의 available_quantity에서 왔음을 눈으로 확인할 수 있습니다. 판정("통과")만 적어 두면 이 근거가 사라집니다.
2

실행 원문을 트레이스로 남긴다

판정만이 아니라, 그 판정을 뒷받침하는 원문을 보존

trace-01.txt · 한 곳만 고치기
트레이스는 요청부터 최종 답까지의 실행 기록입니다. 기록을 남기는 습관이 있어야, 다음에 호출이 달라졌는지 실행이 달라졌는지 최종 답만 달라졌는지 비교할 수 있습니다.

🗂️ 트레이스에 무엇을 담나

  • 트레이스(trace) = 요청부터 최종 답까지의 실행 기록
  • tool-lab 폴더에 trace-01.txt로 저장 — 요청 문장 · [1] 도구 이름과 인자 · [2] 실행 결과 · [3] 최종 답을 순서대로
  • 맨 위에 모델명 · 온도 · 실행 명령도 함께 적는다
  • 통과/실패 판정만 남기지 말고 그 판정을 뒷받침하는 원문을 보존한다
이전 기록을 덮어쓰면 호출 변화와 실행 변화의 근거가 사라진다. 트레이스는 새 파일로 쌓는다.
원문 보존이 핵심입니다. "7개라고 답했다"만 남기면 그 7이 실제 도구 반환에서 왔는지 모델의 추정인지 나중에 구분할 수 없습니다. 실행 명령과 모델 설정도 함께 적어야 재현할 수 있습니다.

🔧 경계 사례는 한 곳만 고쳐 재실행

1요청을 "부산 3번 창고의 A-17 재고"로 바꿔 실행 → 없는 코드로 호출되면 하네스가 {"error": "WAREHOUSE_NOT_ALLOWED"} 반환
2그 뒤 모델이 허용 창고 코드를 다시 묻는지 [3]에서 관찰. 수량을 추정하거나 오류를 무시했다면 그 문장도 그대로 기록
3문제가 있으면 설명 문장 · 스키마 enum · 실패 뒤 행동 중 하나만 고친다 → trace-02.txt에 저장
설명과 enum을 함께 바꾸거나 실패 처리까지 동시에 고치면 어느 변화가 효과를 냈는지 모른다.
두 트레이스를 나란히 놓고 호출 자체가 달라졌는지, 오류 반환은 같은지, 최종 답만 달라졌는지 비교합니다. 한 번에 한 곳만 바꾼 기록이 쌓여야 새 실패와 재등장을 가려낼 수 있습니다.
3

남이 만든 도구를 붙인다 (MCP)

실무의 도구 연결 = MCP 서버를 내 에이전트에 등록하는 일

Qdrant · mcp-server-qdrant · uvx
지금까지는 자기 도구를 직접 만들었습니다. 실무에서는 남이 만든 MCP 서버를 등록해 씁니다. Claude Code와 opencode 모두 같은 설정 파일 방식으로 다루며, 에이전트 입장에선 빌트인 도구든 MCP 도구든 모델에 주입되는 도구 정의라는 점이 같습니다.

🧱 세 이름을 구분한다

이름무엇인가역할
Qdrant문서 조각을 벡터로 보관하고 의미가 비슷한 조각을 찾아 돌려주는 오픈소스 검색 엔진저장소
mcp-server-qdrantQdrant를 MCP 도구로 노출하는 연결 서버 — qdrant-store(저장) · qdrant-find(검색) 둘을 내놓음창구
uvxuvx mcp-server-qdrant 한 줄로 알아서 내려받아 실행 — 패키지 이름을 받아 임시 환경을 만들어 실행하는 uv의 명령실행기
임베딩은 fastembed 기본을 로컬에서 처리 → 회원 가입·API 키 불필요.
저장 위치는 환경 변수로 정합니다. QDRANT_URL이 :memory:면 서버 프로세스 메모리에만 저장되어 세션이 닫히면 사라집니다. QDRANT_COLLECTION은 문서 조각 묶음 이름, EMBEDDER_PROVIDER와 FASTEMBED_MODEL은 벡터 변환 모델을 지정합니다.

📁 Claude Code — .mcp.json

{"mcpServers": {"qdrant": {"command": "uvx", "args": ["mcp-server-qdrant"],
  "env": {"QDRANT_URL": ":memory:", "QDRANT_COLLECTION": "policies",
          "EMBEDDER_PROVIDER": "fastembed",
          "FASTEMBED_MODEL": "BAAI/bge-small-en-v1.5"}}}}
mcpServers 아래 각 항목이 서버 하나. command·args는 실행 줄, env는 환경 변수. 저장 후 claude 실행 → /mcp로 목록 확인.
등록된 도구의 설명 문장은 세션 시작 시 모델의 컨텍스트 창에 자동 주입됩니다. 프로젝트 루트에 .mcp.json을 두는 것만으로 qdrant-store와 qdrant-find가 모델이 부를 수 있는 도구가 됩니다.

📁 opencode — opencode.json

{"mcp": {"qdrant": {"type": "local", "command": ["uvx", "mcp-server-qdrant"],
  "environment": {"QDRANT_URL": ":memory:", "QDRANT_COLLECTION": "policies",
                  "EMBEDDER_PROVIDER": "fastembed",
                  "FASTEMBED_MODEL": "BAAI/bge-small-en-v1.5"}}}}
키 이름은 다르지만(mcp·command·environment) 내용은 같다. 누가 도구를 실행하는지, 무엇을 검색 대상으로 삼는지를 정의하는 같은 서버 실행 지점이다.
서버 랙의 케이블처럼 표기는 달라도 양쪽 연결은 하나의 서버 실행 지점으로 모입니다. 같은 질문을 던지면 앞 실습과 똑같은 Qdrant 도구가 두 에이전트에서 같은 방식으로 주입·호출됩니다.

🔬 관찰 기록 세 가지

1도구 정의가 두 에이전트에서 동일하게 주입되는지 호출 로그로 확인
2같은 질문에 같은 도구를 골랐는지·인자를 같게 채웠는지 — 실측에선 각 기본 모델이 qdrant-store로 문장 셋을 저장하고 qdrant-find로 검색
3인메모리 저장은 세션이 닫히면 사라지므로, 관찰 기록은 세션 안에서 trace-mcp-01.txt로 남긴다 → 과제의 근거 문서 후보로
확인하는 것은 "검색이 됐다"가 아니라 두 에이전트가 같은 도구를 같은 방식으로 썼는가이다.
:memory: 저장은 세션이 닫히면 소멸하므로, 관찰 결과는 반드시 세션 안에서 파일로 보존해야 합니다. 이 트레이스가 나중에 과제의 근거 문서 후보가 됩니다.

📌 이것만은 꼭 — 핵심 4문장

1한 번의 답에는 [1] 요청(모델)·[2] 실행(하네스)·[3] 최종 답(모델) 세 소관이 있다.
2판정만이 아니라 실행 원문을 트레이스로 보존해야 변화의 근거가 남는다.
3경계 사례는 설명·enum·실패 뒤 행동 중 한 곳만 고쳐 재실행하고 나란히 비교한다.
4MCP로 붙인 도구도 빌트인처럼 모델에 주입되는 도구 정의 — 키 이름은 달라도 같은 서버다.
4번이 이 실습의 태도입니다. 도구가 자기 것이든 남의 것이든, 결국 모델에 주입되는 정의이고 하네스가 실행합니다. 그 경로를 원문으로 남기는 습관이 핵심입니다.

✅ 정답 & 해설

A1. [1] 요청·[3] 최종 답은 모델의 소관, [2] 실행은 하네스의 소관(실제 함수 호출).
A2. [3]에서 모델이 수량을 바꾸어 말하거나 도구 결과를 무시하고 답했을 때.
A3. 판정만 남기면 근거가 사라져, 호출 변화·실행 변화를 나중에 비교할 수 없기 때문.
A4. 설명·enum·실패 처리를 함께 바꾸면 어느 변화가 효과를 냈는지 구분할 수 없기 때문.
A5. command·environment가 가리키는 서버 실행 지점이 하나이고, 같은 Qdrant 도구가 같은 방식으로 주입되기 때문.
A1과 A5를 자기 말로 설명할 수 있으면 오늘 목표는 달성입니다. 도구의 출처가 달라도 실행 경로는 같다는 점이 핵심입니다.
