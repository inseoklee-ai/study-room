1

무엇을 상시 로드할지, 신뢰 판단부터

한 번 저장한 문장은 세션마다 행동 규칙 후보로 다시 들어온다

운영 규칙 후보 · 정책 표면
매 세션 자동으로 읽히는 파일은 편리한 메모가 아니라 반복해서 작동하는 운영 규칙 후보입니다. 첫 질문은 "무엇을 적으면 잘 따를까"가 아니라 "이 규칙을 상시 로드해도 안전한가"입니다.

📄 두 파일이 하는 일 — 에이전트에게 프로젝트 안내

CLAUDE.md

Claude Code가 세션에서 읽는, 사람이 작성한 Markdown 지시·메모리 파일. 새 창에서 시작해도 빌드 명령·명명 규칙·반복 주의사항을 다시 전달한다.

AGENTS.md

여러 코딩 에이전트가 공용 규칙 파일로 채택하는 형식. 공통 규칙은 여기에 두고, 필요한 도구별 파일에서 가져오는 방식.

  • 파일에 적었다고 OS 설정처럼 행동을 강제하는 게 아니다 — 모델이 세션의 컨텍스트로 읽는 지시일 뿐
  • 내용 근거·행동 규칙·대화 상태·비신뢰 입력의 구분과 맥락 예산이 그대로 적용된다
⚠️ 두 이름이 같은 방식으로 모든 도구에서 로드된다고 가정 금지. 승인된 빌드 명령은 상시 규칙 후보가 될 수 있어도, 웹에서 발견한 "효율적 배포 절차"는 먼저 출처·변경 이력을 검토한다.
AGENTS.md는 Claude Code가 기본으로 직접 읽는 파일이 아니므로, 공통 본문은 AGENTS.md에 두고 CLAUDE.md에서 import하는 방식이 권장됩니다. 출처: Claude Code 메모리 안내, AGENTS.md 사양.

✅ 상시 로드 검토표 — 이 문장은…

1승인된 작성자·변경 이력이 있나?
2대부분 세션에서 실제 필요한가?
3다른 규칙과 충돌 안 하나?
4주문번호·비밀·개인 주소처럼 매 요청 달라지거나 민감한 값을 담지 않나?
5실패해도 되돌릴 수 있나?
하나라도 답하기 어려우면 파일에 안 넣고, 필요할 때 읽는 문서·사람 승인 절차로 돌린다.
외부 문서에서 복사한 명령, 출처를 잃은 요약, 특정 고객의 주문 정보처럼 검토 안 됐거나 민감한 내용을 편의 때문에 넣어선 안 됩니다. 상시 맥락은 편리한 메모장이 아니라 반복 실행되는 정책 표면입니다.

맥락 파일이 내는 세 효과와 한 비용

얻는 것과 매 세션 지불하는 것을 함께 본다

stateless 보완 · 일관성 · 상시 비용
맥락 파일은 새 세션의 빈 출발을 보완하고 규칙을 일관되게 고정해 주지만, 자동 로드되는 만큼 매 세션 토큰을 지불합니다. 효과와 비용을 함께 저울질하는 것이 이 파트의 핵심입니다.

🔁 두 가지 이득 — stateless 보완·일관성

①stateless 보완 — 새 호출은 이전 세션의 내부 상태를 저절로 보존하지 않는다. 빈 창에서 시작하는 새 세션은 테스트 명령·금지 경로를 모른다. 매번 다시 설명하게 되는 사실을 파일에 남기면 같은 출발 맥락을 재구성한다
②일관성 — "테스트를 실행하고 결과를 보고하라"를 매번 새로 쓰면 표현·위치가 달라진다. 검토된 한 문장을 파일로 고정하면 세션마다 입력 앞부분이 문자 그대로 같아져 같은 질문에 같은 규칙이 적용된다
두 효과 모두 사람이 매번 다시 하던 일을 검토된 한 번의 문장으로 대체한다.
stateless는 "새 세션은 앞선 세션의 상태를 자동으로 이어받지 않는다"는 뜻입니다. 그래서 파일이 그 빈 출발을 메꾸고, 표현이 흔들리지 않도록 고정합니다.

💸 한 비용 — 매 세션 지불하는 토큰

  • 자동 로드는 매 세션이 지불하는 토큰 — 파일이 길수록 정책 문서·현재 코드·대화 이력·도구 정의 자리를 밀어낸다
  • 긴 절차가 한 번도 안 쓰이면 캐시가 있어도 좋은 맥락이 아니다

판정 불가

"품질을 높입니다" — 관찰·시험할 수 없다

짧고 검증 가능

"커밋 전 npm test를 실행하고 결과를 보고합니다"

매번 다시 설명하는 사실만 메모리 파일에, 특정 작업에만 필요한 다단계 절차는 필요할 때 읽는 Skill·경로 범위 규칙으로 분리한다.
Skill은 반복 작업을 묶어 필요할 때 불러오는 절차 단위입니다. 상시 로드가 아니라 필요 시 로드이므로, 가끔 쓰는 긴 절차를 상시 비용에서 떼어냅니다. 공식 안내도 이 분리를 권장합니다.

다중 파일은 추측 말고 표식·로그로

현재 폴더에서 상위 폴더를 향해 규칙을 찾는 구조가 흔하다

고유 표식 · 출력 로그 · 재현
도구마다 세부 규칙은 달라도 현재 작업 폴더에서 상위 폴더를 향해 관련 규칙을 찾는 구조가 흔합니다. 무엇이 언제 로드되는지는 추측하지 말고 파일별 표식과 출력 로그로 확인해야 합니다.

🔎 표식은 추측 장치가 아니라 관찰 장치

my-shop/
├── CLAUDE.md            # @AGENTS.md 와 [ROOT] 표식 규칙
├── AGENTS.md            # 팀 공통 규칙
└── payments/
    ├── CLAUDE.md        # [PAYMENTS] 표식 규칙
    └── charge.py        # 비어 있어도 되는 결제 모듈 파일
  • Claude Code에선 현재·상위 폴더의 CLAUDE.md·CLAUDE.local.md가 세션에 들어오고, 하위 폴더의 CLAUDE.md는 그 폴더 파일을 실제로 읽어 작업하는 시점에 로드될 수 있다
  • 표식이 출력에 없다고 반드시 미로딩은 아니고, 있다고 우선순위까지 증명하는 것도 아니다
표식은 어떤 세션·작업 폴더·파일 접근 뒤에 어떤 흔적이 나왔는지 재현 가능하게 기록하는 용도다.
AGENTS.md는 Claude Code가 기본으로 직접 읽는 파일이 아니므로 CLAUDE.md에서 import하거나 문서·실제 로그로 확인합니다. 출처: Claude Code 메모리 안내.

🧪 관찰 실험 — 한 번에 하나씩

실험조건관찰할 것
①루트에서 새 세션, 결제 폴더 미접근[ROOT] 표식과 루트 파일 로드 기록
②루트 세션에서 payments/charge.py를 읽은 뒤 같은 질문[PAYMENTS] 표식의 추가 여부·시점
③payments/에서 새 세션, 첫 질문 반복시작 시점의 루트·결제 규칙 표식과 로그
1세 실험은 반드시 새 세션에서 — 앞선 대화 상태가 표식을 운반 못 하게
2세션 시작 폴더·파일 접근 순서만 한 번에 하나씩 바꾸고 출력·도구 로그를 함께 저장
3예상과 다르면 모델의 설명으로 확정 말고 도구 버전 문서·최소 저장소에서 재확인
모델의 자기 보고는 단서일 뿐 단독 증거가 아닙니다. 세션·시작 폴더·파일 접근 순서를 하나씩만 바꿔 로그와 함께 저장해야, 무엇이 어느 흔적을 낳았는지 재현 가능하게 설명할 수 있습니다.

🧭 어디에 둘까 — 안전 경계는 루트에

  • 하위 폴더 규칙을 뒤에 추가해 필요할 때만 로드하면, 결제 코드를 안 다루는 세션의 시작 맥락 비용·관련성 경쟁이 준다
  • 단 규칙이 중간에 들어올 수 있어, 중요한 금지 규칙을 하위 파일에만 숨기면 처음의 계획·도구 호출이 그 규칙보다 앞서 나갈 위험
모든 과업에 필요한 안전 경계는 검토된 루트 규칙에, 모듈 특유 빌드·검증 규칙은 가까운 파일에. 캐시 적중을 위해 오래된 규칙을 상시 로드하지 않는다.

첫 줄은 공통 규칙을 가져오고, 아래는 도구별 규칙만. 개인 주문 조회 주소·임시 테스트 값은 공유 파일이 아니라 접근 통제된 환경 변수·그때의 대화 상태로.

"친절하게 답합니다"가 빠진 건 실수가 아니다 — 관찰·시험 불가한 표현은 상시 맥락을 차지하나 판정 기준을 선명하게 못 한다.
각 줄은 서로 다른 경계입니다. 근거 출처 제한 / 주문 사실과 정책의 역할 분리 / 불확실성 처리 / 판단 경로 되짚기 / 민감 행동을 답변에서 분리. 저장 뒤 각 문장의 승인자·변경 이력·필요 빈도·민감도를 재검사하고, 표식 없는 정상 과업으로 동작·로그를 확인합니다.

2하위 폴더 하나 — 그 모듈에만 필요한 규칙 두 줄
3근거 문서 하나 — 규칙이 아니라 정책·사양·일정처럼 원문 내용
점검 — 규칙이 관찰 가능한가 / 바뀔 사실이 AGENTS.md가 아니라 근거 문서에 있나 / 민감정보를 안 넣었나. 세션에서 확인: ① 하위·루트 규칙이 함께 적용되나 ② 답이 조항을 인용하나 ③ 근거 한 문장만 갱신하면 답이 바뀌나.
출력·실행 위치를 기록하면, "파일이 있다"는 주장 대신 자신의 도구에서 확인한 상속과 근거 분리를 갖게 됩니다.

📌 이것만은 꼭 — 핵심 4문장

1첫 질문은 "잘 따를까"가 아니라 "상시 로드해도 안전한가" — 검토표를 통과한 문장만.
2맥락 파일은 stateless를 보완하고 일관성을 주지만, 매 세션 토큰 비용을 지불한다.
3다중 파일 로딩은 추측하지 말고 표식과 로그로 관찰하며, 안전 경계는 루트에 둔다.
4규칙은 파일에, 사실은 근거 문서에 — 사실이 바뀌면 근거 한 문장만 갱신한다.
📚 더 읽기 — Claude Code 메모리 안내 · AGENTS.md 사양.
4번이 규칙과 사실을 분리하는 실무의 핵심입니다. 정책이 바뀔 때마다 규칙 파일을 뒤지지 않고 근거 문서만 갱신하면 답이 따라 바뀝니다.

🎯 이해도 확인 질문

Q1. 맥락 파일을 만들 때 첫 번째로 던져야 할 질문은 무엇인가?
Q2. 맥락 파일의 세 효과와 한 비용은 각각 무엇인가?
Q3. 다중 파일 로딩을 확인할 때 표식은 무엇을 위한 장치인가? 하지 말아야 할 해석은?
Q4. 반품 최소 파일에서 "친절하게 답합니다"를 뺀 이유는?
Q5. 반품 기한이 14일→7일로 바뀌었다. 무엇을 고쳐야 답이 바뀌나?
답이 바로 떠오르지 않으면 앞 장으로 돌아가 확인해 보세요. Q4와 Q5가 규칙과 사실의 분리를 가장 잘 가립니다.

✅ 정답 & 해설

A1. "무엇을 적으면 잘 따를까"가 아니라 "이 규칙을 상시 로드해도 안전한가" — 저장한 문장은 세션마다 행동 규칙 후보로 다시 들어오므로.
A2. 효과: stateless 보완(빈 새 세션의 출발 맥락 재구성) · 일관성(입력 앞부분을 문자 그대로 고정). 비용: 상시 토큰(매 세션 지불, 다른 맥락 자리를 밀어냄).
A3. 표식은 세션·폴더·파일 접근 뒤의 흔적을 재현 가능하게 기록하는 관찰 장치. 없다고 미로딩이라 단정하거나, 있다고 우선순위까지 증명됐다고 보면 안 된다.
A4. 관찰·시험 불가한 표현이라서 — 상시 맥락을 차지하나 판정 기준을 선명하게 못 한다.
A5. 근거 문서(docs/returns-policy.md) 한 문장만 갱신하면 된다. 규칙 파일은 그대로 — 규칙과 사실을 분리한 이득.
A2와 A5를 자기 말로 설명할 수 있으면 오늘 목표는 달성입니다.
