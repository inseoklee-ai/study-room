줄여서 올리기

100MiB 관문 · 형식 넷 · 두 축

압축
파일 하나가 217.5MB입니다. 여기서 올리면 된다고 말하고 싶지만, 안 됩니다.

🚧 100MiB에서 걸린다

  • 올릴 곳은 GitHub Pages — 코드를 올리면 그대로 웹 주소가 된다(서버·빌드 없음). 그런데 파일 하나가 100MiB 넘으면 아예 안 받는다(약 105MB). 우리 파일은 두 배가 넘는다
  • 올라간다고 끝도 아니다 — 링크 받은 사람 브라우저가 통째로 내려받아야 화면이 뜬다
12초 만에 뜨느냐, 3분 가까이 빈 화면이냐10Mbps에서 217.5MB는 3분, 15MB는 12초 — 여기에 링크가 열리느냐 닫히느냐가 걸린다
코드로 어떻게 해 볼 종류가 아니라 통과해야 지나가는 관문. 여기서 크기가 그대로 기다리는 시간이 된다.
MiB는 1,024를 거듭 곱해 세는 단위라 흔히 쓰는 MB로는 약 105MB입니다. 📚 About large files on GitHub, GitHub Docs.

⚡ 명령 한 줄로 열네 배

npx -y @playcanvas/splat-transform@latest -w scene.ply scene.sog
  • 변환 도구는 따로 설치 안 함 — 한 번 쓰고 마는 도구라 받아서 바로 실행. Node.js가 필요한데 코랩엔 이미 있다
  • -w를 빼지 말 것 — 여러 번 돌리는데 같은 이름이 있으면 거기서 멈춘다. Node.js 판이 높아 경고가 뜨지만 동작은 정상
217.5MB → 15.3MB28초, 14.2배. 못 올라가던 파일이 관문을 통과했고 10Mbps에서 12초면 뜬다
📚 playcanvas/splat-transform, GitHub. 점을 만든 그 자리(코랩)에서 그대로 치는 게 가장 빠릅니다.

📦 형식이 넷 — 알갱이는 하나도 안 버린다

형식크기(100만 개)원본 대비변환 시간
.ply 무압축68.0MB1배0.4초
.splat32.0MB2.1배1초
.compressed.ply16.3MB4.2배5초
.sog5.0MB13.6배9초
네 형식 다 알갱이 100만 개가 그대로 100만 개 — 줄어든 건 값을 적는 방식뿐. 가장 흔한 수단이 양자화(자릿수를 몇 단계로 나눠 어느 칸인지만 적음). 뭉갤수록 작아지고 조금 어긋나는데, 알갱이 하나의 몫이 작아 눈에 잘 안 띈다.
.compressed.ply는 형식은 두고 자릿수만 줄여 4배에서 멈춥니다. .splat은 알갱이 하나를 32바이트로 못 박은 초기 형식이라 파일 크기 ÷ 32 = 알갱이 개수입니다.

🖼️ .sog — 숫자를 이미지로 바꿔 사진 압축기에

  • 자리·크기·회전·색을 각각 WebP 이미지로 바꾼다 — 알갱이 100만 개의 자리 값을 1000×1000 격자에 채우면 그것이 곧 그림 한 장(화소 색 자리에 좌표가 든 셈)
  • 사진은 이웃 화소 색이 서로 비슷하고, 사진 압축기는 그 비슷함을 줄이도록 만들어졌다 — 자리끼리·회전끼리 모은 격자도 이웃이 비슷하니 그대로 먹는다
사진 압축이 수십 년 쌓은 것을 3차원 자료가 빌려 쓴다
위 표는 100만 개라 13.6배, 우리 파일은 320만 개라 14.2배 — 같은 형식이라도 몇 배 줄어드느냐는 장면과 알갱이 개수를 함께 봐야 하는 값.
📚 Splat File Formats, PlayCanvas Developer Site.

더 넓은 공간을 찍었거나 사진을 많이 넣어 형식만으로 안 떨어지면 그때 점을 줄이고 K를 함께 올립니다.

⚖️ 기다림과 부드러움은 다른 축

파일 크기 → 기다림

첫 화면이 뜨기까지의 시간. 형식을 바꿔 크기를 줄이면 열네 배로 짧아진다

알갱이 수 → 부드러움

뜬 뒤 매끄럽게 도는가. 그리는 쪽이 매번 상대하는 건 파일이 아니라 화면에 늘어놓을 알갱이 개수

오래 기다린다 → 형식을 바꾼다
뚝뚝 끊긴다 → 알갱이 수를 줄인다
.ply 217.5MB든 .sog 15.3MB든 알갱이는 3,197,944개로 똑같다 — 형식 변환은 적어 두는 방식을 바꿀 뿐 알갱이를 덜어 내지 않는다. 그래서 변환으로 기다림은 줄었지만 부드러움은 그대로.
느리다고 할 때 어디를 손대야 하는지가 이 구분에서 나옵니다.

화면에 띄우고 주소를 켠다

정렬 순서 · Spark · GitHub Pages · 폰

렌더러와 배포
파일을 화면에 띄우기 전에, 그리는 쪽에서 무슨 일이 벌어지는지 봅니다. 알갱이가 반투명이라 생기는 문제 하나가 여기서 드러납니다.

🎨 알갱이를 어떻게 그리나 — 네 걸음

1원근 투영 — 3차원 좌표를 깊이로 나눠 눌러 화면 좌표로. 멀수록 작게 찍히고, 타원이 눌려 얼룩이 된다
2셰이더 — 그 계산을 그래픽 장치가 수천 개씩 동시에. 알갱이 하나를 받아 화면 좌표를 내는 작은 프로그램
3깊이 버퍼 — 같은 화소에 겹치면 가장 가까운 것만 남기고 버림. 불투명한 것이면 이걸로 끝
4그런데 알갱이는 반투명 — 버릴 게 아니라 섞어야(알파 블렌딩). 깊이 버퍼는 못 쓴다
남는 길은 하나 — 먼 것부터 가까운 것 순으로 줄 세워 차례로 바른다. 셀로판지 빨강·파랑·노랑 순서와 노랑·파랑·빨강 순서가 다른 색이 되는 그 이치.
불투명한 것만 그린다면 줄을 세울 이유가 없습니다. 표 하나로 끝날 일을 매번 300만 개 줄 세우기로 치르는 이유가 반투명 하나입니다.

🔀 정렬 순서 — 카메라가 돌면 통째로 바뀐다

카메라 왼쪽청록 → 보라 → 파랑
순으로 바른다
↔
오른쪽으로 돌면파랑 → 보라 → 청록
순으로 뒤집힌다
  • 정면에서 앞이던 알갱이가 반대편으로 돌면 뒤가 된다 → 화면 한 번 그릴 때마다 320만 개를 다시 줄 세운다
  • 이 줄 세우기가 스플랫에서 가장 무거운 작업 중 하나이고, 렌더러들이 갈리는 곳
줄 세우기가 어긋나면 뒤 알갱이가 앞을 덮는다화면을 열고 각도를 크게 여러 번 바꿔 보는 이유가 이것
살짝 돌려서는 안 보입니다. 크게 틀어야 정렬 순서가 제대로인지 드러납니다.

🔌 렌더러를 하나 물린다 — Spark

브라우저는 스플랫을 기본으로 못 그린다. 웹 3D 대표 라이브러리 three.js의 기본 렌더러는 삼각형용이라 알갱이를 못 그린다. 그래서 three.js 위에 얹는 스플랫 렌더러 Spark(MIT)를 붙인다.

형식

.ply·압축 ply·.spz·.splat·.ksplat·.sog를 전부 읽는다 — 오늘 만든 것도 나중에 받아 온 것도 변환 없이

창구

오래된 WebGL2에서 돈다(거의 모든 폰). 최신 WebGPU는 빠르지만 안 열리는 브라우저가 있다 — 누가 열 수 있느냐가 갈린다

빌드 도구는 안 쓴다 — 브라우저 표준 import map으로 CDN에서 바로 불러오면 파일 한 장짜리 정적 페이지로 끝. 마지막에 폰으로 여는 오늘 조건에선 WebGL2 선택이 결정적.
📚 sparkjsdev/spark, GitHub. 어느 창구를 쓰느냐가 곧 누가 그 화면을 열 수 있느냐를 정합니다.

📝 지시문 — 뷰어 페이지

스플랫 파일 하나를 띄우고 마우스로 돌려 볼 정적 페이지를 만들어 주세요.
- three.js + @sparkjsdev/spark, 둘 다 CDN import map, 빌드 도구 없이 index.html 한 파일
- 같은 폴더 파일을 읽되 파일 이름을 맨 위 한 줄에서 바꾸게
- Spark 전용 렌더러를 만들어 장면에 넣기(이 한 줄 빼면 검은 화면, 오류도 안 남)
- 확장자를 그대로 형식 이름으로 넘기지 말고 대응표를 두기(.sog의 안쪽 이름은 pcsogszip)
- OrbitControls로 회전·확대·이동, 감쇠 켜기
- 다 불러온 뒤 알갱이 덩어리 크기를 Spark가 주는 자로 재서 카메라를 그 앞에
  (three.js 바깥 상자는 알갱이에 빈 상자를 돌려줌)
- 거꾸로 서면 위아래 뒤집기 단추 하나
- 왼쪽 위에 단계 목록 5개(라이브러리·렌더러·받기·풀기·크기 재기), 실패 단계엔 무엇을 볼지
- 파일 크기·받는 시간·알갱이 개수를 화면에
단계 목록을 띄우라는 줄이 값어치가 가장 크다 — 막혔을 때 어느 줄을 봐야 하는지가 곧바로 갈린다. 없으면 남는 단서가 검은 화면 하나.
OrbitControls는 three.js에 딸려 오는 조작기입니다. 마우스와 손가락 입력을 한 경로로 받아 터치도 그대로 됩니다.

🕳️ 오류를 안 내는 함정이 둘

1. 검은 화면

전용 렌더러를 장면에 안 넣으면 파일도 받아지고 알갱이 개수도 찍히는데 화면만 검다. 그릴 것이 다 올라간 채 그릴 부품만 빠져 오류를 낼 이유가 없다. 개수 맞는데 검으면 여기부터

2. .sog 안쪽 이름

파일은 scene.sog인데 렌더러가 아는 이름은 pcsogszip. 확장자를 그대로 넘기면 Invalid file type: sog

그래서 확장자를 형식 이름으로 옮기는 대응표가 필요 — ply·spz·splat·ksplat은 그대로, sog만 pcsogszip으로.
둘 다 오류를 안 내서 미리 아는 것과 아닌 것의 차이가 큽니다. 지침 묶음의 함정 목록에 그대로 들어 있습니다.

🔍 나온 것을 무엇으로 판단하나

확인할 것어떻게
개수 표시·실제와 맞나만들 때 센 개수와 대조
개수 맞는데 화면이 검다전용 렌더러를 안 넣은 것 — 오류 안 나니 여기부터
검지도 않은데 안 보인다카메라가 엉뚱한 데를 봄 — 크기 재는 자를 바꾼다
놓았을 때 부드럽게 멈추나감쇠. 뚝 끊기면 안 켠 것
각도 크게 틀 때 앞뒤 안 뒤집히나정렬 순서 — 살짝은 안 보이니 크게 여러 번
방이 바로 서 있나천장이 위면 부호 뒤집기가 들어간 것
여기에 시간의 절반을 쓴다 — 화면이 떴다는 것만으로는 제대로 됐는지 알 수 없다. 각도를 크게 틀 때 앞뒤가 뒤집히는지가 스플랫에만 있는 판단 기준.
검지도 않은데 안 보이는 건 three.js가 알갱이에 빈 상자를 돌려줘 카메라 놓을 자리 계산이 안 서는 것. 마우스를 크게 끌었을 때 뭔가 지나가면 이쪽입니다.

🧩 내 서비스의 한 페이지로 붙인다 (시간 남는 분만)

파일 두 개뿐이라 이미 돌아가는 사이트에 그대로 얹힌다. 페이지를 통째로 /scene/에 두거나, 상세 페이지의 한 칸으로 넣는다. 칸으로 넣으면 고칠 것이 있다.

지금 페이지를 다른 페이지 안에 끼워 넣을 수 있게 고쳐 주세요.
- 창 전체가 아니라 지정한 요소 안에만 그리기(요소 크기 따라 바뀌게)
- 마우스 휠은 페이지 스크롤에 넘기고, 확대는 두 손가락·단추로만
- 화면 밖으로 스크롤돼 안 보이는 동안엔 그리기를 멈추기
- 다 불러오기 전엔 대표 사진 한 장을 대신
휠을 페이지 스크롤에 넘기라는 줄을 빼면 — 끼운 화면이 휠을 먹어 페이지 스크롤이 거기서 멈춘다. 남의 페이지에 들어가는 화면이 제일 자주 저지르는 실수.
안 보일 때 그리기를 멈추라는 줄은 배터리·발열. 대표 사진을 먼저 보이라는 줄은 첫인상 — 빈 칸은 고장으로 보이고 사진 한 장이 있으면 기다립니다.

Q2. 형식 넷이 알갱이를 안 버린다는 건 무슨 뜻이며, .sog는 어떻게 그렇게 작아지나?
Q3. 기다림과 부드러움은 각각 무엇이 정하고, 느릴 때 어디를 손대나?
Q4. 알갱이가 반투명이라 생기는 문제와, 그래서 매번 하는 일은?
Q5. 화면이 검은데 개수는 맞을 때 가장 먼저 볼 곳은?
Q3과 Q4가 이 덱의 핵심입니다.

✅ 정답 & 해설

A1. GitHub Pages가 100MiB 넘는 파일을 아예 안 받고, 올라가도 브라우저가 통째로 받아야 떠서 크기가 그대로 기다림이 된다 — 12초 vs 3분에 링크가 열리느냐 닫히느냐가 걸린다.
A2. 알갱이 개수는 그대로, 값을 적는 방식만 바꾼다(양자화 등). .sog는 자리·크기·회전·색을 이미지로 바꿔 이웃 비슷함을 줄이는 사진 압축기에 태운다.
A3. 파일 크기가 기다림(형식으로 줄임), 알갱이 수가 부드러움(수로 줄임). 오래 기다리면 형식, 뚝뚝 끊기면 알갱이 수.
A4. 뒤엣것과 섞여야 해서 깊이 버퍼를 못 쓴다 → 먼 것부터 가까운 것 순으로 줄 세워 바른다. 카메라가 돌 때마다 320만 개를 다시 줄 세운다.
A5. 전용 렌더러(Spark)를 장면에 안 넣은 것 — 그릴 것은 다 올라갔는데 그릴 부품이 빠져 오류가 안 난다.
A4의 정렬 순서는 각도를 크게 틀어 앞뒤가 뒤집히는지로 확인합니다.
