1

요청 받기 → 처리 → 응답

주문마다 그때그때 만들어 주는 동적 처리

주문서 · 레시피 · 창고 · 완성한 요리
지난 시간의 정적 화면이 창고의 완성품을 그대로 꺼내 주는 것이라면, 백엔드는 주문마다 그때그때 만들어 주는 동적 처리입니다. 이 파트는 그 세 단계를 주방 비유로 잡습니다.

🔁 백엔드의 일은 한 문장

받기요청을 해석
→
처리규칙 검사·계산
데이터 읽기/쓰기
→
응답결과를 돌려줌
  • 프론트가 "이 상품 목록 줘", "이 주문 접수해 줘"라고 보낸다
  • 백엔드는 해석하고 → 규칙 검사·계산·데이터 읽기/쓰기 → 결과를 응답으로
백엔드 = 요청을 받아서, 처리하고, 응답을 돌려준다. 딱 이 세 단계다.
출처: MDN Client-Server overview. 정적 화면과 달리 응답은 매 요청마다 새로 만들어집니다. "처리" 단계 안에 뒤에서 다룰 규칙 검사(비즈니스 로직)와 데이터베이스 읽기/쓰기가 모두 들어 있습니다.

🍳 주방 비유 — 손님은 주방 안을 못 본다

홀홀(프론트)에서 주문서(요청)를 받는다
조리레시피(비즈니스 로직)대로 조리한다
창고창고(데이터베이스)에서 재료를 꺼낸다
응답완성한 요리를 내보냄(응답)
손님은 주방 안을 못 보고 주문과 나온 요리만 주고받는다 — 백엔드가 자신을 바깥에 감추는 방식.
이 비유의 핵심은 두 가지입니다. 하나는 네 단계(주문서·레시피·창고·요리)가 요청→처리→응답에 정확히 대응한다는 것, 다른 하나는 손님이 주방 내부를 볼 수 없다는 것 — 뒤에서 다룰 "프론트는 못 믿는다"의 밑그림입니다.
2

창구·API·CRUD

백엔드는 통째로 열려 있지 않다 — 정해진 창구만 연다

엔드포인트 · API · REST · CRUD
백엔드는 통째로 열려 있지 않고 정해진 몇 개의 창구(엔드포인트)만 엽니다. 이 파트는 창구가 무엇인지, 그 묶음인 API와 관례 REST, 그리고 거의 모든 서비스가 하는 네 동작 CRUD를 봅니다.

🚪 창구 하나 = 주소 + 동작

  • 창구 하나 = "주소(URL) + 동작"의 조합 = 하나의 기능
  • 백엔드는 통째로 열지 않고 정해진 몇 개의 창구만 연다
GET /products상품 목록 주세요
POST /login이 정보로 로그인 처리해 주세요
비전공자에게 필요한 건 완벽한 설계가 아니라 "내 서비스엔 어떤 창구가 필요하지?"를 그려 보는 판단.
쇼핑몰이라면 상품 목록·상세·장바구니 담기·주문하기 정도의 창구를 떠올려 보면 됩니다. 창구는 주소만도 동작만도 아니라 둘의 조합이라는 점이 중요합니다.

📚 창구의 묶음 = API, 관례 = REST

  • 백엔드가 밖에 공개한 창구들의 묶음 = API
  • 잘 짜는 관례(REST)의 핵심: 주소는 '무엇'(명사), 동작은 메서드로
동사 (지양)/getProducts
→
명사 (권장)/products
주소에는 '무엇'을 명사로 담고, '어떻게'는 메서드(GET·POST…)가 맡는다.
REST는 규칙이라기보다 관례입니다. 동사를 주소에 넣지 않는 이유는, 동작은 이미 메서드가 표현하므로 주소는 대상(자원)만 명사로 가리키면 충분하기 때문입니다.

🔤 거의 모든 서비스가 하는 네 가지 — CRUD

동작뜻메서드
Create만들기POST
Read읽기GET
Update고치기—
Delete지우기—
인스타 '게시물 올리기·보기·수정·삭제', 쇼핑몰 '상품 등록·조회·수정·삭제' — 겉만 다를 뿐 속은 이 네 동작의 반복.
API 창구는 CRUD와 짝을 이룹니다(만들기=POST, 읽기=GET…). 그래서 "어떤 창구가 필요할까?"라는 질문은 대개 "이 데이터에 CRUD 중 무엇을 허용할까?"로 바꿔 생각할 수 있습니다.
3

공용어와 언어

둘이 데이터를 주고받는 형식, 그리고 백엔드를 짜는 언어

JSON · Node/Express · Django · FastAPI
프론트와 백엔드는 서로 다른 환경에서 돕니다. 이 파트는 둘이 데이터를 주고받는 공통 형식 JSON과, 백엔드를 실제로 짜는 언어·프레임워크를 봅니다.

🔗 프론트·백엔드의 공용어 — JSON

서로 다른 환경에서 도는 둘이 데이터를 주고받을 땐 JSON이라는 공통 형식. '이름표: 값' 쌍의 가벼운 텍스트.

{"name":"홍길동","age":30,"isMember":true}
사실상 표준이 된 이유 — 사람이 읽기 쉬운 텍스트인 데다 언어를 가리지 않기 때문. 어떤 프론트·어떤 백엔드를 붙여도 서로 알아듣는다.
문법을 외울 필요는 없습니다. "이렇게 생긴 걸로 데이터를 주고받는구나" 정도면 충분합니다. 언어를 가리지 않는다는 점이 핵심이라, 프론트와 백엔드를 서로 다른 언어로 짜도 문제없이 붙습니다.

🧰 백엔드는 무슨 언어로 짜나

언어대표 프레임워크
JavaScript/TypeScriptNode.js 위 Express(가볍고 기본) · NestJS(구조가 잡힌)
PythonDjango(종합형) · Flask(가벼움) · FastAPI(빠르고 요즘 뜨는)
그 밖에Ruby on Rails · Go · Java/Spring 등
첫 서비스의 무난한 기본값 — ①JavaScript 풀스택(언어 하나·자료 많음) 또는 ②Python(읽기 쉽고 AI 붙이기 좋음).
어느 쪽도 정답은 아니고, 코드는 AI가 짭니다. 개념(요청·창구·CRUD·검증)만 잡고 방향을 판단하면 됩니다. JavaScript 풀스택은 프론트·백엔드를 한 언어로 통일한다는 장점이, Python은 문법이 읽기 쉽고 AI 기능을 붙이기 좋다는 장점이 있습니다.

백엔드의 진짜 가치

데이터를 나르는 게 아니라 규칙을 지키는 것

비즈니스 로직 · "프론트는 못 믿는다"
백엔드의 진짜 가치는 데이터를 나르는 게 아니라 규칙을 지키는 것입니다 — 재고가 남았는지, 할인 적용한 최종 가격이 얼마인지, 이 사용자가 이 글을 지울 권한이 있는지. 이런 판단이 비즈니스 로직이고, 이 파트의 주제입니다.

⚖️ 진짜 가치는 규칙을 지키는 것

  • 재고가 남았는지
  • 할인 적용한 최종 가격이 얼마인지
  • 이 사용자가 이 글을 지울 권한이 있는지
이런 판단 = 비즈니스 로직. 백엔드의 진짜 가치는 데이터를 나르는 게 아니라 규칙을 지키는 것.
정적 화면이나 단순 전달만으로는 이 판단을 할 수 없습니다. 재고·가격·권한처럼 서비스가 반드시 지켜야 하는 규칙을 신뢰할 수 있는 곳에서 검사하는 것 — 그것이 다음 장의 보안 원칙으로 이어집니다.

🛡️ 가장 중요한 원칙 — 프론트는 못 믿는다

화면 표시가격 10,000원
→
브라우저에서 조작100원으로 바꿔
주문 요청
→
방어선서버가 자기 데이터로
최종 가격 재계산
가격·수량·권한 검증은 반드시
백엔드에서 다시 한다
프론트(브라우저)는 사용자의 컴퓨터에서 도니 얼마든지 조작 가능
프론트의 검증은 사용자 편의(빠른 오류 안내)를 위한 것 — 진짜 방어선은 언제나 백엔드.
출처: OWASP Input Validation, 그리고 권한은 OWASP Top 10 A01 Broken Access Control. 프론트는 사용자의 컴퓨터에서 돌기 때문에 값이 얼마든지 조작될 수 있습니다. 그래서 최종 가격은 반드시 서버가 자기 데이터로 다시 계산해야 합니다.

📌 이것만은 꼭 — 핵심 4문장

1백엔드 = 요청을 받아서, 처리하고, 응답을 돌려준다(주방 비유).
2서비스는 창구(엔드포인트=주소+동작)만 열고, 그 묶음이 API, 관례가 REST(명사).
3거의 모든 서비스는 CRUD 네 동작의 반복이고, 공용어는 JSON.
4백엔드의 가치는 규칙을 지키는 것 — 가격·수량·권한은 반드시 백엔드에서 다시 검증.
더 읽기: MDN Client-Server overview, OWASP Input Validation, OWASP Top 10 A01 Broken Access Control. 특히 4번이 이 소단원의 태도입니다 — 프론트의 검증은 편의일 뿐, 진짜 방어선은 언제나 백엔드입니다.

✅ 정답 & 해설

A1. 요청을 받아서, 처리하고(규칙 검사·계산·데이터 읽기/쓰기), 응답을 돌려준다.
A2. 주소(URL) + 동작의 조합 = 하나의 기능.
A3. 명사 — 주소는 '무엇'을 명사로(예: /products), 동작은 메서드로.
A4. 만들기(Create)·읽기(Read)·고치기(Update)·지우기(Delete).
A5. 프론트는 조작 가능하므로, 서버가 자기 데이터로 최종 가격을 다시 계산한다. 진짜 방어선은 언제나 백엔드.
A5를 자기 말로 설명할 수 있으면 오늘 목표는 달성입니다. 프론트의 검증은 사용자 편의일 뿐이라는 점을 함께 기억하세요.
