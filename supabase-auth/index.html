로그인까지 — Supabase로
회원가입·로그인 붙이기

스케이트보드 다음의 자전거 — 미뤄 둔 다음 탈것을 올린다

1단계 PRD에서 '이번엔 이름만, 로그인은 다음 단계'로 정해 뒀죠. 이제 계획해 둔 그 다음 탈것을 올릴 차례입니다.

밑바닥부터 만들면 무겁습니다

'누구나 이름만 넣고 신청'에서 '로그인한 사람이 신청하고 자기 내역만 보는' 서비스로 넓힙니다. 이걸 직접 만들면 비밀번호 저장·세션·보안을 다 신경 써야 합니다.

🧰 그래서 요즘은 Supabase 같은 백엔드 서비스(BaaS)에 맡깁니다 — 무료로 시작하는 백엔드에 DB·회원가입·로그인·권한이 딸려 오고, 우리가 짠 서버 로직을 돌리는 기능(Edge Functions, DB 함수)까지 있습니다
  • 강 4에서 "로그인은 직접 만들지 말고 검증된 서비스에 맡기라"고 했죠 — Supabase가 그 자리를 채웁니다
  • 비밀번호 해시·세션·토큰은 Supabase가 알아서 하고, 우리는 '무엇을'만 정합니다
  • ⚠️ 이번 확장은 선택입니다 — 오늘의 MVP(정원 신청)가 이미 굴러가면 그대로도 충분합니다
DB 강의의 '인증은 직접 만들지 마세요'(OWASP)와 강 4의 '검증된 도구에 맡기는 판단'이 여기서 실제 선택이 됩니다.

1. Supabase 무료 프로젝트 만들기

supabase.com에서 무료 프로젝트를 하나 만들면 DB와 인증이 함께 생깁니다. 설정 화면에서 Project URL과 공개 키(publishable/anon key)를 받아 .env에 넣습니다.

🔑 코드에 박지 말 것 — DB 강의의 비밀값 규칙 그대로
"우리 앱에 Supabase를 붙여 줘. Project URL과 공개 키는 내가 .env에 넣을게.
 연결만 잡아 줘."
  • Claude Code를 쓴다면 공식 Supabase 플러그인(MCP)을 붙이면 AI가 내 Supabase에 직접 접속해 표·인증·정책까지 만들어 줍니다
  • /plugin marketplace add anthropics/claude-plugins-official 로 등록해 supabase 플러그인을 켜거나, 소단원 ③처럼 claude mcp add로 붙입니다 — 둘 중 하나면 됩니다
강 4에서 배운 MCP·플러그인이 여기서 쓰입니다.

2. 회원가입·로그인 · 3. 신청을 '내 것'으로

2) "이메일·비밀번호로 회원가입하고 로그인하는 화면을 Supabase 인증으로
    붙여 줘. 로그인하면 신청 화면이 보이고 로그아웃 버튼도 있게."

3) "신청을 로그인한 사용자와 연결하고, 각자 자기 신청만 보거나
    취소할 수 있게 해 줘. 다른 사람 신청은 못 건드리게 행 수준 보안을 켜 줘.
    정원 초과 방지는 그대로 지켜야 해."
⚠️ Supabase는 RLS를 켜지 않으면 로그인한 아무나 남의 데이터를 볼 수 있어 반드시 켜야 합니다
1로그인해 신청하면 내 신청 내역에 뜨는가
2다른 계정으로 로그인하면 앞 사람 신청이 안 보이는가
3앞서 만든 정원 초과 방지가 여전히 지켜지는가
출처: Supabase Docs, "Password-based Auth"; "Row Level Security". 통과하면 커밋. 3번을 꼭 다시 확인하세요 — 기능을 얹다가 앞의 규칙이 깨지는 일이 흔합니다.

여기서 막힙니다 — 미리 알면 안 당하는 함정

실제로 붙여 보며 걸린 지점들

⑤ 로그인까지
이 튜토리얼을 실제로 붙여 보며 걸린 지점들입니다. 미리 알아 두면 시간을 아낍니다.

이메일 관련 함정 셋

1가짜 이메일은 거부됩니다. test@example.com 같은 주소로 가입하면 Supabase가 email_address_invalid로 막습니다(존재하지 않는 도메인 거부). 실제로 받을 수 있는 이메일을 쓰거나, 개발 중엔 이메일 확인을 끄세요
2가입하자마자 로그인하면 실패합니다. 기본 설정은 이메일 확인을 요구해, 확인 링크를 누르기 전에는 로그인이 안 됩니다(Email not confirmed). 무료 티어의 확인 메일은 시간당 몇 통으로 제한됩니다 → 수업 중 빠른 테스트는 대시보드 Authentication에서 'Confirm email'을 잠시 꺼 두기(배포 전엔 다시 켜기)
3실제 사용자에게 메일을 보내려면 커스텀 SMTP. 기본 내장 메일은 테스트용이라 프로젝트 팀 멤버 주소로만, 시간당 두어 통만 나갑니다(그 이상은 over_email_send_rate_limit). Resend·SendGrid·Amazon SES·Postmark 등의 SMTP 접속 정보를 대시보드에 넣으면 발송 한도도 직접 정할 수 있습니다
수업 데모처럼 메일이 굳이 필요 없으면 'Confirm email'을 끄는 편이 빠릅니다. 다만 배포 전에 다시 켜야 합니다 — 안 켜면 남의 이메일로 무제한 가입됩니다.

주소 · 보안 함정 셋

4확인 메일 링크가 localhost로 돌아가면 Site URL 설정 탓입니다. 대시보드 Authentication의 Site URL과 Redirect URLs를 배포한 주소로 바꾸면 정상 복귀합니다
5RLS를 안 켜면 남의 데이터가 다 보입니다. Supabase 표는 행 수준 보안을 켜기 전엔 로그인한 누구나 전체를 읽습니다. 3단계에서 꼭 켜세요
6키 두 개를 구분하세요. 공개 키(publishable/anon)는 화면에 쓰여도 되지만(그래도 .env로), 비밀 키(secret/service_role)는 절대 코드나 git·채팅에 올리지 마세요. 노출되면 RLS를 우회해 DB 전체가 열립니다 — 실수로 올렸다면 즉시 대시보드에서 폐기(재발급)
🔑 이 여섯 함정 중 5·6번은 보안 사고로 이어집니다 — 나머지는 시간만 잡아먹습니다
키 노출은 삭제로 해결되지 않습니다 — 재발급이 유일한 처방입니다(강 4의 CSA 가이드와 동일).

❓ 이해도 확인

Q1. 로그인을 직접 만들지 않고 Supabase에 맡기는 이유는?
A1. 비밀번호 해시·세션·토큰 등 보안 부담이 크다. BaaS에 맡기고 우리는 '무엇을'만 정한다.
Q2. Supabase에서 RLS를 켜지 않으면?
A2. 로그인한 누구나 표 전체를 읽을 수 있다 — 남의 신청이 다 보인다. 반드시 켜야 한다.
Q3. 공개 키와 비밀 키의 차이와, 비밀 키가 노출되면?
A3. 공개 키는 화면에 쓰여도 되지만(그래도 .env), 비밀 키(service_role)는 RLS를 우회해 DB 전체를 열 수 있다. 노출되면 즉시 재발급.
Q4. 로그인을 얹은 뒤에도 다시 확인해야 하는 것은?
A4. 앞서 만든 정원 초과 방지가 여전히 지켜지는지. 기능을 얹다가 앞의 규칙이 깨지는 일이 흔하다.
Q4는 회귀(regression) 감각을 심어 주는 문제입니다.
