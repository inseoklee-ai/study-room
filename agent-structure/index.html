에이전트의 구조

관측을 받아 행동을 고르고 — 결과를 다시 넣는 설계 단위

에이전트는 흔히 "똑똑한 모델의 별명"으로 오해됩니다. 하지만 같은 모델이라도 입력·도구·관측·승인 규칙에 따라 전혀 다른 실행이 됩니다. 이 소단원은 에이전트를 관측을 받아 제한된 행동을 고르고 그 결과를 다음 판단에 다시 넣는 설계 단위로 읽는 법을 세웁니다.

세 파트를 지나면 "이건 에이전트인가?"라는 이름 논쟁 대신 무엇을 관측하고 누가 다음을 정하며 어디서 통제를 회수하는지를 물을 수 있게 됩니다.
1

정의가 달라지는 다섯 관점

이름만으로 자율성 정도나 내부 구조를 결론낼 수 없다

Anthropic · OpenAI · Weng · ReAct · 학술
'에이전트'는 저자마다 다른 것을 강조합니다. 어느 정의도 이름의 필요충분조건을 정하지 않습니다. 다섯 관점을 나란히 놓으면 무엇이 공통이고 무엇이 강조점인지가 보입니다.

🔎 같은 낱말, 다섯 강조점

관점핵심 강조판별 질문
Anthropicworkflow는 코드가 경로를 조율, agent는 모델이 과정·도구를 동적 지휘다음을 누가 정했는가
OpenAI 가이드과업을 독립 완수, 모델이 실행을 관리하고 도구를 동적 사용목표를 받아 끝까지 관리하는 책임
Lilian WengLLM을 두뇌로, 계획·기억·도구를 결합하는 설계 문제세 요소가 다 있어야만 에이전트는 아님
ReAct추론↔행동 교대 — 행동이 환경을 바꾸고 반환값이 다음 선택에길게 생각이 아니라 행동-관측 순환
학술 문헌Wang 등: profile·memory·planning·action 분류 / AgentBench: 상호작용 능력 평가구성요소 분류지 존재론적 정의 아님
OpenAI 가이드는 원문 재대조 전이라 엄밀한 인용이 아니라 관점으로 읽는다. 어느 것도 이름의 필요충분조건을 정하지 않는다.
Anthropic은 제어권, OpenAI는 책임, Weng은 구성요소, ReAct는 순환, 학술은 분류·평가에 방점을 둡니다. 서로 배타적이지 않고 겹쳐 읽어야 전체가 잡힙니다.

🧭 과도하게 좁히지 않은 공통분모

에이전트 = 목표와 환경의 관측을 바탕으로
모델이 다음 행동·도구 사용을 고르고
실행 결과를 다시 관측해 다음 선택을 갱신하며 과업을 진행하는 시스템첫 문장 = 고정 경로와의 차이 · 둘째 문장 = 단발성 답변과의 차이
  • 모델의 "완료 선언"은 관측이 아니다 — 테스트 결과·원문·권한 있는 시스템의 반환값이 다음 선택을 바꿀 때 루프가 닫힌다
  • 계획·기억·persona는 필수 목록이 아니라 지속성·성능·통제 요구에 따라 더하는 선택
  • 여러 번 호출한다고 자동으로 에이전트가 되는 것도 아니다
이 정의의 힘은 무엇을 배제하느냐에 있습니다. 고정 경로도, 한 번 답하고 끝나는 호출도, 단순 반복 호출도 아닙니다. 환경의 ground truth가 다음 선택을 바꾸는 순환이 핵심입니다.
2

agent라는 낱말은 어디서 왔나

같은 단어가 세 전통에서 서로 다른 것을 가리킨다

강화학습 · 고전 AI · 90년대 소프트웨어
오늘의 LLM 에이전트를 정확히 읽으려면 낱말의 세 뿌리를 구분해야 합니다. 세 전통은 행동·관측이라는 언어를 공유하지만, 학습 방식과 강조점이 전혀 다릅니다.

🌳 낱말의 세 전통

RL강화학습 — 환경에서 관측을 받고 행동을 내며 보상으로 정책을 학습하는 주체. MDP(마르코프 결정 과정, 1957 정식화)=상태·행동·보상·전환확률+마르코프 성질. Sutton·Barto(1998)가 교재화. 핵심: 보상으로 정책을 어떻게 갱신하는가
고전고전 AI(Russell·Norvig) — 지각을 받아 행동을 선택하는 시스템, 합리성=성능 척도에서 기대 성능을 높이는 선택. 모든 agent가 실행 중 학습하는 건 아님
SW90년대 소프트웨어·multi-agent — 자율 반응·목표 지향·다른 agent와 상호작용. 위임·상태 유지·역할 협업. 오늘 제품 설명의 "장기 과업·역할 분담·사람 대신 접근"은 이 시스템 은유에 가깝다
RL의 agent는 보상으로 학습하는 의사결정 주체, 고전 AI의 agent는 지각-행동 시스템, 90년대 소프트웨어의 agent는 위임받아 협업하는 자율 프로그램입니다. 오늘 우리가 쓰는 "에이전트"는 주로 셋째 은유에 가깝습니다.

🔁 LLM 에이전트로의 이동

  • ReAct 등은 RL·로봇공학의 행동·관측 언어를 공유한다
  • 그러나 보통의 배포 LLM 에이전트는 실행 중 보상으로 파라미터·정책을 갱신하지 않는다
  • 고정된 모델이 추론 시점에 지시·맥락을 읽고 도구 결과로 다음 행동을 고르는 제어
⚠️ 행동-관측 루프가 있다고 곧 강화학습은 아니다. 관측 구조는 남지만 학습 방식은 다르다.

"agent"를 만났을 때 확인할 네 질문:

①보상으로 정책을
갱신하는가
②무엇을 관측·행동
으로 내보내나
③다음 경로를
누가 정하나
④위임된 권한은
어디까지인가
네 질문으로 같은 "agent"라도 학습 시스템 / 실행 구조 / 위임된 소프트웨어로 갈립니다. ③은 자율성, ④는 책임과 안전으로 이어집니다. 이름 하나가 성능·책임·권한을 보증하지 않습니다.
3

자율성 · 관측 · 분석 모형

어느 결정의 통제권을 넘겼고, 어디서 회수하는가

스펙트럼 · 루프 닫기 · 모델+하네스+루프
자율성을 있다/없다로 나누면 중요한 차이가 사라집니다. 더 정확한 질문은 "어느 결정의 통제권을 모델에게 넘겼는가, 그리고 어디서 다시 회수하는가"입니다.

🎚️ 결정의 통제권 스펙트럼

1고정 경로(workflow) — 순서·재시도·종료 조건을 프로그램이 정함. 비용·실패 지점 예측은 쉽지만 정해진 분기 밖으로 못 나감
2모델이 고르되 승인 경계 — 읽을 파일·검색어·방법은 모델이 선택. 단 외부 발신·결제·운영 데이터 변경은 사람이 승인(명령·대상·예상 변경·되돌림 가능 여부까지 표시)
3열린 위임 — 목표+예산·시간·권한 한도만 주고 순서·도구·반복을 폭넓게 위임. 단 무제한 아님 — 비용 상한·허용 도구·작업공간 격리·중단 조건을 코드가 계속 강제
자율성 단계는 제품 이름이나 호출 횟수가 아니라, 다음 행동과 영향 있는 실행을 누가 결정하는가로 판별한다.
세 단계는 연속적입니다. 핵심은 "완전 자율"이 아니라, 어느 결정을 넘겼고 영향이 큰 실행에서 어떻게 통제를 회수하는가입니다. 2단계의 승인 화면 설계가 실무에서 특히 중요합니다.

🔒 관측으로 루프를 닫는다

  • 모델의 "수정했습니다"는 주장일 뿐 완료 증거가 아니다
  • 코딩=테스트·빌드·린트 결과 / 조사=인용한 원문 / 업무=권한 있는 시스템의 반환값
  • 이 값을 다음 입력으로 넣어야, 모델이 자기 서술이 아니라 환경 상태를 보고 계획을 고친다
ReAct의 핵심도 긴 문장이 아니라
행동 뒤 새로 들어오는 관측환경의 ground truth가 다음 선택을 바꿀 때 비로소 루프가 닫힌다
루프를 닫는다는 것은 모델의 자기 보고 대신 환경이 돌려주는 검증 가능한 값을 다음 판단 재료로 쓴다는 뜻입니다. 이것이 단발성 응답과 에이전트를 가르는 실질적 경계입니다.

🧩 분석 모형 — 모델 + 하네스 + 루프

모델다음 행동 후보
생성 · 판단
+
하네스입력 구성 · 도구 연결
권한과 형식 강제
+
루프행동 · 관측 · 검사
재시도의 순서와 종료
결과가 기대와 다를 때 "모델이 약하다"로 결론내기 전에, 세 층 중 어디서 무엇이 달랐는지 먼저 분해한다.

RL의 agent-environment 그림에서 관측·피드백 구조는 남지만, 보통의 LLM 에이전트는 실행 중 보상으로 정책을 학습하지 않는다 — 이미 학습된 모델이 추론 시점에 도구 호출을 선택하고, 하네스가 권한·승인·종료를 제한한다.

같은 모델이라도 하네스와 루프가 다르면 전혀 다른 실행이 됩니다. 이 세 층 분해가 원인을 모델 탓으로만 돌리지 않고 수정 지점을 찾게 해 줍니다.

🛠️ 하네스가 설계하는 네 영역

설계 영역설계하는 것
지시목표 · 역할 · 출력 형식 · 금지 사항 · 성공 기준
맥락모델이 읽는 문서 · 데이터 · 대화 이력 · 현재 상태
도구검색 · 파일 · 코드 · 외부 시스템의 기능 · 권한 · 반환 형식
루프행동 순서 · 관측 수집 · 검증 · 재시도 · 중단 · 승인 조건
칸은 독립 부품 목록이 아니다 — 도구 설명은 맥락으로, 테스트 결과는 도구 반환값이자 다음 루프의 맥락. 목적은 원인을 한 칸에 가두는 게 아니라 수정 지점을 빠짐없이 추적하는 것.
네 영역은 서로 스며듭니다. 그래서 실패를 한 칸에 딱 배정하려 하기보다, 네 칸을 체크리스트 삼아 어디를 바꿀지 빠짐없이 훑는 데 씁니다.

🧵 멀티턴 예 — 관측이 판단을 바꾼다

1사용자: "배포 뒤 로그인이 안 된다" → 모델: "발생 시각·HTTP 상태 확인"
2로그 도구가 401 · 토큰 만료 · 배포 버전을 반환 (자기 서술이 아닌 환경의 값)
3둘째 턴 "배포 직후부터" → 모델은 첫 요청 + 도구 요청·결과 + 새 정보를 함께 받아 판단
⚠️ 이때 첫 결과를 버리면 근거가 사라지고, 폐기된 설정까지 무차별로 넣으면 근거가 오염된다.
이 예는 루프가 닫히는 순간을 보여 줍니다. 모델의 추측이 아니라 로그 도구가 돌려준 401·토큰 만료라는 관측이 다음 판단을 바꿉니다. 다음 소단원의 주제 — 무엇을 남기고 무엇을 넣을 것인가 — 로 자연스럽게 이어집니다.

📌 이것만은 꼭 — 핵심 4문장

1에이전트는 관측을 받아 다음 행동을 고르고 결과를 다시 넣는 설계 단위 — 이름·호출 횟수로 정해지지 않는다.
2낱말은 강화학습·고전 AI·90년대 소프트웨어 세 전통에서 왔고, 루프가 있다고 곧 강화학습은 아니다.
3자율성은 있다/없다가 아니라 통제권 스펙트럼 — 어디서 넘기고 어디서 회수하는가.
4결과가 갈리면 모델+하네스+루프로 분해하고 지시·맥락·도구·루프 네 영역을 추적한다.
📚 더 읽기 — Sutton·Barto; Russell·Norvig; Anthropic "Building effective agents"; OpenAI "A practical guide to building agents"; Lilian Weng "LLM Powered Autonomous Agents"; Wang 외 서베이; Yao 외 "ReAct".
4번이 이 소단원의 실무 태도입니다. 낮은 결과를 즉시 모델 한계로 결론내지 말고, 세 층과 네 영역에서 무엇이 달랐는지 먼저 분해하세요.

✅ 정답 & 해설
