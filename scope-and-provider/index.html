작아도 끝까지 동작하는 구현

📖 수직 구현 — 작더라도 여러 층을 통과해 끝까지 동작하는 구현. 모델 연결만 따로 만드는 것보다 "사용자 요청 → 모델의 파일 읽기 요청 → 내 프로그램의 실제 읽기 → 결과 전달 → 답변"을 한 번 연결하면 중요한 경계들이 함께 확인됩니다
구분의미예시
필수 제품 목표수업에서 완성하고 검증할 동작범용 자료 작업, 코드 변경·검사, 권한, 상태·기록
최초 수직 작업연결 구조를 처음 확인할 작은 작업지정한 가상 회의록을 읽고 담당자 찾기
후속 필수 구현첫 연결 뒤 확장할 제품 기능변경 확인과 승인, 제한된 테스트 실행
선택 확장필요에 따라 구현하거나 미룰 기능두 번째 제공자, 동시 실행, 원격 접속
⚠️ 읽기부터 시작하는 것은 코딩 기능을 제외한다는 뜻이 아닙니다. 반대로 두 제공자를 붙였다고 코드 변경과 검증이 생략되어도 되는 것은 아닙니다
PRD의 R01~R07을 기준으로 기능을 구현할 순서와 최종 완료 범위를 구별해 적습니다.

첫 모델 제공자 선택

제공자 이름만으로 모델까지 정해지지 않습니다

④ 범위와 제공자
모델 제공자는 프로그램이 모델 실행을 요청하는 서비스나 연결 경로이고, 모델은 그 경로에서 실제 응답을 생성할 대상입니다.

두 경로

선택준비하고 확인할 내용설계에 미치는 영향
OpenAI API제공된 키, 사용 가능한 모델, 선택한 API의 도구 호출 방식자료가 외부 서비스로 전송되며 사용량·오류를 다뤄야 함
Ollama 로컬 모델실행 중인 로컬 서버, 설치된 모델, 도구 호출 지원, 장치 자원로컬 실행 환경과 모델의 응답 품질을 확인해야 함
  • Ollama 자체가 하나의 모델인 것은 아닙니다 — 어떤 모델을 실행하느냐에 따라 도구 요청과 답변 품질이 달라집니다. 작은 모델이 실행된다는 사실만으로 코드 수정까지 잘한다고 판단하지 않습니다
내 환경에서 먼저 연결할 제공자와 모델을 고르자.
도구 호출 지원과 선택 이유를 확인해서 D04에 남겨 줘.
📌 아직 확인하지 못한 사항은 확인 예정이라고 남기고, 추천만으로 CHOSEN으로 바꾸지 않습니다 — 실제 연결 검증은 D01~D07을 정하고 구현을 요청한 뒤 수행합니다
AI의 추천을 읽은 뒤 학생이 선택합니다.

API 호환과 도구 지원의 차이

  • API는 프로그램이 다른 프로그램에 기능을 요청하는 약속 — 요청 주소, 입력 필드, 응답 형식 등
  • Ollama는 OpenAI API의 일부와 호환되는 경로를 제공합니다. 기존 클라이언트를 재사용할 수 있지만 — 모든 기능과 저장 방식이 같다는 뜻은 아닙니다
  • API가 도구 설명을 받는 것과, 선택한 모델이 적절한 도구 호출을 반환하는 것은 별개입니다 — 도구를 지원하는 모델인지 확인하고 실제 응답을 받아 판단해야 합니다
1연결 — 선택한 주소와 인증으로 응답을 받는다
2호출 형식 — 도구 이름과 입력이 프로그램에서 해석할 수 있는 구조로 반환된다
3결과 전달 — 실제 실행 결과를 돌려주면 다음 응답이 이어진다
4내용 품질 — 모델의 답이 실제 자료나 검사 결과와 맞는다
⚠️ 텍스트에 "파일을 읽었습니다"라고 적힌 것만으로 2·3번을 통과한 것은 아닙니다. 반대로 읽기 함수가 성공해도 담당자나 마감일을 잘못 답했다면 4번은 실패입니다
두 제공자를 처음부터 모두 구현할 의무는 없습니다. D08에서 추가 제공자를 DEFERRED로 정할 수 있습니다. 다만 R07의 목적에 맞게 제공자별 요청·응답 처리를 도구 실행 규칙과 구별해 설계합니다.

최초 도구와 작업 범위

도구 이름 목록보다 허용할 행동을 먼저

④ 범위와 제공자
D05에는 어떤 자료에 어떤 행동을 허용할지를 먼저 적습니다.

정할 다섯 가지

1사용할 민감하지 않은 자료와 기준 폴더
2첫 도구가 받는 대상과 반환해야 할 정보
3접근하지 않을 위치와 파일 종류
4결과를 확인할 짧은 사용자 요청
5읽기 이후에 추가할 코드 변경·테스트의 범위
  • 예 — 첫 요청이 "지정한 회의록에서 담당자를 찾아 줘"라면 파일 읽기 하나로 시작할 수 있습니다. 파일을 스스로 찾아야 하는 시나리오라면 목록 조회나 검색이 추가로 필요
  • 처음부터 컴퓨터 전체 접근이나 임의 터미널 명령을 기본 기능으로 넣지 않습니다 — 작은 코드 예제와 정해진 검사부터 선택하면 실제 변경과 검증을 이해하기 쉽습니다
  • 승인 방식은 D06에서 더 구체화하되 — 쓰기와 테스트에 승인이 필요한지 빠뜨리지 않도록 연결해 둡니다
"첫 구현은 작은 읽기 작업 하나로 잡자. 필요한 도구와 접근할 폴더를 PRD에 정리해 줘."

실패할 때의 동작도 기능으로 적기

상황명세에 남길 동작의 예
자료가 없음실패 이유를 반환하고 다른 자료 확인이나 사용자 질문으로 이어감
허용 범위 밖 경로읽지 않고 거절 사실을 남김
API 인증·연결 실패현재 요청을 실패로 표시하고 원인을 확인할 단서 제공
해석할 수 없는 도구 요청실행하지 않고 오류 처리
모델이 근거와 다른 답내용 평가에서 실패로 기록하고 실행 성공과 구별
  • "파일을 읽을 수 있다"만 적으면 파일이 없을 때가 남고, "모델과 연결된다"만 적으면 인증 오류나 응답 형식 오류를 성공처럼 숨길 수 있습니다 — 이런 상황도 사용자가 경험하는 제품 동작입니다
  • 그대로 복사할 최종 정책은 아닙니다. 반복 시도 여부와 중단 조건은 다음 절에서 — 다만 실패했을 때 몰래 다른 제공자나 준비된 답변으로 바꾸어 성공한 것처럼 보이지 않게 한다는 기준은 분명히 둡니다
이제 PRD.md와 DECISIONS.md의 D04·D05에 선택과 이유를 맞춰 적습니다. D08·D09에서 미룬 기능도 이유를 남깁니다.

❓ 이해도 확인

Q1. 수직 구현이란?
A1. 작더라도 여러 층을 통과해 끝까지 동작하는 구현. 요청→도구 요청→실제 실행→결과 전달→답변을 한 번 연결한다.
Q2. Ollama 호환 경로를 쓰면 도구 호출도 보장되나?
A2. 아니다. API가 도구 설명을 받는 것과 모델이 적절한 호출을 반환하는 것은 별개. 실제 응답을 받아 판단한다.
Q3. 네 가지 확인 항목은?
A3. 연결 · 호출 형식 · 결과 전달 · 내용 품질. "파일을 읽었습니다"라는 텍스트만으로 2·3번이 통과된 것은 아니다.
Q3의 네 층은 구현 후 검증에서 그대로 쓰입니다.
