🔀 세 갈래

①공개 클라우드 API — 제공사 공용 인프라에 HTTP 요청. 키 발급만으로 최고 성능 모델, 하드웨어 0대
②관리형 프라이빗 배포 — 사업자 인프라 위 조직 전용 환경. MS Foundry·Amazon Bedrock·Google Vertex AI. 리전 고정 + 학습에 안 씀 보장 + 사설 연결
③로컬 · 온프레미스 — 방금 해본 그것(또는 서버실 버전). 데이터가 조직 경계를 물리적으로 안 넘음
②는 물리적으로는 남의 데이터센터지만, 처리 리전이 계약으로 고정되고, 프롬프트·응답이 학습에 안 쓰인다는 게 문서로 보장됩니다.
공개 API는 시작이 가장 빠르고, 관리형은 규제 산업에서, 로컬은 데이터가 절대 나가면 안 될 때 쓰입니다.

공개 클라우드 API관리형 프라이빗로컬 · 온프레미스
쓸 수 있는 모델그 시점 최고 성능을 가장 먼저사업자 카탈로그 중에서공개 가중치 중 내 하드웨어에 맞는 것

비용의 모양토큰당 종량제, 트래픽에 정비례종량제 + 관리 비용초기 투자 큼, 이후 한계비용은 전기값
데이터가 가는 곳제공사 공용 인프라지정한 리전의 전용 환경내 장비 밖으로 안 나감
비용의 모양이 셋 다 다릅니다 — 종량제 / 종량제+관리 / 초기투자 후 전기값.

📊 세 갈래 비교 (2/2)

공개 클라우드 API관리형 프라이빗로컬 · 온프레미스
학습 사용주요 제공사는 기본적으로 안 씀계약으로 명시해당 없음
남는 로그오남용 모니터링용 보존 기간 존재보존 끄는 옵션 협의 가능내가 안 남기면 없음
어울리는 상황최고 품질 필요 + 민감도 낮음 + 트래픽 들쭉날쭉규제 산업 + 민감 데이터 + 프런티어 품질 필요반출 금지 · 오프라인 · 대량 반복 단가↓
주의점리전·로그 보존·스테이트풀 저장 확인"관리형"=자동 안전 아님, 배포 유형별 처리 리전 다름업데이트·패치·가동률이 전부 내 몫
주의점 열이 특히 중요합니다. "관리형"이라는 단어가 자동으로 안전을 뜻하지 않습니다.

📄 근거 문서를 읽는 것이 엔지니어의 일

🔑 교훈은 정책 문구를 외우는 게 아니라, 이런 문서가 존재하고 그걸 읽는 것이 엔지니어의 일이라는 사실. 무엇을 고르든 근거로 누군가에게 설명해야 하는 자리에 서게 됩니다.
무료 소비자용 서비스와 상용 API의 약관은 완전히 별개의 계약입니다. 이 구분이 자주 혼동됩니다.

최상위 비공개 모델보다 평균 약 4개월 뒤
2026년 1~5월 · ECI 약 8점 (2025년 10월엔 약 3개월, 조금 벌어짐)
  • 단서 ① 공개 모델은 공개 벤치마크에 최적화되는 경향 → 비공개 벤치에선 더 나쁨
  • 단서 ② 선도 연구소가 최강 모델을 항상 공개하진 않음 → 실제 격차는 측정치보다 클 수 있음
  • 작업별로 다름: 코딩(검증 가능 정답)은 거의 따라붙음, 다단계 추론·긴 에이전트는 차이 뚜렷
크기별 최신 순위는 Artificial Analysis 같은 곳에서 계속 갱신되니, 판단할 일이 생기면 그때의 숫자를 직접 확인하세요.

🪜 훨씬 중요한 함정 — 격차는 두 겹

비교에 나오는 "최상위 공개 가중치 모델"은 여러분 노트북에서 돌지 않습니다. 수천억 파라미터 MoE라 4비트로도 수십~수백 GB.

프런티어 비공개 모델
↕ 약 3~5개월치 성능 차이
최상위 공개 가중치 모델
수백 GB · 서버 필요
↕ 이쪽이 훨씬 큰 차이

🔑 두 겹을 구분 안 하면 — "오픈이 프런티어를 따라잡았다" 헤드라인을 읽고 노트북에서 같은 성능을 기대하다 실망. 반대로 로컬에 실망해 "오픈은 멀었다"는 결론도 틀림. 여러분이 만난 건 최전선이 아니라 하드웨어에 맞춰 잘라낸 조각.
"4개월"은 최상위 공개 모델의 이야기이고, 노트북 모델과 프런티어의 실제 격차는 그보다 훨씬 큽니다.

4가지 질문
세 갈래를 배웠으니, 실제로 도구를 고를 때 벌어지는 일을 이야기합니다.

🎭 이름 ≠ 실행 위치

방향 ① 로컬인 줄 알았는데

ollama run qwen3.5:9b vs ...gpt-oss:120b-cloud — 화면상 거의 구별 안 됨인데 -cloud는 프롬프트가 데이터센터로 전송. "보관 안 함"은 정책이지 물리적 격리가 아님

방향 ② API면 학습에 들어간다?

상용 기본 약관을 읽으면 사실 아님. 주요 제공사는 상용 API를 학습에 안 씀 + 무보존 옵션. 무료 소비자용 ≠ 상용 API 약관

🔑 판단 기준은 제품 이름이 아니라 데이터가 실제로 흐르는 길입니다.
Ollama는 "로컬 도구"로 알려졌지만 -cloud 태그 하나로 데이터 흐름이 완전히 달라집니다. 이름은 흐름을 보장하지 않습니다.

❓ 도구가 바뀌어도 똑같이 유효한 4가지 질문

1내가 입력한 문자열이 실제로 어느 물리적 위치의 서버까지 이동하는가
2그 서버에서 문자열이 얼마나 오래 저장되는가, 저장을 끌 수 있는가
3저장된 것을 누가 볼 수 있는가 — 자동 시스템만인가, 사람이 볼 조건이 있는가
4그 답변들이 문서·계약으로 확인 가능한가, 아니면 마케팅 문구인가
답을 확인하는 곳은 대부분 제공사의 데이터 처리 문서입니다. 목차 구조를 눈에 익혀 두면 새 서비스에서도 같은 자리에서 같은 정보를 찾게 됩니다.
이 네 질문은 도구가 바뀌어도 그대로 씁니다. 새 서비스를 만나면 이 질문지를 꺼내세요.

🔄 좋은 질문은 세 축으로 생겼습니다

데이터

이 워크로드의 데이터는 어느 경계를 넘어도 되는가

비용

이 호출량에서는 어느 쪽 비용 구조가 유리한가

주권

이 시스템의 통제권을 누가 쥐고 있어야 하는가

🔑 로컬은 복잡한 추론에서 흔들리고 컨텍스트·형식에서 한계가 있고, 클라우드는 그 문제가 없는 대신 데이터가 손을 떠나고 트래픽에 비례해 청구서가 자랍니다. 그래서 "어느 쪽이 좋은가"가 아니라 "이 워크로드는 어디로"가 옳은 질문.
➡️ 다음 섹션: 이 세 축을 계산 가능한 형태로 바꿔 실행 위치를 결정하는 판단 틀. 오늘 채운 기기 사양서를 옆에 놓고 오세요 — 그 숫자가 계산의 입력값.
세 축은 데이터·비용·주권. 다음 섹션에서 각각을 계산 가능한 형태로 바꿉니다.

📌 이것만은 꼭 — 핵심 6문장

1갈래는 둘이 아니라 셋: 공개 API · 관리형 프라이빗 · 로컬
2관리형은 남의 데이터센터지만 리전 고정·무학습·사설 연결을 계약으로 보장
3"상용 API는 데이터를 학습에 쓴다"는 오해 — 무료 소비자용과 상용 약관은 별개
4품질 격차는 두 겹: 프런티어↔최상위 공개(수백GB)↔내 노트북(수GB)
5도구 이름이 실행 위치를 안 알려줌 → 4가지 질문(위치·보존·열람·문서)으로 판단
6옳은 질문은 데이터 · 비용 · 주권 세 축 — "어느 쪽이 좋은가"가 아니라 "이 워크로드는 어디로"
이 6문장이 다음 섹션(계산 가능한 판단 틀)의 출발점입니다.

✅ 정답 & 해설

A1. 관리형 프라이빗 배포. 사업자 인프라에 조직 전용 환경을 열되, 처리 리전·무학습·사설 연결을 계약/문서로 못 박음(MS Foundry·Bedrock·Vertex).
