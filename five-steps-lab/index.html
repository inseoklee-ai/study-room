대단원 2 · AIFFEL_LMS · 메인 퀘스트 ④ · 따라하기

정원 있는 '원데이 클래스
신청'을 5단계로

PRD → 작업대 → 화면 → 저장+정원 → 한 바퀴+배포

"정원 10명짜리 원데이 클래스에 이름으로 신청받고, 남은 자리를 보여주다가, 정원이 차면 '마감'을 띄운다. 신청은 새로고침해도 남고, 여러 명이 동시에 눌러도 정원을 넘기지 않는다." 로그인·결제·후기는 만들지 않습니다.

다섯 단계와 통과하면 생기는 것

단계이번에 하는 일통과하면 생기는 것
1. PRD만들 것을 한 장으로 정리AI에게 줄 설계도
2. 작업대하네스 고르고 빈 프로젝트 세우기내 화면에 프로젝트가 뜬다
3. 화면눈에 보이게 만들기클래스와 남은 자리가 진짜처럼 보인다
4. 저장 + 정원신청을 저장하고 정원을 지키게신청이 남고, 정원을 넘지 않는다
5. 한 바퀴 + 내보내기처음부터 끝까지 돌려 보고 배포누구나 드는 신청 주소가 생긴다
⛰️ 이 중 4단계('정원을 넘기지 않게')가 오늘의 진짜 산이자, DB 강의의 '동시에 눌러도 안 꼬이는 법'을 실제로 써먹는 자리입니다
표를 먼저 보여 주고 "지금 어디쯤인지" 매 단계마다 짚어 주면 학습자가 길을 잃지 않습니다.

핵심 — 명령을 '무엇을'로 줍니다

❌ 주지 않는 것

"어떤 DB를 써라", "이 방식으로 막아라" 같은 방법(how) — 그건 AI가 정할 몫

✅ 우리가 하는 것

무엇을 원하는지(의도)와 됐는지 확인

  • 한 번에 안 나와도 괜찮습니다 — 바이브 코딩은 지시 → 결과 확인 → 안 되면 다시 지시를 몇 바퀴 도는 일입니다
  • 그래서 단계마다 '막히면 이렇게 다시 지시'를 함께 뒀습니다. 그대로 따라 하세요
이 원칙이 소단원 ⑥(내 도메인)에서 혼자 할 때의 기준이 됩니다.
1

1단계 PRD — 만들 것을 한 장으로

'무엇'과 '어떻게 동작하면 좋겠다'만

④ 다섯 단계
PRD는 무엇을·왜 만들지 정리한 기획서 한 장입니다. 기술 선택은 넣지 않습니다.

작업 폴더를 만들고 하네스를 켭니다

mkdir class-signup
cd class-signup
claude
💡 명령은 한 줄에 하나씩 적었습니다 — 여러 명령을 한 줄에 잇는 방식(&& 같은 것)은 터미널 종류에 따라 다르게 동작해서(윈도우 PowerShell 5, cmd, 맥·리눅스 셸이 제각각), 한 줄씩 실행하면 어디서든 똑같이 됩니다
  • 이 과정은 Claude Code 기준입니다 (2단계에서 설명)
이 주의는 실제로 수업에서 가장 많이 걸리는 지점입니다 — 윈도우 사용자가 && 때문에 막힙니다.

계획부터 — 스택은 정하지 말고 AI에게

[무엇] 정원이 정해진 '원데이 클래스' 신청 페이지.
[기능] 클래스 정보(제목·일시·정원)와 남은 자리를 보여준다 /
       이름을 넣고 '신청'을 누른다.
[동작] 신청은 새로고침해도 남는다. 정원이 차면 더 받지 않고 '마감'을 보여준다.
       여러 명이 거의 동시에 마지막 자리를 눌러도 정원을 넘기지 않는다.
[규칙] 무료 도구만. 비밀값은 코드에 노출하지 않는다.
       로그인·결제·후기는 이번엔 만들지 않는다.

이 PRD로 만들 계획을 세워 줘. 어떤 데이터를 저장할지,
정원을 어떻게 지킬지, 어떤 스택으로 갈지 네가 정해서 먼저 보여 줘.
  • Claude Code라면 /plan을 치고 이 PRD를 그대로 붙여넣으세요
[규칙]의 마지막 줄이 소단원 ②에서 배운 'Won't 목록'입니다.

한 가지 더 — 누가 쓰는가

로그인해서 사용자를 구분해야 하는 서비스인지, 이름만으로 충분한지를 여기서 정합니다.

이 신청 앱

이름만으로 흐름이 완결되니 로그인은 이번 MVP에서 빼고 '다음 단계'로 계획 — 빠뜨리는 게 아니라 순서를 정하는 것(소단원 ②의 스코프 컷 그대로)

반대로

사용자 구분이 서비스의 핵심이라면, 그때는 미루지 말고 이 자리에서 PRD에 넣습니다

🧭 '빼기'와 '미루기'는 다릅니다 — 미룬 것은 소단원 ⑤에서 실제로 올립니다
학습자가 자기 프로젝트에서 이 판단을 해야 합니다. 로그인이 핵심인 서비스(예: 개인 기록 앱)는 미루면 MVP가 성립하지 않습니다.

확인 · 막히면 · 통과하면 커밋

👀확인 — AI가 저장할 데이터(클래스 한 건, 신청 여러 줄)와 정원을 지키는 방법을 계획에 담는가. 정원 얘기가 빠졌으면 여기서 짚어 주세요 — 코드가 나오기 전에 잡는 게 제일 쌉니다
🔁막히면 — AI가 곧장 코드부터 쏟아내면 "아직 코드는 말고, 무엇을 저장할지와 정원을 어떻게 지킬지부터 계획으로 먼저 보여 줘"
git init
git add -A
git commit -m "PRD와 계획"
계획을 PRD.md로 저장하고 커밋합니다. 되돌릴 지점을 만드는 첫 커밋입니다.
2

2단계 작업대 — 하네스 고르고 프로젝트 세우기

브라우저형 · 편집기형 · 터미널형

④ 다섯 단계
하네스는 AI 코딩을 실행·검토하는 작업 환경입니다.

세 종류 — 언제 좋은가

하네스생김새언제 좋은가
브라우저형설치 없이 웹에서 코딩·실행아주 처음, 설치가 부담일 때
편집기형Cursor·VS Code 같은 편집기 + AI파일 여러 개를 다루기 시작하면
터미널형글자로 명령하는 에이전트(예: Claude Code)설치·실행·배포까지 AI가 스스로 하게 할 때
🖥️ 이 과정에서는 Claude Code를 씁니다 — 터미널에서 claude 한 줄로 시작해 계획(/plan)·구현·실행·검증·git 커밋까지 한자리에서 되고, 오늘처럼 저장·배포까지 한 바퀴 도는 데 매끄럽습니다(Claude Pro/Max 구독에 포함)
  • 브라우저형으로 시작해도 좋지만, 배포까지 갈 거라면 Claude Code를 권합니다
에이전트 도구 강의(강 4)의 네 부류와 같은 분류입니다 — 여기선 클라우드형을 뺀 셋만 다룹니다.

빈 화면이라도 한 번 떠야 합니다

"방금 세운 계획대로 빈 프로젝트를 세워 줘. 무료로 시작할 수 있게.
 로컬에서 실행하는 법과, 지켜야 할 규칙을 CLAUDE.md에 정리해 줘."
👀확인 — 실행하는 방법과 화면이 뜨는 걸 눈으로 보세요. 안 뜨면 오류 메시지를 그대로 복사해 AI에게 붙여넣고 물어봅니다
💾통과하면 커밋
  • CLAUDE.md를 여기서 만드는 건 강 4에서 배운 규칙 파일입니다 — 대화를 리셋해도 남습니다
"빈 화면이라도 한 번 떠야 한다"가 이 단계의 통과 기준입니다. 안 뜨는 걸 안고 다음 단계로 가면 원인이 쌓입니다.
3

3단계 화면 — 눈에 보이게 만들기

저장은 아직 없어도

④ 다섯 단계
눈에 보이는 게 있으면 방향이 맞는지 훨씬 빨리 판단할 수 있습니다.

진짜처럼 보이는 예시 값으로 채웁니다

"'원데이 클래스 신청' 화면을 만들어 줘.
 클래스 제목·일시, 남은 자리(예: '7 / 10'), 이름 입력칸,
 '신청' 버튼이 한 화면에 보이면 돼.
 지금은 저장 없이 예시 값(제목 '초보 손그림 원데이',
 일시 '이번 주 토요일 14시', 정원 10명·현재 3명)으로 채워."
1제목·일시·남은 자리·이름칸·'신청' 버튼이 모두 보이는가
2버튼을 눌러 본다 — 반응이 있는가 (아직 저장은 없으니 새로고침하면 사라져도 OK)
  • 막히면 — 보이는 결과(또는 오류)를 그대로 붙여넣고 "이렇게 나왔는데 왜 그런지, 어떻게 고칠지 알려 줘"
  • 통과하면 커밋
목업 데이터로 화면부터 채우는 방식은 프레임워크 강의(mock-and-api)에서 배운 그대로입니다.

한 걸음 더 — frontend-design 스킬로 다듬기

기본으로 나온 화면은 대개 밋밋합니다. 흔한 보라 그라데이션에 기본 폰트, 어디서 본 듯한 카드 — 이른바 'AI 슬롭'이죠. 여기서 강 4에서 배운 스킬을 써먹을 자리입니다.

/plugin marketplace add anthropics/claude-code   # 마켓플레이스 등록 후 frontend-design 켜기

"이 신청 화면을 frontend-design 스킬을 써서 다듬어 줘.
 이 클래스의 분위기(예: 손그림·아늑함)에 맞는 개성 있는 디자인으로,
 남은 자리는 숫자만 말고 눈에 보이게.
 흔한 AI 티 나는 밋밋한 스타일은 피해 줘."
  • 확인 — 색·글꼴·여백이 주제에 맞게 살아났는가, 남은 자리가 한눈에 들어오는가, 마감 상태가 뚜렷한가
  • 마음에 안 들면 방향(예: "더 차분하게" / "더 발랄하게")을 한마디로 다시 주면 됩니다
같은 '클래스 신청' 화면도 스케치북 느낌으로 방향을 하나 정하니 밋밋한 기본 화면과 확 달라집니다. 밋밋한 기본값에서 멈추지 말라는 게 이 슬라이드의 요지입니다.
4

4단계 저장 + 정원 — 오늘의 진짜 산

신청을 남기고, 정원을 지키게

④ 다섯 단계
화면만 있으면 새로고침하면 사라지고, 정원도 안 지켜집니다.

구현 방법은 AI에게, 원하는 동작만 말합니다

"이름을 넣고 '신청'을 누르면 저장돼서 '남은 자리'가 줄고,
 새로고침해도 남게 해 줘.
 정원이 차면 더 받지 말고 '마감'을 보여줘.
 그리고 여러 명이 거의 동시에 마지막 한 자리를 눌러도
 정원을 절대 넘기지 않게 해 줘.
 무료로 시작할 수 있는 방법으로, 비밀값은 코드에 노출되지 않게."
  • 어떤 DB를 쓸지, 어떤 방식으로 막을지는 지시하지 않습니다 — 그건 AI의 몫
소단원 ③에서 본 '원자적 저장(DB 함수)'을 AI가 알아서 제안하는지가 관전 포인트입니다.

확인 — 넷 다 눈으로

1신청하면 '남은 자리'가 즉시 줄고 화면에 반영되는가
2새로고침해도 남는가
3정원까지 채우면 '마감'이 뜨고 더는 신청이 안 되는가
4(오늘의 핵심) "마지막 한 자리를 두고 동시 신청 여러 건을 보내는 간단한 테스트를 만들어 돌려서, 딱 한 건만 성공하고 정원이 10을 넘지 않는지 로그로 보여 줘" → 눈으로 로그를 확인(AI 설명만 믿지 말고)
⛰️ 4번이 DB 강의의 '동시에 눌러도 안 꼬이는 법(트랜잭션·제약)'을 실제로 쓰는 지점입니다 — 마지막 한 자리를 두 사람이 동시에 누르면 11명이 되면 안 되죠. 이걸 코드가 막아야 '정원'이 진짜 정원입니다
AI가 "처리했습니다"라고 말하는 것과 실제 로그가 다른 경우가 흔합니다. 반드시 로그를 요구하세요.

막히면 · 비밀값 확인 · 커밋

🔁막히면 — 동시 신청 테스트에서 11명이 되거나 '마감'이 안 걸리면, 그 로그를 그대로 붙여넣고 "동시에 눌러도 정원을 절대 못 넘기게 한 번의 원자적 저장으로 처리해 줘. 지금은 왜 넘치는지도 짚어 줘"
🔑비밀값 확인 — 민감한 값이 코드가 아니라 별도(예: .env)로 빠지고 버전 관리에서 제외됐는가
💾통과하면 바로 커밋 — 다음 단계의 안전망
"왜 넘치는지도 짚어 줘"를 함께 요구하는 게 중요합니다 — 원인을 모르고 고쳐지면 다음에 또 나옵니다.
5

5단계 한 바퀴 + 내보내기

검증하고 배포

④ 다섯 단계
이제 처음부터 끝까지 한 바퀴 돌려 보고, 내 컴퓨터에서만 보이던 걸 인터넷 주소로 배포합니다.

사용자가 되어 끝까지 해 봅니다

1화면 보기
→
2이름 넣고 신청
→
3남은 자리 감소
→
4'마감' 확인
→
5새로고침 유지
"이 앱을 무료로 인터넷에 올리고 싶어.
 내 프로젝트에 맞는 무료 배포처를 추천하고 필요한 단계를 순서대로 알려 줘.
 재배포·재시작 후에도 저장한 데이터가 남는 곳으로.
 비밀값은 배포 화면의 설정에 넣고 코드에는 넣지 마."
  • 끊기는 데가 없어야 합니다
한 바퀴 테스트를 건너뛰고 배포하면, 배포 후에 문제를 발견해 원인이 두 배로 늘어납니다.

확인 — 데이터가 남는지까지

1한 바퀴가 끊기지 않고 되는가
2다른 기기(또는 시크릿 창)에서 신청 주소를 열어 실제로 신청되는가
3배포한 주소에서 신청한 뒤 잠시 후(또는 재배포 후) 다시 열어도 신청이 남아 있는가 — 서버에 DB를 얹는 무료 배포처는 재시작 시 데이터가 사라지기도 합니다(Supabase 같은 외부 DB를 쓰면 그 걱정은 없죠)
4비밀값이 코드에 노출되지 않았는가
  • 막히면 — 오류나 상황을 그대로 붙여넣고 "이 배포처에서 왜 이런지 짚고, 데이터가 남는 방식으로 다시 안내해 줘"
  • 통과하면 커밋 — 오늘의 가장 중요한 커밋입니다
3번이 무료 배포에서 가장 흔한 함정입니다. "되는 것처럼 보였는데 다음 날 데이터가 없다"가 여기서 나옵니다.

여기까지 못 가도 — 3단계까지면 오늘은 성공

배포까지 끝나면
오늘의 '굴러가는 첫 조각'이 세상에 나온 겁니다
  • 실제로 이 튜토리얼 그대로 만들면 — 정원이 차면 '마감'이 뜨고, 마지막 한 자리에 동시 신청이 몰려도 11명이 되지 않습니다
  • DB 강의에서 배운 트랜잭션이 지켜 준 것입니다
🧭 어디까지 갔든 도달한 지점이 오늘의 성과입니다 — 루브릭의 '기능 완성도'도 그렇게 봅니다

❓ 이해도 확인

Q1. 명령을 줄 때 '무엇을'과 '어떻게' 중 무엇을 주는가?
A1. '무엇을'(의도)만. 어떤 DB·어떤 방식은 AI가 정한다. 우리는 의도와 확인에 집중.
Q2. 명령을 한 줄에 하나씩 적는 이유는?
A2. && 같은 연결은 터미널 종류에 따라 다르게 동작한다(PowerShell 5·cmd·맥·리눅스). 한 줄씩이면 어디서든 같다.
Q3. 4단계에서 AI 설명만 믿지 말고 확인해야 하는 것은?
A3. 동시 신청 테스트 로그. 마지막 한 자리에 여러 건을 보내 딱 한 건만 성공하고 정원이 10을 넘지 않는지 눈으로 본다.
Q4. 배포 후 반드시 확인할 '무료 배포처의 함정'은?
A4. 재배포·재시작 후 데이터가 사라지는지. 서버에 DB를 얹는 무료 배포처가 그렇다 — 외부 DB(Supabase 등)를 쓰면 걱정 없다.
Q3·Q4가 이 소단원의 실전 핵심입니다.
