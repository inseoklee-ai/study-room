1단계 — 지금 쓰는 도구의 불편

넓게 적지 않습니다

⑪ 개선 실험
최근 과업에서 반복해서 멈추거나 되돌린 장면 하나를 고릅니다.

불편은 행동과 결과로 적습니다

❌ 넓은 서술

"도구가 불편합니다"

✅ 구체적 장면

어떤 과업에서 어떤 입력 뒤에 무엇이 지연되거나 잘못되었는지

  • 후보 장면 — 승인 요청이 너무 자주 나왔는지, 필요한 파일을 놓쳤는지, 기록이 길어져 중요한 조건을 잃었는지, 결과를 검토하기 어려웠는지
⚠️ 이 불편이 정말 하네스 기능에서 온 것인지도 함께 의심합니다 — 모델 선택, 과업 난이도, 저장소 상태, 네트워크, 자신의 요청 문장이 원인일 수 있습니다
뒤의 실험은 불편을 확인하는 데 그치지 않고, 원인이 하네스 기능이었다는 설명까지 검토합니다.

2단계 — 반증 가능한 개선 가설

불편을 줄일 수 있는 하네스 기능 하나를 골라 가설로 씁니다. 결과가 반대로 나오면 틀렸다고 말할 수 있어야 합니다.

관찰승인 대기로
과업이 멈췄다
→
가설권한 규칙의 범위를 조정하면
완료 시간이 줄어든다
  • 논문 가설 카드는 가설의 출발점이 아니라 — 근거를 얻는 재료입니다. 비슷한 조건의 가설 원문 인용 · 측정 수치 · 검증하지 않은 것 · 근거 등급을 찾습니다
불편에서 가설이 나오고, 카드에서 근거가 나옵니다. 순서를 뒤집지 않습니다.

근거 등급을 숨기지 않습니다

등급뜻보고서에 남길 것
[학술]학회·학술 논문실험 조건과 일반화하지 않는 범위
[벤더]만든 쪽의 자체 보고독립 비교가 아니라는 점을 명시
[공식 문서]제품 문서·설정 문서구조 확인용이며 정량 실험이 아님
📌 이 중단원에서 본 예 — SWE-agent 18.0%는 [학술], Aider 46%와 mini-swe-agent 74%는 [벤더], Claude Code 권한 모드는 [공식 문서]
루브릭 첫 항목("근거자료를 적절하게 조사하고 근거 수준을 표기하였는가")이 정확히 이 슬라이드입니다.

3단계 — 한 항목만 조작하는 설계

고정 · 조작 · 이중 측정 · 사전 판정식

⑪ 개선 실험
이 넷이 분리되어야 불편의 원인을 다른 조건과 구별할 수 있습니다.

고정 · 조작 · 이중 측정

구분내용
고정모델 · 과업셋 · 토큰 또는 시간 예산
조작관측 개수 N · 편집 포맷 · 권한 정책 · 메모리 표현 가운데 하나만
측정해결률만 적지 않고 토큰 · 승인 횟수 · 시간도 함께
반론예상 반론을 하나 이상 적고, 그 반론과 가설을 구분할 통제 조건을 정합니다
🎯 조작 항목 네 가지는 각각 이 중단원의 ④ 컨텍스트 · ③ 행동 포맷 · ⑧ 권한 · ⑤ 경험에서 왔습니다
루브릭 둘째 항목("실험의 범위가 적절한가")이 이 표입니다.

결과를 보기 전에 판정식을 씁니다

어떤 결과면 가설을 지지하고
어떤 결과면 가설을 버릴지를 수치와 함께 정합니다
  • 고정 조건 · 조작 항목 · 이중 측정 · 사전 판정식이 분리되어야 — 불편의 원인을 다른 조건과 구별할 수 있습니다
  • 결과를 본 뒤에 기준을 정하면 어떤 결과든 지지로 읽히게 됩니다
루브릭 셋째 항목("반증 가능한 가설인가")의 실질적 장치가 사전 판정식입니다.

📌 보고서에는 불편의 진짜 원인이 선택한 하네스 기능이었는지를 돌아보는 문단을 넣습니다 — 가설과 다른 결과가 나왔다면 실패로 감추지 않고, 무엇이 원인 설명을 약하게 만들었는지와 다음에 고정하거나 바꿀 조건을 적습니다
채점 관점: 가설이 반증 가능한지, 고정·조작·측정이 분리되었는지, 근거 등급을 구분해 인용했는지, 불편의 원인이 하네스 기능이었는지를 되돌아보았는지.

과제 진행 예시 — 컴파운드 엔지니어링

Claude Code에서 경험 축적이 실제로 효과가 있는가

⑪ 개선 실험
소단원 ⑤에서 본 ExpeL·Voyager·WikiSkill이 같은 주장을 하는 흐름입니다.

가설과 세 테스크

💡 가설 — 같은 과업을 다시 풀 때 첫 시도의 기록을 notes/에 남기고 다음 요청에서 참조하게 하면, 기록 없이 시작할 때보다 두 번째 시도가 빠르고 정확해집니다
1parse-log — fixture 로그 sample.log에서 오류만 골라 표로 정리하는 parse.py 작성
2refactor-util — fixture util.py의 함수 3개에 타입 힌트와 독스트링 추가
3fix-failing — fixture test_me.py의 실패 2건을 통과하도록 수정
  • 세 테스크의 입력 파일은 미리 만들어 두고 내용을 바꾸지 않습니다 — 이렇게 고정해야 조건 차이가 테스크 난이도 탓이 아니라 경험 기록 탓이라고 말할 수 있습니다
fixture 고정이 '공정한 비교' 루브릭의 핵심입니다.

실험 설계 표

구분내용
고정Claude Code · 같은 모델 · 같은 세 테스크 · 같은 작업 폴더
조작첫 시도 후 notes/에 접근법·주의점을 남기고 다음 요청에서 참조(경험 기록 조건) vs 기록 없이 새로 시작(대조 조건)
측정두 번째 시도의 소요 시간 · 수정 횟수 · 테스트 통과까지의 시도 수 · 토큰
사전 판정식경험 기록 조건이 세 테스크 중 두 개 이상에서 시간·시도 수 모두 적으면 지지, 그 외에는 기각
조작이 '경험 기록의 유무' 하나로 좁혀져 있는지 확인하세요.

실행 절차

1새 폴더에서 세 테스크를 한 번씩 풀고 각 소요 시간·시도 수를 기록합니다
2한 폴더에는 notes/를 만들어 각 테스크의 접근법·만났던 오류·해결을 세 줄 이내로 적고 다음 요청에서 참조하라고 지시합니다. 다른 폴더는 기록 없이 시작합니다
3폴더를 새로 만들지 않은 채 세 테스크를 다시 풀게 하고 같은 지표를 기록합니다
4두 조건의 기록을 나란히 두고 사전 판정식에 대입합니다
3단계에서 폴더를 새로 만들면 '경험이 남아 있는 상태' 자체가 사라집니다.

결과 보고와 제출

  • 세 테스크의 두 조건 기록을 표로 남기고 판정식 결과(지지 또는 기각)를 함께 적습니다
  • 기각되어도 실험은 실패가 아닙니다 — 어느 테스크에서 기록이 도움되지 않았는지가 다음 실험의 재료입니다
  • 제출 파일은 GitHub 저장소의 experiment-01.md
보고서에 차례로 적을 것
가설 → 배경 근거(등급 표기와 함께) → 설계 표 → 실행 기록 → 결과 표 → 판정 결과 → 다음 실험 계획
📌 자기 도구의 불편에서 출발할 때도 흐름은 같습니다 — 테스크를 fixture로 고정하고, 조작을 한 가지로 좁히고, 결과가 나오기 전에 판정식을 쓴다
보고서 마지막에는 선택 도구, 선택 근거, 확인한 경계, 미확인 사항, 재검토 조건을 남깁니다.
